## S1. Прощальный heartbeat освобождает владение

### Факт

При штатной остановке агент шлёт последний heartbeat со `status: "OFFLINE"` и тем же
`X-Agent-Instance` (агент: `src/agent.rs:446-456`). Сервис принимает его как обычный
(`agentRouter.ts:286-319`): статус записан, но владение токеном остаётся за ушедшим процессом,
пока не истечёт аренда `AGENT_OFFLINE_AFTER_SECS` (`agents/service.ts:361`, `claimOwnership`).

Всё это время поднявшийся на замену процесс получает `409 AGENT_INSTANCE_CONFLICT`. Снять
владение сейчас можно только вручную — `releaseOwnership` (`agents/service.ts:393`) вызывается
лишь из панели (`onecRouter.ts:642`). Отсюда жалоба «под этим токеном уже работает другой
экземпляр» после каждого обновления службы.

### Сделать

В обработчике `/heartbeat` после `agents.heartbeat(...)`:

```ts
// Уходящий владелец говорит «я всё» — аренду не держим до срока. Сравнение с владельцем
// обязательно: прощание чужой копии токена не должно снимать владение с работающего агента.
if (p.data.status === "OFFLINE") {
	const instance = agentInstance(req);
	const own = await agents.owner(req.agent!.agentId);
	if (instance && own.instanceId === instance) {
		await agents.releaseOwnership(req.agent!.agentId);
		await audit.write({ event: "agent.instance.released", agentId: req.agent!.agentId,
			details: { instance, reason: "farewell" } });
	}
}
```

Промежуточный обработчик (`agentRouter.ts:129-190`) продлит владение на этом же запросе — это не
мешает: снятие идёт после него.

### Не делать

Команды здесь не закрывать. Забранные команды агент возвращает сам (`AGENT_STOPPING` /
`AGENT_STOPPED`), а оставшиеся за прежним процессом закрывает `failLostByRestart`
(`queue.ts:230`), когда появляется новый.

### Проверить

* Тест: `OFFLINE` от владельца → `owner_instance_id` пуст; `OFFLINE` от другого экземпляра →
  владение не изменилось; `ONLINE` от владельца → не изменилось.
* Стенд: остановить и запустить службу агента. В журнале агента нет «другой экземпляр», первый
  опрос нового процесса проходит сразу, в журнале сервиса нет 409.

## S2. Поздний результат не перетирает отменённую команду

### Факт

`queue.complete` (`queue.ts:425-437`) обновляет запись по `id AND agent_id`, не глядя на
состояние. Поздний результат перезапишет команду, закрытую отменой (S4). Агент такое пришлёт при
остановке службы — это его дефект, он исправляется в A2. Но сервис не должен от него зависеть.

Поздние результаты по ИСТЁКШИМ командам принимать нужно и дальше: агент досылает их из своей
очереди, когда связь вернулась, и это правда о выполненной работе.

### Сделать

В `complete` — `AND state <> 'canceled'`. Строки нет → обработчик уже отвечает `ignored`
(`agentRouter.ts:446-451`); запись в журнал сделать различимой: «результат по отменённой команде
отброшен», а не «неизвестная команда».

### Проверить

Тест: команда в `canceled` → `complete` возвращает `null`, состояние и ошибка прежние. Команда в
`expired` → результат принимается, как сейчас.

## S3. `CLUSTER_CHECK_BASES`

### Контракт агента (готов с 12.09 23:48)

Запрос `{ baseKeys?: string[] }` — пусто означает «все базы кластера». Ответ:

```jsonc
{ "items": [ { "key": "aibek", "dbMissing": true }, { "key": "abdali", "dbMissing": false },
             { "key": "x" /* поля нет: проверить не удалось, прежнее знание не трогать */ } ],
  "checked": 110, "skipped": 1, "note": "…" }
```

Без пароля СУБД у агента — список без признаков и `note` «проверить нечем». Время — до минуты на
110 базах.

### Сделать

1. **Спецификация** в `commands/admin.ts` рядом с `CLUSTER_DROP_INFOBASE`:
   `type: "CLUSTER_CHECK_BASES"`, `title: "Проверить наличие баз данных"`, `operation: "READ"`,
   `capability: "cluster.admin"`, `role: "admin"`, `requiresBase: false`,
   `schema: z.object({ baseKeys: z.array(baseKey).max(1000).optional() }).strict()`.
2. **Склейка чтений.** `run()` даёт READ-командам `requestId = ${type}:${baseKey ?? "-"}`
   (`onecRouter.ts:220`). У этой команды `baseKey` нет, поэтому проверка одной базы и проверка всех
   склеятся в одну команду, и второй получит чужой ответ. Для неё в `requestId` включить
   отсортированный список `baseKeys` (или хэш от него).
3. **Маршрут** `POST /v1/onec/bases/check-db` с телом `{ baseKeys? }` → `run(...)`.
4. **Применение — при приёме результата**, в `agentRouter.ts` рядом с `CLUSTER_LIST_INFOBASES`

   Не через `bases.sync`: в строках только `key` и `dbMissing`, а `sync` рассчитан на полный
   срез. Вынести два `UPDATE` из `bases/service.ts:476-500` (снятие отметки у `false`, отметка у
   `true`) в `bases.applyDbPresence(serverId, items)` и вызывать его и из `sync`, и отсюда.
   Строки без поля — не трогать.

## S4. `AGENT_CANCEL_COMMAND` — прервать начатую команду

**Агент готов: сборка `0.1.0+2026-09-13 14:58 (+05)`** — способность `agent.cancel` (A3), команды управления
без ожидания пропуска (A1), прерванная команда снимается с учёта (A2). Требовать именно
`agent.cancel`: сборки с 12.09 23:48 по 13.09 12:12 объявляют `AGENT_CANCEL_COMMAND`, но у них
отмена не доходит до агента, когда все его пропуски заняты зависшими командами.

### Контракт агента

Запрос `{ commandId, force? }`. Ответ `{ ok: true, commandId, killed: true, note }` либо
`{ ok: false, commandId, reason: "NOT_RUNNING" }` — команда успела закончиться сама.
**Результат прерванной команды агент не отправляет:** задача снята, отвечать за неё некому.

### Сделать

1. **Спецификация:** `type: "AGENT_CANCEL_COMMAND"`, `title: "Прервать выполняемую команду"`,
   `operation: "CRITICAL"`, `capability: "agent.cancel"`, `role: "admin"`, `requiresBase: false`,
   `schema: z.object({ commandId: z.string().min(1).max(64), force: z.boolean().optional() }).strict()`.
   Не `agent.procs`: его объявляют сборки с 11.09, а команды отмены у них нет.
2. **Маршрут** `POST /v1/onec/commands/:id/abort` с телом `{ force? }`:
   * команды нет или она не `dispatched` → отказ: в очереди — «используйте отмену до начала», уже
     завершена — «прерывать нечего»;
   * **только команды, чья спецификация `operation === "READ"`**. Для WRITE и CRITICAL — отказ с
     объяснением: обрыв выгрузки, загрузки или обновления оставляет базу в промежуточном
     состоянии;
   * **адресовать агенту, который её забрал** (`commands.agent_id`), а не `pickAdminAgent`: при
     нескольких серверах отмена ушла бы не туда. Если `run()` так не умеет — добавить ему
     явный `agentId`.
3. **Закрыть прерванную команду самим.** На `ok: true` — новый метод очереди `abort(id, by, note)`:
   `state = 'canceled'`, `error = { code: "COMMAND_ABORTED", message: "Команда прервана по
   запросу оператора", details: { by, note } }`, условие `state = 'dispatched'`. Без этого
   команда держит слот до срока, потому что агент по ней не ответит.
   На `ok: false, NOT_RUNNING` — ничего: итог пришёл или придёт сам.
4. **Слот внутрибазовых.** Отмена не должна ждать место: `dispatchQueued` ограничивает только
   `state = 'dispatched' AND base_key IS NOT NULL` (`queue.ts:346`), а у отмены `base_key` пуст.
   Закрепить тестом.
5. **Для панели** в `onec/batches.ts` рядом с `cancelable` (`:37`, `:252`): признак `abortable`
   у строки и счётчик у задания. Признак ставится, если команда `dispatched`, её спецификация READ
   и у агента есть `agent.cancel`.

### Проверить

Сценарии §1 из [TASK_AGENT_CANCEL_AND_CHECK.md](TASK_AGENT_CANCEL_AND_CHECK.md). Главный:
прерванное чтение сразу освобождает слот — следующая внутрибазовая команда из очереди выдаётся без
ожидания срока.

## S5. Отказы и время команд из heartbeat

### Факт

Агент шлёт в каждом heartbeat `failuresByCode` (давно) и `durationsByType` (со сборки
`0.1.0+2026-09-13 15:21 (+05)`). `heartbeatSchema` (`agentRouter.ts:73-98`) — `z.object` без этих
полей: zod их отбрасывает, и до сервиса они не доходят. У агента есть «`IB_BUSY`: 87» и
«`IB_LIST_USERS` идёт тридцать секунд», а панели взять это неоткуда: каждое «агент тормозит»
по-прежнему меряется вручную, и замеру `AGENT_IB_PARALLEL` (A4 в `TASKS_NEXT_2026-09-12.md`) не
на что опереться.

### Форма

Оба снимка — за время работы процесса агента: после перезапуска службы счёт начинается заново.

```jsonc
"failuresByCode": { "IB_BUSY": 87, "IB_AUTH_FAILED": 3 },
"durationsByType": {
  "IB_LIST_USERS": {
    "count": 42, "avgMs": 28150, "maxMs": 61200,
    "p95LeSecs": 60,                 // 1 | 5 | 15 | 60 | 300 | null (null — дольше 300 с)
    "buckets": { "le1s": 0, "le5s": 2, "le15s": 5, "le60s": 34, "le300s": 1, "over300s": 0 }
  }
}
```

### Сделать

* **Сервис.** В `heartbeatSchema`: `failuresByCode: z.record(z.number().int().nonnegative()).optional()`
  и `durationsByType: z.record(z.object({ count, avgMs, maxMs, p95LeSecs: z.number().int().nullable(),
  buckets: z.record(z.number().int()) })).optional()`. Последний снимок хранить у агента, как
  процессы (`agents.setProcesses`), и отдавать в `GET /v1/onec/agents`. Поля нет — прежний снимок не
  затирать (старая сборка агента).
* **Панель.** В карточке агента две таблицы: «Тип команды · Число · Среднее · 95 % до · Максимум»
  (по убыванию среднего) и «Отказы по кодам» (по убыванию числа). Подпись: «с последнего запуска
  службы».

### Проверить

На стенде после обновления агента: в карточке агента после нескольких «Обновить» у пользователей
базы появляется строка `IB_LIST_USERS` с числом и временем.
