**Готовность.** Агент `0.1.0+2026-09-13 12:12 (+05)` уже на связи. Сервис менять не нужно.

### A2. «Показывать в списке выбора»: подпись врёт, как только 1С начнёт отдавать значение
**Сейчас.** Тумблер редактируется и записывается: у «Оператор бухгалтер» в `_transition` реестр
хранит `show_in_list = false` из успешной команды панели. Но показываемое значение — не из 1С:
агент признак не возвращает (см. B1), и подпись честно говорит «по последней записи из панели».

Проблема в том, что подпись выбирается по `here?.showInList != null`
(`BaseUserForm.tsx:635`), а реестр источник не различает: `syncUsers` делает
`COALESCE(EXCLUDED.show_in_list, base_users.show_in_list)` (`ai/src/onec/registry.ts:69`).
Когда агент начнёт отдавать значение, прочитанное из базы будет подписано «прочитать его
неоткуда».

**Что сделать.**
1. Сервис: колонка `base_users.show_in_list_source` (`'base' | 'panel' | NULL`) — `'base'`
   при `syncUsers` с непустым значением, `'panel'` в `rememberShowInList`. Отдать в API
   `showInListSource`. Миграция — diff схема↔схема.
2. Панель: подпись по источнику — `'base'` без подсказки, `'panel'` — «по последней записи из
   панели», `NULL` — «1С не сообщает».
3. Значение, записанное в конфигураторе мимо панели, при `'panel'` не видно — это и есть
   причина подписи; убрать её можно только после B1.

### A3. Массовое подтверждение не называет административные роли
**Сейчас.** 12.09 в 23:51 и 13.09 в 00:10 пользователю «Оператор бухгалтер» записаны наборы из

массовой правки (добавлено позже, `194102d`) показывает только счёт: «добавить 229».

**Что сделать.** В `massRoleChange` отдельно считать выдаваемые привилегированные роли
(список — константой рядом с `MASS_ROLES`, сравнение без регистра) и называть их в окне
поимённо; выдача любой из них — подтверждение даже при одной роли. Тест в
`onecUserFormPayload.test.ts`.

### A4. Обход «чтение ролей перед записью» можно удалять

## B. Агент на сервере 1С

### B1. `showInList` не приходит ни в одном списке пользователей
**Сейчас.** Контракт (`ONEC_AGENT_CLUSTER_CONTRACT.md`, «Показывать в списке выбора не
читается») отмечает: сборка `23:59` отдаёт `showInList` в `IB_LIST_USERS` и в эхе, «если
платформа отдаёт». По журналу — пять успешных `IB_LIST_USERS` по `_transition` после 23:59
(00:02, 00:07, 00:10, 10:29, 11:01), по 24 пользователя, **поле отсутствует у всех 24 в каждом**.
Значит, чтение свойства не срабатывает ни разу, а не «у части пользователей».

**Что сделать.**
1. Подтвердить, какой сборкой выполнены эти команды (в журнале сервиса версии нет).
2. Выяснить, почему свойство не читается: `ПользовательИнформационнойБазы.ПоказыватьВСпискеВыбора`
   в платформе 8.3 есть; если транспорт списка его не отдаёт (например, `ibcmd`), читать через
   COM или прямо сказать в ответе `showInListReadable: false`.
3. Писать в лог агента причину пропуска поля — сейчас «не отдали» и «не смогли прочитать»
   неразличимы.

**Проверка.** `IB_LIST_USERS` по `_transition`: у «Оператор бухгалтер» `showInList: false`
(так записано панелью 12.09).
