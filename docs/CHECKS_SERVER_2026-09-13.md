## 10. Мелкие пункты

* Пользователь с входом через ОС: признак в списке пользователей верный.

  (причина — в журнале агента). Фантом `aibek`, если не удалён в пункте 9, — «БАЗЫ ДАННЫХ НЕТ».

## 10а. Пароль СУБД — по отчёту с сервера 13.09

В отчёте было: `sqlcmd` — «Login failed for user 'sa'», и из 110 баз наличие базы данных выяснено
только у 14. После обновления агента до `0.1.0+2026-09-14 00:56 (+05)`:

1. Окно агента → «Отладочная информация». Строка `dbPassword`:
   * «задан, но СУБД не приняла вход» — пароль СУБД в настройках агента не подходит к пользователю
     СУБД из регистрации баз (`sa`), проверки баз остановлены на час;
   * «запрос списка баз клиентом СУБД не принят… проверяются через ibcmd» — не пускают только
     `sqlcmd`, `ibcmd` работает.
2. Проверить пароль вручную на сервере 1С — пароль вводится с клавиатуры и в историю не попадает:
   ```
   sqlcmd -S localhost -U sa -Q "SELECT 1"
   ```
   Прошло — значит, в настройках агента другой пароль: окно агента → «Пароль СУБД» → «Сохранить и
   применить». Не прошло — пароль `sa` другой, либо учётная запись заблокирована.
3. Причину отказа называет журнал SQL Server (SQL Server Management Studio → Управление → Журналы
   SQL Server): «Login failed for user 'sa'. Reason: Password did not match…» — неверный пароль;
   «…The account is currently locked out» — учётная запись заблокирована, её разблокируют в свойствах
   входа `sa`.
4. `bpapi-agent bases check --config <конфиг>` — у каждой непроверенной базы теперь есть причина.
   Вывод прислать.

**Ожидание:** `dbPassword: да`, в `bases check` решено запросом к СУБД столько же баз, сколько в
кластере, у живых баз — «база данных на месте».
