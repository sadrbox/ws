> 13.09.2026. Агент готов: сборка `0.1.0+2026-09-13 11:24 (+05)` и новее объявляет способность `ib.roles`.
> Сервису правок не нужно — проверка по эху (`checkRoleIntent`) работает и на поправках.
>
> **Статус 13.09, 15:37: выполнено и пошло дальше.** Панель не просто перестала читать перед
> записью при `ib.roles` — обход удалён целиком (`needsLiveRoles`, `ownCurrentRoles`, строки
> `onecRolesLive*`; задача A4 в `TASKS_ONEC_ADMIN_2026-09-13.md`): роли всегда уходят поправками.
> Разделы ниже про `needsLiveRoles` — история, в коде этой функции больше нет. Поправки проверены

## Что сейчас

Карточка «Пользователь базы», «Применить» при изменённых правах своей базы
(`frontend/src/models/OneCAdmin/BaseUserForm.tsx:403-420`):

1. `fetchBaseUsers(baseKey)` → команда `IB_LIST_USERS`: вход в 1С и чтение ВСЕХ пользователей
   базы со всеми ролями;
2. из прочитанного берутся роли этого пользователя, к ним применяются отметки таблицы;
3. `buildSavePlan({ ownCurrentRoles })` отправляет полный набор `roles`.

Это обход от 12.09: тогдашний агент отвечал успехом на `addRoles`/`removeRoles` и ничего не
менял. Цена обхода:

* **два входа в базу вместо одного.** При `AGENT_IB_PARALLEL = 1` чтение и запись стоят в одной
  очереди агента, между ними могут встать чужие команды;
* **гонка.** Роль, выданная в конфигураторе между чтением и записью, полным набором снимается;
* **лишняя операция на экране.** На каждое «Применить» в «Прогрессе» появляется «Проверить
  пользователей», которую человек не запускал.

Правильный порядок — одна команда: изменение и в её же ответе новое состояние. Эхо (`ib.echo`)
это уже даёт; осталось убрать чтение ДО.

## Что обещает агент со способностью `ib.roles`

Контракт — `ONEC_AGENT_CLUSTER_CONTRACT.md`, раздел «Правка ролей применяется так, как прислана».
Коротко:

* `addRoles` / `removeRoles` применяются в том же соединении, где пишется пользователь: снимается
  только выданная роль, добавляется только отсутствующая. Повтор команды безопасен;
* `roles: []` снимает все роли; отсутствие поля `roles` роли не трогает;
* все имена разбираются до первого изменения: роль, которой нет в конфигурации базы, — отказ
  `IB_ROLE_NOT_FOUND` с именем, в базу не пишется ничего;
* `state.users` читается после записи; сервис сверяет его с поправками и при расхождении
  отвечает отказом `AGENT_ROLES_NOT_APPLIED`.

Признак объявляется всегда, когда сборка его умеет, — независимо от того, проверен ли сейчас вход
в базы (как `ib.echo` и `ib.auth`).

## Что сделать

### 1. Правило — функцией рядом с `buildSavePlan`

В `models/OneCAdmin/userUpdate.ts`, чтобы его проверял тест, а не разметка:

```ts
/**
 * Читать роли у 1С перед записью — только если агент поправки не применяет.
 *
 * Агент со способностью `ib.roles` применяет `addRoles`/`removeRoles` в соединении записи, и
 * свежее чтение ему не нужно: оно стоит лишнего входа в базу и открывает гонку с конфигуратором.
 * Список агентов ещё не загружен — считаем, что способности нет: лишнее чтение безопаснее
 * снятой по догадке роли.
 */
export function needsLiveRoles(
	agentAppliesRoles: boolean, changes?: { add: string[]; remove: string[] },
): boolean {
	if (agentAppliesRoles) return false;
	return !!changes && (changes.add.length > 0 || changes.remove.length > 0);
}
```

### 2. Карточка

В `BaseUserForm.tsx`:

* импорт: `hasCapability` из `src/services/onec/api`, `useAgents` из `./shared`,
  `needsLiveRoles` из `./userUpdate`;
* в теле компонента:
  `const agents = useAgents();`
  `const rolesApplied = hasCapability(agents.data?.items, "ib.roles");`
* в `mutationFn` условие
  `if (ownRoleChanges && (ownRoleChanges.add.length || ownRoleChanges.remove.length))`
  заменить на `if (needsLiveRoles(rolesApplied, ownRoleChanges))`.

`ownCurrentRoles` тогда остаётся `null`, и `buildSavePlan` сам отправит поправки — его менять не
нужно. Комментарий «РОЛИ УХОДЯТ ПОЛНЫМ НАБОРОМ…» над блоком (строки 389–402) переписать: обход
теперь только для агента без `ib.roles`.

### 3. Не трогать

* **Подтверждение массовой правки** — `massRoleChange` считает по кэшу `baseUsers` (строка 544), от
  свежего чтения не зависит.
* **Групповой помощник** — он и так шлёт поправки.
* **Кнопку ⟳ в шапке карточки** (`refreshLive`) — это чтение по просьбе человека, а не перед записью.

### 4. Тест

В `__tests__/onecUserFormPayload.test.ts`:

## «Снять все» на поправках

Отметки «снять все» в таблице уйдут как `removeRoles` со списком ролей, которые карточка знает из
кэша. Роль, выданная в конфигураторе после последнего чтения, в этом списке отсутствует и
**останется** у пользователя. Это безопасная сторона: права по догадке не отняты. Эхо вернёт
фактический набор, сервис положит его в реестр, и таблица покажет оставшуюся роль. Сервис
отказом это не считает: снять просили названные роли, и они сняты.

`roles: []` для «снять все» панели посылать не нужно: он снимает и то, чего человек не видел.

## Когда удалить обход совсем

Когда у всех агентов в «Агентах» есть `ib.roles`: удалить ветку чтения перед записью, параметр
`ownCurrentRoles` в `buildSavePlan` и строки `onecRolesLiveMissing` / `onecRolesLiveFailed`. До
тех пор — оставить: старая сборка на поправки отвечает успехом, ничего не меняя (сервис поймает
это по эху, но человек получит отказ вместо выполненной правки).

## Как проверить

1. На сервере агент `0.1.0+2026-09-13 11:24 (+05)` или новее; в «Агентах» у него в способностях есть `ib.roles`.
2. Карточка пользователя: отметить одну роль → «Применить». В «Прогрессе» одна операция — правка,
   без «Проверить пользователей». В журнале сервиса у этой базы нет `IB_LIST_USERS` ни до
   `IB_UPDATE_USER`, ни после (есть строка «состояние базы применено из ответа команды»). Отметка
   на месте после обновления таблицы.
3. Снять роль — то же самое.
4. Снять все отметки — подтверждение массовой правки, затем одна команда с `removeRoles`; в эхе
   ролей у пользователя нет.
5. Агент без `ib.roles` — поведение прежнее, с чтением перед записью.
