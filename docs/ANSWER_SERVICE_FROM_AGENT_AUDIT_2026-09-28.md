## С3. Файл .cfe в журнале команд

- **Установка, выполненная.** Сразу при закрытии `payload.contentBase64` заменяется сводкой `contentDigest: {size, sha256}`.
- **Установка неуспешная (failed/canceled/expired).** Не сразу, а через **сутки**. «Повторить неуспешные» и повтор при
  «занято» берут файл из самой команды: в задании его намеренно нет. Позже повтор пропускает базу с причиной
  «файл расширения уже не хранится — запустите установку заново».
- **Выгрузка.** `result.contentBase64` → `contentDigest` через час: панель забирает файл сразу после выполнения.
- **Порядок очистки.** Чистит ежечасный проход, порциями; первый после выкладки разберёт накопленное.
- **Аудит и расписания.** Файла там нет и не было — проверили.

## С4. Не выгонять пользователей — принято, с одним отступлением

Как предложено: установка расширения первой попыткой идёт **без подготовки**. Проходит — готово, никого не выгнали.
`IB_BUSY` (в том числе «Ошибка исключительной блокировки…») — повтор уже **через подготовку**: запрет регламентных
заданий, закрытие входа, снятие сеансов, операция, возврат как было. Базу при этом ведёт тот же раннер (КР-12),
пакет закрывает базы по очереди, а не все сразу.

**Отступление.** Первую установку и удаление мы тоже пробуем сначала без подготовки, а не готовим базу сразу:
- сервис не знает наверняка, есть ли у расширения объекты данных: кэш списка расширений бывает устаревшим, а имя в
  `.cfe` может отличаться от присланного;
- по вашей таблице отказ «исключительной блокировки» приходит сразу — платформа не ждёт;
- удаление расширения без данных и первая установка без своих объектов данных, судя по таблице, проходят и при
  пользователях.

Цена — одна быстрая лишняя попытка там, где подготовка всё-таки нужна. **Просим подтвердить:** неудачная попытка
первой установки или удаления при чужом сеансе ничего не оставляет в базе — ни частично записанного расширения, ни
висящих процессов. Если оставляет — вернём подготовку сразу для этих случаев.

**Кому.** Только агенту не старше `2026-09-27 22:42`: он входит в закрытую базу с кодом разрешения. Старшим сборкам
закрытый нами вход отказывал и их собственному соединению (КР-1), им — обычный повтор.

**`IB_SESSIONS_DENIED`** из подготовленной попытки (например, нет прав на `rac infobase update`) раннер не повторяет:
база возвращается, отказ остаётся в задании с подсказкой.

## С6. Организации после загрузки и обновления

- **Полный блок.** `state.organizations` с `complete: true` применяется тем же разбором, что ответ
  `IB_LIST_ORGANIZATIONS`: кэш вкладки заменяется целиком, `mainSource` и `notes` — как в ответе.
- **Блока нет или `complete` не `true`.** После `IB_RESTORE` / `IB_APPLY_UPDATE` сервис ставит `IB_LIST_ORGANIZATIONS`,
  но только сборке, которая знает этот тип.

## С7. `notes`

- **Блоки реквизитов** (`contacts`, `responsible`, `bankAccounts`). По такой записке сервис берёт из прошлого чтения
  только поля этого блока, а панель предупреждает, что часть реквизитов по прошлому чтению. Поля прочитанных блоков
  заменяются как есть: пустое значит «в 1С стёрли».
- **Блок `main`.** Реквизитов не касается: панель поясняет им, почему нет отметки «Основная».
- **Записка без блока или с незнакомым блоком.** Считаем недочитанными все поля.
- **Правило «живых пользователей»** для источника `users` — спасибо, внесено в канон.

## С9 и наша ошибка в разборе текста

Добавили «исключительн… блокировк…». Заодно выяснилось: наши образцы окончаний были написаны как `разделен\w* доступ`,
а в JS `\w` кириллицу не ловит. «Ошибка разделенного доступа» узнавалась только благодаря соседнему образцу «база данных
заблокирована». Исправлено во всех разборах «занято» сервиса. Со стороны агента ничего не нужно: коды `IB_BUSY` вы и так
отдаёте.

## Как проверим вместе

По вашему плану, после обновления агента на SERVER до 13:57 и перезапуска сервиса:

1. Установка расширения в `_transition` (обновление) — без подготовки. В «Прогрессе» — «Путь: соединение с базой
   (COM)», пользователи не выгнаны.
2. Удаление расширения с данными при открытом сеансе. Первая попытка — `IB_BUSY` с держателями, затем повтор через
   подготовку: вход закрыт, сеанс снят, расширение удалено, вход открыт.
3. `IB_INFO` при закрытом входе — сведения приходят.
4. Загрузка выгрузки на тестовой базе — вкладка «Организации» обновилась без «Обновить».
5. Дополнительно — блокировка входа, поставленная изнутри 1С, и любая внутрибазовая команда. Ожидаем
   `IB_SESSIONS_DENIED` без повтора и с подсказкой.
