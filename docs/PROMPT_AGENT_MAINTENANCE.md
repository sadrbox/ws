# ТЗ агенту: обслуживание баз (снятие публикации, выгрузка, восстановление, проверка, обновление)

Документ адресован сессии разработки агента. Он описывает пять команд, которых в
способностях агента сейчас нет, и одну (`IB_BACKUP`), которая есть, но до сегодняшнего дня
не имела контракта со стороны сервиса.

Общий транспорт прежний: `GET /agent/v1/commands` → `POST /agent/v1/commands/{id}/result`.
Общие правила — в `docs/ONEC_AGENT_CLUSTER_CONTRACT.md`; здесь только то, что специфично.

Три правила, которые нарушать нельзя ни в одной из команд:

1. **Отказ 1С — это `ERROR` с текстом для человека, а не 5xx.** Сервис отвечает панели 422;
   пятисотый ответ подменяется страницей прокси, и текст до пользователя не доезжает.
2. **Идемпотентность.** Команда живёт 900 с, панель показывает `TIMEOUT` через 120 и НЕ
   снимает её с очереди: пользователь повторит операцию, которая уже идёт.
3. **Секреты не логировать** — ни пароль СУБД, ни пароль администратора кластера, ни
   содержимое `--*-pwd` в командной строке.

## 1. `IB_UNPUBLISH` — снять публикацию (готово на стороне сервиса)

Панель уже шлёт эту команду группой по отмеченным базам, но агент её не объявляет, и задание
честно отмечает все базы пропущенными.

| Поле | Тип | Обязательность |
|---|---|---|
| `baseKey` | строка | да |
| `alias` | строка | нет (по умолчанию — имя базы) |
| `webServer` | `iis` \| `apache24` | нет |

Результат: `{ "ok": true }`. Транспорт — `webinst -delete` (или эквивалент), тот же, что у
`IB_PUBLISH`. Снятие публикации с неопубликованной базы — `SUCCESS`, а не ошибка.

После успеха сервис сам ставит базе `published = false` и СТИРАЕТ адрес публикации.

## 2. `IB_BACKUP` — выгрузка `.dt` (контракт, которого не было)

Команда у агента есть (T4), но сервис до сих пор её не отправлял: не было согласованной формы.
Фиксируем её здесь; панель уже умеет запускать выгрузку группой по отмеченным базам.

| Поле | Тип | Обязательность |
|---|---|---|
| `baseKey` | строка | да |
| `dir` | строка | нет — каталог назначения |

Панель НЕ передаёт имя файла и не знает раскладку дисков сервера: это дело агента. Без `dir`
берётся каталог из настроек агента.

Результат — путь обязателен:

```jsonc
{ "ok": true,
  "path": "D:\\dt\\buh_alma_2026-09-07.dt",  // ОБЯЗАТЕЛЬНО: панель показывает его в отчёте
  "sizeBytes": 1234567890,                    // желательно
  "transport": "ibcmd" }                      // желательно: ibcmd | designer
```

`path` — единственное, что отличает отчёт «выгружено 110 баз» от бесполезной галочки: без
него не ответить на вопрос «куда легло». Транспорт по умолчанию `ibcmd infobase dump`
(клиентская лицензия не расходуется), запасной — конфигуратор, когда пароль СУБД не задан.

Занятая база: если выгрузка требует монопольного доступа и он не получен — `ERROR` с кодом
`IB_BUSY` и текстом, называющим число активных сеансов. Сеансы не снимать: это решение
пользователя, а не агента.

## 3. `IB_RESTORE` — загрузка `.dt` (T4)

**CRITICAL.** Единственная команда во всём наборе, которая уничтожает данные: содержимое базы
замещается целиком.

| Поле | Тип | Обязательность |
|---|---|---|
| `baseKey` | строка | да |
| `path` | строка | да — файл `.dt` на машине агента |
| `lockSessions` | булево | нет (по умолчанию `true`) |

Порядок, который агент обязан соблюсти сам, не полагаясь на панель:

1. блокировка начала сеансов через `rac` (если `lockSessions` не выключен явно);
2. ожидание выхода активных сеансов; не дождались — `ERROR` `IB_BUSY`, восстановление НЕ
   начинать;
3. `ibcmd infobase restore` (запасной путь — конфигуратор);
4. снятие блокировки — **в том числе при ошибке**: база, оставшаяся запертой после неудачи,
   хуже самой неудачи.

Результат: `{ "ok": true, "transport": "ibcmd" }`.

Идемпотентность здесь недостижима и не требуется: повторная загрузка того же файла даёт тот
же результат, поэтому повтор безопасен, но «уже сделано» агент определять не обязан.

## 4. `IB_CHECK` — проверка и починка базы (T6)

**CRITICAL** (правит данные). Транспорт безальтернативен: конфигуратор `/IBCheckAndRepair`.

| Поле | Тип | Обязательность |
|---|---|---|
| `baseKey` | строка | да |
| `reindex` | булево | нет |
| `logicalIntegrity` | булево | нет |
| `recalcTotals` | булево | нет |
| `repair` | булево | нет — без него только проверка, без изменений |

Результат:

```jsonc
{ "ok": true, "issues": 3, "repaired": 2, "report": "…краткий текст…" }
```

`repair: false` (умолчание) обязано быть безопасным: только диагностика. Панель на этом
построит «сначала проверить, потом чинить», и если умолчание окажется чинящим, пользователь
починит сотню баз, собираясь их всего лишь проверить.

Команда занимает клиентскую лицензию и требует монопольного доступа — правило занятой базы
то же, что у `IB_BACKUP`.

## 5. `IB_APPLY_UPDATE` — обновление конфигурации из `.cfu` (T7)

**CRITICAL.** Самая длинная операция набора; агент выполняет весь цикл сам.

| Поле | Тип | Обязательность |
|---|---|---|
| `baseKey` | строка | да |
| `path` | строка | да — `.cfu` (или каталог с цепочкой обновлений) |
| `backup` | булево | нет (по умолчанию `true`) |
| `lockSessions` | булево | нет (по умолчанию `true`) |

Цикл: блокировка сеансов → ожидание выхода → выгрузка `.dt` → `/UpdateCfg` →
`/UpdateDBCfg -Server` → снятие блокировки. При неудаче — восстановление из выгрузки и
`ERROR` с текстом, который прямо говорит, восстановлена база или нет: это первое, что
спросит пользователь.

Результат:

```jsonc
{ "ok": true, "versionFrom": "3.0.140.1", "versionTo": "3.0.141.2", "backupPath": "D:\\dt\\…" }
```

Скачиванием релизов агент не занимается: файлы берутся из каталога, указанного в payload или
в настройках.

## 6. Порядок и проверка готовности

Порядок по пользе: `IB_UNPUBLISH` (минуты, снимает уже отправляемую панелью команду) →
`IB_BACKUP` (контракт уже ждёт) → `IB_RESTORE` → `IB_CHECK` → `IB_APPLY_UPDATE`.

Каждая команда считается готовой, когда:

1. объявлена в способностях — иначе сервис её не отправит вовсе, а задание отметит базы
   пропущенными («агент не умеет команду»);
2. зонд отвечает успехом на тестовой базе:
   `npm run onec-probe -- --cmd <ИМЯ> --base <ключ>` (изменяющие команды зонд не шлёт —
   проверяйте из панели по одной базе);
3. в отчёте задания видно то, ради чего команда делалась: путь выгрузки, число исправленных
   ошибок, версии «из» и «в».

## 5a. `IB_UPDATE_USER` — изменить пользователя базы

Панель уже шлёт эту команду группой по отмеченным базам (группа — точное совпадение имени),
агент её не объявляет.

| Поле | Тип | Смысл |
|---|---|---|
| `baseKey`, `name` | строка | адрес: в какой базе и кого меняем |
| `newName` | строка | переименование входа; без него имя не меняется |
| `fullName`, `password`, `roles[]`, `disabled`, `showInList` | | новые значения |

**Незаполненное поле означает «не трогать», а НЕ «очистить».** Групповая правка полного
имени не должна заодно стирать всем пароли и роли — это первое, что произойдёт на сотне баз,
если трактовать отсутствие поля как пустое значение.

Почему изменение, а не «удалить и создать заново»: пересоздание теряет настройки
пользователя и его ссылки в базе, а на сотне баз это ещё и сотня шансов остановиться на
середине. Результат: `{ "ok": true }`.

## 6a. Единственность экземпляра (сделано на стороне сервиса, ждёт агента)

Сервис теперь пускает работать один экземпляр на токен: заголовок `X-Agent-Instance` на
каждом запросе, второй экземпляр получает 409 `AGENT_INSTANCE_CONFLICT`. От агента нужно
три вещи:

1. слать `X-Agent-Instance` (например `"<host>#<pid>"`) — без него агент работает как
   раньше, но и защиты нет, и в панели не видно, сколько процессов запущено;
2. не допускать второй копии на своей машине (именованный mutex);
3. получив 409 — **остановиться и написать в лог**, кто владелец (текст ошибки это
   называет), а не ретраить молча: молчаливый ретрай превращает аварию в загадку.

Живой случай, ради которого это сделано: один токен стоял и на сервере 1С, и на машине
разработки; команды доставались то одному процессу, то другому, и половина падала
«база не найдена» — при полностью верных настройках.

## 7. Чего от агента НЕ требуется

`IB_BATCH` (цикл по базам внутри агента) сервис использовать не будет для операций панели.
Групповая операция у нас — это N команд с отдельным результатом по каждой базе: так работает
повтор ТОЛЬКО неуспешных, прогресс и история. Один общий отчёт всего этого лишает. Оставьте
`IB_BATCH` для собственных сценариев агента (например, ночная выгрузка всех баз по
расписанию) — панель его не вызывает.
