# Задача сервису: один бизнес-агент — несколько организаций ERP

21.09.2026. Со стороны агента изменений не требуется: он про организации ERP не знает вовсе — сообщает свои базы
и БИНы организаций в каждой из них (`agent_bases.organizations`), а выбор базы уже делает сервис.

## Зачем

Сейчас бизнес-агент привязан к ОДНОЙ организации ERP (`agents.organization_uuid`), и исполнитель бизнес-команды
выбирается только среди агентов активной организации пользователя (`ai/src/agents/service.ts:296-298`
`pickAgentFor`, `:335+` `resolveBusiness`, `ai/src/chat/workflow.ts:495,500`). Отсюда два живых случая, где
сегодня приходится городить лишнее:

1. **Бухгалтерская фирма с клиентами, у каждого свой вход в ERP.** На одном компьютере фирмы стоит агент и
   десяток клиентских баз. Сотрудник клиента заходит в ERP под своей организацией и пишет в чат — агента для
   его организации «не настроено». Сегодня выход один: ставить по службе на каждую организацию, хотя база, файл
   настроек и компьютер те же самые.
2. **Холдинг: несколько организаций ERP на одну базу или на один сервер 1С.** Та же картина: службы плодятся
   там, где нужна одна.

## Что для этого уже готово (менять не надо)

- **Выбор базы по БИН организации ERP.** Чат читает БИН активной организации (`chat/workflow.ts:97-98` `erpBin`)
  и передаёт его в `resolveBusiness(org, { baseKey, bin })`; база выбирается по БИНам, которые агент сообщил
  (`agents/agentBases.ts` `resolveTarget`), а `organizationBin` дописывается в команду (`workflow.ts:539-541`).
  Это и есть механизм, который разделит организации внутри одного агента.
- **Срез баз и БИНов агента** — `agent_bases` (ключ базы, порядок, организации с БИН, признак «сверх лимита»).
- **Лимит тарифа и активация БИНов** — на агента; менять их привязку не нужно.

## Что сделать

### 1. Связь «агент ↔ организации» вместо одного поля

Таблица `agent_organizations (agent_id, organization_uuid, added_by, added_at)`, уникальность по паре.
`agents.organization_uuid` остаётся ВЛАДЕЛЬЦЕМ (кто завёл, чей тариф, кому писать в аудит) и автоматически
входит в набор. Для админ-агента ничего не меняется — у него организации нет и не должно быть.

### 2. Выбор исполнителя — по набору

`listByOrganization` (`agents/service.ts:259`) и все, кто им пользуется (`pickAgentFor`, `resolveBusiness`,
`pickOnline`, «агент не настроен» в `chat/workflow.ts:500`), берут агентов, у которых организация пользователя
ЕСТЬ В НАБОРЕ. Остальная логика выбора базы не меняется.

### 3. Правило безопасности: чужая база не достаётся даже по имени

Это главное в задаче. Пока агент обслуживает одну организацию, стеной служит сама привязка. Как только агент
общий, стеной становится БИН — и проверять его нужно на КАЖДОМ пути к базе:

- **Выбор без адреса** (`resolveTarget` по `bin`) — уже так работает; нужно лишь запретить запасной путь «взять
  первую базу», когда агент обслуживает больше одной организации: сейчас при `bin = null` выбор сводится к
  «первая база агента» (`agents/service.ts:300-303`). Для многоорганизационного агента это утечка.
- **Явный `baseKey` в команде** (модель получает его из `GET_ORGANIZATIONS`, человек — из подсказки) —
  проверять, что названная база несёт БИН организации пользователя; иначе отказ
  `BASE_FOREIGN_ORGANIZATION` со словами «эта база принадлежит другой организации».
- **Организация ERP без БИН** — для многоорганизационного агента отказ с внятным текстом: «у организации не
  указан БИН, поэтому нельзя понять, какая база ваша». Догадываться здесь нельзя.
- **Контекст диалога** (`idBases`, `baseAgents`, запомненные `organizationId → baseKey`) — при смене активной
  организации пользователем сбрасывать: иначе база прошлой организации доедет до следующего хода.

Отдельный тест на каждый из четырёх путей: пользователь организации Б не получает базу организации А ни одним
из них.

### 4. Панель

- Карточка агента: раздел «Организации» — список с добавлением и удалением (право «Агенты: управление»);
  владелец помечен и не удаляется. Аудит `agent.organizations.add` / `.remove` с указанием, кто и когда.
- Одобрение заявки на подключение (`POST /v1/onec/enrollments/:id/approve`): для бизнес-роли разрешить выбрать
  НЕСКОЛЬКО организаций; первая становится владельцем. Для админ-роли поле по-прежнему не показывается.
- Видимость агента (C11): бизнес-агент виден, если ЛЮБАЯ его организация есть у пользователя
  (`onecRouter.ts:315`, список агентов и процессов — там же по `organizationUuid`).
- В списке баз агента показать, какой организации ERP принадлежит база (по БИН): без этого «десяток баз одного
  агента» перестаёт читаться.

### 5. Миграция

Существующим агентам — строка в `agent_organizations` с их текущей организацией. Поведение без правок в панели
не меняется: один агент, одна организация, всё как было.

## Готово, когда

1. Один бизнес-агент одобрен на две организации ERP; пользователь каждой видит его в панели и разговаривает с
   ним в чате.
2. Пользователь организации Б не может получить базу организации А: ни выбором без адреса, ни явным `baseKey`,
   ни через контекст диалога после переключения организации; отказ называет причину.
3. Организация без БИН у многоорганизационного агента получает внятный отказ, а не чужую базу.
4. У агента с ОДНОЙ организацией поведение прежнее — существующие тесты чата и выбора агента проходят без
   правок.
5. Лимит тарифа и активация БИНов по-прежнему считаются на агента, а не на организацию.

## Чего задача НЕ меняет

- Сторону агента: он про организации ERP не знает и знать не должен. Ставить новую сборку не требуется.
- Админ-агента: он и сейчас без организации, команды кластера выбираются по серверу.
- Расширение `buhprof_api`: прямой канал «1С ↔ сервис» (регистрация базы, чат внутри 1С) к этой задаче
  отношения не имеет.

## Цена и риски

День-полтора со стороны сервиса плюс панель. Главный риск — не в объёме, а в том, что при многоорганизационном
агенте ошибка маршрутизации означает доступ к чужой базе: поэтому §3 (четыре пути и тесты на каждый) — не
украшение задачи, а её суть. Если делать частями, начинать с §3: запрет запасного «первая база» и проверка
явного `baseKey` полезны и сегодня.
