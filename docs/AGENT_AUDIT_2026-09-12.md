# Аудит агента, 12 сентября 2026

Сплошная инспекция после недели плотных правок: за неделю в агенте появились публикации,
версия платформы, процессы, учёт баз-фантомов и три новые команды, и большая часть этого писалась
по следам боевых обращений — то есть быстро.

Объём: 21 254 строки Rust в 30 модулях плюс 857 строк PowerShell-моста, 118 тестов, `clippy`
молчит, релизный файл 5,8 МБ.

Метод: поиск типовых дефектов (паники, блокирующие вызовы в асинхронном коде, удержание замков
через `await`, мёртвый код, дублирование) плюс целевой разбор того, что писалось последним, и
сверка соседних мест с тем, где дефект уже находили. Последнее дало больше всего: **обе
критические находки — это одна и та же ошибка, что чинилась в срезе публикаций, но в других
файлах**.

---

## A. Критическое — исправлено в этот же заход

### A1. Проба входа шла по ОПИСАНИЮ базы, а не по её имени — СДЕЛАНО

`src/readiness.rs`, `pick_base`: база для проверки входа бралась из среза полем `name`, а это
описание базы («Карамурт-Газ ТОО»); имя в кластере лежит в `key`.

**Чем опасно.** Когда `cluster.probe_base` не заполнен, агент проверял вход по имени, которого
в кластере нет. Вход не удавался НИКОГДА, способность `ib.admin` не объявлялась, и сервис
переставал слать внутрибазовые команды — на новом сервере это выглядит как «агент не умеет
работать с базами», хотя всё настроено верно. Отказ при этом ссылался на доступ, уводя в
сторону.

**Сделано:** берётся `key`; поведение закреплено тестом.

### A2. Пакет «по всем базам» собирал список по описаниям — СДЕЛАНО

`src/commands/mod.rs`, `execute_batch`: `IB_BATCH` без поля `bases` брал базы кластера тем же
`name`.

**Чем опасно.** Групповая операция по всем базам (ночная выгрузка по расписанию, массовая
проверка) уходила на имена, которых в кластере нет, — и отказывала по КАЖДОЙ базе разом. На
стенде с заполненным `bases` это не проявлялось, поэтому и не всплыло раньше.

**Сделано:** берётся `key`.

> Общий вывод по A1–A2: пара «`key` — имя в кластере, `name` — описание» уже подводила в срезе
> публикаций. Одной правки в найденном месте мало — стоит проверять ВСЕ места, читающие срез баз.
> Сейчас таких мест четыре, и все проверены.

## B. Оптимизация

### B1. Чистка журналов шла каждую минуту — СДЕЛАНО

`src/agent.rs`, `schedule_loop`: обход каталога с чтением дат файлов выполнялся на каждом такте,
то есть 1440 раз в сутки ради файлов, которые стареют по одному в день. Теперь раз в сутки.

### B2. Фоновый поиск баз-фантомов дёргал `rac` раз в минуту — СДЕЛАНО

`src/cluster/mod.rs`, `bases_without_db_state`: чтобы узнать имена баз, вызывался полный
`list_infobases` — опрос всех кластеров плюс чтение веб-сервера. Раз в минуту, ради списка,
который уже лежит в кэше. Теперь имена берутся из кэша, а `rac` спрашивается только когда кэш
пуст (первый заход после запуска).

### B3. Две копии «записать .cfe во временный файл» — СДЕЛАНО

`Ib::write_temp` и `write_temp_cfe` делали одно и то же: проверка размера, base64, имя файла,
запись. Разойдись они в проверке размера — поведение агента начало бы зависеть от того, каким
транспортом пошла установка. Теперь одна реализация.

### B4. Мёртвый код — СДЕЛАНО частично

`procs::sweep_stuck` не вызывался ни разу за всё время существования: уборка «всё, что работает
дольше предела» опасна по сути (выгрузка базы идёт часами), и её заменила уборка «сирот». Функция
удалена — она создавала видимость защиты, которой нет.

**Осталось** (интерфейс, безвредно, но мусор): `ui::style::accent_hover`, `accent_pressed`,
`ui::style::ok_mark`, `App::new_without_tray`.

### B5. Запись расширения до 64 МБ идёт синхронно в асинхронной задаче — НЕ СДЕЛАНО

`write_temp_cfe`: base64-декод и запись файла (до 64 МБ) выполняются прямо в задаче,
занимая рабочий поток целиком. Это ровно та природа дефекта, что вчера заклинила агента на
обходе каталогов веб-сервера: на четырёх потоках двух-трёх одновременных установок расширения
достаточно, чтобы всё встало, включая heartbeat.

**Сделать:** вынести в `spawn_blocking`, как сделано для обхода каталогов.
**Готово, когда:** одновременная установка расширения на четыре базы не задерживает heartbeat.

### B6. `setup::state(config)` вызывается дважды подряд — НЕ СДЕЛАНО

`src/ui/jobs.rs:67-68`: два вызова в одном снимке, а внутри каждого — чтение конфигурации,
чтение секретов службы из реестра и ПОИСК `rac.exe` по файловой системе. Снимок собирается в
фоновом потоке, поэтому окно не замирает, но работа делается дважды.

**Сделать:** вызвать один раз и взять оба поля из результата.

### B7. Единственная паника в рабочем коде — НЕ СДЕЛАНО

`src/ui/tray.rs:470`: `Icon::from_rgba(rgba, side, side).expect("значок")`. Данные готовит сам
агент, поэтому на практике не падало, но паника в потоке интерфейса убивает окно целиком.

**Сделать:** при неудаче показать значок по умолчанию либо работать без значка — программа
остаётся живой в любом случае.

## D. Рекомендации по развитию

Порядок — по отношению «польза к цене», а не по красоте.

### D1. Проверять базы данных одним запросом к СУБД, а не перебором

Сейчас поиск фантомов стоит одного запуска `ibcmd` на базу. А СУБД отвечает на вопрос «какие
базы у тебя есть» ОДНИМ запросом (`sys.databases` / `pg_database`), и сверка со списком
`dbName` из кластера даёт ответ по всем ста десяти базам разом — мгновенно и без нагрузки.

Цена: клиент СУБД в агенте (`tokio-postgres` и `tiberius` — плюс к размеру файла) либо запуск
`sqlcmd`/`psql`, если они есть на сервере. Начать стоит со второго: находится — используем, нет
— работает нынешний перебор.

### D2. Сводка здоровья сервера одной командой

У агента уже есть по кускам: готовность (`readiness`), процессы, публикации, фантомы, версия
платформы, лицензии. Собрать это в один ответ (и одну команду для панели) — получится страница
«состояние сервера 1С», ради которой сегодня открывают пять экранов и лезут на сервер по RDP.

### D3. Журнал операций агента, доступный из панели

Сейчас разбор любого случая начинается с «пришлите журнал». Агент мог бы отдавать последние N
записей своего журнала отдельной командой (только чтение, с фильтром по уровню). Это закрывает
большую часть переписки, которую видно в `AGENT_FINDINGS`.

### D4. Мера времени команд

`failures_by_code` в heartbeat уже есть. Добавить к нему время исполнения по типам команд —
и станет видно, что `IB_LIST_USERS` идёт 30 секунд, а не «иногда медленно». Без этого каждое
«агент тормозит» приходится измерять вручную, как мы измеряли зависание `ibcmd`.

### D5. Проверка обновлений

Агент знает свою сборку, сервис знает, какая доступна. Одной строки в панели «на сервере
2026-09-01, доступна 2026-09-12» хватило бы, чтобы вопрос «обновлять ли агента» перестал
возникать. Сам файл пусть по-прежнему копирует человек — автообновление службы на сервере 1С
это отдельный риск, который сейчас брать незачем.

### D6. Прогон против mock-сервиса в сборке

`tools/mock_cloud.py` и `tools/e2e_test.py` есть, но запускаются руками. Их прогон при сборке
релиза поймал бы расхождения протокола раньше боевого сервера — сегодня их ловит боевой сервер.

## Что проверено и в порядке

* **Паник в рабочем коде нет**, кроме `tray.rs` (B7): всё остальное — в тестах.
* **Секреты не утекают**: пароли вырезаются из текстов отказов в обоих мостах и в `ibcmd`,
  в командную строку не попадают, `Debug` конфигурации их прячет.
* **Дочерние процессы помечены `kill_on_drop`** везде, кроме конфигуратора, где это сделано
  намеренно и объяснено в коде.
* **Замки не удерживаются через `await`**: единственный долгий мьютекс — в пуле мостов, и там
  это и есть назначение.
* **Очередь отложенных результатов** ограничена сроком (сутки) и числом файлов (тысяча).
* **Предельное время** есть у всех внешних вызовов: `rac`, `ibcmd`, оба моста, HTTP, — после
  вчерашней правки `ibcmd` пробелов не осталось.
* **Три состояния вместо двух** («да» / «нет» / «не знаю») последовательно применены к
  публикации, версии платформы и базам данных — сервис не затирает знание пропуском.

### Отдельно: потеря и восстановление `src/ui/style.rs`

В ходе этих правок модуль оформления окна был уничтожен неверным скриптом (файл с переносами
LF разбирался как CRLF, и вместо двух строк вычистилось всё содержимое). Копий не нашлось:
корзина, теневые копии тома, история редактора, сетевые диски — пусто; репозитория у проекта
нет по решению владельца.

Модуль восстановлен заново по всем местам использования: 34 функции, 6 констант, обе темы,
плотный режим. Сигнатуры воспроизведены точно (их перечислял компилятор), договорённости по виду
соблюдены — радиусы 3 и 5, высота элемента 24, сетка шагом 4, кнопка внутри поля 18. Возможны
расхождения в оттенках и мелких отступах: прежних значений не существует ни в одном файле.

**Что из этого следует для проекта.** Единственная защита от повторения — копии. Раз git
исключён, стоит хотя бы датированный архив `src/` при каждом релизе: одна строка в сборочном
скрипте против потери дня работы.
