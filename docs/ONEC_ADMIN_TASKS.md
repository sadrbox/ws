# Администрирование 1С: задачи по итогам сквозной проверки

2026-09-06. Основано на прогоне 20 сценариев через публичный адрес и зонде `npm run onec-probe`
по живым базам. Формат: что найдено → что делать → чья сторона.

## 0. Что проверено и работает

Все 20 сценариев отвечают корректным кодом, с телом и заголовками CORS:

| Группа | Итог |
|---|---|
| Авторизация: без токена / без права | 401 / 403 |
| Чтение реестра: базы, агенты, задания, сводки | 200 |
| Кластер: сеансы, соединения | 200 за 0.3–0.4 с |
| Ошибки 1С (нет базы, нет доступа) | 422 с текстом от агента |
| Валидация пакетов: тип, пустой список, нет имени, лишнее поле | 400 |
| Не найдено: задание, команда, база | 404 |

Отдельно закрыт класс проблем «ошибка без объяснения»: сервис не отвечает 5xx на ошибки 1С
(их подменял Cloudflare своей страницей без CORS), длинных запросов нет — вместо ожидания
отдаётся 202 и клиент опрашивает готовность.

## 1. Исправлено в ходе проверки (сервис)

- **«Обновить из кластера» отдавал сырой ответ `rac`** вместо реестра, когда срез не удалось
  применить. У них разная форма — панель рисовала пустые колонки, а при пустом ответе агента
  таблица обнулялась. Теперь ручка ВСЕГДА отвечает реестром; пустой срез не применяется
  (иначе `complete+authoritative` пометил бы все базы пропавшими).
- **Лимит частоты бил по своим.** Под общий лимит кластера (60/мин) попадал опрос готовности
  команды — раз в 2 с, то есть половина квоты одним запросом. Из-под лимита выведено всё,
  что до кластера не доходит.
- **«Нет агента» вместо «нет базы».** При неизвестном ключе базы маршрутизация проваливалась
  и пользователь получал `ADMIN_AGENT_UNAVAILABLE`, хотя агент на связи. Теперь `404
  UNKNOWN_BASE` с понятным текстом.
- **Дубли баз в списке.** Идентичностью сервера было его ИМЯ: агент прислал «SERVER» вместо
  «Сервер 1С» — появился второй сервер с теми же 110 базами. Теперь агент, уже закреплённый
  за сервером, при смене имени переименовывает его, а не заводит новый.
- **Фантомные базы не отличались от рабочих.** Отказ `INFOBASE_NOT_FOUND` теперь помечает
  базу в реестре статусом «Нет в кластере»; статусы переведены на человеческий язык.
- **Ливность считалась только по heartbeat.** Агент, забирающий команды, но с оборвавшимся
  heartbeat, числился офлайн. Теперь отметку ставит любой его запрос.

## 2. Задачи по агенту (bpapi_agent)

Порядок — по убыванию блокирующей силы.

1. **Нестабильный поиск базы.** Одна и та же база то находится, то нет. `_transition` вчера
   отдавала расширения, сегодня — `INFOBASE_NOT_FOUND`; `akacapital` наоборот. При этом
   `CLUSTER_LIST_INFOBASES` перечисляет обе. Две собственные команды агента видят кластер
   по-разному — надо свести к одному источнику.
2. **`IB_LIST_USERS`: неверная цепочка COM.** Нужно свойство `ПользователиИнформационнойБазы`
   (`GetProperty`) → метод `ПолучитьПользователей` (`InvokeMethod`), а не один глобальный метод.
3. **Проверка «Служебный админ базы» отсекает всё.** Отказ приходит за 2–6 с, до подключения,
   при заполненных учётных данных. Проверить чтение значения после «Сохранить и применить»,
   сравнение с пустой строкой/null, и сохранить прежний путь (аутентификация ОС) как запасной.
4. **Способность объявляется без проверки.** Агент шлёт `ib.admin`, даже когда работать внутри
   баз не может: гейт пропускает команду, отказ приходит на три шага позже, чем мог бы.
5. **Пустой список баз при SUCCESS.** `CLUSTER_LIST_INFOBASES` однажды вернул `items: []` со
   статусом SUCCESS. Сервис такой срез не применяет, но агенту стоит отвечать ошибкой:
   пустой кластер — это сбой, а не факт.
6. **Второй экземпляр.** Два процесса с одним `agentId` разбирают одну очередь; часть команд
   уходит мимо того экземпляра, который видит администратор. Окно управления должно быть
   наблюдателем службы, а не вторым агентом (уже в промпте, пункт 5).

## 3. Задачи по публикации баз

**Проблема.** На сервере есть базы, не опубликованные на веб-сервере. Сейчас панель о
публикации не знает вовсе: в реестре нет такого поля, и неопубликованная база выглядит
ровно как опубликованная. При этом публикация — обязательное условие перехода на быстрый
HTTP-транспорт (вход в базу через COM стоит ~27 с, через HTTP-сервис — доли секунды).

- **P1. Поле в реестре.** Миграция: `bases.published boolean` (NULL = не проверялось),
  `publish_url text`, `publish_seen_at timestamptz`. NULL и `false` различать обязательно —
  «не знаем» и «точно нет» ведут к разным действиям.
- **P2. Источник данных.** Команда `CLUSTER_LIST_PUBLICATIONS` (или поле `published` в срезе
  баз): агент читает конфигурацию веб-сервера — виртуальные каталоги IIS/Apache и файлы
  `default.vrd` — и отдаёт `{ items: [{ key, published, url? }] }`. Из кластера это не видно:
  публикация живёт на веб-сервере, а не в кластере.
- **P3. Отображение.** Колонка «Публикация» во вкладке «Базы»: «опубликована» (со ссылкой),
  «нет», «не проверялось». Фильтр «только без публикации» — как уже сделанный фильтр
  «только где нет расширения N».
- **P4. Раскатка.** Команда `IB_PUBLISH` уже заведена (payload `{baseKey, alias?, dir?,
  webServer?}` → `{ok, url}`), пакетная, кнопка в панели есть. Осталось её исполнение в
  агенте: запуск `webinst`, только на localhost.
- **P5. Замыкание цикла.** Результат `IB_PUBLISH` пишет `published=true` и `publish_url` в
  реестр — там же, где сейчас оседают списки расширений и пользователей (общий путь приёма
  результатов в `agentRouter`). После этого агент выбирает транспорт по базе: есть публикация
  и расширение → HTTP, иначе → COM.

**Порядок:** P1+P2 дают видимость (сколько баз не опубликовано — сейчас это неизвестно),
P3 — управляемость, P4+P5 — собственно переход на быстрый транспорт.

## 4. Улучшения панели (сервис + фронт)

- **Отключение базы вручную.** `BaseService.setDisabled` есть, ручки и кнопки нет. Нужна для
  фантомных баз и тех, которые администрировать не нужно, чтобы они не попадали в раскатку.
- **Счётчик в заголовке вкладки** — сколько баз всего / доступно / без публикации: сейчас это
  видно только пересчётом строк.
- **Массовое «Проверить» по всем базам** с прогрессом: сейчас проверка идёт по отмеченным,
  а отметить 111 баз — это один клик по заголовку, но прогресс не виден.
- **История команд по базе** — маленькая вкладка «Журнал» с последними командами и их итогами:
  сейчас, чтобы понять «что с этой базой», нужен доступ к БД сервиса.

## 5. Привести «Базы» к общему паттерну списков и форм

**Что не так сейчас.** Вкладка «Базы» собрана самодельно: таблица через
`buildStaticTableProps`, свой переключатель вида, своя карточка `BaseForm`. Это работает,
но расходится с тем, как устроены все остальные списки приложения, — а значит расходится и
поведение: открытие элемента, множественный выбор, предпросмотр, «Показать в списке».

**Как устроен общий паттерн.**

| Слой | Компонент | Что даёт |
|---|---|---|
| Форма списка | `components/ModelList.tsx` | таблица, тулбар, множественный выбор, удаление, поиск, split-предпросмотр (`previewTabs`), открытие элемента через `addPane` |
| Форма элемента | `components/ModelForm.tsx` | вкладки, действия в шапке пейна, «Показать в списке» |
| Состояние списка | `useModelListState` → `useInfiniteModelList` | курсорная подгрузка, колонки из `columns.json`, права по `ENDPOINT_TO_MODEL` |

Для справочников только для чтения там уже есть ровно то, что нужно: **`hideAddDelete`** —
«для СПРАВОЧНИКОВ ТОЛЬКО ДЛЯ ЧТЕНИЯ, записи в которых порождаются документами, а не
пользователем». Базы — тот же случай: их заводят и удаляют в кластере 1С, а не в панели.

**Препятствие.** `ModelList` берёт данные из API ERP по `endpoint`, а базы отдаёт сервис
`ai` (`ai.buhprof.kz/v1/onec/bases`), и панель ходит туда напрямую. Пока это так, штатный
список неприменим. Отсюда развилка:

- **Вариант A — прокси в бэкенде** `/api1/onec/*` (только чтение для списка). Базы становятся
  обычным эндпоинтом ERP, и `ModelList` работает как есть. Попутно закрывает то, ради чего
  прокси предлагался в A0-5: единый контур авторизации, штатные права и аудит бэкенда.
- **Вариант B — обобщить `ModelList`** необязательным источником данных (`fetchPage`).
  Затрагивает общий компонент, на котором держится ~40 списков.

**Рекомендация: A.** Изменение локальное (новый роутер-прокси), общий компонент не трогается,
а список получает штатное поведение целиком.

### Задачи

- **L1. Прокси списка баз.** `GET /api1/onec/bases` в бэкенде: проксирует сервис `ai`,
  отдаёт форму, которую ждёт `useInfiniteModelList` (курсор, `items`, `total`). Только чтение.
- **L2. `columns.json` + `BasesList`** на `ModelList` с `hideAddDelete: true`.
  Удаление и создание НЕ применимы: записи приходят из кластера. Добавить эндпоинт в
  `ENDPOINT_TO_MODEL` → право `OneCAdmin`.
- **L3. `BasesForm` — форма элемента на `ModelForm`**: шапка полями + вкладки «Расширения»,
  «Пользователи», «Сеансы» вложенными таблицами. Только чтение, без сохранения; в шапке
  пейна — действия по базе (проверить расширения/пользователей, опубликовать, заблокировать
  вход).
- **L4. Открытие элемента — штатное**, через `addPane` из `ModelList`, а не подменой тела
  вкладки. Тогда работают вкладки пейнов, восстановление после F5 и «Показать в списке».
- **L5. Предпросмотр — через `previewTabs`**, а не собственный переключатель вида: кнопка
  «Переключить вид списка» уже есть в общем тулбаре и слушает `listLayoutToggle`.
- **L6. Множественный выбор — из коробки** `ModelList`; групповые операции (проверить,
  установить расширение, опубликовать) вешаются на `extraButtons`.
- **L7. Убрать самодельное** после L2–L5: `BaseForm.tsx`, стили `.Split*`, локальный
  переключатель вида, `buildStaticTableProps` для баз.

**Что останется вне паттерна осознанно.** Вкладки «Расширения», «Пользователи», «Задания»,
«Агенты» — это не справочники ERP, а операционные экраны над сервисом; переводить их на
`ModelList` смысла нет. Паттерн нужен там, где есть список сущностей с карточками, — то есть
для баз.
