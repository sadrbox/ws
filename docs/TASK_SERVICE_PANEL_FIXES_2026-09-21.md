## СП1. Процессы бизнес-агента: «Обновить сейчас» и обновление списка после снятия

**Сейчас.** `GET /v1/onec/agent-processes?live=1` ставит `AGENT_LIST_PROCESSES` без адресата
(`ai/src/http/onecRouter.ts:1938-1942`), а исполнитель выбирается через `pickAdminAgent`
(`ai/src/agents/service.ts:372-376`) — он берёт только `role === "admin"`. При этом сам список собирается по
обеим ролям (`onecRouter.ts:1943-1946`), и снятие процесса адресуется правильно (`onecRouter.ts:1962`).

**Что ломается.** На машине бухгалтера с одним бизнес-агентом «Обновить сейчас» отвечает «нет агента на
связи». После снятия процесса сборкой без эха панель сама зовёт `live.mutate()`
(`frontend/src/models/OneCAdmin/ProcessesTab.tsx:99,117`) — список не обновляется, снятый процесс висит в
таблице до следующего heartbeat, и человек снимает его второй раз.

**Сделать.**
1. Панель: `fetchAgentProcesses(true)` принимает `agentId` активной строки и передаёт его в запрос
   (`frontend/src/services/onec/api.ts`, `ProcessesTab.tsx:80-84`).
2. Сервис: `?live=1&agentId=<uuid>` → `run(req, "AGENT_LIST_PROCESSES", {}, { agentId })`. Без `agentId` —
   опрашивать всех агентов на связи, объявивших `agent.procs` (обе роли), и склеивать ответы, а не брать
   первого админ-агента.

**Готово, когда** на установке без админ-агента «Обновить сейчас» возвращает процессы бизнес-агента, а после
снятия его процесса строка исчезает сразу.

## СП2. Сводка бизнес-агента: показать то, что агент теперь отдаёт

**Сейчас.** Панель читает строку базы как `{key, status, transport, extVersion, overLimit, error}`
(`frontend/src/services/onec/api.ts:912`, `AgentActivityTabs.tsx:66-75`). Агент с выпуска `2026-09-21 09:24`
отдаёт оба набора имён, поэтому колонки «База» и «Статус» снова заполнены — но новое остаётся невидимым.

**Что показать дополнительно** (ответ команды `HEALTH` бизнес-агента):

```jsonc
{
  "status": "ok",
  "agent": { "version": "0.1.0+2026-09-21 09:24 (+05)", "build": "…", "instanceId": "…",
             "startedAt": "…", "uptimeSecs": 4210, "os": "windows" },
  "bases": [{ "baseKey": "Dev_01", "key": "Dev_01", "status": "ONLINE|UNAVAILABLE|UNKNOWN",
              "transport": "com", "reachable": true, "probed": true, "extVersion": "1.5.0",
              "organizations": 3, "overLimit": false,
              "lastOkAt": "2026-09-21T09:20:11Z",
              "error": "ONEC_TIMEOUT: база не ответила",
              "lastError": { "message": "ONEC_TIMEOUT: база не ответила", "at": "2026-09-21T09:18:02Z" } }],
  "limits": { "maxBases": 5, "maxBins": 10 }
}
```

**Сделать.** В таблице баз — колонка «Последний ответ» (`lastOkAt`) и время отказа (`lastError.at`): недоступная
база без времени выглядит одинаково и через минуту молчания, и через неделю, а действия по ним разные. Над
таблицей — строка из `agent`: сборка, время работы, экземпляр. Читать `baseKey`/`reachable` как основные поля,
`key`/`status` оставить запасными — они для совместимости.

## СП3. `AGENT_CONFIG_SET`: схема уже, чем белый список агента

**Сейчас** (`ai/src/commands/admin.ts:648-660`):

| Поле | Агент принимает | Сервис |
|---|---|---|
| `logLevel` | error, warn, info, debug, **trace** | debug, info, warn, error |
| `commandTimeoutSecs` | 0…86 400 (**0 — без предела**) | 10…3600 |
| `longCommandTimeoutSecs` | 0…604 800 (**0 — без предела**) | 60…86 400 |
| `ibParallel` | 1…64 | 1…32 |

**Что ломается.** У агента осознанно стоит `long_command_timeout_secs = 0` (ночная выгрузка идёт часами).
Администратор меняет в панели только уровень журнала — форма уходит целиком, и сервис отвечает
`VALIDATION_ERROR` по полю, которого человек не трогал.

**Сделать.** Принимать `0` у обоих пределов и `trace` в `logLevel`; панели — слать только изменённые поля.
Верхние границы (32, 3600, 86 400) оставить как есть, это разумная страховка.

**Готово, когда** правка уровня журнала у агента с нулевым пределом проходит без отказа.

## СП4. Решение: база бизнес-агента двоится в реестре

**Сейчас.** Правка 21.09 (`ai/src/http/agentRouter.ts:376-386`) даёт агенту без организации своё пространство
имён серверов (`serverOrg = organizationUuid || "agent:<id>"`) — это верно и закрывает смешивание баз разных
клиентов. Но `bases.sync` вызывается для обеих ролей (`agentRouter.ts:416-420`, `forRegistry` роль не
различает), а бизнес-агент живёт в пространстве своей организации. Итог: бизнес- и админ-агент одного
физического сервера пишут базы в **разные строки `servers`**, и одна база получает две строки в реестре.

Видно это так: в списке «Базы» база двоится; скрытие или блокировка одной строки не влияет на вторую.
Маршрутизация команд не страдает — `pickAdminAgent` собирает все серверы с этим ключом
(`ai/src/agents/service.ts:385-389`).

**Варианты (нужно решение сервиса).**

1. **Срез бизнес-агента не трогает `bases`** — он и так живёт в `agent_bases`. Минимальная правка:
   `if (role === "admin") await bases.sync(...)`. Цена: на машине, где админ-агента нет вовсе (файловая база у
   бухгалтера), базы исчезнут из общего списка «Базы» — их придётся показывать из `agent_bases` (карточка
   агента это уже умеет).
2. **Связывать агентов одной машины явно**: в карточке бизнес-агента — выбор сервера из уже известных; при
   регистрации сервер берётся из этой привязки, а не из имени. Дороже, но честно: имя перестаёт быть
   идентичностью, а связь становится видимой и правимой.
3. Оставить как есть и признать, что у бизнес-агента свой «сервер» (рабочее место). Тогда в списке баз нужен
   признак, откуда строка, чтобы двойники не выглядели ошибкой.

**Сторона агента уже сделана:** окно и README больше не обещают, что одинаковое имя связывает агентов
(подсказка поля «Рабочее место», README §«Две роли»).

## СП5. Потолок способностей роняет регистрацию целиком

**Сейчас.** `registerSchema.capabilities: z.array(z.string().max(50)).max(100)`
(`ai/src/http/agentRouter.ts:87`). Агент объявляет типы команд поимённо: 52 у роли «Кластер 1С», 42 у
бизнес-роли. Как только их станет больше сотни, зод отвергнет **всю регистрацию** (400 «Некорректная
регистрация») — агент уйдёт в офлайн целиком, сразу после обновления сборки, и причина будет неочевидна.

**Сделать.** Поднять предел до 300 и не ронять регистрацию при превышении: обрезать список, записав в журнал
`agent.capabilities.truncated` с числом отброшенных.

## СП6. Мелочи

- Гейт `AGENT_HEALTH` и `AGENT_LOG_TAIL` стоит на `agent.procs` (`ai/src/commands/admin.ts:291,304`), хотя агент
  с 20.09 объявляет `agent.log`. Пока обе объявляются вместе — не видно; перевести гейт журнала на `agent.log`,
  чтобы впредь не расходилось.
- Отказ обновления «хост не в списке доверенных» (`agent.update_hosts` в `agent.toml`) панель показывает как
  ошибку команды. Стоит объяснить в тексте, что это настройка на машине агента: доверие к узлу раздачи сборок
  раздаёт владелец машины, а не отправитель команды.
