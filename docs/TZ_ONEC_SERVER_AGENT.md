# Серверный агент 1С: администрирование всех баз кластера

Версия 1.0 · 2026-09-03 · статус: план задач (реализация не начата)

## 1. Задача

Бухгалтерская компания обслуживает **до 100 баз** разных клиентов, все базы — на одном
сервере 1С. Требуется:

- **один агент на сервер** (а не по агенту на базу), умеющий работать со всеми базами кластера;
- административные операции через чат ИИ-помощника — в частности «создать пользователя во
  всех базах»;
- **административная панель в aleppo.kz**: базы, сеансы, показатели, управление.

## 2. Что мешает сделать это «как есть»

В сервисе `ai/` понятия «база 1С» **нет**:

| Факт | Где |
|---|---|
| `agents.organization_uuid text NOT NULL` — агент жёстко привязан к одной организации | `ai/migrations/001_init.sql` |
| Агент отдаёт единственный `onec { reachable, version }` — то есть одна база | `ai/src/http/agentRouter.ts:32` |
| Команда адресуется парой `agent_id` + `organization_uuid`, без базы | `ai/src/commands/queue.ts:84` |
| Исполнитель выбирается как «онлайн-агент этой организации» | `ai/src/agents/service.ts:102` |
| Все 20+ инструментов — бизнес-операции внутри одной базы (`CREATE_SALE`, `SEARCH_…`) | `ai/src/tools/registry.ts` |

Плюс два обстоятельства именно нашего случая:

1. **Организация ≠ база.** В aleppo.kz бухгалтерская компания — одна организация; 100 баз
   клиентов — это новое измерение *внутри* организации. Текущая модель его не выражает.
2. **Два разных транспорта к 1С.** Администрирование распадается на два класса, и это
   определяет весь план:
   - **кластерные операции** (список баз, сеансы, соединения, снятие сеанса, блокировка
     начала сеансов) — через **RAS/`rac`**, вход в базу не нужен, расширение не нужно,
     нужен только администратор кластера;
   - **внутрибазовые операции** (создание пользователя ИБ, роли, сброс пароля) — нужно
     попасть **внутрь каждой базы**: либо COM-соединение (`V83.COMConnector`, только
     Windows) под администратором ИБ, либо расширение `bpapi`, опубликованное в базе.

   Отсюда следствие, которое надо принять до кода: «создать пользователя во всех базах»
   требует **служебного администратора ИБ в каждой из 100 баз**. Там, где его ещё нет,
   получается «курица и яйцо» — нужен разовый bootstrap (задача A7).

⚠️ **Немедленно, до подключения второй базы:** в `ai/.env` стоит `AGENT_ORG_BINDING=any`.
Это режим одного стенда: организация без своего агента получает *любой* онлайн-агент.
При нескольких базах это означает уход команды в чужую базу. Переключить на `strict`.

## 3. Решения, которые нужны до старта (A0)

| # | Вопрос | Почему блокирует |
|---|---|---|
| 1 | ОС сервера 1С — Windows или Linux? | COM-соединение есть только на Windows. На Linux внутрибазовые операции возможны только через расширение `bpapi` или пакетный запуск `1cv8`. |
| 2 | Поднят ли `ras` (порт 1545), версия платформы, учётка администратора кластера | Весь кластерный блок (A3-1) строится на `rac`. |
| 3 | Служебный админ ИБ: единый логин/пароль во всех базах или свой на базу | Определяет формат реестра баз и процедуру bootstrap. |
| 4 | Где хранить учётки баз: в БД `ai` (шифровано) или в конфиге агента на сервере 1С | **Рекомендация: на агенте.** Секреты не покидают сервер 1С; в `ai` хранится только ключ базы, без пароля. |
| 5 | Транспорт админ-панели: напрямую в `ai` (как `AiAssistant`) или прокси через backend | **Рекомендация: прокси `/api1/onec/*`.** Работают существующие права и аудит, нет второго CORS-контура. |

## 3.1. Роли агентов: их два

Бизнес-операции и администрирование разводятся на **два агента — две отдельные службы на
сервере 1С**, с разными ролями и разными учётными данными ОС:

| | Бизнес-агент (`role=business`) | Админ-агент (`role=admin`) |
|---|---|---|
| Что делает | документы и справочники внутри баз (`CREATE_SALE`, `SEARCH_*` …) | кластер, сеансы, пользователи ИБ (`CLUSTER_*`, `IB_*`) |
| Транспорт | расширение `bpapi`, опубликованное в базе | `rac` (RAS) + COM-соединение |
| Права | пользователь базы с рабочими ролями | администратор кластера + администратор ИБ |
| Capabilities | `onec.business` | `cluster.admin`, `ib.admin` |
| Что даёт в `bases` | `ext_version` (где стоит расширение) | сам список баз, `onec_version`, сеансы |

Смысл разделения — **разный радиус поражения**: компрометация бизнес-пути не даёт прав
администратора кластера. Поэтому агенты должны быть именно **разными процессами под разными
учётками ОС**; две регистрации внутри одного процесса дали бы разделение только на бумаге.

Это про коннекторы, не про ИИ: **помощник в чате остаётся один**, админ-инструменты в нём
закрыты правом `OneCAdmin` и классом `CRITICAL` (карточка подтверждения).

## 4. План задач

### A1. Модель «сервер → базы → агенты» в сервисе `ai` — P0

Агенты привязываются не к базе, а к **серверу 1С**, и различаются **ролью** (см. §3.1):
источник истины по списку баз — админ-агент (видит их через `rac`), наличие и версию
расширения подтверждает бизнес-агент.

- миграция `ai/migrations/002_bases.sql`:
  ```sql
  CREATE TABLE servers (                 -- сервер (кластер) 1С
      id uuid PRIMARY KEY,
      organization_uuid text NOT NULL,
      name text NOT NULL DEFAULT '',
      ras_host text, ras_port int,
      created_at timestamptz NOT NULL DEFAULT now()
  );
  ALTER TABLE agents ADD COLUMN server_id uuid REFERENCES servers(id);
  ALTER TABLE agents ADD COLUMN role text NOT NULL DEFAULT 'business';  -- business | admin

  CREATE TABLE bases (
      id uuid PRIMARY KEY,
      server_id uuid NOT NULL REFERENCES servers(id),
      key text NOT NULL,              -- имя ИБ в кластере
      name text NOT NULL DEFAULT '',
      status text NOT NULL DEFAULT 'UNKNOWN',
      onec_version text,
      ext_version text,               -- версия расширения bpapi; NULL = не установлено
      sessions_count int, last_seen_at timestamptz, disabled_at timestamptz
  );
  CREATE UNIQUE INDEX bases_server_key_idx ON bases (server_id, key);
  ALTER TABLE commands ADD COLUMN base_key text;
  ```
- `ai/src/bases/service.ts`: upsert из heartbeat, список, вкл/выкл базы;
- маршрутизация в `ai/src/agents/service.ts`: `pickOnline(org)` →
  `pickAgentFor(org, baseKey, role)` — база даёт сервер, сервер + роль дают агента;
  команда без нужной роли не ставится вообще (а не уходит «хоть кому-то»);
- идемпотентность: `request_id` уникален в пределах пары (агент, база), а не агента.

### A2. Протокол агента v2 — P0

- `POST /agent/v1/register`: `bases[]` + `capabilities: ["cluster.admin", "ib.admin", …]`;
- `POST /agent/v1/heartbeat`: состояния баз (доступна, версия платформы, версия расширения,
  число сеансов). **Троттлинг обязателен:** 100 баз каждые 30 с — это лишний трафик и
  лишние обращения к кластеру; полный срез раз в N минут, между ними — дельты;
- `GET /agent/v1/commands` возвращает команды по разным базам; агент исполняет с
  **ограничением параллелизма** (см. A6 про лицензии);
- обратная совместимость: агент без `bases[]` = одна псевдо-база `default`.

### A3. Административные команды (whitelist) — P0/P1

Кластерные, через `rac` (**P0**, вход в базу не нужен):
`CLUSTER_LIST_INFOBASES`, `CLUSTER_LIST_SESSIONS`, `CLUSTER_LIST_CONNECTIONS`,
`CLUSTER_TERMINATE_SESSION`, `CLUSTER_SET_SESSIONS_LOCK`, `CLUSTER_INFOBASE_INFO`.

Внутрибазовые (**P1**, требуют A7):
`IB_LIST_USERS`, `IB_CREATE_USER`, `IB_UPDATE_USER` (роли, сброс пароля), `IB_DISABLE_USER`.

Классы операций (`OperationClass` в `ai/src/tools/registry.ts`): чтение — `READ`;
`IB_CREATE_USER`, `IB_UPDATE_USER`, `CLUSTER_TERMINATE_SESSION`, `CLUSTER_SET_SESSIONS_LOCK`
— `CRITICAL`, то есть проходят через уже готовую карточку подтверждения в
`ai/src/chat/workflow.ts`.

### A4. Пакетные операции «во всех базах» — P1

Одна фраза в чате → N команд. Нужен уровень задания:

- таблица `command_batches (id, organization_uuid, user_uuid, type, payload, total, done, failed, state)`
  + `commands.batch_id`;
- инструмент чата `admin_create_user` с областью `scope: { all | bases[] | tag }`;
- карточка подтверждения показывает **список баз и их количество** до запуска;
- прогресс в диалоге, отчёт по базам (успех/ошибка), **повтор только неуспешных**;
- батч не блокирует очередь: обычные команды идут вперёд пакетных.

### A5. Админ-панель в aleppo.kz — P0 (вкладки «Базы»/«Сеансы»), P1 (остальное)

Новый пейн `frontend/src/models/OneCAdmin/`, вкладки:

| Вкладка | Содержимое | Приоритет |
|---|---|---|
| Базы | список, статус, версия платформы и расширения, число сеансов, последняя связь | P0 |
| Сеансы | фильтр по базе/пользователю, снятие сеанса (подтверждение) | P0 |
| Пользователи базы | список, создать / отключить / сбросить пароль | P1 |
| Задания | батчи с прогрессом и отчётом по базам | P1 |
| Агенты | регистрация, выдача и ротация токена, статус | P1 |

Плюс: право `OneCAdmin` в системе прав, пункт NavList под ним, транспорт по решению A0-5.

### A6. Безопасность, лицензии, аудит — сквозная, P0

- админ-команды ставятся только агенту с `capabilities: cluster.admin` / `ib.admin`;
- **лицензии 1С**: COM-соединение занимает сеанс на время работы → пул с жёстким лимитом
  параллелизма и таймаутом; 100 последовательных подключений — это минуты, и это нормально;
- аудит каждой админ-команды (кто, база, что) — механизм `ai/src/audit/index.ts` уже есть;
- учётки баз — по решению A0-4; если всё же в БД `ai`, то шифрованием ключом из env;
- rate limit на кластерные опросы, чтобы панель не «долбила» `rac`.

### A7. Раскатка на 100 баз (bootstrap) — P1

- инвентаризация: `rac infobase summary list` → импорт в таблицу `bases`;
- служебный администратор ИБ: пакетное создание + проверка, отчёт «где не удалось»;
- расширение `bpapi`: пакетная установка через конфигуратор в фоновом режиме, версия
  расширения приходит в heartbeat → в панели видно, **где расширение не стоит или отстало**;
- регламент обновления расширения на всех базах.

## 5. Очерёдность

- **P0 (первый заход, без риска для данных):** A0 → A1 → A2 → кластерная часть A3 (только
  чтение + снятие сеанса) → вкладки «Базы» и «Сеансы» в A5. Уже даёт полную видимость по
  серверу и не требует ни расширения, ни служебных учёток в базах.
- **P1:** A7 (bootstrap) → внутрибазовая часть A3 → A4 (батчи) → остальные вкладки A5.
- **P2:** метрики (размер ИБ, память рабочих процессов), плановые задания, оповещения.

## 6. Открытые вопросы

1. Нужна ли изоляция: должен ли конкретный сотрудник видеть только закреплённые за ним базы?
2. Хранить ли соответствие «база 1С ↔ клиент/контрагент в aleppo.kz» (для отчётов и прав)?
3. Нужны ли операции над самим кластером (создание/удаление ИБ) или только над сеансами и
   пользователями?
