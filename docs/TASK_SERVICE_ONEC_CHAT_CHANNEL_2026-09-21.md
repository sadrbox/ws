# Задача сервису: канал «расширение 1С ↔ сервис» — загрузка вложений, идемпотентность хода, ротация токена

21.09.2026. Основание — разбор канала `/v1/onec-chat/*` (см. `CONTRACT_1C_CHAT_2026-09-19.md`,
`CONTRACT_BASE_REGISTRATION_2026-09-19.md`). **Сторона расширения уже сделана** (`buhprof_api`, модуль
`BPAPI_Чат`): оно шлёт новые заголовки, умеет загружать вложения отдельным запросом с откатом на прежний путь и
принимает смену токена. Заглушка `buhprof_api/tools/mock_chat_service.py` реализует всё описанное ниже — на ней
пара проверена (загрузка 4096 байт с совпавшим sha256, повтор хода по ключу, смена токена в ответе хода).

Порядок — по пользе. §1 и §2 стоит сделать вместе: они про одно и то же — чтобы обрыв связи не стоил ни
дубля в диалоге, ни повторной отправки многомегабайтного файла.

## Правка 22.09 со стороны расширения: приём base64 в ходе больше не нужен

Расширение `buhprof_api` **ещё нигде не установлено** — оно в разработке. Значит защищать совместимость со
старым способом передачи вложения (base64 в `attachments[].content`) не от чего: установленных баз, которые
слали бы его, не существует. Откат на base64 из расширения убран — путь один, через `POST /uploads`; сервис без
этого маршрута расширение называет прямо («сервис не принимает вложения — обновите BuhProf AI»), а не шлёт
молча раздутый ход. Заглушка приведена к тому же: `content` в ходе отвергается (`UNSUPPORTED_ATTACHMENT`),
неизвестный `fileId` — тоже.

Сервису из этого следует — **сделано 22.09**:

1. ✔ Приём `content` в `attachments` убран: ход с base64 отвечает `415 UNSUPPORTED_ATTACHMENT` и называет
   лечение («загрузите файл запросом `POST /v1/onec-chat/uploads` — обновите BuhProf AI»). Молчаливый приём
   означал бы, что раздутые ходы живут дальше, а находятся уже по памяти службы.
2. ✔ Предел тела JSON разведён на два: веб-чат ERP (`POST /v1/chat`) по-прежнему принимает вложения base64
   и держит прежний запас, всем остальным маршрутам — `JSON_BODY_MAX_MB` (**2 МБ**, было 82). Сначала стояло
   восемь — из опасения, что печатная форма приедет в `toolResults` байтами; аудит 22.09 нашёл ответ в самом
   контракте канала: форма 1С файлы в сервис не отправляет, вместо содержимого кладёт
   `{"contentOmitted": true, "bytes": N}`. Опасение было напрасным, предел вернули к обычному.
3. ✔ `X-Ext-Version`, `EXT_TOO_OLD` и `features` оставлены как есть.

## Дополнено аудитом 22.09: отзыв токена базой

Аудит согласованности нашёл маршрут, обещанный контрактом регистрации и не сделанный:

## 1. `POST /v1/onec-chat/uploads` — вложение отдельным запросом

**Зачем.** Сейчас PDF едет внутри хода в base64: 20 МБ файла превращаются в ~27 МБ тела, и ход целиком
держится в памяти и в 1С, и на сервисе (отсюда `express.json({ limit: MAX_MB × 4 + 2 })`). Отдельная загрузка
это снимает.

**Чего она НЕ делает — дозагрузки** (уточнение 22.09, прежняя формулировка вводила в заблуждение). Обрыв на
90-м проценте по-прежнему означает отправку файла заново: протокол не умеет продолжать с середины. Разница в
другом — заново уходит только файл, а не весь ход с ним вместе, и расширение повторяет загрузку само (один
раз, только при обрыве связи). Настоящая дозагрузка — отдельная задача, см. §6.

```
POST /v1/onec-chat/uploads?fileName=<percent-encoded>
X-Base-Token, X-1C-User-Id, X-Ext-Version, X-Request-Id
Content-Type: application/pdf
<бинарное тело, без base64>

200 { "success": true, "data": { "fileId": "uuid", "bytes": 4096, "sha256": "…" } }
413 { "success": false, "error": { "code": "FILE_TOO_LARGE", "message": "файл больше 20 МБ" } }
```

- Тело — сырые байты: для этого маршрута нужен `express.raw({ type: "application/pdf", limit: … })`, а не
  `express.json`. Общий лимит тела JSON можно вернуть к обычному, когда расширения обновятся.
- `fileId` живёт до конца диалога (или сутки), привязан к паре «база + пользователь», у чужой пары не
  открывается.
- Имя файла кириллическое, поэтому едет в строке запроса закодированным: в заголовке HTTP ему нельзя.

**Ход после загрузки** несёт вместо `content` идентификатор:

```jsonc
"attachments": [{ "fileName": "Выписка за август.pdf", "mimeType": "application/pdf", "fileId": "uuid" }]
```

~~Приём `content` (base64) остаётся и не устаревает~~ — **отменено правкой 22.09** (см. раздел выше): путь
один, `content` в ходе отвергается с `UNSUPPORTED_ATTACHMENT`. Неизвестный `fileId` — отказ `UNKNOWN_FILE`.

**Как расширение узнаёт, что сервис умеет загрузку.** Пробует `POST /uploads`; при `404`/`UNKNOWN_ROUTE`
отката больше нет — расширение называет причину человеку («сервис не принимает вложения — обновите
BuhProf AI»). Отдельно `GET /ping` отдаёт `features` (см. §4) — по ним панель и журнал видят, что умеет
эта установка.

**Отличия от задуманного.** Срок жизни `fileId` — не «до конца диалога или сутки», а общий срок файлов
диалога (`FILE_TTL_DAYS`, по умолчанию 7 дней): загруженное ложится в ту же `chat_files`, где живут вложения
и печатные формы, и убирается той же уборкой. Отдельного хранилища с отдельным сроком заводить не стали —
оно означало бы вторую уборку и второй способ потерять файл. Предел тела JSON снижен 22.09 (см. раздел о
правке): прежний `CHAT_ATTACHMENT_MAX_MB × 4 + 2` остался только у веб-чата ERP, который действительно
возит вложения в теле.

## 2. `Idempotency-Key` на `POST /turn`

**Зачем.** Оборванный ответ не говорит, дошёл ход или нет. Сегодня расширение показывает «нет связи», человек
пишет заново — и, если первый ход всё-таки дошёл, в диалоге два одинаковых сообщения, а модель отвечает дважды.

Расширение теперь шлёт заголовок `Idempotency-Key` (UUID на круг) и **ровно один раз** повторяет ход с тем же
ключом, когда ответа не было вовсе.

**Сделать.** Запомнить пару «ключ → ответ» (ключ в пределах базы и пользователя, хранить сутки). Повтор с тем
же ключом отдаёт сохранённый ответ и НЕ создаёт второй ход. Ключ пришёл, а прошлый ход ещё выполняется —
ответить `202` с тем же `conversationId` и состоянием `PROCESSING`, а не начинать заново.

Тела при повторе сверять не нужно: ключ рождается на стороне 1С один раз и не переиспользуется.

**Отличие от задуманного.** Добавлено правило, которого в задаче не было: ход, сорвавшийся ПО ВИНЕ СЕРВИСА
(`5xx`), ключ освобождает. Иначе единственная поломка сервиса запирала бы этот ход на сутки: расширение
повторило бы его с тем же ключом и получило бы в ответ ту же ошибку, уже без попытки выполнить. Ответы `400`
и `404` сохраняются как есть — это ответ, и повтор обязан получить тот же.

## 3. Тихая смена токена базы

**Зачем.** Токен базы живёт до отзыва, то есть годами. Смена вручную — поход к каждому клиенту, поэтому её
никто не делает; украденный токен работает, пока о нём не узнают.

**Сделать.** Сервис кладёт новый токен в поле `baseToken` любого успешного ответа (проще всего — ответа
обычного хода) и с этого момента принимает оба: новый и прежний, в течение перекрытия (сутки хватит).
Расширение сохраняет новый в безопасное хранилище само — это уже сделано и проверено на заглушке.

Разумная политика: ротация раз в 90 дней и немедленно — по кнопке в панели («Сменить токен базы»), если есть
подозрение на утечку. Отзыв (`POST /revoke`) остаётся как был.

**Отличия от задуманного — три, и все в одну сторону: база не должна остаться без связи из-за смены,
которой не просила.**

1. **Смену получает только расширение `1.5.0` и новее** (`ONEC_EXT_ROTATION_MIN`, версия — из `X-Ext-Version`).
   Старое расширение новый токен проигнорирует, и по истечении перекрытия база замолчала бы совсем.
2. **Недошедший токен отдаётся ТОТ ЖЕ.** Копия преемника хранится закрытой (aes-256-gcm, ключ из секрета
   сервиса) до первого успешного запроса новым токеном. Выпускать новый токен на каждый недошедший ответ
   значило бы плодить годные ключи — ровно то, от чего ротация и защищает.
3. **Перекрытие продлевается, пока преемник не подтверждён.** Иначе база, не сохранившая новый токен,
   через сутки теряет доступ; отозвать связь немедленно по-прежнему можно кнопкой «Отозвать».

Токен кладётся в ответ ХОДА (`POST /turn`), а не любого успешного ответа: так и было предложено как
«проще всего», и так и сделано. Кнопка в панели названа «Сменить» и стоит рядом с «Отозвать».

## 4. Версия расширения, номер запроса и `features`

Расширение с этой сборки шлёт в КАЖДОМ запросе:

| Заголовок | Значение |
|---|---|
| `X-Ext-Version` | версия расширения, например `1.5.0` |
| `X-Request-Id` | UUID запроса; тот же номер пишется в журнал 1С при сбое связи |

**Сделать.** Писать оба в журнал сервиса рядом с `baseId`/`userId`. По версии — отвечать внятно, когда
расширение старое (`EXT_TOO_OLD` вместо непонятного отказа на незнакомое поле). `X-Request-Id` возвращать в
заголовке ответа: тогда разбор «у клиента что-то не сработало» сводится к поиску одного значения в двух
журналах.

`GET /ping` дополнить полем `features` — список того, что сервис умеет сверх базового контракта:
`["uploads", "idempotency", "token-rotation"]`. Форма «Подключение к BuhProf AI» показывает его администратору,
а поддержка по нему сразу видит, чего ждать от этой установки.

**Отличия от задуманного.** В журнал строкой на запрос пишутся только ход и загрузка; остальное — на уровне
`debug`. Форма опрашивает `GET /conversations/:id` раз в секунду, пока идёт распознавание выписки, и строка на
каждый опрос утопила бы в шуме то, ради чего журнал ведётся. `EXT_TOO_OLD` отвечает `426` и только когда
`ONEC_EXT_MIN_VERSION` задан, а версия пришла: сборка до §4 версии не шлёт вовсе, и отсекать её по молчанию
нельзя. `features` называет ровно включённое: чего в установке нет, того и не обещаем.

## 5. Ход по идентификатору вместо удержания соединения (позже)

Сейчас `POST /turn` держится до 120 секунд и при таймауте отвечает `PROCESSING`, а расширение дочитывает
диалог через `GET /conversations/:id`. Это работает, но зависит от прокси между базой и интернетом: корпоративный
прокси рвёт такие запросы раньше, и выглядит это как «сервис не отвечает».

Предложение на потом: `POST /turn` сразу возвращает `{ turnId, state: "PROCESSING" }`, а `GET /turn/:id`
отдаёт результат. Расширение сможет опрашивать короткими запросами. Делать сейчас не обязательно — нынешняя
схема с `PROCESSING` рабочая; но если появятся жалобы «ход обрывается ровно на минуте», причина будет эта.

## 6. Дозагрузка после обрыва (пока НЕ делается)

**Как есть сейчас.** Загрузка — один запрос на файл. Оборвалась связь — расширение повторяет её один раз, и
файл уходит с нуля; повтор не удался, ход продолжается без этого вложения и говорит об этом пользователю.
Отказ сервиса (размер, место, токен) не повторяется: вторым разом он не станет другим.

**Чего это стоит.** 20 МБ по офисному каналу — секунды, и полный повтор незаметен. Больно становится на
медленной или рвущейся связи (мобильный модем, сельский офис): там обрыв на 90-м проценте означает начать
сначала, и с некоторой вероятностью так и не дойти.

**Если понадобится** (жалобы «выписка не отправляется» с плохих каналов), дозагрузка выглядит так:

```
POST /v1/onec-chat/uploads/init?fileName=…   → { uploadId, chunkSize }
PUT  /v1/onec-chat/uploads/<uploadId>?offset=N   (кусок, бинарно) → { received }
GET  /v1/onec-chat/uploads/<uploadId>            → { received }   ← сколько сервис уже принял
POST /v1/onec-chat/uploads/<uploadId>/complete   { sha256 } → { fileId, bytes }
```

Расширение читает файл кусками (`ЧтениеДанных`, 1–4 МБ) и после обрыва спрашивает `received`, продолжая с
этого места. Незавершённая загрузка убирается по сроку (час). Оценка: сторона 1С — день, сервис — день-два
вместе с уборкой и тестами. Сейчас не делаем: пока нет ни одной установки, о поведении на плохих каналах
известно ровно ноль, а угадывать здесь дороже, чем дождаться первой жалобы.

## 6. Дозагрузка прерванного файла (позже, не начато)

Сегодня оборванная загрузка начинается сначала: протокол не умеет продолжать с середины. На двадцати
мегабайтах по слабому каналу это заметно, но лечится не скоро — дозагрузка означает третий маршрут
(`PATCH /uploads/:id` или `Content-Range`), хранение незаконченных кусков и их уборку, то есть ещё один
способ потерять файл. Делать стоит, когда появятся жалобы именно на это, а не «на всякий случай».

Признак, что пора: в журнале повторные `POST /uploads` одного и того же файла с одной базы подряд.

## Готово, когда

1. Вложение уходит отдельным запросом: в журнале сервиса видно `POST /uploads` и ход с `fileId`; ход с
   `content` теперь невозможен — он отвергается (правка 22.09), так что признак проверяется самим отказом. Дозагрузки нет и не обещается — см. §6.
2. Повтор хода с тем же `Idempotency-Key` не создаёт второго сообщения в диалоге — ни при нормальной работе,
