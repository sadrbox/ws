# Задача агенту: установка расширения в базу кластера — не через `ibcmd`

27.09.2026. Основание — живые прогоны `IB_INSTALL_EXTENSION` по базе `_transition` (SERVER, агент
`2026-09-25 21:58`), журнал команд сервиса с 16.09.

## Что происходит

Все установки расширения в `_transition` с 16.09 (восемь команд) кончаются одинаково:

```
IB_TIMEOUT: ibcmd extension create по базе «_transition» не ответил за 180 с — процесс снят.
Обычно это занятый рабочий каталог или блокировка в самой базе
```

(две попытки агента по 180 с = 361 с на команду), а 16.09 — «Ошибка разделенного доступа к базе данных.
База данных заблокирована: … приложение: Фоновое задание». Единственный успех — 16.09 04:25 («esf», 68 с).

27.09 сервис стал делать перед установкой то, что предписывает контракт («Запрет регламентных заданий»):
`CLUSTER_SET_SCHEDULED_JOBS {denied:true}` → `CLUSTER_SET_SESSIONS_LOCK {enabled:true}` → `CLUSTER_LIST_SESSIONS`
(вернул `items: []`) → выпуск команды. Результат тот же: `ibcmd extension create` висит 180 с и снимается
(команда `cmd_391b0d58b3064116`, 07:17–07:23 UTC). Сеансов нет, задания запрещены, вход закрыт — а `ibcmd` базу
не получает. Держит её не сеанс, а соединение рабочего процесса кластера с СУБД: rphost не отпускает базу
после ухода сеансов, а `rac` до соединений с СУБД не дотягивается. Для базы, зарегистрированной в кластере,
`ibcmd` — путь монопольный, и в рабочем кластере он не сработает никогда, кроме случайного простоя.

## Что сделать

1. **Ставить расширение через кластер, а не мимо него.** У агента путь через COM есть (контракт: «`IB_INSTALL_EXTENSION`
   через COM со сборки `23:24`»; `PROMPT_AGENT_IB.md`, «Работа с расширениями через COM») — для базы кластера
   он должен быть основным: `РасширенияКонфигурации().Создать()` / `Записать()` через соединение с базой не требует
   монопольного доступа для расширения, не меняющего структуру данных; `safeMode` — свойство расширения.
   `ibcmd` оставить для файловых баз и для случая, когда вход в базу невозможен.
2. **Не ждать 180 с дважды.** Если `ibcmd` выбран и не получил базу за первые секунды (блокировка), переходить
   на COM в той же команде, а не повторять `ibcmd`. Итог одной команды — не 6 минут.
3. **Сказать, каким путём ставили.** В ответе `IB_INSTALL_EXTENSION` — `via: "com" | "ibcmd" | "designer"` и в
   отказе — на каком пути упало; сейчас в `details` только `pid/host/build`, и сервису не по чему различать.
4. **Список сеансов базы.** `CLUSTER_LIST_SESSIONS {baseKey:"_transition"}` дважды вернул `items: []` при
   фоновых заданиях в базе (16.09 их видел сам `ibcmd`). Проверить, что отбор по `baseKey` совпадает с именем
   базы в `rac` (регистр, ключ vs имя) и что фоновые задания попадают в список.

## Добавлено вечером 27.09: «Ошибка при работе с файлом» и кодировка вывода

Попытка 16:03 UTC (та же база, `buhprof_api`, safeMode): подготовка сервиса прошла, `ibcmd` на этот раз базу
получил — и через 3 мин 4 с ответил:

```
ibcmd: [WARN] ╨Ю╤И╨╕╨▒╨║╨░ ╨┐╤А╨╕ ╤А╨░╨▒╨╛╤В╨╡ ╤Б ╤Д╨░╨╣╨╗╨╛╨╝
[WARN] ╨Ю╤И╨╕╨▒╨║╨░ ╨┐╤А╨╕ ╤А╨░╨▒╨╛╤В╨╡ ╤Б ╤Д╨░╨╣╨╗╨╛╨╝

```

Две вещи:

5. **Кодировка.** «╨Ю╤И╨╕╨▒╨║╨░» — это UTF-8 «Ошибка», прочитанный как cp866: агент декодирует stdout/stderr
   `ibcmd` не той кодовой страницей. Раз так читается вывод, так же, вероятно, и пишется командная строка:
   путь к временному `.cfe` с кириллицей или пробелом (профиль службы, `%TEMP%`) уходит в `ibcmd` искажённым —
   отсюда «Ошибка при работе с файлом» при заведомо целом файле (контейнер 1С, заголовок `FFFFFF7F`, 380 157 байт).
   Вывод `ibcmd` читать в UTF-8 (`ibcmd` пишет UTF-8 независимо от консоли), временный файл класть в путь из
   ASCII (например `C:\ProgramData\BPAPIAgent\tmp\<uuid>.cfe`) и передавать путь в UTF-16 API процесса.
6. **Что за файл падает.** Если это не путь, а само содержимое — сказать в отказе, какой файл и на каком шаге
   (`extension create` / `config load --extension`), и вернуть первые байты/размер: сервис отдаёт файл как есть
   из панели, и без этого нельзя отличить битый `.cfe` от битого пути.

## Новая команда: `IB_EXPORT_EXTENSION` — выгрузка расширения в .cfe

Панель получила в карточке базы («Расширения» → меню «Расширение») пункт «Выгрузить расширение в .cfe».
Сервис ставит команду `IB_EXPORT_EXTENSION {baseKey, name}` (READ, `ib.admin`, база обязательна, срок 900 с);
сборка агента без неё получает отказ `CAPABILITY_MISSING` до постановки — ничего не ломается, но пункт не работает.

Ожидаемый ответ: `{ "ok": true, "name": "buhprof_api", "contentBase64": "<файл .cfe>", "version": "1.8.3",
"fileName": "buhprof_api.cfe" }` — файл целиком в результате (как `contentBase64` при установке, в обратную
сторону; предел тела ответа сервису — `JSON_BODY_MAX_MB`, по умолчанию 5 МБ). Путь — тот же, что и у чтения
расширений (COM `РасширенияКонфигурации()` → `Получить()`/`Выгрузить()`, либо `ibcmd extension export` для
файловых баз). Расширения нет — `IB_ERROR` «расширение «…» не найдено» с перечнем имеющихся имён.

## Что уже сделано сервисом (27.09)

Подготовка базы перед `IB_INSTALL_EXTENSION` и `IB_DELETE_EXTENSION` (`ai/src/onec/exclusiveOps.ts`): запрет
заданий → закрытие входа → снятие сеансов → операция → вход открыт, запрет по `was`; состояние шагов — в команде,
восстановление после перезапуска сервиса; повторы «база занята» идут через ту же подготовку; имя расширения
проверяется как идентификатор до постановки. Это остаётся и после вашей правки — лишним не будет.

## Проверка

На `_transition` с живым фоновым заданием: `IB_INSTALL_EXTENSION {name:"buhprof_api", safeMode:true}` → `ok:true`
за десятки секунд, расширение в `IB_LIST_EXTENSIONS`; в ответе `via`. Повтор с тем же именем — «уже существует»
или обновление, но не `IB_TIMEOUT`.
