# Промпт для сессии bpapi_agent: четыре недостающие команды кластера + открытые дефекты

2026-09-06. Копия того, что отдаётся в сессию разработки агента (та машина этот репозиторий
не видит). Предыдущие: `PROMPT_AGENT_IB.md`, `PROMPT_AGENT_TRANSPORT.md`.

Сверка по факту: в сервисе заведено **17** команд, агент объявляет **13**. Не реализованы
четыре — все читающие, кроме одной, и все идут через `rac`, в базы не заходят.

---

В bpapi_agent нужно реализовать четыре команды кластера. Сервис их уже принимает,
маршрутизирует и показывает в панели; сейчас он отвечает «обновите агента на сервере 1С»,
потому что агент не объявляет эти типы в `capabilities`.

## 1. `CLUSTER_LIST_LOCKS` — блокировки

```jsonc
// payload
{ "baseKey": "buh_alma" }   // необязателен: без него — блокировки всего кластера
// результат
{ "items": [ { "session": "…", "connection": "…", "object": "…", "locked": "…" } ] }
```

Зачем: «база висит» почти всегда означает блокировку. Без этого списка снятие сеанса —
действие наугад, и мы это делали вслепую весь день.

## 2. `CLUSTER_LIST_PROCESSES` — рабочие процессы

```jsonc
{}   // payload
{ "items": [ { "host": "…", "port": "…", "pid": "…", "enabled": "…", "running": "…",
               "memorySize": "…", "avgCallTime": "…", "connections": "…" } ] }
```

Зачем: панель знает про базы и сеансы, но ничего про сервер, на котором всё это живёт.

## 3. `CLUSTER_LIST_LICENSES` — лицензии

```jsonc
{}   // payload
{ "items": [ { "userName": "…", "host": "…", "appId": "…", "licenseType": "…", "series": "…" } ] }
```

Зачем: отказы при одновременных подключениях к базам упирались в лицензии, а увидеть, кто
их держит, было нечем. Это самый практичный из четырёх пунктов.

## 4. `CLUSTER_DISCONNECT` — разорвать соединение (**CRITICAL**)

```jsonc
{ "connectionId": "<uuid соединения>", "baseKey": "…" }   // baseKey необязателен
{ "ok": true }
```

⚠ Идентификатор — **UUID соединения**, а не его номер. На сеансах это уже проверено зондом:
`rac session terminate` на номер отвечает «Ошибка разбора параметра: session», на UUID —
«Сеанс с указанным идентификатором не найден». У соединений ожидается то же самое.

## Общие требования

- **Объявить типы в `capabilities`** при регистрации: сервис проверяет перечень ДО постановки
  команды в очередь и без объявления откажет сразу. Способность прежняя — `cluster.admin`.
- **Строки — словари строк**, ключи как отдаёт `rac`: панель показывает их как есть,
  переименовывать не нужно. Имена выше — ожидаемые, но если `rac` вашей версии называет поля
  иначе, присылайте как есть и скажите как.
- **Набор аргументов `rac` меняется между версиями** — проверяйте на живом кластере, а не по
  документации. На `session terminate` мы на этом уже спотыкались.
- Ошибки — прежними кодами: `RAC_UNAVAILABLE`, `RAC_TIMEOUT`, `CLUSTER_NOT_FOUND`, `RAC_ERROR`
  (с текстом утилиты в `message`).

## Открытые дефекты, которые важнее новых команд

1. **Нестабильный поиск базы.** Одна и та же база то находится, то нет: `_transition` вчера
   отдавала расширения, сегодня — `INFOBASE_NOT_FOUND`; `akacapital` наоборот. При этом
   `CLUSTER_LIST_INFOBASES` перечисляет обе. Две собственные команды агента видят кластер
   по-разному.
2. **`IB_LIST_USERS`** — цепочка COM: свойство `ПользователиИнформационнойБазы`
   (`GetProperty`) → метод `ПолучитьПользователей` (`InvokeMethod`), а не один глобальный метод.
3. **Проверка «Служебный админ базы»** отсекала все базы при заполненном поле; на последнем
   прогоне отказ сменился на `IB_AUTH_FAILED`. Нужно: сохранить прежний путь входа под
   учётной записью службы как запасной и не объявлять `ib.admin`, пока проверка не проходит.
4. **Пустой список баз при SUCCESS.** `CLUSTER_LIST_INFOBASES` однажды вернул `items: []` со
   статусом SUCCESS. Сервис такой срез не применяет (иначе пометил бы все 111 баз пропавшими),
   но агенту следует отвечать ошибкой: пустой кластер — это сбой, а не факт.

## Что уже работает и ломать не надо

`CLUSTER_LIST_INFOBASES`, `CLUSTER_INFOBASE_INFO`, `CLUSTER_LIST_SESSIONS`,
`CLUSTER_LIST_CONNECTIONS`, `CLUSTER_TERMINATE_SESSION`, `CLUSTER_SET_SESSIONS_LOCK`,
`IB_LIST_EXTENSIONS` — отвечают корректно, формы результата согласованы.

`IB_PUBLISH` объявлена, но ни разу не выполнялась: публикация делается запуском `webinst`
(не через COM), только на localhost — см. `PROMPT_AGENT_TRANSPORT.md`, п. 3.

## Как проверить

На стороне сервиса есть зонд, он ставит команды напрямую в очередь и печатает таблицу
«база → итог → время»:

```bash
cd /mnt/ws/app/ai
npm run onec-probe -- --cmd CLUSTER_LIST_LOCKS --cluster
npm run onec-probe -- --cmd CLUSTER_LIST_PROCESSES --cluster
npm run onec-probe -- --cmd CLUSTER_LIST_LICENSES --cluster
```

Успех — `OK (кластер) N шт.`. Скажите, когда сборка готова, — прогоню все 17 команд и
сообщу, что осталось.

## Аутентификация в кластере — обязательна, если она включена

С поля пришла ошибка на всех READ-командах кластера (`CLUSTER_LIST_SESSIONS`,
`CLUSTER_LIST_CONNECTIONS`, `CLUSTER_LIST_PROCESSES`):

```
rac завершился с ошибкой: Ошибка операции администрирования
Администратор кластера не аутентифицирован
```

Это не про базу и не про права в 1С:Предприятии — это про сам `rac`. В кластере заведён
администратор кластера, и **каждый** вызов обязан представляться:

```
rac session list --cluster=<uuid> --cluster-user=<имя> --cluster-pwd=<пароль>
```

Две учётки, которые нельзя путать:

| Учётка | Где заводится | Флаги rac | Для чего |
|---|---|---|---|
| Администратор кластера | ветка «Кластеры → Администраторы» | `--cluster-user` / `--cluster-pwd` | сеансы, соединения, ИБ, блокировки, лицензии |
| Администратор центрального сервера | ветка «Central server → Администраторы» | `--agent-user` / `--agent-pwd` | список кластеров, рабочие процессы, серверы |

### Отказ не различает имя и пароль

С поля пришло сообщение агента: «Агент представился как «admi». … имя заполнено, значит
платформа отвергла именно пароль». **Этот вывод неверен.** 1С отвечает
«Администратор кластера не аутентифицирован» ОДИНАКОВО и на неверный пароль, и на
неизвестное имя — заполненность имени не доказывает ничего.

Более того, «admi» — это на один знак короче «admin», и обрезание последнего символа
выглядит именно так. Прежде чем менять пароль, проверьте:

- длину имени в сохранённой настройке (`admi` = 4 знака, `admin` = 5) — не потерялся ли
  символ при разборе `--cluster-user=admin`, при снятии кавычек или при усечении поля;
- не ушёл ли этот символ в начало пароля (типичная ошибка сдвига при разборе пары);
- как имя попадает в командную строку: `--cluster-user="admin"` и `--cluster-user=admin`
  разбираются по-разному, если кавычки снимаются вручную.

В сообщении об ошибке агенту полезно печатать **длину** имени, а не только само имя:
глазами «admi» и «admin» в одну строку не различить, а число — различить.

Требования к реализации:

- флаги подставляются **всегда**, когда учётные данные заданы, а не только там, где команда
  однажды отказала: список администраторов меняют без предупреждения;
- пароль не логировать и не подставлять в текст ошибки (командная строка `rac` попадает
  в лог целиком — вырезайте `--*-pwd`);
- учётные данные хранит агент (его конфиг/зашифрованное хранилище), сервис их не передаёт
  и хранить не будет: панель управляет базами, а не секретами машины.

Панель уже расшифровывает эту ошибку пользователю как «чинится в настройках агента», но
до исправления все вкладки живого состояния кластера остаются пустыми.
