# Задача расширению buhprof_api: реквизиты организаций в заявке на подключение

26.09.2026. От стороны сервиса стороне 1С (расширение `buhprof_api`, форма «БухПроф AI → Подключение к BuhProf
AI»). Контракт — [CONTRACT_BASE_REGISTRATION_2026-09-19.md](CONTRACT_BASE_REGISTRATION_2026-09-19.md), разделы
«Реквизиты организаций в заявке (26.09)» и уточнение 26.09 о повторе заявки.

## Зачем

Базу `nordbeer` (ТОО Nord Beer, БИН 180240037695) подключали через заявку, а организации в ERP не было. Одобрить
заявку без организации ERP нельзя: на неё выпускается токен базы, ей принадлежат диалоги чата в 1С, задачи и
находки проверок учёта. Администратору BuhProf пришлось бы заводить организацию руками и переписывать реквизиты с
экрана 1С.

Теперь в окне одобрения («Управление 1С» → «Расширение БухПроф AI» → заявки) есть кнопка **«Создать
организацию»**. Она заводит в ERP организацию вместе с адресами, телефонами, руководителем, главным бухгалтером и
банковскими счетами и сразу подставляет её в поле «Организация ERP». Реквизиты для этого должна прислать 1С в
самой заявке.

**Почему в заявке, а не отдельной операцией «получить реквизиты».** До одобрения у сервиса нет пути в базу:
токена у неё ещё нет, а сама база обращается к сервису только заявкой и опросом решения. Запрос реквизитов через
ответ опроса работал бы, лишь пока открыта форма подключения, и ничего не давал бы сверх реквизитов в заявке.

## Что уже сделано на стороне сервиса и панели

- `POST /v1/onec-chat/register` принимает `organizations[].details` и разбирает их мягко: длинное обрезает,
  мусор и неизвестные поля отбрасывает, из-за реквизитов заявку не отклоняет (`ai/src/bases/orgDetails.ts`).
- Повтор заявки с секретом опроса (`pollSecret` в теле или `X-Registration-Secret`) обновляет ту же заявку и
  код; без секрета заводится новая заявка с новым кодом (Б11 аудита 26.09).
- Панель показывает реквизиты в окне одобрения до нажатия и создаёт организацию через ERP
  (`POST /api/v1/organizations/from-onec`, только администратор BuhProf).
- Заявки без `details` (нынешние версии расширения) работают как раньше: организация создаётся с наименованием и
  БИН.

## Задачи

### Р1. Реквизиты организаций в заявке — главное

В каждый элемент `organizations[]` заявки добавить `details` в формате контракта:

```jsonc
{ "id": "…", "name": "ТОО Nord Beer", "bin": "180240037695",
  "details": {
    "legalName": "…", "kind": "legal | individual", "kbe": "17",
    "vatSeries": "…", "vatNumber": "…", "vatDate": "YYYY-MM-DD",
    "okedCode": "…", "okedName": "…",
    "legalAddress": "…", "actualAddress": "…",
    "phones": ["…"], "emails": ["…"], "website": "…",
    "director":        { "fullName": "…", "position": "…" },
    "chiefAccountant": { "fullName": "…", "position": "…" },
    "bankAccounts": [ { "iban": "KZ…", "bik": "…", "bankName": "…", "currency": "KZT", "isPrimary": true } ]
  } }
```

Где брать. Имена объектов — ориентир, сверить с конфигурацией «Бухгалтерия для Казахстана» 3.0:

| Поле | Источник |
|---|---|
| `legalName`, `kind` | `Справочник.Организации`: полное наименование, `ЮрФизЛицо` (юрлицо → `legal`, ИП → `individual`) |
| `kbe` | реквизит организации «КБе», если он есть в конфигурации; нет — не слать |
| `vatSeries`, `vatNumber`, `vatDate` | сведения о постановке на учёт по НДС на текущую дату; не плательщик НДС — не слать |
| `okedCode`, `okedName` | основной вид деятельности организации, если ведётся |
| `legalAddress`, `actualAddress`, `phones`, `emails`, `website` | контактная информация организации (БСП `УправлениеКонтактнойИнформацией`); адрес — одной строкой, как его представление |
| `director`, `chiefAccountant` | ответственные лица организации на текущую дату: ФИО и должность |
| `bankAccounts` | `Справочник.БанковскиеСчета`, владелец — организация, без помеченных на удаление: номер счёта (IBAN), банк (БИК, наименование), буквенный код валюты; `isPrimary` — основной счёт организации |

Правила:

1. Все поля необязательные: шлётся только заполненное. Пустых строк, `null` в массивах и пустых объектов не
   слать.
2. Организации — те же, что уходят в `organizations` сейчас. Права не повышать: чего пользователь не видит, то не
   уходит.
3. **Сбой чтения реквизитов не должен срывать заявку.** Ошибка по организации — отправить её без `details` и
   записать причину в журнал регистрации. Заявка — единственный путь базы к подключению.
4. Персональных данных сверх ФИО и должности не слать: ни ИИН руководителя, ни документов.
5. Пределы сервиса: строки до 500 знаков, телефонов и адресов почты до 10, счетов до 20. Лишнее сервис обрежет,
   но лучше не слать.

### Р2. Повтор заявки — с секретом опроса (согласование с Б11)

Сервис изменил правило повтора: ту же заявку и код возвращает только повтор с секретом прежней заявки. Без секрета
заводится новая заявка с новым кодом. Если администратор базы нажмёт «Отправить заявку» ещё раз, он продиктует
оператору другой код, и оператор найдёт в панели две заявки.

- «Отправить заявку» при нерешённой заявке — слать секрет из безопасного хранилища: поле `pollSecret` в теле или
  заголовок `X-Registration-Secret`. Ответ несёт новый `pollSecret`: сохранить его вместо прежнего (прежний
  перестаёт действовать).
- Так же обновляются реквизиты: поправили их в 1С (например, заполнили БИН) и нажали «Отправить заявку» —
  заявка и код те же, реквизиты новые.
- Заявка решена или просрочена — слать без секрета, как новую.

Если задача по Б11 уже ушла отдельно — этот пункт считать её частью, а не второй задачей.

### Р3. Форма подключения: что уходит и чего не хватает

- Перед отправкой показать, какие реквизиты уйдут: по строке на организацию, например «ТОО Nord Beer, БИН
  180240037695: адрес, 2 телефона, руководитель, 1 счёт». Человек должен видеть, что отправляет.
- У организации без БИН — предупреждение: «Не заполнен БИН — без него подключение не одобрят». Организацию ERP без
  БИН создать нельзя.
- После повтора с секретом — «Заявка обновлена, код прежний: …».

### Р4. Заглушка и тесты

- `tools/mock_chat_service.py`: принимать `details` (хранить и отдавать в отладочном выводе) и новое правило
  повтора (с секретом — та же заявка, без секрета — новая).
- Проверки: заявка с полными реквизитами; организация без банковских счетов и без НДС; организация без БИН;
  ошибка чтения реквизитов одной организации (заявка уходит, у остальных `details` есть); повтор с секретом (код
  прежний, реквизиты новые); повтор без секрета (новый код).

## Версия

Следующая версия расширения. Сервису номер версии не важен: `details` необязательное поле, и старые версии
продолжают работать.

## Как проверить вместе

1. База с организацией, которой нет в ERP, отправляет заявку новой версией.
2. В панели в окне одобрения видны реквизиты. «Создать организацию» заводит её, и она подставляется в поле.
3. «Применить» — при следующем опросе 1С получает токен, форма показывает организацию ERP.
4. В карточке организации ERP видны контакты, контактные лица и банковские счета из 1С.
