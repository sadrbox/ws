## A1. Команды управления не ждут пропуска — P1

### Факт

Главный цикл идёт за командами, только взяв пропуск `agent.max_parallel` (`src/agent.rs:325-329`;
умолчание 4, `src/config.rs:289`). Вторая и следующие команды пачки ждут пропуск внутри своей
задачи (`src/agent.rs:374-383`).

Отмена нужна ровно тогда, когда пропуски заняты зависшими командами. При четырёх застрявших
`ibcmd` агент не опрашивает очередь вообще, и `AGENT_CANCEL_COMMAND` до него не дойдёт. То же с
`AGENT_LIST_PROCESSES` и `AGENT_KILL_PROCESS` — инструментами разбора именно этой ситуации.

### Сделать

* Команды управления (сверить состав `Kind` из группы LOCAL: `AgentCancelCommand`,
  `AgentListProcesses`, `AgentKillProcess`) исполнять без пропуска.
* Опрос очереди не должен целиком зависеть от свободного пропуска. Предлагаемое правило: опрашивать,
  пока задач, ЖДУЩИХ пропуск, меньше `max_parallel`; пропуск берёт сама задача, и только для
  обычных команд.

  Лишнего так не набирается: внутрибазовые команды сервис и так выдаёт не больше
  `AGENT_IB_PARALLEL`, а ждущие пропуск остаются на учёте «не начата» и при остановке честно
  возвращаются как `AGENT_STOPPING`.
* Альтернатива без набора впрок — отдельный опрос «только команды управления» — требует фильтра
  по типам на стороне сервиса; брать её, только если первое правило себя не оправдает.

### Проверить

Тест: при всех занятых пропусках команда отмены исполняется, обычная — ждёт. На стенде: четыре
долгих чтения плюс отмена одного из них — отмена отрабатывает за секунды.

## A2. Прерванная команда снимается с учёта взятых — P1

### Факт

После `abort` задача не доходит до строк `src/agent.rs:390-391`, и запись в `taken` остаётся с
пометкой «работа начата». При следующей остановке службы `return_taken` (`src/agent.rs:1032`)
отправит по уже прерванной команде `AGENT_STOPPED` — «результат неизвестен, проверьте базу».
Сервис перезапишет им итог отмены: `queue.complete` не смотрит на состояние (у сервиса это S2).
Та же дыра — при панике внутри задачи.

### Сделать

Снятие с учёта перенести в охранный объект внутри задачи: `Drop` убирает запись из `taken` и из
реестра отмены. Он срабатывает и при обычном завершении, и при `abort`, и при панике.

`taken` сейчас `tokio::sync::Mutex`, а в `Drop` ждать нельзя. Перевести на `std::sync::Mutex`:
удержание короткое, через `await` не переносится.

### Проверить

Тест: задача прервана → `taken` пуст, `cancel::is_running` ложно. Остановка после отмены не шлёт
`AGENT_STOPPED` по прерванной команде.

## O1. Наличие баз данных — одним запросом к СУБД — P2

### Цена сейчас

* **Фон:** пять баз в минуту (`src/agent.rs:1180-1208`). Каждая стоит вызова `rac infobase info` и
  процесса `ibcmd` (`src/cluster/mod.rs:1013-1034`, `:1196-1220`). На 110 базах — около 22 минут
  после каждого истечения знания, а годность знания — сутки (`src/cluster/mod.rs:1003`).
* **По требованию:** пачки по 8 процессов `ibcmd`, ожидание до 5 с на базу
  (`src/cluster/mod.rs:1057-1062`). До минуты и 110 процессов на сервере 1С.

### Предложение

СУБД знает список своих баз, и на сервер СУБД хватает одного запроса.

1. Параметры (`dbms`, `dbServer`, `dbName`, `dbUser`) брать из `infobase info`, как сейчас, но
   хранить в `db_state.json`: меняются они только при переносе базы. Годность — сутки; не нашлась
   база по сохранённым параметрам — перечитать их.
2. Сгруппировать базы по `(dbms, dbServer, dbUser)`.
3. Запрос:
   * MSSQL — `sqlcmd -S <сервер> -U <пользователь> -h -1 -W -Q "SET NOCOUNT ON; SELECT name FROM sys.databases"`,
     пароль — переменной `SQLCMDPASSWORD`;
   * PostgreSQL — `psql -h <сервер> -U <пользователь> -d postgres -At -c "SELECT datname FROM pg_database"`,
     пароль — переменной `PGPASSWORD`.

   Утилиту искать в `PATH` и стандартных каталогах установки. Пароль в командную строку не
   попадает и вырезается из текста ошибок.
4. Сравнение имён: MSSQL — без учёта регистра, PostgreSQL — точно.
5. Запрос выполнился — `dbMissing` для всех баз этого сервера разом. Не выполнился или утилиты
   нет — прежний путь через `ibcmd` для этих баз. «Не смог спросить» — не «базы нет».
6. Фон: если запрос доступен — полная сверка раз в несколько часов вместо пяти баз в минуту.

Права: список баз по умолчанию виден любому пользователю СУБД (`VIEW ANY DATABASE` у `public` в
MSSQL, `pg_database` в PostgreSQL). Отказ по правам — тот же откат на `ibcmd`.

### Проверить

* Тесты: разбор вывода `sqlcmd` и `psql`, группировка, сравнение с учётом регистра, откат на
  `ibcmd`.
* На сервере: `bpapi-agent bases check` — время до и после; фантом `aibek` → `dbMissing: true`,
  рабочие базы → `false`; без утилит поведение прежнее.

## O2. Время выполнения команд в heartbeat — P2

### Факт

Heartbeat несёт `failures_by_code` (`src/state.rs:56`, `src/agent.rs:995`,
`src/cloud/protocol.rs:109`), но не время. Каждое «агент тормозит» измеряется вручную, как
зависание `ibcmd` 11.09. Настройке `AGENT_IB_PARALLEL` (A4 в `TASKS_NEXT_2026-09-12.md`) не на
что опереться, кроме разовых замеров.

### Сделать

* В `State` по каждому типу команды: число, сумма, максимум и счётчики корзин (≤1 с, ≤5, ≤15, ≤60,
  ≤300, >300 с). 95-й процентиль считается по корзинам, без хранения выборки.
* Окно — с прошлой успешной отправки.
* Поле heartbeat `durationsByType` необязательное: схема сервиса неизвестные поля отбрасывает, и
  старый сервис не сломается.
* Сервису — отдельной задачей после: хранить последний снимок у агента и показывать в карточке
  агента.

### Проверить

Тест накопления и сброса после отправки; на стенде — поле в теле heartbeat.
