## Высокая

**АГ1. Отменённая команда оставляет живой мост занятым чужим запросом.**
`ib/bridge_pool.rs:158-171`: мост снимается только при своём таймауте. Если команду снял общий предел агента
(`agent.rs`, `command_timeout_secs` = 600 с), `MutexGuard` освобождается, а PowerShell ещё выполняет прежний
запрос. Следующая команда в этом слоте читает **чужой** ответ. Для COM-шлюза это «шлюз не оставил ответа» и
повтор, пока первая операция ещё идёт. Для админ-роли (тот же пул) — подмена результата чужой команды.
Повторы COM: 5 × (120 + 120 с) больше предела команды.
*Исправить:* охранник в `Pool::call`, который при сбросе future убивает мост; сумма попыток COM не больше
остатка предела команды.

**АГ2. Разорванное COM-соединение «прилипает» к мосту.**
`bridge.ps1`: ошибка внутри действия превращается в ответ (`DoneMark`), и `$ib`/`$current` не сбрасываются.
Пул теперь предпочитает мост с тем же ключом базы. После перезапуска сервера 1С все попытки идут в мёртвое
соединение, база «недоступна» до перезапуска службы.
*Исправить:* при ошибке `gateway` обнулять `$ib`/`$current`; на стороне Rust убивать мост после
транспортного отказа.

**АГ3. Живые мосты бессрочно держат сеансы 1С и файловые базы.**
Пул поднимает до `max_parallel` мостов. Проба обходит все базы, включая базы сверх лимита. Соединение
закрывается только с остановкой службы. У клиента заняты лицензии. К файловой базе всегда кто-то подключён,
поэтому **обновить конфигурацию из Конфигуратора нельзя**, пока служба жива.
*Исправить:* закрывать соединение по простою (около 60 с), не открывать по COM базы сверх лимита, для проб
брать уже живой мост.

**ОК1. Пароль и токен, вписанные в `[[onec.bases]]` руками, теряются при первом сохранении из окна, а окно
показывает «сохранён».**
`setup/mod.rs` (`state` считает пароль из файла сохранённым, `build_toml` его не пишет, `apply` не переносит
в хранилище).
*Исправить:* в `apply` переносить `password`/`token` из файла в `…@<база>`.

**ОК2. Дополнительная HTTP-база без токена: окно сохраняет, служба не стартует.**
У доп. базы нет поля токена, `validate` его не требует, а служба требует.
*Исправить:* поле токена у HTTP-базы (`BPAPI_ONEC_TOKEN@<база>`) и проверка в `validate`.

**ОК3. Окно и служба ищут файлы обмена в разных каталогах; две бизнес-службы делят один каталог.**
- `business::state_dir_for` берёт каталог установленной программы, а служба — каталог своего exe, который
  может быть любым.
- `build_toml` всегда пишет `data_dir = ""`: заданное вручную стирается.
- Две бизнес-службы на машине делят `business-state.json`, `activation-requests.json` и флаг пробы.
- Итог: запрос активации «передан службе» и молча теряется, либо его забирает чужая служба.

*Исправить:*
- каталог — от программы службы (`service_program`);
- сохранять `data_dir`;
- файлы обмена именовать по имени службы.

**РС1. Чат и «Подключение» нельзя открыть из интерфейса.**
`CommonForms/BPAPI_Чат.xml:18`, `BPAPI_НастройкиЧата.xml:18`: `UseStandardCommands=false`, общих команд нет.
Раздел «БухПроф AI» пуст.
*Исправить:* `UseStandardCommands=true` у обеих форм (или общие команды).

**РС2. HTTPS без проверки сертификата; адрес без схемы уходит по HTTP.**
`BPAPI_Чат:539`: `Новый ЗащищенноеСоединениеOpenSSL` без корневых сертификатов. Перехватчик получает токен
базы, секрет заявки и сам токен при одобрении. `РазобратьАдрес` адрес без схемы отправляет на `http:80`.
*Исправить:*
- `ОбщегоНазначенияКлиентСервер.НовоеЗащищенноеСоединение()` (БСП, проверка по сертификатам ОС);
- адрес без схемы считать `https`;
- `http` не на localhost — отказ.

## Средняя

- **АГ4. Сбой одной пробы стирает организации базы.** `business/mod.rs` `probe_one`: `organizations = []`

  «организаций нет», а при правиле «первые N» состав обслуживаемых БИНов скачет. *Исправить:* при неудаче
  хранить прежние организации, в срез отдавать `None`.
- **АГ5. Контроль БИНов обходится.** Проверяется только `organizationBin ∈ over_bins`. Без `organizationBin`
  (одна база, `baseKey`, `organizationId`) или с непроверенной базой команда по неактивированной
  организации проходит, хотя при `activeBins` должны обслуживаться «ровно эти». *Исправить:* при
  `activeBins` требовать `bin ∈ allowed`, организацию определять и по `organizationId`.
- **АГ6. Запросы активации теряются с нынешним сервисом.** Файл удаляется после любого успешного heartbeat,
  а сервис поле пока отбрасывает; в окне навсегда «Отправлен». *Исправить:* удалять запрос после подтверждения
  (`activation` с этим БИН), `SENT` со временем возвращать в очередь.
- **АГ7. Одно неожиданное поле ломает разбор всего ответа сервиса.** `Activation.bin` без default,
  `state: null`, `maxBases: 3.0` превращают `RegisterData`/`HeartbeatData` в пустые: теряются лимиты,

- **АГ8. Первая проба задерживает регистрацию на минуты.** Все базы последовательно до register; одна
  висящая сетевая файловая база — около 8 мин без команд. *Исправить:* COM-пробу — в фон после регистрации.
- **АГ9. «Проверить базы сейчас» запускает параллельные пробы** и не обновляет `onec_reachable`.
  *Исправить:* флаг «проба идёт», вызов `probe_with`.
- **АГ10. Недоступная COM-база перепроверяется раз в 15 мин, если жива хоть одна HTTP-база.**
  *Исправить:* решать по каждой базе.
- **АГ11. Гонки на файлах обмена.** Окно пишет запросы без временного файла. Служба может прочитать

- **ОК4. Переименование доп. базы (даже смена регистра) теряет её пароль**, окно пишет «сохранён».
  *Исправить:* хранить исходный ключ и переносить секрет.
- **ОК5. «Забыть пароль» у доп. базы не действует** (признак не уходит в `apply`).

  - Лишние параметры (`Locale=` и др.) выбрасываются.

## Проверено и в порядке

- `requestId` доходит до 1С и по COM; `MISSING_REQUEST_ID` проверяется для обоих транспортов; исключения 1С
  шлюз отдаёт как `INTERNAL_ERROR` без повтора.
- Выбор базы по БИН при нескольких базах верен: базы сверх лимита всегда в конце порядка, а статус БИНа един
  для всех баз.
- Новые поля протокола совместимы со старым сервисом. Секретов в `business-state.json` и в данных окна нет
  (кроме АГ14).
- Идентификаторы виджетов egui не пересекаются. TOML с кириллицей и кавычками экранируется верно. Бизнес-роль
  не хранит административных секретов.
- Директивы форм и серверного модуля корректны. Привилегированный режим в `ТокенБазы` нужен и безопасен.
  Заголовки только ASCII. Поля и состояния совпадают с контрактами и заглушками.

## Опровергнуто

- «Шлюз `BPAPI_Шлюз` не виден через внешнее соединение (`ExternalConnection=false`)» — неверно для этой схемы.
  19.09 через COM на Dev_01 прошли `GET_ORGANIZATIONS`, `SEARCH_COUNTERPARTIES`, `CREATE_SALE` с повтором и
  `RUN_REPORT` (PDF). Серверный модуль доступен коду внешнего соединения. На **серверной** базе через
  `Srvr=` путь ещё не проверялся.
