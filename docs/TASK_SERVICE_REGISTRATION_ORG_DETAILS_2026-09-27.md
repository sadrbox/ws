## Что фактически уходит в `details`

Только заполненное; пустых строк, `null` и пустых объектов нет (тест проверяет каждое поле).

| Поле | Источник в БК 3.0.73.1 | Примечание |
|---|---|---|
| `legalName` | `Организации.НаименованиеПолное` | до 500 знаков |
| `kind` | `Организации.ЮрФизЛицо` → `legal`/`individual`; ИП — `individual` | |
| `kbe` | `Организации.КБЕ` | |
| `vatSeries`, `vatNumber`, `vatDate` | `Организации.Серия/Номер/ДатаСвидетельстваПоНДС` | `vatDate` — `YYYY-MM-DD`; без номера свидетельства не уходит |
| `okedCode`, `okedName` | `Организации.ОсновнойВидДеятельности` → `ВидыДеятельности.КодОКЭД`, наименование | |
| `legalAddress`, `actualAddress` | `РегистрСведений.КонтактнаяИнформация`, виды `ЮрАдресОрганизации`, `ФактАдресОрганизации` | представление одной строкой |
| `phones[]` | вид `ТелефонОрганизации` | до 10 |
| `emails[]`, `website` | **в этой конфигурации у организаций таких видов контактной информации нет** | не уходят никогда |
| `director`, `chiefAccountant` | `РегистрСведений.ОтветственныеЛицаОрганизаций.СрезПоследних` (Руководитель, ГлавныйБухгалтер) | только `fullName` и `position` (`ДолжностиОрганизаций`) |
| `bankAccounts[]` | `Справочник.БанковскиеСчета`, владелец — организация, без пометки удаления | `iban`, `bik`, `bankName`, `currency` (буквенный код), `isPrimary` = `Организации.ОсновнойБанковскийСчет`; до 20 |

Пример с полными реквизитами (стенд Dev_01, посев «ПРОВЕРКА»): `legalName, kind, kbe, vatSeries, vatNumber, vatDate,
okedCode, okedName, legalAddress, actualAddress, phones, director, chiefAccountant, bankAccounts` — 14 полей.
Организация только с наименованием и счётом: `legalName, kind, bankAccounts`. Без счетов и без НДС: `legalName, kind`.

Правила задачи: права не повышаются (запросы с `РАЗРЕШЕННЫЕ`), персональных данных сверх ФИО и должности нет,
строки обрезаются до 500. Сбой чтения по одной организации — заявка уходит без её `details`, причина в журнале
регистрации (`chat.register`, предупреждение).

## Повтор заявки (Р2)

- Прежняя заявка с секретом лежит в безопасном хранилище. Пока она не решена, повтор «Отправить заявку» несёт
  `pollSecret` в теле и `X-Registration-Secret` в заголовке — и то и другое.
- Новый `pollSecret` из ответа записывается вместо прежнего.
- Если сервис вернул прежний код — форма пишет «Заявка обновлена, код прежний: %1. Реквизиты организаций
  отправлены заново». Иначе — обычный текст с новым кодом.
- Одобренная или отклонённая заявка забывается, следующая уходит без секрета.

## Проверки (Р4)

`python tools/registration_test.py [--e2e] [--port N]` на стенде Dev_01 (замок на базу), 16/16:

- реквизиты всех 4 организаций стенда — правило «только заполненное», допустимый `kind`, КБе из двух цифр,
  у каждого счёта IBAN, основной счёт один, у ответственных лиц только ФИО и должность;
- полный набор у организации с посевом — 14 полей; сводка для формы;
- состав заявки: строка на организацию; организация без БИН (стирается и восстанавливается) помечена, флаг поднят;
- заглушка: заявка принята; повтор с секретом в теле и в заголовке — та же заявка и код, новый секрет; без
  секрета и с неверным секретом — новая заявка с новым кодом;
- `--e2e`: заявка через само расширение в заглушку и повтор с текстом «код прежний»; адрес сервиса и сохранённая
  заявка восстанавливаются; заглушка запущена с `--approve-after 1000000000`, чтобы не выдать токен.

**Проверить потом:** «ошибка чтения реквизитов одной организации при уходе заявки» — ветка защищена `Попытка`
внутри перебора организаций, но воспроизвести падение на стенде нечем; на живой базе проверяется по журналу.
