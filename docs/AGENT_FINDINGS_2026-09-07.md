# Проверка обновлённого агента 07.09.2026 — что нашлось

Проверка шла зондом (`npm run onec-probe`) и по журналу команд сервиса. Ниже только то,
что подтверждено ответами самого агента.

## 0. Главное: отвечает агент на машине x57, у которой в кластере НЕТ клиентских баз

Пока это так, проверить работу `ibcmd` по клиентским базам невозможно — их на этой машине нет.

Доказательства:

| Что спросили | Ответ | Чем это доказано |
|---|---|---|
| `CLUSTER_LIST_INFOBASES` ×6 подряд | 6 отказов «кластер localhost:1545 ответил пустым списком баз» | кластер с 110 базами не может вернуть ноль |
| `CLUSTER_LIST_PROCESSES` | 1 процесс, `host: "x57"`, память 151 МБ, 1 соединение | это не боевой сервер на 110 баз |
| `CLUSTER_LIST_PUBLICATIONS` | 1 публикация: `Dev_01 → http://localhost/db` | в 07:45 тот же запрос давал 204 публикации |
| `IB_LIST_EXTENSIONS` по 8 базам | «база «…» не найдена на сервере x57» | баз кластера на x57 нет |

Последний ответ боевого сервера — 07:45:54 (204 публикации, 110 баз). После этого отвечает
только x57. Токен один на две машины — это та же причина, что и раньше (см.
`docs/ONEC_AGENT_CLUSTER_CONTRACT.md`, раздел про `instanceId`).

**`instanceId` агент по-прежнему не присылает** — таблица экземпляров пуста, и панель не может
показать, сколько процессов и с каких адресов работают под одним токеном. Это первое, что стоит
закрыть: без него любая следующая проверка снова упрётся в вопрос «а кто ответил».

## 1. `ibcmd`: параллельные запуски дерутся за рабочий каталог

```
ibcmd: Ошибка блокировки каталога данных сервера.
Рабочий каталог заблокирован процессом: 8704
```

Получено на `IB_LIST_EXTENSIONS` при двух одновременных командах. `ibcmd` поднимает свой
автономный сервер в рабочем каталоге и берёт на него блокировку; два процесса в одном каталоге
несовместимы.

Лечится одним из двух: свой каталог на вызов (`--data <временный каталог>`, удалять после) либо
сериализация вызовов `ibcmd` внутри агента независимо от `max_parallel`. Первое лучше: `ibcmd`
и заводился ради массовых операций.

## 2. `CLUSTER_LIST_PUBLICATIONS`: в `key` попадает представление базы, а не её имя в кластере

Ответ на 204 записи разбирается так:

| Записи | `key` | Совпало с реестром |
|---|---|---|
| 101 с `published: true` | алиас публикации (`bustravel_ip`) | 76 из 101 |
| 103 с `published: false` | **наименование базы** («Карамурт-Газ ТОО») | 3 из 103 |

По контракту `key` — это **имя ИБ в кластере**, которым база адресуется во всех остальных
командах. Наименование (`name`) в него класть нельзя: сопоставить такую запись с базой нечем,
и 103 записи из 204 пропадают впустую.

Ещё 25 опубликованных записей не совпали ни с чем: это публикации под алиасом, отличным от
имени базы. Их тоже можно сопоставить — имя базы лежит в самой публикации, в строке
соединения `default.vrd` (`ib="Srvr=…;Ref=<имя базы>;"`). Поэтому:

```jsonc
{ "items": [ { "key": "buh_alma",            // имя ИБ из Ref= в default.vrd — ОБЯЗАТЕЛЬНО
               "alias": "buh_alma_web",      // виртуальный каталог, если отличается
               "url": "http://localhost/buh_alma_web",
               "published": true } ],
  "complete": true }
```

**`complete` не приходит вовсе.** Без него сервис не имеет права пометить базу «нет публикации»:
отсутствие в списке может означать и «не просмотрен второй веб-сервер». Пока флага нет, у части
баз состояние остаётся «не проверялась» навсегда — то есть половина смысла команды теряется.

## 3. Подозрение: результат приписан не той команде

Команда с `baseKey = _transition` вернула ошибку «база «abdali» не найдена». Обе команды были
поставлены в одну секунду; у самой `abdali` текст ошибки пришёл пустым.

Случай единичный, но проверить сопоставление команда→результат при параллельном исполнении
стоит: если результаты меняются местами, доверять отчёту задания нельзя вовсе.

## 4. Состав способностей

Появилось: `IB_RESTORE`, `CLUSTER_LIST_PUBLICATIONS`.
Нет до сих пор: `IB_UNPUBLISH` (панель её уже шлёт), `IB_CHECK`, `IB_APPLY_UPDATE`.
Контракты всех пяти — в `docs/PROMPT_AGENT_MAINTENANCE.md`.

## 5. Порядок проверки, когда боевой агент вернётся

1. `npm run onec-probe -- --cmd CLUSTER_LIST_INFOBASES --cluster` — должно быть 110 баз;
2. `npm run onec-probe -- --cmd IB_LIST_EXTENSIONS --limit 8 --parallel 2` — здесь и проявится
   драка за каталог `ibcmd`, если она не вылечена;
3. `npm run onec-probe -- --cmd IB_LIST_USERS --limit 5` — путь COM, он не менялся;
4. `CLUSTER_LIST_PUBLICATIONS` — сверить `key` с именами баз и дождаться `complete: true`.

## 2026-09-11. Срез публикаций не читает публикации

Проверено на живом стенде (сборка агента `0.1.0+2026-09-10 18:09 (+05)`), измерением, а не
чтением кода.

**Что происходит.** `CLUSTER_LIST_PUBLICATIONS` отвечает списком из 109 записей, в которых:

* `key` — **имя** базы («Карамурт-Газ ТОО»), а не её ключ (`karamurt_gaz`);
* `published: false` у **всех** записей, `url: null` у всех;
* `complete: true` — то есть список объявлен полным;
* базы, опубликованной **минутой раньше нашей же командой**, в списке НЕТ вовсе.

**Как это выглядело со стороны панели.** Наш `IB_PUBLISH` возвращает
`{ok: true, url: "http://localhost/_transition", urlConfirmed: false}` — публикация сделана.
Следующий «полный» срез объявляет неопубликованными все сто девять баз, и реестр честно
применяет это: сто десять баз получают «не опубликована», включая только что опубликованную.
Человек видит «не опубликована» у работающей базы.

**Что сделано на стороне сервиса, чтобы не врать.**

1. Признак публикации из среза БАЗ (rac) принимается только положительный: «нашёл» — факт,
   «не нашёл» — незнание. Отрицательный ответ имеет право дать лишь срез публикаций.
2. Записи среза публикаций сопоставляются и по ключу, и по ИМЕНИ — иначе ответ целиком уходит
   в никуда.
3. Срез, в котором **нет ни одной опубликованной базы**, реестр не трогает вовсе: веб-сервер
   без единой публикации снаружи неотличим от читателя, который не умеет читать. В журнале —
   предупреждение с образцом ключа.
4. Состояние, выдуманное прежним поведением, сброшено в «не проверялось» (миграция 015).

**Что нужно от агента.**

* В `key` класть **ключ информационной базы** — тот же, что в срезе баз и в командах. Имя,
  если нужно, отдельным полем.
* Действительно читать публикации веб-сервера (`default.vrd` / каталоги `webinst`): сейчас
  `published: true` не приходит ни для одной базы ни при каких условиях.
* Не объявлять `complete: true`, пока список не прочитан целиком: это обещание, по которому
  сервис имеет право снять признак у всех отсутствующих.
* `urlConfirmed: false` в ответе `IB_PUBLISH` — полезно; стоит объяснять в тексте, почему
  адрес не подтверждён (веб-сервер не отвечает? нет доступа?).

До исправления агента признак публикации в панели живёт только по нашим собственным командам
публикации и снятия — он верен для тех баз, которые панель трогала, и «не проверялось» для
остальных. Это честно и не мешает работе, но «Обновить публикации» бесполезно.

## 2026-09-11, ответ агента: срез публикаций исправлен

Разобрано по следам раздела выше. Причина у всех трёх симптомов оказалась разная, поэтому
по порядку.

**1. В `key` было наименование — ошибка в одной строке.** Срез брал у базы поле `name`, а в
ответе `list_infobases` это ОПИСАНИЕ базы («Карамурт-Газ ТОО»); имя в кластере лежит в `key`.
Отсюда же и «109 записей вместо 110»: у технических баз описания нет, пустое значение
отбрасывалось, и `_transition` выпадала из среза вовсе — та самая база, которую опубликовали
минутой раньше. Теперь `key` — имя базы в кластере, наименование отдаётся отдельным полем
`name`. Правка закрыта тестом: база без описания обязана остаться в срезе.

**2. `published: false` у всех — следствие первого.** Публикация ищется по `Ref=` из
`default.vrd`, а там стоит имя базы; сравнение с русским наименованием не совпадало никогда.
Ни одна запись из найденных не могла сопоставиться ни с одной базой.

**3. `complete: true` при пустом срезе — отдельный дефект, и самый опасный.** Обход каталогов
объявлял просмотр полным, если нашёлся хоть один типовой корень веб-сервера. Пустой
`C:\inetpub\wwwroot` на сервере, где публикации лежат в другом месте, давал ровно это:
«просмотрено всё, не опубликовано ничего» — то есть разрешение снять признак у всех ста
десяти баз. Теперь **срез без единой публикации полным не объявляется никогда**: доказательством
полноты служит хотя бы одна найденная публикация, а не факт существования каталога.

**Что добавилось в ответ.** Поля `source` (`iis` | `scan`) и `lookedIn` — где именно агент
искал. Пустой срез без них неотличим от поломки; с ними сразу видно, что смотрели не в том
каталоге. Контракт (`ONEC_AGENT_CLUSTER_CONTRACT.md`, раздел `CLUSTER_LIST_PUBLICATIONS`)
обновлён — стоит показывать их рядом с пустым срезом.

**Про `urlConfirmed`.** Теперь рядом идёт `urlNote` с причиной: либо «веб-сервер отвечает, но
каталога нет — публикация легла не на тот сайт», либо «веб-сервер не спросить: нет IIS или у
службы агента нет прав на appcmd». Это разные беды и чинятся по-разному.

**Если публикации лежат не там, где агент их ищет** — теперь это лечится настройкой, а не
правкой кода:

```toml
[cluster]
publication_roots = ["D:\www", "E:\1c-publications"]
```

**Проверить на самом сервере:** `bpapi-agent publications` — печатает, чем собран срез, какие
каталоги просмотрены, сколько баз и сколько из них опубликовано. Если найдено ноль, команда
прямо говорит, что признак публикации панель не снимет, и предлагает назвать каталог.

**Что осталось верным из ваших замечаний.** Сопоставление по имени на стороне сервиса (пункт 2
вашего разбора) теперь избыточно, но и не мешает: агент присылает ключ. Защиту «срез без
опубликованных не применяем» лучше оставить — она дублирует нашу и стоит дёшево.

Симптом со стороны панели: «расширения базы не показывает, „Обновить“ не показывает
расширения». Измерено на двух базах, сборка агента `2026-09-10 18:09 (+05)`, `pid 7036`,

| Команда | База | Итог | Время |
|---|---|---|---|
| `IB_LIST_USERS` | `_transition` | `SUCCESS` | 22–37 с (шесть замеров подряд) |
| `IB_LIST_USERS` | `bustravel_ip`, `akbiik1`, `ecoinnovaciya`, `bekholod` | `SUCCESS` | 22–26 с |
| `IB_LIST_EXTENSIONS` | `_transition` | `TIMEOUT` | 575 с |
| `IB_LIST_EXTENSIONS` | `almaz67` | `TIMEOUT` | 600 с |

Обе команды идут одним и тем же COM-входом в ту же базу, с одинаковым payload `{baseKey}`
по контракту. Вход в базу исправен — это доказывает `IB_LIST_USERS` на той же базе за
полминуты. Виснет именно перечисление расширений, и текст ошибки агента («операция не
уложилась в 600 с и снята агентом») говорит, что снял её сторож агента, а не 1С.

Важная зацепка: **раньше это работало**. Последнее удачное чтение расширений в реестре
сервиса — `2026-09-06 17:26` (8 расширений базы `almaz67`, 5 у `jenis`, 4 у `_transition`);
33 записи всего. Сборка агента тогда была другой. Между 06 и 10 сентября чтение расширений
перестало возвращаться.

Где смотреть: `РасширенияКонфигурации.Получить()` по-русски (см.
`docs/PROMPT_AGENT_IB.md`) — английское имя члена даёт мгновенный `DISP_E_MEMBERNOTFOUND`,
а не зависание, так что дело не в нём. Похоже на ожидание внутри перебора расширений —
блокировка конфигурации, попытка открыть расширение на запись или сеанс, который не
закрывается.

**Просьба к агенту, кроме починки:** не молчать до сторожевого таймаута. Если перебор идёт
дольше разумного — вернуть ошибку с тем местом, где встал. Десять минут тишины стоят
человеку десяти минут ожидания, после которых он узнаёт только слово «TIMEOUT».

**`synonym` по-прежнему не приходит.** Во всех 33 записях реестра он `null`, хотя контракт
просит его с самого начала (`ONEC_AGENT_CLUSTER_CONTRACT.md`). Без синонима сводка по
расширениям — список `EF_00_00062442`.

**Что сделано на нашей стороне, пока это чинится.** Карточка базы больше не зависит от
живого чтения: вкладки «Расширения» и «Пользователи» открываются кэшем реестра
(`GET /v1/onec/bases/:key/extensions/cached`, у пользователей такой путь был всегда) и
показывают колонку «Прочитано» — когда эти данные брали у 1С. То, что известно, видно
сразу; «Обновить» по-прежнему идёт в базу. Пустая вкладка теперь объясняет, что расширения
ещё не читались, а не молчит пустой таблицей.

### Про пункт 1: у каждого вызова `ibcmd` теперь свой рабочий каталог

`ibcmd` поднимает внутри себя автономный сервер и берёт исключительную блокировку на каталог
данных. Каталог по умолчанию один на машину — поэтому два вызова **по разным базам** дрались за
него, и второй получал «Рабочий каталог заблокирован процессом: 8704». Замок по базе от этого
не спасал: базы-то разные, а массовые операции — весь смысл этого транспорта.

Сделано: каталог создаётся на каждый вызов во временной папке и удаляется после (`--data`).
Версии платформы, которые ключа не знают, распознаются по тексту отказа — вызов повторяется
без него, с записью в журнал. Сам отказ блокировки теперь объяснён словами (`IB_BUSY`,
«повторите; если повторяется, на сервере работает ibcmd, запущенный вручную»), а не приходит
голым текстом платформы.

**Как проверить:** `npm run onec-probe -- --cmd IB_LIST_EXTENSIONS --limit 8 --parallel 2` — это
и был ваш пункт 2 в порядке проверки. Сборка агента: `0.1.0+2026-09-11 12:24 (+05)`.

**Проверено на сборке `2026-09-11 12:24 (+05)`** (та, где исправлен срез публикаций):
`IB_LIST_EXTENSIONS` по базе `almaz67` снова снят сторожем на 600-й секунде. Третий замер,
третий таймаут; `IB_LIST_USERS` по тем же базам продолжает отвечать за 22–37 с.

**Срез публикаций той же сборки:** `key` теперь ключ базы (`karamurtgaz`), наименование
приехало отдельным полем `name`, `complete: false`, `source: "iis"`, `lookedIn` — 105
каталогов вида `C:\inetpub\wwwroot\<ключ базы>`. Ключи и полнота исправлены, но
`published: true` по-прежнему не приходит НИ ПО ОДНОЙ базе из 110 — при том, что каталог
публикации у каждой из них агент сам же и перечислил. Похоже, найденные каталоги не
сопоставляются с базами: список `lookedIn` и список `items` живут отдельно друг от друга.
Панель такой срез не применяет (нет ни одной положительной записи и `complete: false`) —
то есть состояние публикации не портится, но и не заполняется.

**`synonym` в `IB_LIST_EXTENSIONS`** — всё ещё `null` во всех записях реестра.

  heartbeat — это поле панель берёт для строки агента (`a.platform`);
* версия проставляется каждой базе в срезе `bases[]` и в ответе `CLUSTER_LIST_INFOBASES`
  полем `onecVersion` — то, что контракт и предусматривал. Панель показывает её в карточке базы
  без обходного пути «взять у админ-агента»;
* определяется она **по пути к `rac`** (`…\1cv8\8.3.25.1257\bin\rac.exe`) — без запуска
  процесса и, что важно, **даже когда RAS не отвечает**; если путь версии не называет (rac
  найден в PATH), агент спрашивает саму утилиту `rac --version`. Результат кэшируется на запуск
  процесса: платформу обновляют с остановкой сервера, а значит и службы агента.

Двухчастные «8.3» из пути версией не считаются: это название ветки платформы, и такой ответ был
бы хуже отсутствующего — выглядит достоверно.

**Проверить на сервере:** `bpapi-agent diag` печатает строку `платформа: 8.3.25.1257` в разделе
кластера (она выводится и тогда, когда RAS молчит — то есть ровно в тех разборах, ради которых
диагностику и собирают).

## 2026-09-11: состояние публикации и зависание `IB_LIST_EXTENSIONS`

Сборка `0.1.0+2026-09-11 13:57 (+05)`.

### Признак публикации теперь идёт в срезе баз

Контракт ждёт `published`/`publishUrl` в `CLUSTER_LIST_INFOBASES` и в `bases[]` — агент их не
слал вовсе. Состояние публикации держалось только на отдельной команде «Обновить публикации» и
на собственных публикациях панели; у базы, опубликованной мимо панели (а так публикуют почти
всегда), в карточке стояло «не проверялась».

Теперь в каждом срезе баз идут **три состояния**, как и просит контракт:

* публикация найдена → `published: true` + `publishUrl`;
* не найдена при ПОЛНОМ просмотре веб-сервера → `published: false`;
* не найдена при неполном → поля нет вовсе — «не знаю», прежнее значение сохраняется.

Чтение веб-сервера кэшируется на минуту (признак идёт в каждом срезе, а публикации меняются
руками); кнопка «Обновить публикации» читает заново и обновляет этот же кэш — иначе две команды
отдавали бы панели разные состояния одной базы. В срезе заодно появился `id` базы (UUID
кластера) — сервис его принимает и использует для отбора сеансов.

### Адрес публикации: путь целиком и настоящий порт

Две ошибки в сборке адреса, обе давали ссылку, по которой ничего нет:

* брался только ПОСЛЕДНИЙ сегмент виртуального каталога — для вложенной публикации
  («Default Web Site/1c/buh») адрес вёл в никуда;
* адрес всегда собирался как `http://localhost/…`, хотя сайт публикаций часто слушает свой
  порт или имя узла. Теперь берётся привязка сайта (`appcmd list site`): `http/*:8080:` →
  `http://localhost:8080`, `http/*:80:apps.local` → `http://apps.local`. Только https —
  адреса не даём вовсе: догадка про http вела бы на закрытый порт.

### `IB_LIST_EXTENSIONS` висел до сторожевого таймаута — причина найдена

**`ibcmd` запускался без своего предела ожидания.** Ждали ровно столько, сколько он молчал, —
то есть до сторожа самой команды, отсюда ваши 575 и 600 с. Это же объясняет, почему
`IB_LIST_USERS` отвечал нормально: пользователи идут через COM-мост, у которого предел есть,
а расширения на этом сервере — через `ibcmd`.

Что сделано:

* быстрым операциям (`extension list`, `create`, `delete`, `config load/apply`) — предел 180 с;
  выгрузка и загрузка базы идут без своего предела, их сторожит время команды;
* отказ называет операцию и базу: «ibcmd extension list по базе «almaz67» не ответил за 180 с
  — процесс снят. Обычно это занятый рабочий каталог или блокировка в самой базе». Десяти минут
  тишины больше нет — ответ приходит через три минуты и говорит, на чём агент встал;
* сама вероятная причина зависания устранена в прошлой правке: у каждого вызова `ibcmd` теперь
  свой рабочий каталог (`--data`), и вызовы по разным базам не дерутся за общую блокировку.

### `synonym`: перестали затирать

Причина, похоже, в переходе на `ibcmd`: в коротком выводе он отдаёт одни имена, а агент слал
`synonym: ""` — и пустая строка ложилась поверх синонима, прочитанного раньше через COM.
Теперь пустые `synonym`, `version`, `purpose` не отправляются вовсе (ни из `ibcmd`, ни из
COM-моста): пропуск значит «не знаю», и прежнее значение в реестре сохраняется.

Если у ваших расширений синоним в самой базе пуст — это видно командой на сервере:
`bpapi-agent ib extensions <база>`.

### Продолжение: почему `ibcmd` молчит и что теперь происходит вместо ожидания

Предел в 180 с показал главное: дело не в блокировке рабочего каталога. Проверка на стенде —
`ibcmd extension list` со своим каталогом данных (`--data`) и недоступной СУБД отвечает ошибкой
за полминуты, то есть сам по себе он не виснет.

Остаётся причина в базе: **`ibcmd` работает с базой напрямую через СУБД, мимо кластера**. На
базе, которую держит рабочий кластер, он то ждёт блокировки, то не отвечает вовсе — при том что
тот же список через кластер (COM) читается за 20–40 секунд, как и показали ваши замеры по
`IB_LIST_USERS`.

Поэтому чтение расширений больше не упирается в `ibcmd`:

* предел на чтение снижен со 180 до **60 с** — за ним всё равно стоит запасной путь, и ждать
  дольше, чтобы потом пойти туда же, значит втрое удлинять ответ;
* по молчанию (`IB_TIMEOUT`) или занятости (`IB_BUSY`) агент **уходит на кластер** и
  возвращает список оттуда — команда отвечает данными, а не отказом. В журнале это видно
  предупреждением;
* **только чтение.** Установку и удаление так не повторяют: снятый `ibcmd` мог успеть тронуть
  базу, и второй заход сделал бы работу дважды.

Побочно это чинит и `synonym`: список, прочитанный через кластер, синонимы отдаёт, а короткий
вывод `ibcmd` — нет.

## 2026-09-11, ответ агента: клин при двух параллельных командах

### Ваша проверка выполнена: параллельные `ibcmd` друг другу не мешают

Два `ibcmd extension list` по разным базам, каждый со своим каталогом данных, запущены
одновременно: оба завершились за 27 с — ровно столько же, сколько один. Общего ресурса между
ними нет, и «занятый рабочий каталог» тут ни при чём. Клин был внутри агента.

### Причина: синхронная работа занимала рабочие потоки целиком

В сборке от 13:57 признак публикации стал идти в каждом срезе баз, и ради него агент читает
веб-сервер — **обходом каталогов**, если `appcmd` недоступен. Обход синхронный: он занимает
рабочий поток asyncа целиком на всё время чтения диска, а на сервере с сотней публикаций это
не миллисекунды.

Рабочих потоков у агента было столько, сколько ядер отдано серверу. На двух ядрах ДВУХ таких
обходов достаточно, чтобы встал **весь** агент — и heartbeat вместе с ним. Отсюда и ваша
таблица: ни ответа, ни heartbeat, предел ожидания `ibcmd` не срабатывает (до него дело не
доходило).

Исправлено в трёх местах:

1. Обход каталогов и чтение `default.vrd` вынесены в отдельный поток (`spawn_blocking`) —
   асинхронные задачи больше не стоят на файловых операциях.
2. Рабочих потоков у службы не меньше четырёх независимо от числа ядер.
3. Срез публикаций кэшируется на 5 минут (было 60 с); кнопка «Обновить публикации» читает
   заново и обновляет тот же кэш.

### Heartbeat больше не ждёт кластер — как вы и просили

`collect_bases` ходит к `rac` и к веб-серверу, и heartbeat ждал его без ограничения. Теперь
ждёт **25 секунд**: не успели — heartbeat уходит БЕЗ среза баз, а сервис попросит полный срез
на следующем такте. Состояние агента, его процессы и счётчики приходят вовремя при любой
занятости — то есть именно тогда, когда они нужнее всего.

Спасибо за обе временные меры на вашей стороне. Правило «забравший команду не считается
молчащим» стоит оставить навсегда — оно верно по существу. `AGENT_IB_PARALLEL = 1` можно
поднимать: причина клина была не в параллельных `ibcmd`, а в потоках агента; после проверки на
боевом сервере верните обычное значение.
