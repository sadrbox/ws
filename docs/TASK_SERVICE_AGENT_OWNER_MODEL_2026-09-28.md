# Задача сервису и панели: убрать связь агента 1С с организацией и допуск БИН

28.09.2026. Сервис AI (`ai/`) и панель («Управление 1С» → «Подключение агентов», карточка агента).

## Зачем

При одобрении заявки агента администратор выбирает **одну организацию ERP**. Но бизнес-агент на сервере фирмы
обслуживает базы многих клиентов, то есть много организаций. Вопрос «какая у агента организация» для него не имеет
ответа, а от ответа зависит, кому агент будет выполнять команды.

Разбор кода показал: в поле `agents.organization_uuid` склеены три разных понятия.

| Понятие | Сколько | Где сейчас используется организация агента |
|---|---|---|
| **Владелец** — чей это агент и сервер: фирма-аутсорсер, сам клиент или BuhProf | одна или нет | сервер агента записывается за ней (`agentRouter.ts`, `ensureServer`); видимость серверов, баз и агентов при `ONEC_SERVER_SCOPE=organizations` (`onecRouter.ts`: `allowedServers`, `agentVisible`) |
| **Обслуживаемые организации** — чьи данные агент отдаёт | много | выбор исполнителя: `pickAgentFor` берёт только агентов, у которых организация равна организации пользователя (`agents/service.ts`); на этом держатся чат (`chat/workflow.ts`, `pickOnline`) и карточка организации |
| **Организация команды** — чьи данные запрошены | своя у каждой команды | пакетные команды, проверки учёта и монопольные операции пишут в `commands.organization_uuid` организацию **агента** (`onec/batchRunner.ts`, `onec/accountingChecksRunner.ts`, `onec/exclusiveOps.ts`), и по ней решается, кто видит результат (`commandVisible`) |

Для агента одной организации эти три значения совпадают, и всё работает. Для агента фирмы они расходятся:

- Клиенту фирмы некому отвечать: исполнителя ищут среди агентов его организации, а агент заведён за фирмой.
  Пример 28.09 — ТОО «SHAHS»: «Прочитать из 1С» отвечало «некому спросить».
- Команда по данным клиента числится за фирмой. Клиент не видит её результат, а сотрудники фирмы видят данные клиента,
  даже если фирма с ним уже не работает.
- Если выбрать организацию «для галочки», агент будет выполнять команды не той организации.

Первым вариантом была одна организация в другом смысле — **владелец**: кто в панели видит и настраивает агента.
Владелец BuhProf решил иначе (Р1, Р2 ниже): связь агента с организацией убирается совсем, допуск БИН — тоже. Кого
агент обслуживает, определяют только его базы. Организация остаётся у команды — чьи данные запрошены.

## Исходное состояние

В рабочем дереве на 28.09 лежит незакоммиченная заплатка другой сессии. Эти задачи строятся поверх неё — перед началом
договоритесь с этой сессией.

- Организация бизнес-агента при одобрении стала необязательной. Бизнес-агент без организации называется «агентом
  сервера».
- Если своих агентов у организации нет, `resolveBusiness` ищет агента для базы, одобренной за БИН организации
  (`resolveServiced`). Годится агент, заведённый за владельцем сервера базы, или агент сервера, если **имя сервера**
  совпало (`sameServerName`). Имя сервера человек сам вписывает в поле «Рабочее место» окна агента.
- `explainUnresolved` объясняет словами, почему базу некому спросить.

Что остаётся нерешённым:

- Путей выбора исполнителя два: «свой агент» и «агент фирмы или сервера», с разными правилами.
- Доверие к агенту сервера держится на имени, которое вписал человек.
- Обзорные команды чата (`GET_ORGANIZATIONS` и др.) по-прежнему идут через `pickOnline` своей организации.
- Команды записываются за организацией агента.
- Агент без организации хранится с пустой строкой в `organization_uuid NOT NULL`. В режиме `organizations` его не видит
  никто, кроме администраторов BuhProf.

## Решения владельца (28.09)

- **Р1. Связь агента с организацией не нужна** — ни как «владелец», ни как «кого обслуживает». Агент — установка
  BuhProf: доверие к нему даёт одобрение его заявки администратором BuhProf, и только оно.
- **Р2. Допуск БИН для агента не нужен.** Агент обслуживает все организации, которые видит в своих базах. Активация БИН
  (`activeBins`, запросы активации) и лимит `maxBins` отменяются; лимит числа баз `maxBases` остаётся.

## Последствия удаления связи (что от неё сейчас зависит)

| Что держится на организации агента | Что станет без неё | Задача |
|---|---|---|
| Выбор исполнителя для пользователя организации: чат, карточка организации, «Долги и остатки» (`pickAgentFor` берёт агентов своей организации) | никому не ответит никто, если не заменить | В2 |
| За кем числится команда и кто видит результат (`batchRunner`, `accountingChecksRunner`, `exclusiveOps`, `commandVisible`) | команды без организации, результаты видят только администраторы BuhProf | В4 |
| Видимость «по организациям» (`ONEC_SERVER_SCOPE=organizations`, C11): серверы, базы и агенты видит организация-владелец | режим теряет смысл. Сейчас он не включён, а «Управление 1С» не входит в клиентскую сборку — панель внутренняя | В5 |
| Доверие агенту фирмы к базам клиентов (`resolveServiced`: агент заведён за владельцем сервера) | правило отпадает вместе с организацией | В3 |
| Одобрение заявки и ручное заведение агента (`POST /agents` требует активную организацию) | поле и требование убираются | В6 |
| Пространство имён сервера (`servers` уникальны парой «организация + имя») | уже работает без организации: сервер агента живёт в `agent:<id>` | не трогать |
| Токен чата базы: организация по умолчанию — организация сервера (`bases/tokens.ts`) | для сервера агента подставилось бы `agent:<id>` вместо организации. Сейчас не срабатывает (заявка базы передаёт организацию явно), но умолчание опасно | В7 |
| Журнал (`agent.register`, `agent.bin_activation.requested`) пишет организацию агента | поле пустое, история остаётся в журнале | В1 |

**Чего связь с организацией не касается и что остаётся:** связь **базы** 1С с организацией из заявки базы (расширение
BuhProf, `base_registrations`, `base_organizations`, токены чата `base_tokens`). Это не допуск агента, а то, какую базу
организация назвала своей. Она нужна чату внутри 1С и используется ниже как правило выбора, когда БИН есть в нескольких
базах (В2).

**Новый риск без организации и допуска — один БИН в базах нескольких агентов:** копия базы у прежней фирмы, тестовая
копия, база клиента на двух серверах. Сейчас кандидаты — только агенты своей организации. Без неё кандидатами станут все
агенты BuhProf, и команда могла бы уйти в копию. Правило выбора — в В2.

## Задачи

### В1. Убрать организацию из агента

- Код больше не читает и не пишет организацию агента: `AgentView.organizationUuid`, `listByOrganization`,
  `setOrganization`, `req.agent.organizationUuid`.
- Миграция удаляет `agents.organization_uuid` и `agent_enrollments.organization_uuid` — только после того, как код их не
  читает. Действующие значения пропадают. История одобрений остаётся в журнале (`audit`).
- `AGENT_ORG_BINDING` (`any` / `strict`) удаляется из настроек: привязывать не к чему.
- **Критерий:** поиск по `organization_uuid` в `ai/src/agents` находит только данные баз и команд, но не агента.

### В2. Один выбор исполнителя бизнес-команды — по БИН организации

- `resolveBusiness(organizationUuid, orgBin, { baseKey?, preferAgentId? })` — единственный путь. Кандидаты — все
  включённые бизнес-агенты, у которых БИН организации есть в срезе баз (`agent_bases.organizations`), в пределах
  `maxBases`.
- **Если БИН найден в нескольких базах**, порядок такой:
  1. явно запрошенная база (`baseKey`) или агент диалога (`preferAgentId`);
  2. база, которую организация назвала своей: одобренная заявка базы или действующий токен чата
     (`base_organizations.approved_at`, `base_tokens`);
  3. если этого нет — команда **не уходит никому**. Ответ `BASE_AMBIGUOUS` перечисляет базы и серверы и говорит, как
     выбрать: подключить базу к BuhProf AI из самой 1С.

  Агент на связи выбирается только среди баз одного из этих уровней, а не вместо них.
- Ветки `pickOnline(org)` и `pickAgentFor(org, …)` для бизнес-команд удаляются: из чата (`chat/workflow.ts`, в том числе
  обзорные команды вроде `GET_ORGANIZATIONS`), из карточки организации, из «Долгов и остатков».
- `explainUnresolved` пересобирается под новое правило: «базы с этим БИН нет ни у одного агента», «агент не на связи»,
  «БИН в нескольких базах».
- **Критерий:** клиент без своего агента получает ответ из своей базы, в том числе в обзорных командах чата. При двух
  базах с одним БИН команда уходит в базу, одобренную за организацию, а без одобренной — отказ с перечнем баз.

### В3. Убрать доверие «по владельцу» и «по имени сервера»

- Удалить из `resolveServiced` условие «агент заведён за владельцем сервера базы» и сравнение имени сервера
  (`sameServerName`) — имя, которое человек вписал в поле «Рабочее место» окна агента.
- `resolveServiced` становится частью В2 или удаляется целиком.
- Если реестру кластера (карточка базы, токены чата) нужна связь базы из среза агента с `bases`, связывать по
  идентификатору информационной базы. Если агент его в срезе не шлёт — поставить задачу агенту.

### В4. Организация команды — организация запроса

- `commands.organization_uuid` хранит организацию, чьи данные затронуты:
  - у бизнес-команд — организацию из запроса (её даёт `resolveBusiness`);
  - у пакетных команд, проверок учёта и монопольных операций внутри базы — организацию базы: по БИН из среза, а при
    нескольких — первую по порядку агента. Не `agent.organizationUuid`;
  - у команд кластера — `NULL`.
- Результат команды (`/commands/:id`) видят:
  - пользователи организации команды;
  - сотрудники фирмы, которая её обслуживает (ERP `service_links`);
  - администраторы BuhProf.

  Особый случай `serverAgent` в `commandVisible` удаляется.
- **Критерий:** клиент видит команды по своим данным, кто бы их ни выполнил. Фирма, у которой больше нет связи с
  клиентом, его команд не видит.

### В5. Видимость в панели «Управление 1С»

- Режим `ONEC_SERVER_SCOPE=organizations` удаляется: он держится на владельце сервера. Агентов, серверы и базы видят
  все, у кого есть право «Администрирование 1С» (как в режиме `all`, который включён сейчас).
- Проверки C11 (`allowedServers`, `agentVisible`, `batchVisible`) упрощаются. Проверка организации **команды** (В4)
  остаётся.

### В6. Окно одобрения и заведение агента

- Поле организации убирается у агентов любой роли. Тексты `onecEnrollOrgHint`, `onecEnrollServerAgentHint` и
  `onecEnrollNoOrg` удаляются, понятие «агент сервера» — тоже.
- В подсказке одобрения — одна фраза: одобренный агент будет отвечать всем организациям, которые видит в своих базах.
  Одобряйте только агентов на серверах, которые обслуживает BuhProf.
- `POST /agents` больше не требует активную организацию. Колонка «Организация» в списке агентов (`AgentsTab.tsx`)
  заменяется на «Обслуживает»: число организаций и баз из среза.
- После одобрения в карточке агента — список «Обслуживает организации»: БИН, организация ERP, база.

### В7. Токен чата базы — только с явной организацией

- `BaseTokenStore.issue` принимает организацию только явно. Умолчание «организация сервера» удаляется: при сервере
  агента оно дало бы `agent:<id>`.

### В8. Отменить допуск и лимит БИН

- Сервис больше не шлёт агенту `limits.activeBins` и `activation`, а `maxBins` отдаёт как `null`. По контракту `null`
  значит «без ограничения», и агент обслуживает все БИН своих баз. `maxBases` остаётся.
- `resolveTarget` больше не отказывает `LICENSE_LIMIT` по БИН; отказ по `maxBases` остаётся.
- Удаляются:
  - запросы активации (`agents/activation.ts`, маршруты `/activation-requests/*`, `/active-bins/fix-all`,
    `PUT /agents/:id/active-bins`);
  - разбор `activationRequests` в heartbeat — поле принимаем и молча игнорируем, старые агенты его ещё шлют;
  - вкладка панели «Запросы активации» (`ActivationRequestsTab.tsx`) и список активных БИН в карточке агента.
- Таблица реестра активации удаляется отдельной миграцией после выкладки: так откат кода не встретит пустую схему.
- **Задача агенту:** если сервис не шлёт `activeBins` и `activation`, кнопки «Запросить активацию» в окне агента не
  показывать. Статус «Не активен» по БИН не писать.
- Контракт [CONTRACT_BASE_REGISTRATION_2026-09-19.md](CONTRACT_BASE_REGISTRATION_2026-09-19.md), часть 2, помечается
  отменённой со ссылкой на этот документ.

### В9. Тесты

- **Выбор исполнителя:**
  - свой агент;
  - агент фирмы;
  - агент BuhProf;
  - БИН в двух базах — с одобренной базой и без неё (`BASE_AMBIGUOUS`);
  - агент не на связи — `AGENT_OFFLINE`;
  - база сверх `maxBases`.
- **Видимость команд:** организация команды, обслуживающая фирма, бывший клиент фирмы, администратор BuhProf.
- **Миграции:** удаление колонок на копии БД; старый агент шлёт `activationRequests` — heartbeat не падает.
