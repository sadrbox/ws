# План развития buhprof_api и бизнес-агента (утверждён 19.09.2026)

Заменяет раздел «Архитектура» в [PLAN_1C_CHAT_2026-09-19.md](PLAN_1C_CHAT_2026-09-19.md); этапы чата оттуда вошли сюда.

## Архитектура

Расширение `buhprof_api` ставится в любую базу «Бухгалтерии для Казахстана»: на нашем сервере 1С, на сервере
1С клиента, в файловой базе на компьютере клиента. Облако (`ai.buhprof.kz`) в базу не ходит никогда — все
соединения исходящие: от агента или от самой 1С.

### Две роли агента — один исполняемый файл, две разные службы

| Роль | Служба | Что может | Чего не может |
|---|---|---|---|
| **Кластер 1С** | `BPAPIAgentAdmin` | всё управление сервером и базами: кластер, сеансы, блокировки, пользователи и расширения баз, выгрузка, загрузка, обновление, публикация (реализовано, интерфейс — панель администрирования) | бизнес-операций в базах не выполняет |
| **Бизнес-агент 1С** | `BPAPIAgent` | только бизнес-операции через `buhprof_api`: справочники, документы, банк, печать, отчёты | **никаких административных возможностей**: ни кластера, ни пользователей и расширений, ни процессов |

Бизнес-агент работает и с файловой базой, и с сервером 1С. На сервере с многими базами — одна служба на все
базы сервера (задача БА2), на компьютере клиента — одна служба на его базу.

### Сервер, которому нужны обе роли

**Две службы рядом на одном сервере** — `BPAPIAgentAdmin` (роль «Кластер 1С») и `BPAPIAgent` (роль «Бизнес-агент 1С»),
один и тот же исполняемый файл, у каждой свой файл настроек (`--config`), свой идентификатор и токен в сервисе,
свой журнал. Агент к этому готов: окно находит все службы агента на машине и рассчитано на пару «бизнес и админ»
(`setup/mod.rs:116-135`), запрет второго экземпляра привязан к идентификатору агента, а не к машине
(`agent.rs:172`).

Почему не одна служба с обеими ролями:
- **Цена ошибки.** У кластер-агента пароли администратора кластера и служебного администратора баз. Команды из
  чатов с клиентами не должны идти через процесс, который держит эти пароли: ошибка или утёкший токен бизнес-пути
  не должны дотягиваться до администрирования всех баз.
- **Разные учётные записи.** Кластер-агент входит служебным администратором, бизнес-агент — пользователем API
  (`bpapi`) с его ролями.
- **Разная нагрузка.** Часовая загрузка базы и сотни коротких запросов бухгалтеров не делят одну очередь и одни
  пределы параллельности.
- **Разные права в сервисе.** Административные команды требуют права «Администрирование 1С», бизнес-команды —
  привязки к организации.

Как они работают вместе: кластер-агент подключает базу к AI (КА1 — расширение, публикация, пользователь, токен),
бизнес-агент затем обслуживает бизнес-команды этой базы. Сервис связывает обе службы с одним сервером по его имени
(`serverName` в настройках).

Оговорка: исполняемый файл у служб общий, поэтому обновление агента перезапускает обе — обновлять вне долгих
административных операций (загрузка, обновление конфигурации).

### Какой путь у какой команды

| Откуда команда | Путь | Под чьими правами |
|---|---|---|
| Чат внутри 1С (форма расширения) | форма → облако (только модель) → вызовы инструментов возвращаются в форму и выполняются в сеансе пользователя | **пользователя 1С** |
| Чат в ERP, Telegram, автоматические задания | облако → очередь → бизнес-агент → база | пользователя API (`bpapi`) |
| Администрирование сервера | панель → облако → кластер-агент → кластер / база | служебного администратора |
| Подключение новой базы к AI | панель → кластер-агент: расширение + публикация + пользователь + токен | служебного администратора |

**Фундамент — единая точка входа операций в расширении**: одна функция «операция + параметры → ответ»
для всех транспортов (HTTP, COM, форма чата). Сейчас сервисный слой завязан на HTTP-ответ и через COM не
вызывается (`tools/RUNBOOK.md`, раздел про COM).

### Состояние ролей в коде агента (проверено 19.09)

- Объявление способностей разделено верно: бизнес-роль не объявляет ни кластерных, ни внутрибазовых, ни
  служебных команд (`commands/mod.rs:390-400`).
- Кластерные и внутрибазовые команды бизнес-агент отвергает: объекты кластера и базы создаются только для роли
  «Кластер» (`agent.rs:82, 104`), на команду — `CAPABILITY_MISSING`.
- Окно показывает административные разделы только роли «Кластер» (`ui/form.rs:190-266`).
- **Пробел:** команды о процессах агента (`AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND`, `AGENT_LIST_PROCESSES`,
  `AGENT_LOG_TAIL`) выполняются при любой роли без проверки (`commands/mod.rs:2321`) — задача БА1.

## Возможности для развития buhprof_api

| Группа | Возможности | Ценность |
|---|---|---|
| **Встроенный чат** | форма в 1С, выбор организации, PDF-вложения, подтверждения кнопками, ссылки на созданные документы, печать и отчёты табличным документом, «Спросить AI» из формы документа | главная: бухгалтер работает, не выходя из 1С |
| **Ответы на вопросы** (только чтение) | остатки товаров по складам; задолженность контрагента и взаиморасчёты; остатки денег в кассе и на счетах; продажи и выручка за период; журнал документов за период с отбором; неоплаченные счета; договоры контрагента; цены номенклатуры | высокая: большая часть вопросов бухгалтера — «сколько» и «покажи» |
| **Справочники** | контрагент по БИН (с договором и банковским счётом), номенклатура, договор | высокая: без них документ не создать |
| **Новые документы** | ПКО и РКО; счёт-фактура на основании реализации; возврат от покупателя и поставщику; реализация и оплата на основании счёта | средняя |
| **Документы из PDF** | поступление из накладной или счёта поставщика (распознать, сопоставить номенклатуру, создать); акт сверки контрагента — сравнение с 1С | высокая: убирает ручной ввод |
| **Банк** | разнесение оплат по счетам и реализациям (сопоставление платежей с документами) | средняя |
| **Журнал в базе** | регистр операций AI: кто, что, когда, `requestId`, результат — видно в самой 1С | средняя: доверие и разбор |
| **Интеграции** | ЭСФ по реализации через расширение `buhprof_esf` | после стабилизации `buhprof_esf` |

Закрытие месяца, регламентированная отчётность и удаление данных через чат — **не делаем**: цена ошибки выше
пользы.
