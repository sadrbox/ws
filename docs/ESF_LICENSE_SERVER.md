# Сервер лицензирования ЭСФ (esf.buhprof.kz) — состояние на 2026-08-28

Серверная часть лицензирования 1С-расширения `esf_exchange`. Код:
`backend/services/esfLicense.js` (логика) + `backend/api/router/esfLicense.js` (HTTP),
админка — `frontend/src/models/EsfLicenses/`.

## Публичный контракт (зашит в 1С — пути и формат менять нельзя)

Префикс `/api1/esf-license` (смонтирован ДО authMiddleware, без авторизации).

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/token?bin=` | 200 `{token}` · 403 `{error, message}` (`unknown`/`inactive`/`expired`/`install_limit`) · 429 · 500 |
| POST | `/heartbeat` `{bin, installId, time}` | 200 `{ok:true}` либо `{ok:true, revoked:true}` |
| POST | `/activation-request` `{bin, installId}` | 200 `{ok:true}` |
| POST | `/verify` `{bin, token, installId}` | 200 `{valid:true, expiresAt}` · 200 `{valid:false, reason}` (`signature`/`expired`/`revoked`/`unknown`) |
| GET | `/health` | 200 `{ok:true, signing, tokenTtlHours, at}` · 503 (БД недоступна) |

Токен: `<БИН>|<expUnix>|<подпись>` — подпись по умолчанию старая, совместимая с
установленным расширением: `base64(sha256("<secret>|<БИН>|<exp>|<secret>"))`.
При включённом `LICENSE_TOKEN_ACTIVE_KID` подпись считается HMAC-SHA256, а к токену
добавляется четвёртый сегмент `|<kid>` (старый клиент такой токен НЕ примет — см. ниже).

## Что закрыто

| Задача | Состояние |
|---|---|
| S-01 отказ отключённому БИН | 403 с `error`+`message`; причины различаются (`unknown`/`inactive`/`expired`) |
| S-02 отзыв через heartbeat | `{revoked:true}` для любого недействующего БИН → клиент чистит кэш и идёт за токеном, получая 403 |
| S-03 TTL токена | по умолчанию **4 часа** (`LICENSE_TOKEN_TTL_HOURS`, 1..168) |
| S-04 проверка на сервере | `POST /verify` готов; **в 1С нужна парная правка T-13** (пока клиент проверяет подпись сам и секрет остаётся в коде) |
| S-05 HMAC + kid | реализовано, **выключено по умолчанию**: включать только вместе с T-13 |
| S-06 журнал | таблица `esf_license_logs` (время, БИН, installId, endpoint, результат, причина, статус, IP), ретенция `LICENSE_LOG_RETENTION_DAYS` (180 дней, чистка оппортунистическая) |
| S-07 лимит установок | таблица `esf_license_installs`; учёт включён, **отказ выключен** (`LICENSE_INSTALL_LIMIT_ENFORCE=false`) — превышение видно в админке и в журнале |
| S-08 ограничение частоты | `/token` 120/мин на IP + 20/мин на БИН; POST-ы 60/мин на IP + 20/мин на БИН; `/verify` 600/мин на IP; ответ 429 |
| S-09 заявки на активацию | дедупликация была и есть; новая заявка → запись в журнал + вебхук `LICENSE_ALERT_WEBHOOK_URL` (если задан) |
| S-10 мониторинг | `GET /api1/esf-license/health` для внешней проверки; сам мониторинг/алерты — на стороне эксплуатации |

Не закрыто намеренно: T-13 в 1С (пока не сделана — секрет остаётся в коде расширения,
и это по-прежнему главная дыра), внешняя система мониторинга и алертов.

## Админка (только superadmin)

`/api/v1/esf-licenses` — стандартный CRUD справочника; дополнительно:

- `GET /esf-licenses/:id/installs` — базы 1С этого БИН (активная / нет обращений / отвязана), счётчик и лимит;
- `DELETE /esf-licenses/:id/installs/:installUuid` — отвязать установку (перенос базы);
- `GET /esf-licenses/:id/logs` — журнал обращений по БИН.

В карточке лицензии: поле «Лимит установок» (пусто — общий лимит сервера), счётчик
активных установок и вкладки «Установки» / «Журнал обращений». В списке — колонка
«Активных установок».

## Переменные окружения

См. `backend/.env.example`, раздел «Лицензирование ЭСФ». Ключевое:

- `LICENSE_TOKEN_SECRET` — общий с 1С секрет старой подписи (обязателен, пока не сделана T-13);
- `LICENSE_TOKEN_TTL_HOURS=4` — окно автономной работы;
- `LICENSE_TOKEN_KEYS` / `LICENSE_TOKEN_ACTIVE_KID` — HMAC-ключи и активный kid (S-05);
- `LICENSE_INSTALL_LIMIT=2`, `LICENSE_INSTALL_LIMIT_ENFORCE=false`, `LICENSE_INSTALL_STALE_DAYS=30`;
- `LICENSE_LOG_RETENTION_DAYS=180`, `LICENSE_VERIFY_CACHE_SECONDS=60`, `LICENSE_ALERT_WEBHOOK_URL`.

## Порядок включения защиты «по-настоящему» (S-04 + S-05)

1. В 1С: `ТокенДействителен` вызывает `POST /verify`, `СекретЛицензии` удаляется из кода;
   явно решить поведение при недоступности `/verify` (короткий льготный период по
   последнему успешному ответу — либо отказ).
2. Обновлённое расширение раскатывается на всех клиентов.
3. Только после этого на сервере задать `LICENSE_TOKEN_KEYS` + `LICENSE_TOKEN_ACTIVE_KID`
   (подпись станет HMAC). Уже выданные старые токены продолжат проверяться, пока
   `LICENSE_TOKEN_SECRET` остаётся в окружении; удалять его — после истечения TTL.

## Эксплуатационные оговорки

- pm2 поднимает 4 воркера: счётчики rate-limit и кэш `/verify` — на воркер. Лимиты
  фактически вчетверо мягче; отзыв доходит до `/verify` за время до
  `LICENSE_VERIFY_CACHE_SECONDS` (по умолчанию минута).
- Недоступность сервера не блокирует работу клиентов (так задумано), но и отзыв в это
  время не действует — отсюда мониторинг `/health` (S-10).
- Отвязка установки освобождает место в лимите; если та же база снова обратится, она
  зарегистрируется заново (отвязка рассчитана на перенесённую или погашенную базу).

`pm2 restart all`. Проверить, что реверс-прокси роутит `/api1/*` на бэкенд.
