# Промпт для сессии bpapi_agent: пользователи, публикация, выбор транспорта

Копия того, что отдаётся в сессию разработки агента (та машина этот репозиторий не видит).
Дата: 2026-09-05. Предыдущий промпт: `docs/PROMPT_AGENT_IB.md`.

---

Замеры на живом сервере (110 баз, зонд `npm run onec-probe` на стороне сервиса):

- `CLUSTER_*` — работают, казахские буквы целы;
- `IB_LIST_EXTENSIONS` — работает: 13 из 16 баз последовательно, 10 из 12 при параллелизме 4;
- **медиана 27 с на базу**, максимум 48 с — это цена подъёма COM-соединения, не работы;
- параллелизм 4 безопасен: отказов от одновременности больше нет;
- `IB_LIST_USERS` — падает на ВСЕХ базах;
- 3 базы (`aibek`, `akacapital`, `asal`) дают `INFOBASE_NOT_FOUND`, хотя `rac` их видит.

Четыре задачи, по убыванию важности.

## 1. `IB_LIST_USERS` — неверная цепочка COM

Ошибка одинаковая на всех базах, за 20–26 с:

```
IB_ERROR: платформа не знает метод ПолучитьПользователейИнформационнойБазы / GetInfoBaseUsers:
InvokeMember … DISP_E_UNKNOWNNAME
```

Такого **глобального** метода в 1С нет. Нужны два шага:

1. взять **свойство** `ПользователиИнформационнойБазы` (англ. `InfoBaseUsers`) у объекта соединения — `GetProperty`;
2. на полученном объекте вызвать **метод** `ПолучитьПользователей` (`GetUsers`) — `InvokeMethod`.

Свойства пользователя для ответа: `Имя` → `name`, `ПолноеИмя` → `fullName`, `Роли` → `roles[]`
(коллекция, обход по `Количество()`, у каждой роли `Имя`). Поля `disabled` у пользователя ИБ
**не существует** — слать `false`, оно необязательное.

Расширения из тех же баз читаются, значит соединение и права в порядке — ошибка только в вызове.

## 2. `INFOBASE_NOT_FOUND` на живых базах

`aibek`, `akacapital`, `asal` — устойчиво, каждый раз, падение за 8–9 с (то есть даже не доходя
до подключения). При этом `CLUSTER_INFOBASE_INFO` их отдаёт, `dbServer: localhost`.

Значит поиск базы для входа идёт не по тому источнику, что перечисление через `rac`. Дешёвая
проверка: `rac cluster list` — если кластеров на сервере больше одного, а COM-путь смотрит
только в первый, картина объясняется полностью.

## 3. Новая команда `IB_PUBLISH` — публикация базы на веб-сервере

Публикация не делается ни через COM, ни из кода 1С: это настройка веб-сервера (виртуальный
каталог + `default.vrd`). Но агенту она доступна как **запуск процесса** — ровно так же, как
он уже запускает `rac.exe`:

```cmd
webinst -publish -iis -wsdir <alias> -dir "<путь>" -connstr "Srvr=localhost;Ref=<baseKey>;" -confPath …
```

Контракт (тип уже согласован со стороной сервиса, реализуйте под него):

```jsonc
// payload
{ "baseKey": "buh_alma", "alias": "buh_alma", "dir": "C:\\inetpub\\1c\\buh_alma", "webServer": "iis" }
// результат при SUCCESS
{ "ok": true, "url": "http://localhost/buh_alma" }
```

`alias`, `dir`, `webServer` необязательны — при отсутствии агент подставляет свои значения по
умолчанию (alias = baseKey, каталог из конфига).

⚠ **Публиковать только на localhost.** Агент ходит в HTTP-сервис с той же машины; открывать
110 клиентских баз наружу не нужно и опасно.

Способность: та же `ib.admin`. Класс операции — CRITICAL (меняет конфигурацию веб-сервера).

## 4. Выбор транспорта по каждой базе

Главная задача, ради которой всё остальное. Сейчас каждая операция стоит ~27 с — это подъём
внешнего соединения. Через HTTP-сервис опубликованной базы то же самое занимает доли секунды.

```
команда на базу X
   └─ в базе стоит наше расширение И база опубликована?
        да  → HTTP-сервис расширения
        нет → COM-соединение (как сейчас)
```

**Контракт команд при этом не меняется вовсе** — типы, payload и форма результата те же.
Меняется только транспорт внутри агента. Это важно: базы переезжают на быстрый канал
поштучно, по мере раскатки, и никакого общего переключения не требуется.

Порядок раскатки на базу: `IB_PUBLISH` → `IB_INSTALL_EXTENSION` (через COM) → дальше HTTP.

### Проверка API из расширения

Перед тем как строить транспорт, стоит убедиться, что API доступен из HTTP-сервиса. Три строки
в существующем расширении на базе `_transition`:

```bsl
Функция ПользователиGET(Запрос)
    Ответ = Новый HTTPСервисОтвет(200, "application/json; charset=utf-8");
    Массив = Новый Массив;
    Для Каждого П Из ПользователиИнформационнойБазы.ПолучитьПользователей() Цикл
        Массив.Добавить(Новый Структура("name, fullName", П.Имя, П.ПолноеИмя));
    КонецЦикла;
    Запись = Новый ЗаписьJSON; Запись.УстановитьСтроку();
    ЗаписатьJSON(Запись, Массив);
    Ответ.УстановитьТелоИзСтроки(Запись.Закрыть());
    Возврат Ответ;
КонецФункции
```

Отдаёт список — путь рабочий. Падает — текст ошибки скажет, во что упёрлись: права
«Администрирование» или безопасный режим расширения (в безопасном режиме запись
пользователей ИБ запрещена платформой, расширение должно стоять с `БезопасныйРежим = Ложь`).

## Что не менять

- Форму ответа `IB_LIST_*`: список **полный**, чего нет в ответе — сервис удаляет из реестра.
- Идемпотентность: команды живут 900 с, панель ждёт 45 с и не снимает их с очереди.
- Пароли не логировать.
- `sessionId` в `CLUSTER_TERMINATE_SESSION` — это **UUID** сеанса, не номер (проверено зондом).

## Что сообщить обратно

1. Опубликована ли хоть одна база сейчас (нужно для планирования раскатки).
2. Сколько кластеров на сервере (`rac cluster list`) — для задачи 2.
3. Работает ли тест HTTP-сервиса из §4 — от этого зависит, имеет ли смысл весь HTTP-путь.
