# Админ-агент 1С: установка и проверка

Версия 1.0 · 2026-09-04 · платформа 8.3.25.1257, сервер 1С — Windows

Пошаговая настройка второй службы агента (`role = admin`), которая работает с кластером 1С
через `rac`: список баз, сеансы, соединения, блокировка начала сеансов. Бизнес-агент
(документы через расширение `buhprof_api`) настраивается отдельно и здесь не затрагивается.

Почему две службы, а не одна с двумя ролями: разный радиус поражения. Компрометация
бизнес-пути не должна давать прав администратора кластера, а для этого нужны разные учётные
записи ОС — две роли в одном процессе дали бы разделение только на бумаге.

---

## 1. Проверить, что RAS запущен

RAS — отдельная служба поверх агента сервера 1С; сама она не поднимается. На **сервере 1С**:

```cmd
"C:\Program Files\1cv8\8.3.25.1257\bin\rac.exe" cluster list localhost:1545
```

| Что вывелось | Что это значит |
|---|---|
| Блок `cluster : <uuid>`, `host`, `port`, `name` | RAS работает, кластер без аутентификации — можно к шагу 2 |
| `Администратор кластера не аутентифицирован` | RAS работает, кластер защищён — понадобятся логин и пароль администратора кластера |
| Ошибка соединения | RAS не запущен — см. ниже |

Если службы нет, найти точное имя службы агента сервера и создать службу RAS:

```cmd
sc query state= all | findstr /i "1C"

sc create "1C:Enterprise 8.3 Remote Server" ^
   binPath= "\"C:\Program Files\1cv8\8.3.25.1257\bin\ras.exe\" cluster --service --port=1545" ^
   start= auto ^
   depend= "<имя службы агента сервера из первой команды>"
sc start "1C:Enterprise 8.3 Remote Server"
```

RAS слушает только локально, если не указано иное, — этого достаточно: агент работает на том
же сервере. Открывать порт 1545 наружу не нужно и не следует.

## 2. Завести агента в AI Service

На машине с сервисом (`/mnt/ws/app/ai`):

```bash
node --experimental-strip-types --env-file=.env tools/admin.ts create-agent \
  --org <uuid организации ERP> \
  --name "Сервер 1С, админ" \
  --agent-toml /tmp/admin-agent.toml
```

Токен показывается один раз и сразу вписывается в указанный файл конфигурации. Файл затем
переносится на сервер 1С.

---

## 3. Настроить службу на сервере 1С

Скопировать `bpapi-agent.exe` в **отдельный** каталог (не тот, где бизнес-агент) и положить
рядом `agent.toml`. Минимальный вид для админ-роли:

```toml
[agent]
id = "<uuid из create-agent>"
name = "Сервер 1С, админ"
role = "admin"
server_name = "Сервер 1С (офис)"   # ТО ЖЕ имя, что у бизнес-агента этого сервера
max_parallel = 4

[cloud]
url = "https://ai.buhprof.kz"
token = ""                          # или BPAPI_CLOUD_TOKEN

[cluster]
rac_path = "C:\\Program Files\\1cv8\\8.3.25.1257\\bin\\rac.exe"
ras_host = "localhost"
ras_port = 1545
timeout_secs = 60

[logging]
level = "info"
dir = "logs"
```

Секция `[onec]` админ-агенту не нужна: он в базы не заходит.

`server_name` обязан совпадать у обоих агентов одного сервера — по нему сервис связывает базы
с агентами. Разные имена дадут два «сервера» в реестре и команду, которой некому исполнить.

Секреты — переменными окружения службы, не в файле:

| Переменная | Что это |
|---|---|
| `BPAPI_CLOUD_TOKEN` | токен агента из `create-agent` |
| `BPAPI_CLUSTER_USER`, `BPAPI_CLUSTER_PWD` | администратор кластера (если кластер защищён) |
| `BPAPI_IB_USER`, `BPAPI_IB_PWD` | служебный администратор ИБ — **только** для блокировки начала сеансов |

Установка и запуск:

```cmd
bpapi-agent check-config
bpapi-agent service install --config C:\bpapi-admin\agent.toml
sc start BPAPIAgent
```

Служба должна работать под **своей** учётной записью ОС, отдельной от бизнес-агента: в этом и
состоит разделение ролей. Учётка нужна с правами на запуск `rac` и чтение каталога платформы.

## 4. Проверить

1. В логе агента (`logs\`) при старте — строка «зарегистрирован в Cloud» с `role=admin`.
2. В aleppo.kz открыть меню → **Администрирование 1С**.
3. Вкладка «Базы» пуста до первого полного среза — нажать **«Обновить из кластера»**: список
   должен наполниться именами баз из кластера.
4. Щелчок по базе открывает её сеансы; список берётся из кластера в момент открытия.
5. Проверить снятие сеанса на заведомо ненужном сеансе (например, своём тестовом) — операция
   необратима, поэтому проходит через подтверждение.

### Если что-то пошло не так

| Сообщение | Причина |
|---|---|
| `Админ-агент 1С не настроен или не на связи` | служба не запущена, не зарегистрировалась, или у неё `role = business` |
| `Агент не умеет «…»: нет способности cluster.admin` | агент зарегистрировался с ролью `business` — проверьте `agent.role` |
| `RAC_UNAVAILABLE` | не найден `rac.exe` по пути `cluster.rac_path` |
| `RAC_TIMEOUT` | `rac` не ответил за `cluster.timeout_secs` — обычно RAS не отвечает |
| `CLUSTER_NOT_FOUND` | RAS отвечает, но кластера по адресу нет — проверьте порт |
| `RAC_ERROR` + текст утилиты | ответ самого `rac`: чаще всего аутентификация или синтаксис версии платформы |

Последний случай стоит прислать вместе с текстом: набор аргументов собран по документации и
на живом кластере ещё не проверялся.

---

## Что это НЕ даёт (пока)

Создание пользователей внутри баз (`IB_*`), пакетные операции «во всех базах» и раскатка
расширения на сто баз — это задачи A7 и A4. Им нужен служебный администратор ИБ в каждой базе,
и до его появления доступны только кластерные операции, которым вход в базу не требуется.
