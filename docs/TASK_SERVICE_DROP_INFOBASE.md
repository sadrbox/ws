# Задача сервису: удаление мёртвой регистрации базы из кластера

Со стороны агента готово (сборка `0.1.0+2026-09-12 11:04 (+05)`): команда `CLUSTER_DROP_INFOBASE`
объявляется, исполняется и защищена. Чтобы ею можно было пользоваться из панели, нужна
спецификация в whitelist и кнопка в карточке базы.

## Зачем

Регистрация в кластере переживает свою базу данных. `rac` такую базу перечисляет, панель
показывает её наравне с рабочими, а любое обращение внутрь отказывает:

```
База данных отсутствует в сервере баз данных
Не найдена база данных 'aibek' в SQL-сервере 'localhost'
```

Убрать её можно было только руками на сервере — и потому не убирали. Список баз копит мусор,
групповые операции честно отчитываются о неудачах по базам, которых физически нет, а человек
каждый раз заново выясняет, почему «база не работает».

## Команда

### `CLUSTER_DROP_INFOBASE` — удалить регистрацию базы из кластера

| Поле | Тип | Смысл |
|---|---|---|
| `baseKey` | строка | база (имя в кластере) |
| `confirm` | булево | явное согласие; без него команда отказывает |

Ответ: `{ "ok": true, "baseKey": "aibek", "note": "регистрация удалена из кластера; база данных
не трогалась — её не было" }`.

`operation: "CRITICAL"`, `capability: "cluster.admin"`, `role: "admin"`, `requiresBase: true`,
схема `.strict()`.

## Чего команда НЕ делает — это и есть её безопасность

**Не удаляет базу данных.** Ключи `--drop-database` и `--clear-database` не передаются никогда:
агент удаляет запись в кластере, а не данные.

**Не трогает живые базы.** Имя базы приходит снаружи, и удалять по нему вслепую нельзя:
опечатка убрала бы из кластера рабочую базу — данные остались бы в СУБД, но все, кто ею
пользуется, потеряли бы доступ до ручного восстановления записи со всеми параметрами. Поэтому
перед удалением агент сам проверяет через СУБД, что базы данных действительно нет:

| Что выяснил агент | Что делает |
|---|---|
| базы данных нет | удаляет регистрацию |
| база данных на месте | **отказ**: «база «X» РАБОТАЕТ: её база данных на месте, и регистрацию агент не удалит» |
| проверить не удалось (нет пароля СУБД, нет `ibcmd`, база занята) | **отказ** с названной причиной |

Последняя строка важна: «не смог убедиться» и «база мертва» — разные вещи, и агент их не
смешивает. На сервере без заполненного `cluster.db_password` команда не сработает вовсе, и это
правильное поведение, а не недоделка.

## Что сделать в панели

1. Спецификацию команды в whitelist (поля выше).
2. Кнопку в карточке базы — показывать её ТОЛЬКО у базы с признаком «войти нельзя»
   (`ibUnreachableAt`, см. ниже) или прямо после отказа с кодом `IB_DB_MISSING`. Кнопка у
   рабочей базы бессмысленна: агент всё равно откажет.
3. Подтверждение с названием базы и прямым текстом: «Запись о базе будет удалена из кластера.
   База данных не удаляется — её нет. Восстановить запись можно только вручную, со всеми
   параметрами подключения».

## Связанное: признак «войти нельзя»

У сервиса уже есть `markIbReachable` и поле `ibUnreachableAt`, но вызовов в коде нет. Теперь для
них есть точный повод: **код `IB_DB_MISSING`** в результате команды означает, что в базу войти
нельзя и повтор не поможет. Стоит ставить признак по нему (и снимать на любом успешном
обращении), а такие базы исключать из групповых операций.

## Как проверить

1. У базы с отсутствующей базой данных команда с `confirm: true` возвращает `ok` и база
   исчезает из списка после ближайшего среза кластера.
2. У РАБОЧЕЙ базы та же команда возвращает отказ со словами «база РАБОТАЕТ» — и ничего не
   меняет. Это главная проверка: она защищает от опечатки в имени.
3. Без `confirm` — `VALIDATION_ERROR` с требованием явного согласия.
4. На сервере без пароля СУБД — отказ с объяснением, а не молчаливое удаление.

## Что доступно уже сейчас, без панели

`bpapi-agent bases check` на сервере: проходит по базам кластера, показывает, у каких нет базы
данных, и печатает готовые строки `rac infobase drop --cluster=<uuid> --infobase=<uuid>` для
каждой.

## Статус: сделано на стороне сервиса и панели (2026-09-12)

1. **Спецификация в whitelist** — `ai/src/commands/admin.ts`: `CLUSTER_DROP_INFOBASE`,
   `operation: CRITICAL`, `capability: cluster.admin`, `role: admin`, `requiresBase: true`,
   схема `.strict()` с обязательным `confirm: z.literal(true)` (умолчания нет — цена опечатки
   слишком высока).
2. **Ручка** — `POST /v1/onec/bases/:key/drop-registration` (`ai/src/http/onecRouter.ts`),
   клиент `dropBaseRegistration` в `frontend/src/services/onec/api.ts`.
3. **Кнопка** — в карточке базы, раздел «Доступность базы»
   (`frontend/src/models/OneCBases/BaseAvailability.tsx`): показывается ТОЛЬКО у базы с
   признаком «войти нельзя» (`ibUnreachableAt`), с подтверждением и текстом из §«Что сделать
   в панели» дословно.
4. **Признак «войти нельзя» теперь ставится.** Вызов `markIbReachable` был — не было повода
   его вызвать: агент отвечал общим `IB_ERROR`, и отметка не появлялась. Теперь причина
   разбирается (`ibFailureReason` в `ai/src/bases/service.ts`): код `IB_DB_MISSING` → `NO_DB`,
   `INFOBASE_NOT_FOUND` → `NO_INFOBASE`, плюс разбор текста для старых сборок агента. Причина
   хранится отдельной колонкой (`bases.ib_unreachable_reason`, миграция 018) и показывается
   словами: «Нет в СУБД», «Нет доступа». Базы с `NO_DB` / `NO_INFOBASE` исключены из ВСЕХ
   групповых операций, включая публикацию.
5. **Скрытие базы** — `POST /v1/onec/bases/:key/hidden`: когда решение об удалении регистрации
   ещё не принято, базу можно просто убрать из работы. Обратимо.
