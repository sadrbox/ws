# Контракт: встроенный чат в 1С ↔ AI-сервис (этап 1 плана, СВ1 и СВ2)

19.09.2026. Общий для сессии расширения (`buhprof_api`, задачи РА4, РА5) и сессии сервиса (`W:\app\ai`, СВ1,
СВ2). План — [PLAN_BUHPROF_API_2026-09-19.md](PLAN_BUHPROF_API_2026-09-19.md).

## Суть

Форма `BPAPI_Чат` в 1С отправляет ход в сервис. Сервис ведёт диалог с моделью как в чате ERP (тот же
`ChatWorkflow`, промпт, белый список инструментов, карточки подтверждения), но **инструменты не ставит в очередь
агенту, а возвращает форме**: форма выполняет их в сеансе пользователя 1С через шлюз расширения и присылает
результаты следующим ходом. Модель вызывается только в сервисе; ключ модели в 1С не попадает.

Вызов инструмента описывается **теми же `commandType` и `payload`, что сейчас уходят агенту** (`CREATE_SALE`,
`SEARCH_PRODUCTS`, … — `ai/src/tools/registry.ts`). Сопоставление «команда → операция расширения» повторено в
шлюзе расширения (`BPAPI_Шлюз.ВыполнитьКоманду`) один в один с агентом (`bpapi_agent/src/commands/mod.rs`,
`build_route`), поэтому сервису ничего сопоставлять не нужно.

Бизнес-агент для этого канала не нужен.

## Аутентификация

| Заголовок | Значение |
|---|---|
| `X-Base-Token` | токен базы: выдаётся в панели администрирования для базы, в сервисе хранится хэшем, отзывается. В 1С — в безопасном хранилище БСП |
| `X-1C-User-Id` | UUID пользователя ИБ (`ПользователиИнформационнойБазы.ТекущийПользователь().УникальныйИдентификатор`) |

**Только ASCII в заголовках**: имя пользователя 1С кириллическое и в заголовок не помещается (HTTP-заголовок
кириллицу не пропускает — проверено 19.09 на `smoke_test`). Имя идёт в теле (`user.name`).

Токен базы привязан к базе, а база — к организации ERP (для учёта, лимитов и истории). Организация 1С, с которой
работает пользователь, приходит в каждом ходе (`organization`) — это **контекст диалога**, а не проверка доступа:
права пользователя на организацию проверяет сама 1С (список в форме строится под его правами, операции
выполняются под ними же).

Отказы: `401 BASE_TOKEN_INVALID` (нет, неверный, отозван), `403 BASE_DISABLED`, `429 RATE_LIMITED` (+ `Retry-After`).

## Маршруты сервиса

Конверт ответа — как у всего сервиса: `{"success": true, "data": …}` / `{"success": false, "error": {code, message}}`.

### `GET /v1/onec-chat/ping`

Проверка связи и токена для кнопки «Проверить связь» в настройках. Ответ: `{base: {key, name}, organization:
{uuid, name}, serviceVersion}`.

### `POST /v1/onec-chat/turn` — ход диалога

```jsonc
{
  "conversationId": "uuid | null",          // null — новый диалог
  "user": { "id": "uuid", "name": "Бухгалтер" },
  "organization": { "bin": "831111302342", "name": "ИП Азимов С.М.", "id": "uuid ссылки" },
  "text": "Создай реализацию Физули на облачное хранилище, 1 шт, 5000",   // может быть пустым
  "attachments": [ { "fileName": "выписка.pdf", "mimeType": "application/pdf", "content": "base64" } ],  // до 3, до 20 МБ каждый
  "decision": { "accepted": true },          // ответ на карточку подтверждения (вместо текста «да»/«нет»)
  "toolResults": [                            // результаты вызовов из прошлого ответа
    { "callId": "…", "result": { "success": true, "data": { … }, "status": 201 } }
  ]
}
```

Ответ `data`:

```jsonc
{
  "conversationId": "uuid",
  "state": "COMPLETED | WAITING_CLARIFICATION | WAITING_CONFIRMATION | TOOL_CALLS | PROCESSING | FAILED",
  "text": "…",                                // для пользователя; при TOOL_CALLS может быть пустым
  "confirmation": { "tool": "create_sale", "card": "…" },   // только при WAITING_CONFIRMATION
  "calls": [                                   // только при TOOL_CALLS
    { "callId": "…", "commandType": "CREATE_SALE", "payload": { … }, "requestId": "uuid" }
  ],
  "documents": [ { "type": "sale", "id": "uuid", "number": "…", "title": "Реализация №…" } ]   // созданные и найденные, для ссылок
}
```

Состояния — те же, что у чата ERP (`WorkflowState`), плюс два:
- **`TOOL_CALLS`** — выполните `calls` и пришлите `toolResults` следующим ходом (без текста). Цикл повторяется, пока
  не придёт другое состояние. Порядок выполнения — порядок в массиве.
- **`PROCESSING`** — ход идёт в фоне (распознавание PDF). Опрашивайте `GET /v1/onec-chat/conversations/:id`, пока
  состояние не сменится.

### `GET /v1/onec-chat/conversations` и `GET /v1/onec-chat/conversations/:id`

Список диалогов пользователя 1С и один диалог: сообщения, текущее состояние, ожидающая карточка и **ожидающие
вызовы** (`calls`, если диалог стоит в `TOOL_CALLS` — форма, закрытая посреди цикла, продолжит его).

## Выполнение вызовов в 1С

Форма для каждого вызова выполняет в сеансе пользователя:

```
BPAPI_Шлюз.ВыполнитьКоманду(commandType, payload, requestId, "form")  →  { success, data | error, status }
```

Правила — те же, что у агента:
- изменяющие команды (`CREATE_*`, `POST_*`, `UNPOST_*`, `IMPORT_BANK_STATEMENT`, `POST_BANK_DOCUMENTS`,
  `CREATE_RECONCILIATION_ACT`) без `requestId` не выполняются (`MISSING_REQUEST_ID`); повтор с тем же `requestId`
  безопасен;
- `REQUEST_IN_PROGRESS` форма пережидает и повторяет, как агент;
- **файлы в сервис не отправляются.** Если результат содержит `data.content` (печатная форма, отчёт), форма
  сохраняет файл у себя и показывает его пользователю, а в `toolResults` вместо `content` кладёт
  `{"contentOmitted": true, "bytes": N}`. Модели содержимое файла не нужно, а десятки мегабайт туда-обратно — лишние.

**Подтверждения.** Изменяющий вызов сервис присылает только после карточки, которую пользователь подтвердил
(`decision.accepted: true`), — как в чате ERP. Форма дополнительно ничего не спрашивает.

## Что меняется в сервисе (СВ1, СВ2)

1. Субъект «пользователь 1С» (`X-Base-Token` + `X-1C-User-Id`), таблица токенов баз с хэшем и отзывом, миграция;
   выпуск токена в панели для базы (ПН1 — можно позже, на время разработки — служебной командой).
2. Диалог принадлежит паре «база + пользователь 1С»; аудит с каналом `1c`.
3. В `ChatWorkflow` — режим выполнения инструментов «на стороне клиента»: вместо `queue.enqueue` + `waitResult` —
   сохранить ожидающие вызовы в состоянии диалога и вернуть `TOOL_CALLS`; на ход с `toolResults` — отдать
   результаты модели и продолжить. Белый список, защита от выдуманных id и подтверждения — прежние.
4. Организация хода — из `organization` запроса: БИН подставляется в инструменты (`organizationBin`), модель не
   спрашивает «какая организация».
5. PDF-вложения — прежним путём (распознавание в фоне, `PROCESSING`), итог — `TOOL_CALLS` с `IMPORT_BANK_STATEMENT`.
6. Лимиты на пару «база + пользователь 1С».

## Версии

Расширение: `ВыполнитьКоманду` — с 1.4.0. Сервис объявляет поддержку канала в `ping` (`serviceVersion`).
