# Контракт: встроенный чат в 1С ↔ AI-сервис (этап 1 плана, СВ1 и СВ2)

19.09.2026. Общий для сессии расширения (`buhprof_api`, задачи РА4, РА5) и сессии сервиса (`W:\app\ai`, СВ1,
СВ2). План — [PLAN_BUHPROF_API_2026-09-19.md](PLAN_BUHPROF_API_2026-09-19.md).

## Суть

Форма `BPAPI_Чат` в 1С отправляет ход в сервис. Сервис ведёт диалог с моделью как в чате ERP (тот же
`ChatWorkflow`, промпт, белый список инструментов, карточки подтверждения), но **инструменты не ставит в очередь
агенту, а возвращает форме**: форма выполняет их в сеансе пользователя 1С через шлюз расширения и присылает
результаты следующим ходом. Модель вызывается только в сервисе; ключ модели в 1С не попадает.

Вызов инструмента описывается **теми же `commandType` и `payload`, что сейчас уходят агенту** (`CREATE_SALE`,
`SEARCH_PRODUCTS`, … — `ai/src/tools/registry.ts`). Сопоставление «команда → операция расширения» повторено в
шлюзе расширения (`BPAPI_Шлюз.ВыполнитьКоманду`) один в один с агентом (`bpapi_agent/src/commands/mod.rs`,
`build_route`), поэтому сервису ничего сопоставлять не нужно.

Бизнес-агент для этого канала не нужен.

## Аутентификация

| Заголовок | Значение |
|---|---|
| `X-Base-Token` | токен базы: выдаётся в панели администрирования для базы, в сервисе хранится хэшем, отзывается. В 1С — в безопасном хранилище БСП |
| `X-1C-User-Id` | UUID пользователя ИБ (`ПользователиИнформационнойБазы.ТекущийПользователь().УникальныйИдентификатор`) |

Расширение с 1.5.0 шлёт в КАЖДОМ запросе ещё два заголовка — они ничего не решают, но без них разбор сбоя
превращается в сличение времени:

| Заголовок | Значение |
|---|---|
| `X-Ext-Version` | версия расширения, например `1.5.0`. По ней сервис отвечает внятно (`426 EXT_TOO_OLD`), когда сборка слишком стара, и по ней же решает, отдавать ли новый токен базы. С 23.09 сервис ещё и ЗАПОМИНАЕТ её рядом с базой вместе со временем запроса — см. ниже |
| `X-Request-Id` | UUID запроса. Возвращается в заголовке ответа и пишется в журнал сервиса рядом с базой и пользователем; тот же номер 1С пишет в свой журнал регистрации при сбое связи |

**Версия и последний обмен запоминаются (23.09).** Раньше `X-Ext-Version` читался только на месте: в журнал и
на пороги. База, работающая ТОЛЬКО этим каналом — без агента вовсе, — оставалась в панели без версии и без
времени последнего обмена, хотя отвечала двадцать раз за день; на вопрос «какая сборка у клиента» отвечать было
нечем. Теперь любой запрос канала (включая `GET /ping` и отказ `426 EXT_TOO_OLD` — база при этом на связи, и
именно её сборку в такую минуту и спрашивают) обновляет у базы две отметки: версию расширения и время запроса.
Пустой заголовок время обновляет, а известную версию не затирает: пусто — это «не знаем», а не «нет».

Запись идёт не чаще раза в минуту на базу, но СМЕНУ версии сервис пишет немедленно: форма опрашивает диалог раз
в секунду, и запись на каждый опрос была бы платой в базу данных за поле, которое читают раз в день, — а
обновление расширения у клиента это ровно то событие, из-за которого в панель и смотрят.

В панели это видно в «Расширение БухПроф-AI» → «Базы с расширением»: колонка версии с источником (`agent` —
срез агента, `chat` — сама база, `registration` — со слов заявки) и «Последний обмен» — позднее из «видел
агент» и «обратилась сама». Ступень состояния расширение считает у себя тем же числом, поэтому два окна об
одной базе отвечают одинаково.

**Только ASCII в заголовках**: имя пользователя 1С кириллическое и в заголовок не помещается (HTTP-заголовок
кириллицу не пропускает — проверено 19.09 на `smoke_test`). Имя идёт в теле (`user.name`).

Токен базы привязан к базе, а база — к организации ERP (для учёта, лимитов и истории). Организация 1С, с которой
работает пользователь, приходит в каждом ходе (`organization`) — это **контекст диалога**, а не проверка доступа:
права пользователя на организацию проверяет сама 1С (список в форме строится под его правами, операции
выполняются под ними же).

Отказы: `401 BASE_TOKEN_INVALID` (нет, неверный, отозван), `403 BASE_DISABLED`, `429 RATE_LIMITED` (+ `Retry-After`).

## Маршруты сервиса

Конверт ответа — как у всего сервиса: `{"success": true, "data": …}` / `{"success": false, "error": {code, message}}`.

### `GET /v1/onec-chat/ping`

Проверка связи и токена для кнопки «Проверить связь» в настройках. Ответ: `{base: {key, name}, organization:
{uuid, name}, serviceVersion, protocol, chat, features}`.

`features` — что эта установка умеет сверх базового контракта: `["uploads", "idempotency", "token-rotation"]`.
`limits` — её пределы: `attachmentsPerTurn` (сколько файлов принимать в одном сообщении, `CHAT_ATTACHMENTS_MAX`,
по умолчанию 20) и `attachmentMaxBytes` (размер одного файла). Реализовано 22.09; превышение числа файлов —
`400 TOO_MANY_ATTACHMENTS` с названным пределом, а не текст проверки схемы.
Список объявляет ровно включённое: чего в нём нет, того у этой установки нет, и расширение идёт прежним путём.
Форма «Подключение к BuhProf AI» показывает его администратору, а поддержка по нему сразу видит, чего ждать.

### `POST /v1/onec-chat/uploads?fileName=<percent-encoded>` — вложение отдельным запросом

Тело — **сырые байты** (`Content-Type: application/pdf`), без base64. Имя файла кириллическое, поэтому едет в
строке запроса закодированным: в заголовке HTTP ему нельзя.

```
200 { "success": true, "data": { "fileId": "uuid", "bytes": 4096, "sha256": "…" } }
413 { "success": false, "error": { "code": "FILE_TOO_LARGE", "message": "Файл больше 20 МБ" } }
404 { "success": false, "error": { "code": "UNKNOWN_ROUTE", … } }   // загрузка в этой установке не включена
```

`fileId` живёт столько же, сколько файлы диалогов (`FILE_TTL_DAYS`), и привязан к паре «база + пользователь»:
у чужой пары он не открывается. Путь один: `404 UNKNOWN_ROUTE` означает, что установка загрузку не умеет, и
расширение говорит об этом человеку («сервис не принимает вложения — обновите BuhProf AI»). Отката на base64
нет ни у расширения, ни у сервиса (правка 22.09): ход с `content` отвергается — `415 UNSUPPORTED_ATTACHMENT`.
Умеет ли установка загрузку, видно и заранее — по `features` в `GET /ping`.

### `POST /v1/onec-chat/revoke` — база отключается сама

С `X-Base-Token`, без тела. Отзывает токен, которым подписан запрос: кнопка «Отключить базу» в 1С стирает
токен у себя, и если не сказать об этом сервису, он остаётся действующим — копией такого токена можно
говорить от имени базы (аудит РС10). Ответ `{"revoked": true}`; повтор отвечает тем же — база могла не
получить ответ, и вторая попытка не должна выглядеть ошибкой. В установке без отзыва — `404 UNKNOWN_ROUTE`.

### `POST /v1/onec-chat/organizations` — список организаций базы

`{"organizations": [{"bin", "name", "id"}]}` (до 500). Форма шлёт его при открытии чата: по БИН сервис
находит базу для команд организации и показывает связь в карточке организации ERP (ПН4). Список полностью
заменяет прежний срез этой базы; пустой — «база не назвала организаций», а не «их нет».

### `POST /v1/onec-chat/turn` — ход диалога

```jsonc
{
  "conversationId": "uuid | null",          // null — новый диалог
  "user": { "id": "uuid", "name": "Бухгалтер" },
  "organization": { "bin": "831111302342", "name": "ИП Азимов С.М.", "id": "uuid ссылки" },
  "text": "Создай реализацию Физули на облачное хранилище, 1 шт, 5000",   // может быть пустым
  "attachments": [ { "fileName": "выписка.pdf", "mimeType": "application/pdf", "fileId": "uuid" } ],
                                              // ТОЛЬКО `fileId` — файл загружается отдельным запросом
                                              // (POST /uploads выше). `content` (base64) убран 22.09:
                                              // ход с ним — 415 UNSUPPORTED_ATTACHMENT, неизвестный
                                              // fileId — 400 UNKNOWN_FILE.
                                              // Сколько файлов за раз — настройка установки
                                              // (CHAT_ATTACHMENTS_MAX, по умолчанию 20); её же называет
                                              // `limits.attachmentsPerTurn` в ответе /ping, а превышение —
                                              // 400 TOO_MANY_ATTACHMENTS. Размер файла — CHAT_ATTACHMENT_MAX_MB.
  "decision": { "accepted": true },          // ответ на карточку подтверждения (вместо текста «да»/«нет»)
  "toolResults": [                            // результаты вызовов из прошлого ответа
    { "callId": "…", "result": { "success": true, "data": { … }, "status": 201 } }
  ]
}
```

**Заголовок `Idempotency-Key`** (UUID на круг, необязателен). Оборванный ответ не говорит, дошёл ход или нет;
расширение повторяет ход с тем же ключом **ровно один раз**, когда ответа не было вовсе. Сервис помнит пару
«ключ → ответ» сутки в пределах базы и пользователя:

- повтор после ответа получает **тот же ответ дословно** и второго сообщения в диалоге не создаёт;
- повтор, пока прежний ход ещё идёт, получает `202` с тем же `conversationId` и состоянием `PROCESSING`;
- сбой сервиса (`5xx`) ключ освобождает: повтор после своей же поломки обязан сработать.

Тела при повторе не сверяются: ключ рождается в 1С один раз и не переиспользуется.

Ответ `data`:

```jsonc
{
  "conversationId": "uuid",
  "state": "COMPLETED | WAITING_CLARIFICATION | WAITING_CONFIRMATION | TOOL_CALLS | PROCESSING | FAILED",
  "text": "…",                                // для пользователя; при TOOL_CALLS может быть пустым
  "confirmation": { "tool": "create_sale", "card": "…" },   // только при WAITING_CONFIRMATION
  "calls": [                                   // только при TOOL_CALLS
    { "callId": "…", "commandType": "CREATE_SALE", "payload": { … }, "requestId": "uuid" }
  ],
  "documents": [ { "type": "sale", "id": "uuid", "number": "…", "title": "Реализация №…" } ],  // созданные и найденные, для ссылок
  "baseToken": "bpb_…"                        // ИНОГДА: новый токен базы, сохранить вместо прежнего (см. ниже)
}
```

**Тихая смена токена базы.** Токен живёт до отзыва, то есть годами; менять его вручную — идти к каждому клиенту,
поэтому никто не меняет. Раз в `BASE_TOKEN_ROTATE_DAYS` (по умолчанию 90) сервис кладёт новый токен в поле
`baseToken` успешного ответа хода. Расширение сохраняет его в безопасное хранилище и с этого мига ходит с ним;
прежний токен принимается ещё сутки (`BASE_TOKEN_OVERLAP_HOURS`) — на случай, если ответ не дошёл. Если ответ
действительно не дошёл, следующий ход привезёт **тот же самый** токен, а не ещё один, и перекрытие продлится:
база не должна остаться без связи из-за смены, которой не просила.

Смену получает только расширение версии `ONEC_EXT_ROTATION_MIN` (1.5.0) и выше: старое новый токен
проигнорирует. Немедленная смена — кнопка «Сменить» в карточке базы, панель → «Чат в 1С». Отзыв (`revoke`)
остаётся как был: он обрывает связь сразу и требует новой заявки.

Состояния — те же, что у чата ERP (`WorkflowState`), плюс два:
- **`TOOL_CALLS`** — выполните `calls` и пришлите `toolResults` следующим ходом (без текста). Цикл повторяется, пока
  не придёт другое состояние. Порядок выполнения — порядок в массиве.
- **`PROCESSING`** — ход идёт в фоне (распознавание PDF). Опрашивайте `GET /v1/onec-chat/conversations/:id`, пока
  состояние не сменится.

### `GET /v1/onec-chat/conversations` и `GET /v1/onec-chat/conversations/:id`

Список диалогов пользователя 1С и один диалог: сообщения, текущее состояние, ожидающая карточка и **ожидающие
вызовы** (`calls`, если диалог стоит в `TOOL_CALLS` — форма, закрытая посреди цикла, продолжит его).

## Задачи и заметки организации (ERP)

Ведутся в ERP, адресуются БИН организации, выбранной в форме; БИН должен принадлежать базе
(иначе `403 ORG_NOT_IN_BASE`). Автор — пользователь 1С по имени из тела запроса.

| Маршрут | Что делает |
|---|---|
| `GET /v1/onec-chat/task-statuses` | справочник статусов ERP: `code`, `name`, `isFinal`, `sortOrder` |
| `GET /v1/onec-chat/tasks?bin=&state=open\|all&limit=` | задачи организации; у каждой `url` — адрес карточки в панели, если сервису задан `PUBLIC_PANEL_URL` |
| `POST /v1/onec-chat/tasks` | создать; кроме `name`/`description`/`deadline`/`executorName` принимает ссылку на объект: `sourceType` + `sourceUuid` (+ `sourceLabel`) |
| `PATCH /v1/onec-chat/tasks/:uuid` | изменить или закрыть (`close: true`) |
| `GET /v1/onec-chat/notes?bin=&limit=` | заметки организации |
| `POST /v1/onec-chat/notes` | создать заметку |
| `PATCH /v1/onec-chat/notes/:uuid` | исправить СВОЮ заметку (чужая — `403`, чужой организации — `404`) |
| `DELETE /v1/onec-chat/notes/:uuid` | убрать СВОЮ заметку; тело обязательно — в нём БИН и имя автора |

**Происхождение и ссылка — разные вещи.** У задачи, пришедшей из чата 1С, ERP сама ставит
`origin = "1c-chat"` и `originLabel = "Чат в 1С — <база>"`. Поля `sourceType`/`sourceUuid` остаются
свободны под ссылку на объект: задача может быть и «из 1С», и «про реализацию №12» одновременно.
Документ, созданный в 1С, ссылается типом с приставкой — `1c:sale`: панель показывает его подписью,
но не делает ссылкой, потому что самого документа в ERP нет.

Изменяющие вызовы (`POST`/`PATCH`/`DELETE` задач и заметок) ограничены отдельно от ходов чата:
`RATE_LIMIT_TASKS_WRITE_PER_MIN` на пару «база + пользователь», по умолчанию 20 в минуту.

## Выполнение вызовов в 1С

Форма для каждого вызова выполняет в сеансе пользователя:

```
BPAPI_Шлюз.ВыполнитьКоманду(commandType, payload, requestId, "form")  →  { success, data | error, status }
```

Правила — те же, что у агента:
- изменяющие команды (`CREATE_*`, `POST_*`, `UNPOST_*`, `IMPORT_BANK_STATEMENT`, `POST_BANK_DOCUMENTS`,
  `CREATE_RECONCILIATION_ACT`) без `requestId` не выполняются (`MISSING_REQUEST_ID`); повтор с тем же `requestId`
  безопасен;
- `REQUEST_IN_PROGRESS` форма пережидает и повторяет, как агент;
- **файлы в сервис не отправляются.** Если результат содержит `data.content` (печатная форма, отчёт), форма
  сохраняет файл у себя и показывает его пользователю, а в `toolResults` вместо `content` кладёт
  `{"contentOmitted": true, "bytes": N}`. Модели содержимое файла не нужно, а десятки мегабайт туда-обратно — лишние.

**Подтверждения.** Изменяющий вызов сервис присылает только после карточки, которую пользователь подтвердил
(`decision.accepted: true`), — как в чате ERP. Форма дополнительно ничего не спрашивает.

## Что меняется в сервисе (СВ1, СВ2)

1. Субъект «пользователь 1С» (`X-Base-Token` + `X-1C-User-Id`), таблица токенов баз с хэшем и отзывом, миграция;
   выпуск токена в панели для базы (ПН1 — можно позже, на время разработки — служебной командой).
2. Диалог принадлежит паре «база + пользователь 1С»; аудит с каналом `1c`.
3. В `ChatWorkflow` — режим выполнения инструментов «на стороне клиента»: вместо `queue.enqueue` + `waitResult` —
   сохранить ожидающие вызовы в состоянии диалога и вернуть `TOOL_CALLS`; на ход с `toolResults` — отдать
   результаты модели и продолжить. Белый список, защита от выдуманных id и подтверждения — прежние.
4. Организация хода — из `organization` запроса: БИН подставляется в инструменты (`organizationBin`), модель не
   спрашивает «какая организация».
5. PDF-вложения — прежним путём (распознавание в фоне, `PROCESSING`), итог — `TOOL_CALLS` с `IMPORT_BANK_STATEMENT`.
6. Лимиты на пару «база + пользователь 1С».

## Версии

Расширение: `ВыполнитьКоманду` — с 1.4.0; `X-Ext-Version`, `X-Request-Id`, загрузка вложений отдельным запросом,
`Idempotency-Key` и приём нового токена — с 1.5.0. Сервис объявляет версию и свои умения в `ping`
(`serviceVersion`, `features`).
