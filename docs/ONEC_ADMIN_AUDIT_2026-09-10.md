# Аудит панели «Администрирование 1С»

Сплошная инспекция: команды, экраны, механизмы. Проверялись `frontend/src/models/OneCAdmin`,
`frontend/src/models/OneCBases`, `frontend/src/services/onec/api.ts`, сервис `ai`
(`http/onecRouter.ts`, `http/agentRouter.ts`, `commands/*`, `onec/*`, `bases/*`) и живые
данные стенда.

Дата: 2026-09-10. Объём: 22 команды в сервисе, 26 способностей у агента, 36 эндпойнтов
панели, 16 экранов и форм, 263 ключа перевода.

## 2. Найденное, по важности

### P0 — работает не так, как выглядит

**A1. `UsersTab` объявляет проп и молча его игнорирует.**
`UsersTab.tsx:52` — `FC<{ onBatchStarted: (id: string) => void }> = () => {`: пропсы не
принимаются вовсе. Панель (`index.tsx:349`) передаёт обработчик, который переключил бы на
«Задания» после групповой команды, и уверена, что он сработает. Не срабатывает.
`ExtensionsTab` тот же проп принимает и вызывает — то есть два соседних экрана ведут себя
по-разному без причины.

**A2. Проверка содержимого базы делается двумя разными механизмами.**
Пользователи идут через общий `useBaseUsersCheck` (реестр операций, блокировка карточек,
итог сообщением, обновление сводок). Расширения — через `checkBases` напрямую
(`ExtensionsTab.tsx:141`): ни следа во вкладке «Прогресс», ни блокировки, ни обновления
реестра. Одна и та же по смыслу кнопка на двух экранах делает разное — ровно тот дефект,
который уже чинили для пользователей.

**A3. Реестр операций живёт только в памяти вкладки.**
`progress.ts` — модульный стор. Перезагрузили страницу (или открыли панель во второй
вкладке) — прогресс пуст, хотя команды идут. Вкладка «Прогресс запросов и команд» при этом
выглядит как «ничего не выполняется», а карточки перестают блокироваться: правка поверх
идущей команды снова возможна.

### P1 — мешает или врёт по мелочи

**B1. Учётные данные базы расходуют квоту кластера.**
`onecRouter.ts:92` — под лимит `RATE_LIMIT_ONEC_CLUSTER_PER_MIN` попадает всё, кроме
перечисленных GET. `/bases/:key/credentials` в списке исключений нет, а `PUT`/`DELETE`
не-GET по определению. Ни один из них до `rac` не доходит: это своя таблица.

**B2. `batches.list` — N+1 на каждый опрос.**
`onec/batches.ts:128` вызывает `progress()` для каждого из 20 заданий, а каждый `progress()`
— это 3–5 запросов (закрытие просроченных, шапка, команды, учётные записи, способности).
Опрос идёт раз в 3 секунды и в двух местах сразу («Задания» и «Прогресс»). До 100+ запросов
в секунду на пустом месте при одной открытой панели.

**B3. Журнал аудита сервиса не чистится.**
`retention.ts` удаляет диалоги, выписки и команды; `audit_log` не трогает. Пишется он на
каждую админ-команду, включая чтения.

**B4. 16 кнопок могут быть заблокированы без объяснения.**
`AgentForm` (4), `BaseGroupCommands` (2), `ElementForm` (4), `ExtensionsTab` (2),
`RolesPicker` (3), `BatchesTab` (1) — `disabled` без `title`. Правило «нет необоснованных
disabled» соблюдено только на переделанных экранах.

**B5. Серверные механизмы построены, но в интерфейс не выведены.**
`fetchUserHistory` (`/users/:name/history`) и `fetchRoleHolders` (`/roles/:role/holders`) не
используются нигде. Второй писался под защиту «последний администратор» — её нет, а ключ
`onecLastAdminBlock` лежит мёртвым. `CLUSTER_INFOBASE_INFO` — та же история.

**B6. Пустое раскрытие роли молчит.**
При переходе на строки-потомки потерялась ветка «база ни разу не читалась»
(`onecUserNeverRead` больше не используется): у пользователя без прочитанных баз раскрытие
просто пустое.

### P2 — гигиена

**C1. 64 мёртвых ключа перевода `onec*`** из 263 (и столько же в казахском) — остатки
снятых экранов: `onecTabMatrix`, `onecViewBy`, `onecAlignToReference`, `onecRoleGrant`, …

**C2. Разнобой в подсказках.** В «Пользователях баз» подсказки `.Hint` убраны по требованию,
на остальных вкладках остались (`AgentsTab`, `BatchesTab`, `ElementForm`, `RolesPicker`,
`index.tsx`). Один и тот же по смыслу текст выглядит по-разному.

**C3. Две вкладки об одном.** «Задания» и «Прогресс запросов и команд» читают один и тот же
`/batches`; первая — журнал заданий, вторая — операции этой сессии, включая чтения. Границу
между ними человеку никто не объясняет.

**C4. `agent_instances` копятся** — 48 строк за сутки на одного агента (строка на каждый
перезапуск службы). `pruneInstances` чистит старше 7 дней и вызывается оппортунистически.

## 4. Что проверено и работает

* **Права и изоляция.** Весь `/v1/onec/*` закрыт правом «Администрирование 1С»
  (`isSuperAdmin || canOnecAdmin`), организация намеренно ни при чём: сервер 1С один на
  установку.
* **Разрушающие операции подтверждаются**: снятие сеанса, разрыв соединения, блокировка
  входа, удаление агента, удаление пользователя, удаление расширения — все через модальное
  окно с явным «Да» и названным объектом.
* **Ошибки разведены по назначению**: отказ 1С и сервиса — `Notice` на месте данных,
  системные сообщения — `UIToast`. Диагностика ошибок входа в базу называет, по чьей
  учётной записи получен отказ.
* **Единственность экземпляра агента** удерживается арендой владельца; на стенде сейчас
  один живой экземпляр из восьми записей — остальные прежние запуски той же службы.
* **Учётная запись отдельной базы** хранится зашифрованной, подставляется только в момент
  выдачи команды, наружу отдаётся лишь признак «задан».
* **Лимит кластера** защищает `rac`, а не организацию, и не считает локальные чтения.
