# Дубль пользователя в справочнике «Пользователи»: вход в 1С невозможен (17.09.2026)

**Что наблюдали.** В `_transition` пользователь `new2` создан из панели, роли стоят верно, но при входе:

> Не удалось выполнить автоматическую регистрацию администратора в списке по причине: «Пользователю ИБ "new2" с
> идентификатором "bb42a0fe-…" соответствует более одного элемента в справочнике: …ref=…f89, …ref=…f8a».

Два элемента справочника с идущими подряд ссылками (`…89`, `…8a`) на одного пользователя ИБ. Типовая (БСП) такого не
допускает и не пускает в программу.

## Вывод

**Дубли создал агент на командах с `disabled`, а не панель и не сервис.** Доводы:

1. **Команда создания одна**, повторов (`attempt`, `retried_by`) нет — дважды пользователь не создавался.
2. **Успешных команд с `disabled` ровно две** — и элементов справочника ровно два, со ссылками подряд.
3. **Отказ «Конфликт блокировок при выполнении транзакции»** — это блокировка ДАННЫХ. Запись самого пользователя ИБ
   (`ПользователиИнформационнойБазы`) данные не блокирует; значит, путь `disabled` пишет в данные конфигурации —
   в справочник «Пользователи».
4. **Другие пользователи этой базы** (`newuser`, `test2`, `testuser`) создавались без переключения `disabled` — жалоб
   нет. «Оператор бухгалтер» переключался многократно, но это давний пользователь: элемент справочника у него уже был.
   `new2` — единственный, кому `disabled` меняли ДО первого входа, то есть когда элемента ещё не было.

Похоже, при `disabled` агент ищет элемент справочника по пользователю ИБ, не находит (элемента ещё нет или поиск
через COM не совпадает по типу идентификатора) и **создаёт новый — на каждой команде**. Подтвердить может только
агент: исходников агента в этом репозитории нет, в `docs/PROMPT_AGENT_MAINTENANCE.md` запись в справочник не описана.

## Ответ агента (17.09, сборка `2026-09-17 19:16`)

**Вывод «дубли создал агент на командах с `disabled`» кодом агента не подтверждается.** Агент справочник «Пользователи»
не читал и не писал никогда: в мосте (`src/ib/bridge.ps1`) до этой сборки нет ни одного обращения к справочникам,
запроса или записи данных конфигурации. Путь `disabled` меняет у объекта `ПользовательИнформационнойБазы` только
`АутентификацияСтандартная` и `АутентификацияОперационнойСистемы` и вызывает его `Записать()` — больше ничего.

**Кто создаёт элемент справочника.** Сама типовая: `ПользователиСлужебный` при авторизации пользователя с ролями
администратора, которого нет в справочнике, вызывает `Пользователи.СоздатьАдминистратора` (`CommonModules/
ПользователиСлужебный/Ext/Module.bsl:115-190`, выгрузка БП для Казахстана). Текст из жалобы — «Не удалось выполнить
автоматическую регистрацию администратора в списке» — ровно из этого места: при очередном входе `new2` типовая пошла
регистрировать его и нашла два элемента. `СоздатьАдминистратора` ставит управляемую блокировку по
`ИдентификаторПользователяИБ` и перепроверяет наличие внутри транзакции, поэтому две параллельные авторизации дубль
обычно не создают; второй элемент мог появиться путём в обход этой блокировки — например, созданием или
сопоставлением пользователя в форме «Пользователи» рядом с автоматической регистрацией.

**Отказ «Конфликт блокировок» в 12:59:47** — не запись справочника агентом: такой записи в агенте нет. Вероятнее
всего (на сервере не проверено), ждал сам вход агента: при начале сеанса внешнего соединения типовая выполняет свой
код в транзакции, и она 20 с ждала чужую. По времени — через полторы минуты после создания `new2` — это согласуется
с первой авторизацией `new2` и его регистрацией в справочнике.

**Как подтвердить на сервере.** Журнал регистрации `_transition` за 17.09 12:58–13:05, событие «Пользователи.
Администратор зарегистрирован в справочнике Пользователи» (типовая пишет его при автоматической регистрации) и
события записи справочника «Пользователи» по `new2`: сколько их, от какого пользователя и приложения.

**Что сделано в агенте** — то, что имеет смысл при таком раскладе:

- **Дубль ловится ДО записи.** `IB_CREATE_USER` (для существующего пользователя) и `IB_UPDATE_USER` считают элементы
  справочников «Пользователи» и «ВнешниеПользователи» по `ИдентификаторПользователяИБ` — параметром типа
  `УникальныйИдентификатор`, не строкой. Больше одного — отказ **`IB_USER_DUPLICATE`**: «у пользователя ИБ «…»
  элементов справочника: 2 (Пользователи ref=…, …). Вход в программу невозможен, команда остановлена до записи —
  ничего не изменено…». Ссылки полями — `error.details.duplicates: [{ref, catalog, deleted}]`.
- **Справочник в ответе.** Успех `IB_CREATE_USER`, `IB_UPDATE_USER` и `IB_DELETE_USER` несёт
  `catalog: {found, created: false, items: [{ref, name, catalog, deleted}]}`. `created` всегда `false`: агент
  элементов не создаёт. Справочника нет (конфигурация не на БСП) — поля нет; не прочиталось — `{found: null, error}`,
  команда при этом не останавливается. У удаления `catalog` — то, что осталось в справочнике: удаление пользователя
  ИБ элементы не трогает.
- **Проверено на стенде Dev_01** (БП для Казахстана, только чтение): у `bpapi` и `support` найдено по одному
  элементу, ссылки совпали со встречной сверкой по всему справочнику; у пользователей без элементов — 0. По дороге
  найдены и обойдены две ловушки COM, каждая из которых молча давала «элементов нет»: `Метаданные.Справочники`
  приходит массивом без `Найти` (теперь `НайтиПоПолномуИмени`), а таблица значений и её строки разворачивались
  PowerShell в плоский список (теперь выборка `Выбрать`/`Следующий` прямыми вызовами).
- **Самопроверка** получила шаг «справочник пользователей читается»: ошибка чтения — провал шага, а не «дублей нет».
