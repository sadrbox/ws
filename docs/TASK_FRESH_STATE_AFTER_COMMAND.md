# Задача: актуальное состояние возвращается САМОЙ командой, без второго входа в базу

Сформировано 12.09.2026 по запросу «после операции панель должна возвращать актуальную
информацию, не выполняя дополнительных запросов». Затрагивает три стороны: агент (`bpapi_agent`),
сервис (`ai/`), панель (`frontend/src/models/OneCAdmin`). Формат — как у
`TASK_AGENT_CANCEL_AND_CHECK.md`: сперва факт, потом контракт, потом чего не делаем, потом проверка.

> **Состояние на 12.09.2026 (вечер).** Сделано и проверено тестами: **сервис** (`ai/src/onec/echo.ts`,
> приём в `agentRouter`, `tests/echo_state.test.ts`) и **агент** (`src/ib/bridge.ps1` —
> `Read-UsersList` / `Read-ExtensionsList` / `Get-StateEcho`, способность `ib.echo` в
> `src/commands/mod.rs`). На живом стенде не прогонялось: нужен перезапуск сервиса и сборка
> агента. **Панель** — не начата, делается отдельно; её раздел ниже переписан под то, как
> получилось на самом деле.

## Факт: сейчас за одним изменением идут ещё два обращения

1. **Вторая команда в 1С.** После успешного изменения сервис ставит В ОЧЕРЕДЬ чтение того же
   содержимого — `ai/src/http/agentRouter.ts:392` (`REFRESH_AFTER`): `IB_CREATE_USER` →
   `IB_LIST_USERS`, `IB_INSTALL_EXTENSION` → `IB_LIST_EXTENSIONS` и так далее. Это ещё один
   вход в базу: COM-коннектор, аутентификация, сеанс и лицензия 1С — от секунды до трёх до
   начала полезной работы, плюс ожидание, пока агент заберёт команду длинным опросом.
2. **Второе (и третье) чтение из панели.** `refreshAfterWork()`
   (`frontend/src/models/OneCAdmin/progress.ts:165`) сбрасывает кэш девяти ключей и **повторяет
   это через 5 секунд** — ровно потому, что в момент «команда выполнена» свежие данные ещё едут
   из пункта 1. В комментарии это названо честно: «один запоздалый повтор дешевле, чем показать
   старое значение как новое».

**Цена на пакетах.** Групповая операция по 110 базам сегодня порождает 110 изменяющих команд
**и ещё 110 читающих** — сто десять лишних входов в базы, сеансов и лицензий, при
`AGENT_IB_PARALLEL = 1` выстроенных в одну очередь. Это не оптимизация «на полсекунды»: это
удвоение самой дорогой части работы.

**Причина, по которой так сделано, остаётся верной:** реестр обязан обновиться, иначе панель
показывает состояние «до» и человек назначает роль второй раз. Менять нужно не цель, а способ.

## Что делаем: изменение возвращает новое состояние в СВОЁМ ответе

Соединение с базой уже открыто — тем самым, в котором только что выполнена запись. Прочитать
в нём список сразу после записи стоит миллисекунды против секунд на новый вход. Поэтому
изменяющая команда отдаёт результат вместе с новым состоянием:

```jsonc
{ "ok": true,
  "state": {
    "users": { "items": [ { "name": "…", "fullName": "…", "disabled": false, "roles": ["…"] } ],
               "complete": true,
               "readAt": "2026-09-12T14:21:03Z" }
  } }
```

### Что к чему приложено

| Команда | Поле `state` | Содержимое |
|---|---|---|
| `IB_CREATE_USER`, `IB_UPDATE_USER`, `IB_DELETE_USER` | `state.users` | то же, что отдаёт `IB_LIST_USERS` |
| `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` | `state.extensions` | то же, что отдаёт `IB_LIST_EXTENSIONS` |
| `CLUSTER_TERMINATE_SESSION` | `state.sessions` | то же, что `CLUSTER_LIST_SESSIONS` по этой базе |
| `CLUSTER_DISCONNECT` | `state.connections` | то же, что `CLUSTER_LIST_CONNECTIONS` по этой базе |
| `IB_PUBLISH` / `IB_UNPUBLISH` | — | уже работает: сервис применяет `url` из ответа (`agentRouter.ts:355`) |

Форма элементов — **ровно та же**, что у соответствующей `*_LIST_*`-команды. Двух форматов
одного списка быть не должно: сервис применяет их одним и тем же кодом (`registry.syncUsers`,
`registry.syncExtensions`).

### Правила, без которых это опасно

* **`complete: true` обязателен, и он — обещание.** Список замещает кэш базы ЦЕЛИКОМ: частичный
  молча «потеряет» пользователей. Это то же правило, что уже записано для `IB_LIST_*` в
  `ONEC_AGENT_CLUSTER_CONTRACT.md` §3.2.
* **Не удалось перечитать — `state` НЕ ШЛЁМ ВООБЩЕ.** Изменение при этом успешно: команда
  отвечает `{"ok": true}` без `state`, и сервис возвращается к прежнему поведению (ставит
  читающую команду). Пустой или неполный `state` хуже его отсутствия.
* **Пароль в `state` не попадает** — по общему правилу: его нет ни в логе, ни в ответе.
* **Способность `ib.echo`** объявляется при регистрации (`capabilities`). По ней сервис
  понимает, ждать состояния или сразу ставить чтение. Без объявленной способности всё
  работает как сегодня — старый агент остаётся совместимым.

### Где это сделано в агенте

**COM-мост** (`src/ib/bridge.ps1`). Сбор списка вынесен в `Read-UsersList` /
`Read-ExtensionsList` — их зовёт и команда чтения, и эхо (`Get-StateEcho`,
`Write-ResultWithState`) в действиях `create-user` / `update-user` / `delete-user` /
`install-extension` / `delete-extension`. Именно в скрипте, а не вторым вызовом моста из Rust:
тогда это одно COM-соединение независимо от настройки `agent.persistent_bridge` (по умолчанию
она выключена, и второй вызов означал бы новый вход в базу — то самое, от чего уходим).

Попутно поднята глубина `ConvertTo-Json` (6 → 12): прежние шесть уровней оказались ровно на
границе, и с эхом любое новое поле внутри строки списка молча превратило бы роли пользователя в
строку вместо массива.

**Быстрый путь `ibcmd`** (`src/commands/mod.rs`, `attach_state`). Расширения на базе БЕЗ сеансов
ставятся через `ibcmd`, мимо COM, — и именно этим путём идёт ночная раскатка по сотне баз. Там
эхо собирается чтением `ibcmd extension list` сразу после изменения: процесс уже настроен,
кластер не нужен. Не прочиталось — состояния нет, сервис спросит сам.

**Проверка без 1С:** `tools/bridge_echo_test.ps1` — берёт сами функции из `bridge.ps1`,
подставляет заглушки вместо COM и проверяет форму ответа, целостность ролей после JSON, отказ от
состояния при неудачном перечитывании и законность пустого списка.

## Сторона сервиса

1. **Принять и применить.** В обработчике результата (`agentRouter.ts`, рядом с `REFRESH_AFTER`):
   есть `state.users.complete` → `registry.syncUsers(base.id, …)` немедленно; есть
   `state.extensions.complete` → `registry.syncExtensions`. Кэш актуален в тот же момент, когда
   команда стала `done`.
2. **Не ставить чтение, если состояние пришло.** `REFRESH_AFTER` срабатывает только когда `state`
   в ответе нет. Это и есть экономия: минус одна команда на каждое изменение, минус 110 команд
   на пакет по 110 базам.
3. **`state` в командную запись не сохранять.** Применили — и вырезали перед записью в
   `commands.result`: иначе задание на сто баз положит в БД сто списков пользователей, которые
   никто никогда не прочитает. В ответ панели состояние уходит, в журнал — нет.
4. **Ничего не менять в ручках.** `GET /v1/onec/commands/:id` уже отдаёт `row.result` как есть
   (`onecRouter.ts:828`), а синхронный путь `run()` (до `ONEC_COMMAND_TIMEOUT_SECS`, сейчас 20 с)
   — тем более. Состояние доезжает до панели существующим путём, новых эндпойнтов не нужно.

## Сторона панели (делается отдельно; сервис и агент уже готовы)

**Главное, что изменилось для панели: гонки больше нет.** К моменту, когда команда стала
`done` (задание показывает её выполненной), реестр сервиса УЖЕ содержит новый список. Значит
`/bases/:key/users/cached` и `/bases/:key/extensions/cached` отвечают свежим сразу — это
запрос в БД сервиса, без 1С.

* **Убрать повтор через 5 секунд** в `refreshAfterWork()`
  (`frontend/src/models/OneCAdmin/progress.ts:165`). Он существовал ровно потому, что свежие
  данные ехали второй командой; теперь одного сброса кэша достаточно.
* `state` в результате команды искать НЕ нужно: применённые списки сервис из ответа вырезает
  (иначе задание на сто баз положило бы в журнал сто списков). В результате остаётся то, чему
  реестра нет, — например `state.sessions` после снятия сеанса.
* **Старый агент.** Панель уже получает `capabilities` агента (`GET /v1/onec/agents`). Нет
  `ib.echo` — сборка состояния не возвращает, сервис по-прежнему ставит читающую команду, и
  задержка после операции остаётся. Это стоит показывать там же, где показывается отсутствие
  `ib.auth`: иначе «у одних обновляется сразу, у других нет» выглядит как случайность.
* Формы, открытые в других пейнах, обновляются как сейчас, через общий `refreshAfterWork`.

## Чего эта задача НЕ делает

**Не отменяет читающие команды.** `IB_LIST_USERS` и `IB_LIST_EXTENSIONS` остаются: кнопка
«Обновить» в карточке базы — это вопрос к живой 1С, и её никто не трогает.

**Не превращает изменение в чтение.** Если перечитать не удалось, команда всё равно сообщает об
успехе изменения. Успех записи и свежесть списка — разные факты, и смешивать их нельзя.

**Не решает задачу «изменил другой оператор».** Эхо обновляет ТОГО, КТО НАЖАЛ. Чужие изменения и
фоновые срезы — следующий раздел.

## Как проверить на стенде (не прогонялось)

Сервису нужен перезапуск (`pm2 restart` службы `ai`), агенту — сборка и установка. Порядок
любой: сервис без эха работает по-старому, агент с эхом против старого сервиса — тоже (лишнее
поле в ответе сервис просто сохранит).

Смотреть **не в результат команды**: применённое сервис оттуда вырезает. Признак работы —
строка в журнале сервиса «состояние базы применено из ответа команды — читающая команда не
нужна» и отсутствие следом `IB_LIST_USERS`.

1. Создать пользователя в базе: в журнале сервиса есть строка о применённом состоянии и **нет**
   поставленной следом `IB_LIST_USERS`; `GET /v1/onec/bases/<ключ>/users/cached` сразу после
   завершения команды уже содержит нового пользователя.
2. Выдать роль существующему: та же проверка по `…/users/cached` — роль видна СРАЗУ, а не после
   «Обновить».
3. Пакет по 10 базам: в задании 10 команд, а не 20; кэш всех десяти баз обновлён.
4. Расширение на базе без сеансов (путь `ibcmd`): то же самое, но по `…/extensions/cached`, — и
   в журнале агента виден `transport: ibcmd`.
5. Старый агент (без `ib.echo`): всё работает как раньше — читающая команда ставится, панель
   обновляется с задержкой. Совместимость обязана сохраниться.
6. Заведомо сломанное перечитывание (например, изменение в базе, где список читается дольше
   таймаута): команда — `SUCCESS`, состояния нет, сервис ставит чтение, реестр не пустеет и
   панель не показывает «пользователей нет».

# Следующий шаг: живое обновление одним соединением (P2, отдельная задача)

Эхо состояния закрывает «я нажал — я увидел». Оно не закрывает «изменилось само»: результат
пакетной операции по сотне баз, срез кластера с heartbeat, работа другого администратора. Сегодня
это видно только опросом.

**Половина инфраструктуры уже есть.** `frontend/src/services/liveEvents.ts` держит ОДНО
`EventSource`-соединение на всё приложение (`GET /chat/stream`), подписка идёт по типу события;
`backend/services/chatBus.js` — шина, `backend/api/router/chatStream.js` — поток с heartbeat
каждые 15 с (иначе cloudflared рвёт простой). Добавить тип `onec` — это подписка вместо опроса
для всей панели: списки баз, задания, прогресс.

**Чего не хватает, и почему это отдельная задача:**

* шина `chatBus` — in-process `EventEmitter` **внутри backend**, а панель 1С обслуживает ДРУГОЙ
  процесс — сервис `ai/`. Событию из `ai/` до неё не добраться;
* при включении кластера pm2 (задача **D2**, 4 воркера) in-process шина перестанет работать и для
  самого backend: подписчик сидит в одном воркере, событие публикуется в другом. Это уже записано
  в комментарии самого `chatBus.js`;
* решение на оба случая одно и без новых зависимостей — **PostgreSQL `LISTEN`/`NOTIFY`** как
  транспорт между процессами: `ai/` и любой воркер backend публикуют в канал, `chatStream`
  раздаёт подписчикам организации.

Порядок работ: сперва эхо состояния (оно самостоятельно и снимает половину лишних обращений),
затем `LISTEN/NOTIFY` под существующий SSE-канал — и только потом перевод экранов панели с
опроса на события.
