# Задача сервису и панели: многобазовый бизнес-агент и лимит тарифа (БА2 → СВ3, ПН)

19.09.2026. Агент готов: сборка `2026-09-19 16:22` (`bpapi_agent/README.md`, раздел «Много баз на одном
компьютере и лимит тарифа»). План — [PLAN_BUHPROF_API_2026-09-19.md](PLAN_BUHPROF_API_2026-09-19.md).

## Что изменилось в агенте

Одна служба бизнес-агента обслуживает **сколько угодно баз** одного компьютера, каждую по HTTP или по COM
(без веб-сервера). Сколько баз и БИНов ей можно обслуживать — **решает сервис**.

### 1. Срез баз (register, heartbeat с `wantFullBases`)

Бизнес-агент шлёт строку на КАЖДУЮ свою базу. Новые поля (схема `baseStateSchema` их сейчас молча
отбрасывает — не `.strict()`, но и не сохраняет):

```jsonc
{
  "key": "Бух_ТОО_Альфа",
  "status": "ONLINE | OFFLINE | OVER_LIMIT",
  "extVersion": "1.4.0",
  "transport": "http | com",
  "organizations": [ { "id": "uuid", "name": "ТОО Альфа", "bin": "123456789012" } ],   // нет поля — не знаю
  "overLimit": false                                                                   // нет поля — лимитов нет
}
```

### 2. Лимиты — от сервиса агенту

В ответе `POST /agent/v1/register` и `POST /agent/v1/heartbeat`:

```jsonc
{ "ok": true, "data": { "limits": { "maxBases": 5, "maxBins": 10 } } }   // null в поле — без ограничения
```

Нет `limits` — агент работает без ограничений (совместимость). Агент обслуживает первые `maxBases` баз по
порядку своих настроек и первые `maxBins` разных БИНов по порядку баз и организаций (один БИН в двух базах —
одна организация). Сверх лимита отвечает `LICENSE_LIMIT`.

### 3. Какая база выполнит команду

Агент выбирает базу так: `payload.baseKey` → база, где есть организация `payload.organizationBin` →
единственная база. Иначе — `BASE_REQUIRED` со списком баз. `baseKey` в 1С не уходит.

Без адреса и при нескольких базах: `HEALTH` — сводка по базам (`bases[]`, `limits`), `GET_ORGANIZATIONS` —
организации всех баз в пределах лимита, каждая с полем `baseKey`.

Новые коды отказа: `BASE_REQUIRED`, `BASE_NOT_FOUND`, `LICENSE_LIMIT`, `EXTENSION_MISSING` (в базе нет шлюза
buhprof_api 1.4.0 — для COM).

## Что сделать в сервисе (СВ3)

1. **Лимиты агента**: колонки `max_bases`, `max_bins` (NULL — без лимита) у бизнес-агента, миграция. Отдавать
   `limits` в ответах register и heartbeat. Смена лимита действует со следующего heartbeat.
2. **Сохранять срез**: `organizations`, `transport`, `overLimit` базы бизнес-агента (таблица организаций базы
   или JSON в `bases`). По ним — счёт БИНов агента и выбор базы.
3. **Контроль на стороне сервиса — главный.** Считать тем же правилом, что агент (порядок баз из среза,
   разные БИНы). Команду в базу или по БИН сверх лимита не ставить в очередь: сразу `LICENSE_LIMIT` с
   понятным текстом («тариф: 5 баз, подключено 7»).
4. **База в каждой бизнес-команде.** Сейчас бизнес-команды уходят без базы — с несколькими базами агент
   ответит `BASE_REQUIRED`. Сервис знает организацию ERP и её БИН: класть в payload `baseKey` базы, где этот
   БИН есть (из среза), либо хотя бы `organizationBin`. Если БИН есть в нескольких базах — `baseKey` первой по
   порядку, и показать это в панели.
5. **`pickAgentFor(organizationUuid, baseKey)`** — у бизнес-агента теперь много баз одного сервера: выбирать
   агента, у которого в срезе есть база с этим БИН.
6. Подсказки в `errorHints.ts` для четырёх новых кодов.
7. Инструмент `get_organizations` в чате: при нескольких базах в ответе у организаций есть `baseKey` —
   модели его не показывать, но сохранять в контексте и передавать в следующих вызовах (как `organizationBin`).

## Что сделать в панели (ПН)

1. Карточка бизнес-агента: список его баз (ключ, транспорт HTTP/COM, версия расширения, организации с БИН,
   статус ONLINE/OFFLINE/**сверх лимита**) и счётчики «баз N из M», «БИНов N из M».
2. Правка лимитов агента (только администратор BuhProf): два поля, пусто — без лимита.
3. Базы и организации сверх лимита — отдельной пометкой с подсказкой «увеличьте тариф или уберите базу из
   настроек агента».

## Готово, когда

- агент с 3 базами (2 COM, 1 HTTP) и лимитом `maxBases=2` виден в панели: третья база «сверх лимита»,
  команды в неё отвергаются сервисом, не доходя до агента;
- команды чата ERP по организации уходят с `baseKey` нужной базы;
- лимит `maxBins=1` при двух организациях: команда по второй — `LICENSE_LIMIT` с текстом про тариф.

Проверить без живого агента можно заглушкой `bpapi_agent/tools/mock_cloud.py --max-bases N --max-bins M`
(она отдаёт лимиты) — и наоборот, живым агентом против сервиса.
