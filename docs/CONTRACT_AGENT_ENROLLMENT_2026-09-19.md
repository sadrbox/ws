# Контракт: подключение агента по коду (идентификатор и токен агента без копирования)

19.09.2026. Агент (`bpapi-agent`, выпуск `2026-09-19 21:36`) сделан по этому контракту: окно, вкладка
«Подключение», карточка «Агент» → «Подключить агента по коду…». Сервису и панели — реализовать (задача СВ5/ПН).
Проверка без сервиса — `bpapi_agent/tools/mock_cloud.py` (одобряет на третьем опросе).

**Сторона сервиса и панели — сделано (19.09, ночь):** миграция `037_agent_enrollments.sql`,
`ai/src/agents/enrollments.ts`, `ai/src/http/agentEnrollRouter.ts` (до `agentRouter`), маршруты панели
`/v1/onec/enrollments*`, панель: «Агенты» → «Подключить по коду» и «Заявки» → «Подключение агентов». Решения сверх
контракта: токен выпускается при первом опросе после одобрения (`rotate-token`), при одобрении создаётся агент без
показа токена; повторное подключение той же службы (компьютер + служба) по умолчанию получает прежнего агента с новым
токеном — прежний токен перестаёт действовать; в окне одобрения можно выбрать «новый агент». Заявка живёт 24 часа.

**Организация ERP — только у бизнес-агента (21.09).** Агент кластера обслуживает весь сервер 1С: базы всех
клиентов, исполнитель кластерных команд выбирается по серверу (`pickAdminAgent`), а доступ даёт право
«Администрирование 1С». Поэтому при одобрении заявки с `role: "admin"` организация не спрашивается и агент
заводится без неё (пустая `organization_uuid`); у бизнес-агента она по-прежнему обязательна — по ней выбирается
исполнитель команд чата и считается лимит тарифа. То же в ручном создании: `POST /v1/onec/agents {name, cluster:
true}` — без активной организации.

## Зачем

Сейчас идентификатор и токен агента выдаёт `tools/admin.ts create-agent` (или панель) и их копируют в окно агента
руками — два длинных значения, ошибка в символе видна только по отказу службы. По коду: агент сам просит
подключение, администратор BuhProf одобряет заявку в панели, агент получает идентификатор и токен и подставляет их.
Так же, как регистрация базы 1С (`CONTRACT_BASE_REGISTRATION_2026-09-19.md`).

## `POST /agent/v1/enroll` — заявка (без токена)

Лимит: 5 заявок в час с одного IP.

```jsonc
{
  "name": "Бухгалтерия, 2 этаж",       // «Название в панели»
  "role": "business | admin",
  "serverName": "SRV-1C",               // «Сервер баз» / «Имя сервера 1С»
  "serviceName": "BPAPIAgent",
  "computer": "BUH-PC-02",
  "version": "0.1.0+2026-09-19 21:36 (+05)"
}
```

Ответ `data`: `{ "enrollmentId": "uuid", "code": "K7M-42Q", "pollSecret": "…ASCII…", "expiresAt": "…", "pollAfterSecs": 5 }`.
Повтор с того же компьютера и службы, пока заявка не решена, — та же заявка.

## `GET /agent/v1/enroll/:enrollmentId` — решение

Заголовок `X-Enrollment-Secret`. Неверный секрет — 404.

```jsonc
{
  "state": "PENDING | APPROVED | REJECTED | EXPIRED",
  "note": "причина отказа",
  // ИДЕНТИФИКАТОР И ТОКЕН — только при APPROVED и только ОДИН раз; дальше этих полей нет:
  "agentId": "uuid",
  "token": "bpa_…",
  // Организация приходит при КАЖДОМ опросе после одобрения (уточнено 21.09): окно агента показывает,
  // к какой организации его подключили, и запоминать это ему не нужно.
  "organization": { "uuid": "…", "name": "ИП Азимов С.М." }
}
```

При одобрении сервис создаёт агента тем же путём, что `POST /admin/v1/agents` (роль и сервер — из заявки),
токен — как у `create-agent`. Не забранный токен при повторной заявке отзывается (`rotate-token`).

## Панель (ПН)

«Администрирование 1С» → «Агенты» → «Подключить по коду»: ввод кода (или список заявок), карточка заявки
(название, роль, сервер, компьютер, версия), выбор организации ERP, «Одобрить» / «Отклонить» с причиной.
Кто одобрил — в аудит.

## Токен расширения (не сервис)

Токен расширения `buhprof_api` для баз на веб-сервере агент теперь выпускает сам: окно базы → «Выпустить токен в
базе» (`POST <публикация>/hs/bpapi/v1/setup/token` под пользователем 1С, случайные 32 байта). Базам по COM
(сервер 1С в сети, файловые) токен не нужен.
