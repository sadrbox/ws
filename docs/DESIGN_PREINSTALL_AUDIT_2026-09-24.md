# Проект: подготовка системы к помощнику установки

24.09.2026. Основание — задача владельца: прежде чем делать помощник установки
([PLAN_DEPLOY_AND_MODULES_2026-09-24.md](PLAN_DEPLOY_AND_MODULES_2026-09-24.md), часть А), проверить
сценарии пользователей (права доступа, модули организации) на пригодность и охват и продумать, что менять,
если проект ставится на МНОГО разных веб-серверов и каждая установка самостоятельна.

**Реализации здесь нет — только проект.** Ни одна строка кода этим документом не меняется.

Проверялось на коде: `backend/utils/auth.js`, `backend/server.js`, `backend/services/moduleAccess.js`,
`backend/api/router/*` (110 файлов), `backend/prisma/seed.js`, `frontend/src/services/api/client.ts`,
`frontend/src/components/UI/NavList.tsx`, `ai/src/config.ts`, `ecosystem.config.js`.

## Итог одной страницей

Система рассчитана на ОДНУ установку — нашу. Это видно в трёх местах сразу: права «открыты по умолчанию»
там, где путь не описан в карте; модули останавливают только создание документов и только у одиннадцати
путей; адрес `api.aleppo.kz` и два наших IP зашиты в код. Ни одно из этого не мешает сегодня и каждое
становится дефектом в тот день, когда установок станет две.

Работы разбиты на три группы: **П** — права, **М** — модули, **С** — самостоятельность установки. Критичных
для установщика — семь (П1, П3, М1, С1, С2, С4, С6), и все семь дешевле сделать ДО первой чужой установки,
чем после.

## Часть I. Сценарии пользователей

### 1.1. Кто вообще обращается к системе

Субъектов восемь, и правами по модели проверяются только три из них:

| Субъект | Чем входит | Что его ограничивает |
|---|---|---|
| Суперадмин | JWT, `isSuperAdmin` | Ничего: минует и права, и модули |
| Администратор организации | JWT, `AccessRight.role = "admin"` | Только своя организация; права на модели не проверяются |
| Сотрудник | JWT | `AccessPermission` (модель × организация) + изоляция арендатора |
| **«admin» в dev-режиме** | JWT, имя пользователя `admin` | **Ничего** — см. П3 |
| Пользователь 1С (чат в базе) | `X-Base-Token` + `X-1C-User-Id` | Токен базы, организация базы; прав на модели нет |
| Агент 1С | `Authorization: Bearer` + `X-Agent-Id` | Способности агента, лимиты тарифа |
| AI-сервис → ERP | `X-Api-Key` (`BPAI_API_KEY`) на `/bpai/*` | Ключ; **ни прав, ни модулей** |
| Внешние без авторизации | — | `/api1/esf-license/*` (токен, heartbeat, заявка, проверка), вебхук WhatsApp — только rate limit |

**Вывод для установщика.** Мастер первого запуска должен завести не одного «админа», а понятную начальную
раскладку: суперадмин установки (техническая учётная запись), администратор организации (бухгалтер) и
служебные ключи каналов (`BPAI_API_KEY`, ключ агента). Сегодня об этих ключах знает только автор.

### 1.2. Права доступа — находки

**П1. Открыто по умолчанию — критично.** `accessPermissionMiddleware` определяет модель по первому сегменту
пути через карту `ROUTE_TO_MODEL`, и если модели нет: `if (!modelName) return next()` — запрос проходит.
Из 39 сегментов путей в карте — 12. Без проверки прав идут, в частности:

`/reports`, `/classifiers`, `/notes`, `/object-marks`, `/documents` (цепочка «на основании»),
`/document-number`, `/document-number-settings`, `/awp`, `/snt`, `/egov`, `/sync`, `/module-settings`,
`/chat`, `/wa`, `/data`, `/admin` (бэкапы), `/task-statuses`, `/tasks`.

Часть из них проверяет изоляцию арендатора (`tenantFilter`) — то есть чужую организацию не покажет, — но
права на модель не спрашивает никто. Умолчание выбрано неверно: незнакомый путь должен **запрещаться**, а не
разрешаться. Сейчас каждый новый роутер по умолчанию открыт, и это замечают только на аудите.

**П2. Отчёты доступны без права на предмет отчёта — критично.** `api/router/reports.js`: семь отчётов
(продажи по товару, ABC, XYZ, по менеджерам, оборотная ведомость, партии, движения) фильтруют по
организации и не спрашивают ничего больше. В меню они закрыты `can("Sale")`, `can("Purchase")` — то есть
**запрет есть только в интерфейсе**. Прямой запрос к `/api/v1/reports/sales-by-product` отдаёт выручку
сотруднику, которому продажи не открывали. Для установки у клиента это первое, что найдёт его безопасник.

**П3. Пользователь `admin` всемогущ вне production — критично.** `hasUnconditionalAccess()`:
`isDev && username === "admin"` даёт полный доступ мимо прав. А `ecosystem.config.js` без `APP_MODE=production`
поднимает всё в `NODE_ENV=development`. То есть установка, поднятая «как обычно», имеет вечного суперадмина
по имени — даже если флаг `isSuperAdmin` у него сняли. Установщик обязан либо запрещать не-production режим,
либо выкидывать эту ветку вовсе.

**П4. Нет профилей прав.** Право — это строка «пользователь × модель × организация». Моделей в карте 71.
Чтобы завести бухгалтера, кладовщика и кассира на новой установке, нужно проставить сотни галочек руками, и
так на КАЖДОЙ установке. Нужны именованные профили («Бухгалтер», «Кладовщик», «Кассир», «Руководитель»,
«Только просмотр») как наборы прав: мастер первого запуска предлагает их, дальше их правят.

**П5. Уровней всего два.** `readonly` и `full`: GET требует первого, POST/PUT/DELETE — второго. Нельзя
выразить «создаёт, но не удаляет», «видит, но не проводит», «правит только своё». Для учётной системы это
мало: проведение документа и его удаление — разные по весу действия. Расширять модель прав до установщика не
обязательно, но решение нужно принять сейчас: профили (П4) проектируются под ту модель, которая будет.

**П6. `seed.js` — не место для схемы.** Он делает `ALTER TABLE` мимо миграций (добавляет `isSuperAdmin`,
`avatarPath`, `organizationUuid`, если их нет) и заводит `admin` с паролем `admin`, а существующему — **сбрасывает
пароль на `admin`**. На чужом сервере это недопустимо: пароль задаёт мастер, а схему — только миграции.

### 1.3. Модули организации — находки

**М1. Гард закрывает лишь создание документов — критично.** `moduleGuardMiddleware`: только `POST`, только
11 точных путей, только если в теле есть `organizationUuid`. Значит у организации с отключённым модулем
«Продажи» по-прежнему: читаются списки продаж, правятся и удаляются существующие документы, строятся отчёты,
печатаются формы, работает терминал продаж, помощник предлагает провести реализацию. Отключение — это
сегодня «скрыли меню и запретили кнопку», ровно то, от чего владелец и просит уйти.

**М2. Половина документов не покрыта даже этим.** Вне `POST_PATH_MODULE`: возвраты продаж и закупок, заказы
покупателей и поставщиков, счета входящие и исходящие, счета на оплату, коммерческие предложения, резервы,
заявки на закупку, фискальные чеки, ГТД по импорту, основные средства и их принятие, сделки CRM, ЭСФ, ЭДО.

**М3. Служебные каналы гард не проходят вовсе.** `/bpai/*` (задачи и заметки из 1С) смонтирован до `/api/v1`
и о модулях не знает. Инструменты помощника (`ai/src/tools/registry.ts`, 34 бизнес-команды) исполняются
агентом внутри базы 1С и к нашему гарду не обращаются в принципе. То есть отключённый модуль остаётся
доступен через чат — а это самый заметный для клиента канал.

**М4. Модуль и право — два разных ответа на один вопрос.** «Можно ли пользователю создать реализацию?»
решается и правом на модель `Sale`, и состоянием модуля `sales`. Механизмы не знают друг о друге: коды
ошибок разные (403 `MODULE_DISABLED` против 403 прав), места проверки разные, интерфейс скрывает разделы
двумя независимыми способами (`can()` и `moduleOn()`). Их стоит свести в одну проверку доступа с двумя
причинами отказа — иначе при установке модулей клиенту придётся объяснять разницу между «нет права» и
«нет модуля», хотя человек видит одно и то же пустое место.

**М5. 7 ключей модулей на 101 модель.** Большая часть системы (бухучёт, ОС, ЭСФ, ЭДО, CRM, банк, фискальные
чеки, серии и партии, терминал, задачи, 1С-администрирование, AI, отчёты) не принадлежит ни одному модулю и
потому не может быть ни установлена, ни снята. Это работа Б2 из плана; здесь фиксируем, что без неё
«установка модулей» будет управлять седьмой частью системы.

**М6. Отчёты не знают о модулях.** Как и о правах (П2). Отключение модуля не убирает его отчёты.

## Часть II. Самостоятельность установки

Требование: каждая установка живёт сама по себе, ничего не зная о наших серверах.

**С1. Наши адреса зашиты в код — критично.**

| Где | Что зашито |
|---|---|
| `frontend/src/services/api/client.ts` | `REMOTE_API_URL = "https://api.aleppo.kz/api/v1"`, локальный `http://192.168.1.112:3000/api/v1` |
| `frontend/src/services/ai/endpoint.ts` | `http://192.168.1.112:3100` |
| `backend/server.js` | `app.set("trust proxy", "192.168.1.113")` — IP нашего cloudflared |
| `ai/src/config.ts` | `ALLOWED_ORIGINS` по умолчанию `https://aleppo.kz,…`; `PUBLIC_URL`, `PUBLIC_PANEL_URL` |
| `frontend/vite.config.ts` | `allowedHosts` со списком наших имён, HMR на `aleppo.kz` |
| `ecosystem.config.js` | `VITE_HMR_HOST: "192.168.1.112"` |

На чужом сервере фронт будет стучаться на `api.aleppo.kz`, а бэкенд — доверять заголовкам от IP, которого в
той сети нет (что ломает и rate limit, и аудит: все запросы придут с адреса прокси).

**С2. Адрес API выбирается по имени хоста браузера — критично.** `isLocal = hostname.includes("192.168.") ||
hostname === "localhost" || …` → локальный адрес, иначе — наш удалённый. Это не настройка, а угадывание, и
на чужом домене оно угадывает неверно. Адрес API должен приходить из конфигурации установки (переменная
сборки или отдаваемый сервером `config.json`), а не выводиться из того, как открыли страницу.

**С3. У установки нет имени.** Ни идентификатора, ни версии поставки, ни отметки «кем и когда установлена».
Это нужно раньше, чем кажется: в логах поддержки, в обращениях клиента, в заявках агентов 1С и в
лицензировании. Предложение: `installation_id` (UUID, создаётся один раз при установке), `installation_name`
(как её называет клиент), версия поставки — в `AppSetting` и в ответе `/health`.

**С4. Клонирование установки ломает 1С — критично.** Типовой путь «скопировали базу на второй сервер» тихо
ломает каналы 1С: токен агента уникален (один токен на двух машинах → отказы через раз), токены баз чата
тоже. Нужен явный сценарий «клон/перенос»: при смене `installation_id` — отзыв токенов агентов и баз и
требование пройти подключение заново. Без этого клиент получит «работает через раз» и не поймёт почему.

**С5. Секреты.** `JWT_SECRET` общий у `backend` и `ai` (так и задумано — сервис проверяет тот же токен), но
на каждой установке он обязан быть СВОИМ и генерироваться установщиком. `BPAI_API_KEY`, `PIPE_API_KEY`,
`AGENT_ADMIN_KEY` — то же самое. `doctor` должен отказываться работать, если секрет совпал со значением из
примера или если у `.env` права шире `600`.

**С6. Прод-режим не по умолчанию — критично.** `ecosystem.config.js` без `APP_MODE=production` поднимает
dev-сервер Vite и `NODE_ENV=development`, что включает П3 и отдаёт наружу исходники с sourcemaps. Для чужой
установки умолчание должно быть обратным: production, а разработка — явным флагом.

**С7. Сервер лицензий ЭСФ.** `/api1/esf-license/*` (выдача токена, heartbeat, заявка на активацию, проверка)
живёт В ЭТОМ ЖЕ приложении, без авторизации. На множестве установок нужно решить: лицензии выдаёт одна наша
центральная установка (тогда у клиентских установок этот роутер не монтируется вовсе — и это первый кандидат
на «модуль, которого нет в поставке»), или каждая сама себе (тогда лицензирование теряет смысл). Решение
влияет на состав поставки, поэтому нужно до установщика.

**С8. Внешние зависимости — на совести клиента.** ИС ЭСФ (контур `test3`/`prod`), ключ eGov, провайдер
модели (`ANTHROPIC_API_KEY`), `AGENT_LATEST_BUILD`, фискальный провайдер Kaspi. Установщик обязан: спросить,
разрешить пропустить, и честно сказать, что без ключа выключено (система должна подниматься и работать без
единого внешнего ключа — сегодня это, похоже, так, но нигде не проверяется).

**С9. Тестовые данные рядом с боевыми.** `seed-testdata.js` и `seed-mock-*.js` лежат в одной папке с
`seed.js`. На чужом сервере запуск не того файла — это выдуманные контрагенты в учёте. Разделить явно:
«начальные данные» (валюты, единицы, план счетов, налоги, классификаторы) и «демо-данные», причём вторые
требуют подтверждения и метки в базе.

**С10. Настройки живут в трёх местах.** `.env` (секреты и адреса), `AppSetting` (модули, настройки учёта),
код (умолчания). Что где — нигде не описано. Для установщика нужен реестр настроек: имя, где живёт, кто
задаёт (установщик / мастер / администратор), обязательна ли, что будет, если пусто.

## Часть III. Что спроектировать до установщика

Порядок — по тому, насколько дорого чинить ПОСЛЕ первой чужой установки.

### Обязательно до (иначе установка будет заведомо дефектной)

| № | Работа | Суть проекта |
|---|---|---|
| **П1** | Запрет по умолчанию | Незнакомый путь → 403, а не пропуск. Каждый маршрут объявляет свой предмет (модель или «публичный») явно; тест-ворота: маршрут без объявления валит сборку. Переход делать «списком исключений», чтобы не погасить работающее одним днём |
| **П3** | Убрать dev-admin | Ветку `isDev && username === "admin"` убрать совсем; для разработки — отдельный флаг окружения, которого нет в поставке |
| **С6** | Production по умолчанию | `ecosystem.config.js` наоборот: прод, если не сказано иное. `doctor` предупреждает о dev-режиме |
| **С1, С2** | Адреса — из конфигурации | Один источник: сервер отдаёт `/config.json` (адрес API, адрес AI, имя установки), фронт читает его при старте. Убрать угадывание по hostname, `api.aleppo.kz`, оба IP и `trust proxy` из кода в `TRUSTED_PROXY_IPS` |
| **С4** | Идентичность установки | `installation_id` + сценарий клона: смена идентификатора отзывает токены агентов и баз 1С с понятным сообщением |
| **М1** | Гард на весь модуль | Проверка не «POST этих 11 путей», а «путь принадлежит модулю» — на всех методах, включая чтение, печать и выгрузки |
| **П2** | Отчёты под право и под модуль | Каждый отчёт объявляет, чей он (модель + модуль), и проверяется как всё остальное |

### Желательно до (иначе установку придётся донастраивать руками)

| № | Работа | Суть проекта |
|---|---|---|
| **П4** | Профили прав | Именованные наборы: «Бухгалтер», «Кладовщик», «Кассир», «Руководитель», «Только просмотр». Мастер первого запуска предлагает их вместо сотни галочек |
| **П6** | Разделить seed и схему | Из `seed.js` убрать `ALTER TABLE` и пароль `admin`: схему двигают миграции, администратора заводит мастер |
| **С9** | Начальные данные ≠ демо | Два набора, демо — только по подтверждению и с меткой в базе |
| **С3** | Имя и версия установки | В `AppSetting` и в `/health`; видно в интерфейсе — в обращениях поддержки это первый вопрос |
| **С10** | Реестр настроек | Таблица «настройка → где живёт → кто задаёт → что если пусто». Из неё же растут вопросы установщика (A3) и веб-мастера (A4) |
| **М4** | Одна проверка доступа | Право и модуль сводятся в один ответ с двумя причинами отказа; интерфейс скрывает разделы одним механизмом |
| **С7** | Решить судьбу лицензий ЭСФ | Центральная установка или ничья. От ответа зависит состав поставки |

### Можно после (не блокирует установщик)

| № | Работа |
|---|---|
| **П5** | Расширение модели прав (создание / правка / удаление / проведение) — но решение принять сейчас, профили П4 проектируются под него |
| **М2, М3, М5, М6** | Полное покрытие модулями: остальные документы, служебные каналы (`/bpai`, инструменты помощника), разметка границ (Б2 плана), отчёты |
| **С5, С8** | Проверка секретов и внешних ключей в `doctor` — делается вместе с самим `doctor` (A2) |

## Порядок

1. **С10** — реестр настроек. С него начинается и установщик, и мастер: пока неизвестно, что спрашивать,
   писать нечего.
2. **С1, С2, С6, С3** — отвязка от наших адресов и имя установки. Это чистая замена умолчаний, риск низкий,
   а без неё чужая установка не заработает вовсе.
3. **П1, П3, П2** — права: запрет по умолчанию, убрать dev-admin, закрыть отчёты. Делать вместе: у них общая
   правка — объявление предмета у каждого маршрута.
4. **М1, М4** — модули: гард на весь модуль и единая проверка доступа.
5. **П4, П6, С9** — профили прав, чистый seed, разделение начальных и демо-данных.
6. **С4** — сценарий клона и переноса, вместе с первым же переносом на живом стенде.
7. **С7** — решение по лицензиям ЭСФ (вопрос владельцу, не работа).

После шага 5 можно начинать часть А плана — установщик будет ставить систему, а не наш частный случай.

## Чего в этом проекте нет

- **Реализации.** По условию задачи: здесь только разбор и проект.
- **Разметки границ модулей (Б2 плана).** Это отдельная и самая долгая работа; здесь лишь зафиксировано, что
  без неё модулями управляется седьмая часть системы.
- **Оценки трудоёмкости в днях.** Они появятся, когда по каждой строке части III будет отдельная задача.
- **Пересмотра модели прав (П5)** — только требование принять решение до профилей.
