# Аудит согласованности № 3: со стороны расширения buhprof_api

23.09.2026. Третий проход после двух 22.09 ([первый](AUDIT_CONSISTENCY_2026-09-22.md),
[второй](AUDIT_CONSISTENCY_2_2026-09-22.md)). За сутки расширение впервые загружено в `Dev_01`, форма чата
перестроена под раскладку «рабочее место», появились индикатор состояния, пределы вложений из `/ping` и
таблица вложений с прогрессом фонового задания.

Сторона сервиса и панели в этот же день проверена отдельно —
[TASK_EXTENSION_SECTION_FIXES_2026-09-23.md](TASK_EXTENSION_SECTION_FIXES_2026-09-23.md) (А1–А5). Этот
проход смотрит с другой стороны, из расширения, и А1–А5 намеренно не повторяет.

**Итог.** Вчерашняя находка Д1 — «одно поле, два имени» — была закрыта не до конца. У кассового ордера
разошлись и запрос, и ответ: из двенадцати команд 1.6.0 одна не работала вовсе, и увидеть это до живого
прогона было нечем — потому что единственный сквозной тест отказывался запускаться на текущей сборке.

## Е1. Кассовый ордер не создавался ни разу

`registry.ts:791-820` кладёт в команду `{direction: "in"|"out", counterpartyId, amount, purpose, …}`.
`BPAPI_Сервис.ПодготовитьДанныеКассовогоОрдера` требовал `income` — обязательное булево, которого сервис
не слал никогда, — и читал основание из `basis`. «Создай расходный ордер на 85 000» упиралось в
`VALIDATION_ERROR: income — поле обязательно`.

Это тот же класс, что Д1 22.09, и та же причина: команды писались с двух сторон по одному плану, но по
разным образцам. Вчерашняя правка накрыла четыре команды из пяти найденных — кассовый ордер тогда никто не
сверил по полям, потому что сверялись МАРШРУТЫ, а маршрут у него совпадал.

**Сделано.** Расширение читает `direction` (`in`/`out`, прочее — отказ с перечнем значений) и `purpose`.

## Е2. Расходный ордер открывался как приходный

`workflow.ts:1221-1226`: вид документа для ссылки сервис берёт из `data.direction` ответа 1С, потому что по
команде его не угадать. Расширение возвращало только `type: cashIn|cashOut`, и всякий РКО получал ссылку
на ПКО — то есть на чужой документ.

**Сделано.** `BPAPI_Касса.Описание` отдаёт и `type` (он нужен печати), и `direction`; ответное поле `basis`
переименовано в `purpose` — запрос и ответ теперь зовут основание одинаково.

## Е3, Е6. Сквозной тест не запускался и не покрывал новое

`EXPECTED_VERSION = "1.5.0"` против `ВерсияAPI() = "1.6.0"`. Тест обрывался на первом шаге и печатал «новый
код не применён — загрузка из файлов → Ctrl+F7 → F7 → iisreset»: человек пошёл бы перезагружать правильно
загруженное расширение. Покрытия команд 1.6.0 не было вовсе.

**Сделано.** Версия сверяется как «не старее» (`MIN_VERSION`, сравнение числами): расширение новее — работа
продолжается с предупреждением. Добавлен блок РБ11: виды и списки документов по каждому виду, отбор по
сумме, заведение контрагента и номенклатуры с повтором (тот же объект, `created: false`), задолженность,
остатки по списку счетов и отказ на несуществующий счёт, обороты в разрезе контрагентов, кассовый ордер
полями контракта с проверкой `direction` в ответе, проведение, отмена, повтор и конфликт `requestId`,
самопроверка базы.

## Е4. Заглушку нельзя было использовать для половины формы

Форма чата при открытии зовёт `POST /organizations`, `GET /tasks`, `GET /notes`. Заглушка знала только
диалог, регистрацию и загрузку файлов, поэтому раздел «Задачи» всегда показывал «сведения не получены».

**Сделано.** Заглушка умеет организации (с отпечатком), задачи (создание, правка, закрытие, отбор
открытых), заметки, справочник статусов и отказы `VALIDATION_ERROR` / `ORG_NOT_IN_BASE`; ключ `--no-tasks`
воспроизводит `503 TASKS_DISABLED`. Проверено прогоном: пятнадцать проверок маршрутов сошлись.

## Е5. Одно имя, два смысла

`kind` у `create_counterparty`: сервис шлёт роль (`buyer`/`supplier`/`both`), расширение понимало вид лица
(`legal`/`individual`) и всё прочее определяло по БИН. Роль не доезжала никуда и доехать не может — в
типовой её задаёт вид договора.

**Решение владельца.** Вид лица зовётся `entityKind`; `kind` из схемы сервиса убрать. В расширении сделано,
сервису — задача.

## Е7, Е8. Пределы и возможности сервиса

`ЗапомнитьПределы` вызывалась только из «Проверить связь», доступной администратору базы. Пока он не
заходил, действовал запасной потолок 30 МБ против 20 МБ у сервиса по умолчанию: файл на 25 МБ уезжал по
сети целиком и получал `413`. Список `features` не читал никто, хотя сервис его объявляет.

**Сделано.** `ОбновитьПределыФоном()` освежает числа не чаще раза в сутки — на той же фоновой дороге, по
которой панель чата ходит за задачами. `features` сохраняются рядом; нет `uploads` — отказ до первой
загрузки, а не двадцать одинаковых отказов по сети.

## Е9, Е10. Лоток вложений

Файл, который не уехал, исчезал из таблицы вместе с отправленными — о потере говорила только реплика в
ленте. Прогресс искал строку по имени файла, и два одноимённых вложения делили одно состояние.

**Сделано.** После хода уходят только строки с прогрессом 100; прогресс несёт номер строки, имя осталось
для сверки.

## Е13. Версия расширения у базы без агента

Сервис читает `X-Ext-Version` в каждом запросе чата (журнал, `EXT_TOO_OLD`, порог ротации) и нигде не
сохраняет. Панель берёт версию из heartbeat админ-агента и из среза бизнес-агента (после А1). База, которая
работает только чатом из 1С, остаётся без версии — хотя сервис видит её постоянно. Там же взялось бы и
«последний обмен», который расширение теперь считает у себя.

Задача: [TASK_SERVICE_FROM_1C_AUDIT_3_2026-09-23.md](TASK_SERVICE_FROM_1C_AUDIT_3_2026-09-23.md).

## Что проверено и сошлось

- **Имена полей всех остальных команд.** Реализация, счёт, поступление (`customerId`/`supplierId`,
  `organizationId`, `contractId`, `warehouseId`, `items`, `comment`), акт сверки, печать, отчёты, банк —
  совпадают в реестре инструментов сервиса, контракте, шлюзе расширения и `build_route` агента.
- **Путь COM** читает поля payload по контрактным именам; `accounts` принимается и списком, и строкой.
- **Ход чата**: `user.id` равен заголовку `X-1C-User-Id`; пустой текст вместе с `decision` сервис
  принимает; задачи уходят методом `PATCH`, как он и ждёт.
- **Идемпотентность, ротация токена, порог `1.5.0`, реестр баз** — без изменений со вчерашнего прохода.
- **Формы расширения**: разметка и модули сошлись полностью — сверены все обращения `Элементы.*`, команды
  и пути данных по трём формам.

## Чего этот аудит не проверял

Живой работы всё ещё нет: ни одна команда 1.6.0 не выполнялась в базе, канал «1С ↔ сервис» ни разу не
сделал ход с настоящим сервисом, перезапуск и обновление агента на службе Windows не проверялись. Находки
Е1 и Е2 — ровно того сорта, который ловится первым прогоном; теперь его есть чем сделать.
