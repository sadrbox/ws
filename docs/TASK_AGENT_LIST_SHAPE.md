# Задача агенту: список в ответе не должен быть вложен в лишний массив

Сформировано 12.09.2026 вечером по факту: панель перестала показывать пользователей баз, а
кэш реестра по прочитанным базам опустел.

## Факт

С 16:38 UTC (21:38 местного) `IB_LIST_USERS` отвечает вложенным списком:

```jsonc
// было (119 команд до 16:23 UTC)
{ "items": [ { "name": "a1", … }, { "name": "maya", … } ] }

// стало (18 команд после 16:38 UTC)
{ "items": [ [ { "name": "a1", … }, { "name": "maya", … } ] ] }
```

Массив с единственным элементом-массивом. Так выглядит результат, собранный в PowerShell
через `@()` поверх уже готового массива (или `,$list` вместо `$list`) — классическая ловушка
`ConvertTo-Json`.

## Чем это обошлось

Сервис видел НЕПУСТОЙ массив, не находил в его единственном элементе имени (это массив, а не
запись), пропускал его как негодную строку — и затем выполнял вторую половину синхронизации:
удалял из кэша всех, «кого нет в новом срезе». Полный срез, разобранный неправильно,
неотличим от «пользователей больше нет».

Результат: у баз `_transition` и `abdali` в реестре стало ноль пользователей вместо 24 и 14.
Панель показывала пустую таблицу — и правильно показывала, знание было стёрто. Кэш
восстановлен из журнала команд (последний успешный срез каждой базы).

## Что сделано на стороне сервиса

* **Форму разворачиваем на входе** (`ai/src/onec/listShape.ts`): вложенный список из одного
  элемента принимается и разворачивается, в журнал пишется предупреждение. Это терпимость к
  чужой опечатке, а не одобрение: панель не должна ослепнуть из-за пары скобок.
* **Неузнанная форма больше не считается пустым срезом**: кэш в этом случае не трогается
  вовсе. Плюс гард в реестре — срез из непустого списка без единого имени отвергается
  исключением, а не применяется (`syncUsers`, `syncExtensions`).
* Оба правила закрыты тестами (`ai/tests/list_shape.test.ts`), включая «честно пустой срез
  по-прежнему очищает кэш»: у базы может не остаться ни одного расширения.

## Что нужно от агента

Отдавать список плоским — как отдавал до сегодняшней сборки и как описано в
`ONEC_AGENT_CLUSTER_CONTRACT.md`: `{"items": [ {…}, {…} ]}`. Проверить заодно все команды,
собирающие список одним и тем же кодом: `IB_LIST_USERS`, `IB_LIST_EXTENSIONS`,
`IB_LIST_ROLES`, `CLUSTER_LIST_*` — ловушка `@()` одинакова для всех.

Отдельно: **эхо состояния** (`state.users.items`) сегодня приходит ПЛОСКИМ, то есть два пути
в одной сборке собирают список по-разному. Это само по себе повод свести их в один.

## Как проверить

1. `IB_LIST_USERS` по любой базе: `items` — массив объектов; в журнале сервиса нет
   предупреждения «список пришёл вложенным».
2. Карточка базы → «Пользователи»: список непустой сразу после чтения, «Прочитано» — свежее.
3. Нарочно вложенный ответ (старая сборка): сервис его развернёт и предупредит, а кэш
   останется целым — это и есть проверка страховки.

# Приложение: команда, потерянная при перезапуске агента (12.09, 23:14 местного)

**Факт.** Агент зарегистрировался новой сборкой (`0.1.0+2026-09-12 23:06 (+05)`) в 18:14:28 UTC.
Команда `IB_LIST_USERS` по базе `abdali` была выдана в 18:14:04 — за секунды до этого — и
результата не дала ВОВСЕ: в 18:22 она всё ещё числилась выданной, при живом heartbeat (15 с) и
при том, что такие же команды до и после отвечали за 8–26 секунд. Возвращённая в очередь
руками, она была забрана новым процессом за 9 секунд.

Вывод: команда ушла процессу, который в этот момент останавливался, и умерла вместе с ним.
Агент об этом не сообщает — сервису остаётся только срок жизни команды.

**Что сделано на стороне сервиса.** Команда, забранная процессом, который больше не работает,
закрывается сразу, а не через четверть часа: при регистрации нового экземпляра сервис видит по
`commands.dispatched_instance` (миграция 021), что её забирал прежний, и объявляет её потерянной
с кодом `AGENT_RESTARTED` (`queue.failLostByRestart`, тест `ai/tests/command_restart.test.ts`).
Различение ПО ЭКЗЕМПЛЯРУ здесь обязательно: агент регистрируется не только при старте, и
закрывать команды по самому факту регистрации значило бы убивать свои же идущие — например
выгрузку базы, которая честно работает третий час.

До этой правки одна потерянная команда держала единственный слот входа в базу до истечения
срока: пятнадцать минут при обычном ответе за десяток секунд — именно это и выглядело в панели
как «Проверить пользователей — 0 из 1 — Выполняется» у базы за базой.

**Что желательно от агента.** Перед остановкой возвращать взятые и не начатые команды (или
отвечать по ним отказом): сервис узнаёт о перезапуске только по смене экземпляра, а между
выдачей и регистрацией нового процесса есть окно, в котором команда исчезает молча. Это же
закрывает и задачу `AGENT_CANCEL_COMMAND` (A1) с другой стороны.

## Сделано агентом, сборка `0.1.0+2026-09-12 23:48 (+05)`

**Диагноз подтверждён и воспроизведён.** Ловушка сработала на сочетании двух мест:
`Read-UsersList` возвращает массив как ОДИН объект (`return ,@(…)` — иначе PowerShell развернул
бы его при возврате, и список из одной записи стал бы записью), а вызывающий оборачивал вызов
в `@(…)`. Такая обёртка собирает поток ИЗ ОДНОГО ЭЛЕМЕНТА — самого массива:

```
@(f)          → {"items":[[{…},{…}]]}     ← так было
$x = f; @($x) → {"items":[{…},{…}]}       ← так собиралось эхо (потому и было плоским)
f без @()     → {"items":[{…},{…}]}       ← так теперь везде
```

Проверено на живом PowerShell, включая случаи «одна запись» и «пусто» — оба дают правильную
форму.

**Исправлено в трёх местах:** `IB_LIST_USERS`, `IB_LIST_EXTENSIONS` и эхо состояния. Проверены
все остальные списки: `IB_LIST_ROLES` собирает массив в переменной (`@($items)` — безопасная
идиома), `Get-UserRoles` и `Get-IbUsers` возвращают массив обычным путём, `CLUSTER_LIST_*`
собираются в Rust и к этой ловушке отношения не имеют. Опасных функций в мосте ровно две, обе
поправлены.

**Защита от повторения — в сборке, а не во внимательности.** `build.rs` ищет функции с
`return ,` и валит сборку, если где-то встречается `@(ИмяФункции …)`:

```
bridge.ps1, строка 563: `@(Read-UsersList …)` даёт ВЛОЖЕННЫЙ список — Read-UsersList
возвращает массив как один объект. Передавайте вызов без обёртки либо сначала присвойте
его переменной.
```

Проверено нарочной поломкой: сборка падает с этим текстом.

Спасибо за терпимость к форме на вашей стороне — её стоит оставить: она закрывает не только
этот случай, но и любую старую сборку агента, которая ещё ходит по серверам.

### По приложению: потерянная команда

Агент теперь **отвечает по взятым командам перед остановкой**, различая два случая:

* работа не начиналась (команда ждала свободного исполнителя) — `AGENT_STOPPING`, «команда НЕ
  выполнялась, её можно повторить»;
* работа началась — `AGENT_STOPPED`, «результат неизвестен, проверьте состояние базы перед
  повтором». Соврать здесь «не выполнялась» нельзя: выгрузка могла записать файл, а установка
  расширения — дойти до базы.

Если результат не доставлен (сервис недоступен в момент остановки), он ложится в очередь
отложенных и уходит при следующем запуске — команда всё равно не будет висеть до истечения
срока.

Ваш `reclaimDispatched` при этом остаётся нужным: он закрывает случай, когда агента сняли
жёстко и сказать он уже ничего не успел.
