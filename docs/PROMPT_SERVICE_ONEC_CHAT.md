Реализуй в AI-сервисе задачи СВ0, СВ1 и СВ2 из плана `docs/PLAN_BUHPROF_API_2026-09-19.md`, строго по контракту

**СВ0 — коды расширения 1.3.0** (малая, сделать первой). В `errorHints.ts` (или где живут подсказки к ошибкам
команд):
- `409 REQUEST_IN_PROGRESS` — «операция с этим requestId уже выполняется», повторяемая; агент сам повторяет её,
  сервису пересоздавать команду нельзя.
- `403 SETUP_DISABLED` — стендовая операция выключена в базе.
- у `500 INTERNAL_ERROR` есть `error.details.errorId` — показывать как «код для поиска в журнале 1С».

**СВ1 — канал «база 1С»**:
1. Токен базы: таблица (миграция) — база, организация ERP, хэш токена, создан/отозван, кто выпустил. В открытом
   виде токен показывается один раз при выпуске. На время разработки выпуск — служебной командой/скриптом
   (панель — задача ПН1, позже).
2. Middleware: `X-Base-Token` (сверка по хэшу, отозванный = `401 BASE_TOKEN_INVALID`, выключенная база =
   `403 BASE_DISABLED`) + `X-1C-User-Id` (UUID, иначе `400 VALIDATION_ERROR`). **Заголовки только ASCII** —
   имя пользователя 1С приходит в теле (`user.name`), не в заголовке.
3. Маршруты `/v1/onec-chat`: `GET /ping` → `{base: {key, name}, organization: {uuid, name}, serviceVersion}`;
   `POST /turn`; `GET /conversations`, `GET /conversations/:id` (сообщения, состояние, ожидающая карточка,
   ожидающие `calls`).
4. Диалог принадлежит паре «база + пользователь 1С»; чужой диалог — `404`. Аудит с каналом `1c`.
5. Лимиты на пару «база + пользователь 1С», `429 RATE_LIMITED` + `Retry-After`.

**СВ2 — выполнение инструментов на стороне клиента** (крупная):
1. В `ChatWorkflow` режим «клиентские инструменты»: вместо `queue.enqueue` + `waitResult` — сохранить вызовы в
   состоянии диалога и ответить `state: "TOOL_CALLS"`, `calls: [{callId, commandType, payload, requestId}]`.
   `commandType` и `payload` — **ровно те же, что сейчас уходят агенту** (`ai/src/tools/registry.ts`);
   сопоставление с операциями 1С делает расширение. У изменяющих команд `requestId` обязателен (без него 1С
   отвечает `MISSING_REQUEST_ID`); при повторе того же вызова — тот же `requestId`.
2. Ход с `toolResults: [{callId, result: {success, data | error, status}}]` — отдать результаты модели и
   продолжить. Неизвестный или чужой `callId` — `400`. Результаты файлов приходят без содержимого:
   `data.contentOmitted: true, data.bytes: N` — модели сказать «файл сформирован и открыт у пользователя в 1С».
3. Подтверждения — прежние карточки: `WAITING_CONFIRMATION` + `confirmation: {tool, card}`; ответ приходит полем
   `decision: {accepted: true|false}` (не текстом). Изменяющий вызов уходит в `calls` только после
   `accepted: true`.
4. Организация хода — из `organization` запроса (`bin`, `name`, `id`): подставлять `organizationBin` в
   инструменты, модель не спрашивает «какая организация». Это контекст, не проверка прав — права проверяет 1С.
5. PDF (`attachments`, до 3, base64, до 20 МБ каждый) — прежним путём распознавания в фоне: ответ
   `PROCESSING`, форма опрашивает `GET /conversations/:id` каждые 5 с; итог — `TOOL_CALLS` с
   `IMPORT_BANK_STATEMENT` (форма выполнит его, получив `calls` из этого GET).
6. `documents` в ответе — созданные и найденные документы (`type, id, number, title`); форма и сама делает ссылки
   по результатам `CREATE_*`, так что поле необязательное.

**Готово, когда**: e2e от имени пользователя 1С — «найди физули» (TOOL_CALLS → COMPLETED), «создай реализацию
…» (карточка → подтверждение → TOOL_CALLS CREATE_SALE → COMPLETED), «ОСВ за август» (RUN_REPORT, файл не пришёл
в сервис), PDF выписки (PROCESSING → TOOL_CALLS IMPORT_BANK_STATEMENT); сценарии `chat-e2e` ERP-чата не
сломаны. Контракт не менять без согласования: если что-то в нём неудобно — опиши в
`docs/CONTRACT_1C_CHAT_2026-09-19.md` раздел «Вопросы сервиса» и остановись.
