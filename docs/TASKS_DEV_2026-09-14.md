> 14.09.2026. Агентская часть готова в сборке `0.1.0+2026-09-14 00:29 (+05)` (`TASKS_AGENT_2026-09-13.md`, раздел
> «Развитие 14.09»). Сверено с кодом `ai` и `frontend` на 14.09.
>
> Цель плана — чтобы серверы 1С обслуживались из панели: состояние, журнал, проверка и скорость
> видны и управляются отсюда, а на сервер заходят только ставить агента.

**Порядок:** R1, R2, R4 — сразу после развёртывания агента (контракты ниже). R3 — вместе с R1 (одна

Все новые команды — только тому агенту, у которого есть их тип в `capabilities` (проверка
`agentCanRun` по типу уже работает: старая сборка их не получит).

## R1. Состояние сервера 1С — `AGENT_HEALTH`

### Контракт агента

Payload `{}`. Команда локальная: в 1С не ходит, пропуска агента не ждёт (отвечает и тогда, когда
агент занят зависшей работой). Время ответа — до 10 с (опрос `rac` с пределом), остальное из кэша.

```jsonc
{
  "collectedAt": "2026-09-14T09:10:00Z",
  "agent": {
    "version": "0.1.0", "build": "2026-09-14 01:30 (+05)", "instance": "SERVER/BPAPIAgentAdmin/996/…",
    "role": "admin", "server": "Сервер 1С", "serviceName": "BPAPIAgentAdmin",
    "state": "ONLINE", "lastError": null, "uptimeSecs": 5321, "ibReady": true,
    "maxParallel": 4, "persistentBridge": false,
    "commandTimeoutSecs": 600, "longCommandTimeoutSecs": 14400
  },
  "capabilities": ["cluster.admin", "ib.admin", "ib.auth", "agent.procs", "ib.echo", "agent.cancel", "ib.roles"],
  "readiness": { "items": [ { "key": "rac", "ok": true, "note": "…" }, { "key": "dbPassword", "ok": false, "note": "…" } ] },
  "commands": {
    "done": 128, "failed": 3,
    "failuresByCode": { "IB_BUSY": 2, "IB_AUTH_FAILED": 1 },
    "durationsByType": { "IB_LIST_USERS": { "count": 42, "avgMs": 2810, "maxMs": 9100, "p95LeSecs": 5, "buckets": { "le1s": 3, "…": 0 } } }
  },
  "processes": [ { "pid": 7692, "tool": "ibcmd", "what": "extension list", "base": "abdali", "ageSecs": 12, "orphan": false } ],
  "cluster": {                                   // null у бизнес-агента
    "platform": "8.3.25.1257",
    "clusters": [ { "name": "Локальный кластер", "host": "SERVER", "port": "1541" } ],   // или { "error": "…" }
    "bases": { "known": 110, "dbChecked": 110, "dbMissing": ["aibek"] },
    "publications": { "found": 34, "complete": true, "ageSecs": 120 },                  // null — не читали
    "dbPassword": true,
    "dbmsClients": [ { "name": "sqlcmd (MS SQL)", "path": "C:\\…\\SQLCMD.EXE" }, { "name": "psql (PostgreSQL)", "path": null } ]
  },
  "logProblems": ["2026-09-14T09:01:02Z  WARN …", "…"]   // последние 20 WARN/ERROR, секреты вырезаны

```

Паролей в ответе нет: настройки — признаками, строки журнала очищены агентом.

### Сделать

* **Сервис.** Спецификация: `type: "AGENT_HEALTH"`, `title: "Состояние сервера 1С"`,
  `operation: "READ"`, `capability: "agent.procs"`, `role: "admin"`, `requiresBase: false`,
  `schema: z.object({}).strict()`. Маршрут `GET /v1/onec/agents/:id/health` — адресовать ЭТОМУ
  агенту (как отмену в S4), ключ склейки чтений — с идентификатором агента.
* **Панель.** Карточка агента → вкладка «Состояние сервера»: блоки «Агент» (сборка, состояние,
  время работы, параллельность, живой мост), «Готовность» (строки «да/нет — пояснение»),
  «Кластер» (платформа, кластеры или ошибка, базы: известно / проверено / без базы данных —
  поимённо, публикации, пароль СУБД, клиенты СУБД), «Процессы», «Последние ошибки журнала».
  Кнопка «Обновить» — новая команда. Время и отказы команд — ссылкой на уже готовую вкладку S5.

## R2. Журнал агента — `AGENT_LOG_TAIL`

### Контракт агента

Payload: `lines` 1–1000 (по умолчанию 200), `level` — `all` или `problems` (только WARN и ERROR),
`contains` — отбор по тексту без учёта регистра, до 100 знаков. Локальная команда, без пропуска.

```jsonc
{ "file": "bpapi-agent.log.2026-09-14", "lines": ["…", "…"], "matched": 1840, "truncated": true }
```

Отказы: `VALIDATION_ERROR` (неверные `lines`/`level`), `LOG_UNAVAILABLE` (агент пишет журнал
только в консоль — у службы так не бывает). Секреты вырезаны ДО отбора по тексту: поиск по куску
пароля ничего не находит.

### Сделать

* **Сервис.** Спецификация: `type: "AGENT_LOG_TAIL"`, `title: "Журнал агента"`, `operation: "READ"`,
  `capability: "agent.procs"`, `role: "admin"`, `requiresBase: false`,
  `schema: z.object({ lines: z.number().int().min(1).max(1000).optional(), level: z.enum(["all", "problems"]).optional(), contains: z.string().max(100).optional() }).strict()`.
  Маршрут `GET /v1/onec/agents/:id/log?lines=&level=&contains=` — этому агенту; ключ склейки — с
  параметрами. Ответ до 1000 строк (~200 КБ): в `commands.result` его хранить не дольше, чем нужно
  панели, либо обрезать `lines` после выдачи.
* **Панель.** Карточка агента → вкладка «Журнал»: число строк (200 / 500 / 1000), переключатель
  «только предупреждения и ошибки», поиск, моноширинный список, «Обновить», «Скопировать». Без
  автообновления.

## R3. «Агент устарел»

Агенту менять нечего: версия со сборкой (`0.1.0+2026-09-14 01:30 (+05)`) и способности уже приходят
в регистрации и heartbeat.

* **Сервис.** Настройка `AGENT_LATEST_BUILD` (строка сборки, например `2026-09-14 01:30`) — меняется,
  когда выпущена новая сборка агента. В `GET /v1/onec/agents`: `buildOutdated` (`true` / `false` /
  `null` — эталон не задан или сборка не разобрана) и `missingFeatures` — по таблице:

  | функция панели | чего не хватает у агента |
  |---|---|
  | «Прервать» | способность `agent.cancel` |
  | правка ролей | способность `ib.roles` (без неё сервис уже отказывает, C5) |
  | время и отказы команд | `durationsByType` в heartbeat |
  | состояние сервера | тип `AGENT_HEALTH` |
  | журнал агента | тип `AGENT_LOG_TAIL` |
  | самопроверка | тип `IB_SELFTEST` |

* **Панель.** В списке агентов — отметка «Устарел»; в карточке — «Нет в этой сборке: …» и
  подсказка «на сервере: `bpapi-agent update`».

## R4. Самопроверка из панели — `IB_SELFTEST`

### Контракт агента

Payload `{ baseKey, dryRun? }`. Внутрибазовая команда: замок базы, проверка «база есть в кластере»,
пробный прогон (`dryRun` → план). Создаёт временного пользователя `bpapi_selftest_<процесс>`,
проверяет чтение, создание, повтор, роли (добавить, снять, заменить набор, снять все), изменение,
запреты, удаление и повтор удаления — и убирает пользователя. Идёт минуту и дольше.

```jsonc
{ "ok": false,
  "steps": [ { "name": "список пользователей", "ok": true, "note": "24 шт." },
             { "name": "снять все роли", "ok": false, "note": "…" } ] }
```

Результат команды — `SUCCESS`, если прогон состоялся; `ok: false` значит «есть неудачные шаги».
`ERROR` — прогон не начался (`IB_BUSY`, база не найдена, нет входа).

### Сделать

* **Сервис.** Спецификация: `type: "IB_SELFTEST"`, `title: "Проверить операции агента в базе"`,
  `operation: "WRITE"` (временный пользователь), `capability: "ib.admin"`, `role: "admin"`,
  `requiresBase: true`, `schema: z.object({ baseKey, dryRun: z.boolean().optional() }).strict()`.
  Реестр не трогать: пользователь временный, эхо внутри прогона сервису не уходит.
* **Панель.** Карточка базы → «Обслуживание» → «Проверить операции агента»: подтверждение с планом
  («создаст временного пользователя и удалит его; лучше на технической базе»), итог — таблица
  шагов «шаг · итог · пояснение»; `ok: false` — предупреждение, а не «Выполнено». Для `readonly`
  не показывать.

## R7. «Одна операция — актуальные данные в ответе»

Сверено по коду всех трёх частей 14.09. Команды, которые что-то меняют, и итог:

| Команда | Итог | Что не так |
|---|---|---|
| `CLUSTER_TERMINATE_SESSION` | соответствует | — (счётчик сеансов базы в реестре — до heartbeat) |
| `CLUSTER_DISCONNECT` | частично | таблица «Блокировки» на том же экране не обновляется |
| `CLUSTER_SET_SESSIONS_LOCK` | **не соответствует** | агент возвращает повтор запроса, а не прочитанное состояние; сервис его не хранит; панель нигде не показывает, заперта ли база, а `bases.refetch()` после команды бесполезен |
| `CLUSTER_DROP_INFOBASE` | **не соответствует** | реестр не обновляется: удалённая база видна с прежним статусом до полного среза и попадает в пакеты |
| `CLUSTER_CHECK_BASES`, `CLUSTER_LIST_INFOBASES`, `CLUSTER_LIST_PUBLICATIONS` | соответствуют | — |
| `IB_CREATE_USER`, `IB_DELETE_USER` | агент и сервис — да, **панель — нет** | карточка базы после команды ставит живое `IB_LIST_USERS` (`OneCBases/index.tsx:271-272` → `shared.tsx:262`), хотя эхо уже в реестре; при склейке с ранее стоявшим чтением карточка получает список ДО изменения |
| `IB_UPDATE_USER` | частично | таблица пользователей в карточке базы (`["onec","base-users",key]`) не входит в `REFRESH_KEYS` (`progress.ts:83-92`) и устаревает |
| `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` | соответствуют | — (кэш ролей после расширения не перечитывается) |
| `IB_PUBLISH`, `IB_UNPUBLISH` | соответствуют | — |
| `IB_BACKUP`, `IB_CHECK` (и с `repair`) | соответствуют | — |
| `IB_RESTORE` | **не соответствует** | после полной замены данных кэш пользователей и расширений — от прежней базы |
| `IB_APPLY_UPDATE` | частично | новая версия конфигурации только в тосте, не хранится; расширения и роли не перечитаны |
| `AGENT_KILL_PROCESS` | **не соответствует** | таблица процессов до 30 с показывает снятый процесс (снимок — только с heartbeat) |
| `AGENT_CANCEL_COMMAND` | соответствует | — (снимок процессов — до heartbeat) |
| `ElementForm` (любая правка из общей формы) | **не соответствует** | `invalidateQueries(["onec"])` сразу после постановки (`ElementForm.tsx:167`) перечитывает все активные запросы, включая живые списки кластера и ролей |
| Бизнес-команды (документы) | соответствуют | ответ расширения — сам документ или построчный итог; сервис ничего не дочитывает |

### Задачи по R7 (ждут согласования)

**Панель — не ждут агента:**

* **R7-П1.** Карточка базы после создания и удаления пользователя — перечитывать кэш реестра, а не
  живое `IB_LIST_USERS` (`OneCBases/index.tsx:271-272`, `BaseUserCommands.tsx:71-77, 91-95`).
* **R7-П2.** Таблица пользователей карточки базы — в `REFRESH_KEYS`. Осторожно: если её `queryFn` —
  живое чтение, сброс кэша сам поставит команду агенту; сперва перевести её на `…/users/cached`.
* **R7-П3.** `ElementForm.tsx:167` — сбрасывать только ключи реестра и по завершении команды, а не
  всё `["onec"]` сразу после постановки.

**Сервис:**

* **R7-С1.** `CLUSTER_DROP_INFOBASE` `SUCCESS` → сразу пометить базу удалённой в реестре (по образцу
  `markStatus`).
* **R7-С2.** `CLUSTER_SET_SESSIONS_LOCK` → хранить состояние блокировки базы из `state.base` и отдать
  в API.
* **R7-С3.** `AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND` → `setProcesses` из `state.processes`.
* **R7-С4.** `IB_APPLY_UPDATE` → хранить версию конфигурации (`configVersion`); `state.users` и
  `state.extensions` из ответа применяются уже существующим путём эха.

**Агент (следующая сборка):**

* **R7-А1.** `CLUSTER_SET_SESSIONS_LOCK` — после `infobase update` прочитать `infobase info` и вернуть
  `state.base { sessionsDeny, deniedMessage, deniedFrom, deniedTo, permissionCode }`.
* **R7-А2.** `CLUSTER_DROP_INFOBASE` — `state.infobase { key, removed: true }`.
* **R7-А3.** `CLUSTER_DISCONNECT` — к `state.connections` добавить `state.locks`.
* **R7-А4.** `IB_RESTORE` — после загрузки `state.users` и `state.extensions` (полные списки).
* **R7-А5.** `IB_APPLY_UPDATE` — `state.extensions` и `state.users` после обновления.
* **R7-А6.** `AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND` — `state.processes`.

**Статус агента (14.09):** А1–А6 сделаны вместе с E1–E6 — формы по
