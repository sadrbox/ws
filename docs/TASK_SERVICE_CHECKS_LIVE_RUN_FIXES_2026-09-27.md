## П1. Помеченные на удаление в `documents.unposted`

Условие проверки с первой версии: `НЕ Док.Проведен И НЕ Док.ПометкаУдаления И Док.Дата < &Порог` — и в
запросе, и в отборе общего прохода по документам (1.8.0 это уже включало, сравнил исходники сборок).
Тест на стенде: непроведённому документу ставится пометка → он уходит из `unposted` (74 → 73) и
появляется в `deletion_marked`; пометка снимается → снова в `unposted`.

Почему «СНТ № 8652 от 14.08» стоит в обоих списках: по коду это возможно только если это **два разных
документа с одним номером** — у СНТ номер приходит из ИС ЭСФ и повторяется при перевыпуске (один
перевыпущенный документ помечен на удаление, другой не проведён). Проверить просто: у двух находок
сравнить `documents[0].id` — отпечатки и идентификаторы разные. Если id совпадёт, пришлите оба JSON:
тогда это новая для нас находка.

## П2. `accounts.unnatural_balance` → версия 2

- Новый параметр `bidirectionalAccounts` (string[]), умолчание — счета прибыли и убытка по
  предопределённым именам плана счетов базы: **5610, 5620, 5710** в типовой БК 3.0. Сальдо на них не
  проверяется вовсе. Сервис может расширить список под клиента (1250, 1280, 3390 — по ситуации);
  `excludeAccounts` работает как раньше.
- Счета расчётов **1210, 3310, 1710, 3510**: сальдо не той стороны — **предупреждение** (`rule` =
  `settlement_debit` / `settlement_credit`, в `details.hint` — «проверьте, не должен ли остаток стоять на
  парном счёте (долг ↔ аванс)»). Явное правило применяется первым: на типовом плане 3310 пассивный, и
  без этого дебет по поставщику остался бы ошибкой.
- Деньги (1010, 1030) в минусе и любой другой счёт с сальдо против вида — **ошибка**, как и было.
- Заголовок: «Счёт 3310: дебетовое сальдо 70 000,00 (ТОО X) — вероятно, остаток должен быть на парном
  счёте расчётов»; «Счёт 1030: кредитовое сальдо 19 300 000,00 на активном счёте (…)».
- **Отпечатки не изменились.** У прежних находок по 3310/1210/3510/1710 сменится только `severity`
  (error → warning) под тем же `fingerprint`; находки по 5610 пропадут — считать закрытыми.

Проверено на стенде посевом: дебет на 5610 — 0 находок; дебет по поставщику на 3310 — предупреждение;
кредит на 1030 — ошибка.

## П3. Сборные контрагенты

**Признак** (функция `СборныеКонтрагенты()` в модуле проверок):
1. физическое лицо (`ЮрФизЛицо = ФизЛицо`) без ИИН;
2. ИИН из одних нулей (`000000000000`) — так «Физ.лицо» заводят чаще всего, у любого вида;
3. явная отметка администратора: новая константа `BPAPI_СборныеКонтрагенты` — наименование или
   идентификатор, по одному в строке. Редактируется в форме «БухПроф AI → Подключение к BuhProf AI»,
   группа «Проверки учёта» (только администратор базы).

**Исключение** из `catalogs.counterparty_requisites` (v2), `counterparties.contacts` (v3),
`settlements.advances_offset` (v3), `settlements.aging` (v4). Версии подняты, потому что изменился состав
находок; отпечатки прежние.

**Заметка.** В ответе `RUN_ACCOUNTING_CHECK` новое поле **`notes: string[]`** (у всех проверок, обычно
пустое): «сборных контрагентов исключено: N» — только когда исключение было. В печатном отчёте —
строка «        · сборных контрагентов исключено: N» под итогом проверки. Это не находка: чинить нечего,
но исключение видно.

Проверено на стенде: «Розничная выручка» (физлицо, ИИН из нулей) исключена по правилу; контрагент из
списка — исключён из requisites (10 → 9 находок, заметка «исключено: 2»); обычный контрагент без БИН —
находка как раньше; посев долга и аванса на сборного и на обычное ТОО — по авансам и старению находка
только у ТОО, у сборного заметка.

## П4. Горизонт

В строке итога каждой проверки отчёта — скобка по `periodKind`: `period` → «[за период]», `onDate` →
«[на дату]», `none` → «[вся база]»; у `stock.chronology` — «[за 24 мес.]», как и было. Старение и авансы

## П5. `same_amount_date`

Ключ группы **с 1.7.x**: `вид документа | контрагент | сумма | день` (строка 1110 модуля в 1.8.0), и
условие `ЗначениеЗаполнено(Контрагент)` — без контрагента группа не строится. 23 предупреждения NORD BEER
— это пары документов **одного** контрагента на одну сумму в один день; заголовок «Совпадают контрагент,
сумма и дата у 2 документов» этого не показывал, отсюда и прочтение.

Изменён заголовок: «**«ТОО X»: 2 документов на 150 000,00 от 14.08.2026** — совпадают контрагент, сумма и
дата»; у `same_incoming_number` и `same_bank_document` — тоже с контрагентом. Приёмка «две реализации
разным покупателям — 0 находок; две одному — предупреждение» выполняется по построению ключа.

## П6. Вид отчёта

1. Представление документа в заголовках (`unposted`, `deletion_marked`, `stock.chronology`) — без
   хвоста «0:00:00»; у документов со временем время остаётся.
2. В JSON `title` **всегда был полным** — обрезки в `НоваяНаходка` нет; резалась только печатная форма.
   Теперь печать — до 140 знаков и с «…».
3. `fixed_assets.zero_residual`: `groupKey` = подразделение из первоначальных сведений ОС; без
   подразделения ключ пуст, и строка «все в одной группе: —» не печатается.

## Вопрос по `settlements.aging`: 7,4 → 10,6 с и 53 → 54 находки

Расчёт менялся — **в 1.8.1, версия проверки 3** (в ответе поле `version`; в 1.8.0 было 2):

1. **Окно истории по умолчанию 1095 → 3650 дней.** Оборотов читается втрое больше — отсюда +3 с.
2. **Сальдо на начало окна входит в очередь ФИФО первым элементом** (самый старый долг). В 1.8.0
   очередь начиналась с первого оборота внутри окна, и долг, возникший раньше, «объяснялся» ближайшими
   оборотами — то есть выглядел моложе. Теперь остаток может лечь на более старый непогашенный оборот, и
   возраст переходит порог 60 дней: отсюда +1 предупреждение по 3310. У таких находок в `details` есть
   `oldestDate`, а при долге старше окна — `ageIsAtLeast: true`.

Это не новый документ, а другое правило; сервису стоит считать находки `version < 3` результатом старого
правила. Между 1.8.2 и 1.8.3 старение менялось только исключением сборных (v4).
