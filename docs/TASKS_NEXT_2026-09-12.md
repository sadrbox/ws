Сформировано по аудиту 12 сентября (`AUDIT_2026-09-12.md`). Каждая задача — с фактом, из
которого она выросла, критерием приёмки и ценой бездействия. Идентификаторы сквозные с
аудитом: **D** — эксплуатация, **O** — оптимизация, **A** — панель 1С, **F** — новая

агента на сервере 1С, часть — решения администратора. Смешивать нельзя: половина прошлых
разборов уходила на выяснение, чья это работа.

## Волна 1. Эксплуатация — день работы, эффект для всех

### D1. Прод перевести на собранный фронт (P0, наша)

**Факт.** `ecosystem.config.js` запускает `npx vite --host` с `NODE_ENV=development`. Люди
получают неминифицированный код, dev-предупреждения React, sourcemaps и HMR-сокет на
локальный адрес. Сборка работает: 27 с, главный чанк 194 кБ gzip.

**Что сделать.** Процесс раздачи `frontend/dist` (статика через cloudflared/nginx либо
`serve`), `NODE_ENV=production` у бэкенда, dev-сервер оставить только для разработки.

**Приёмка.** В ответе страницы нет `@vite/client`; `NODE_ENV` бэкенда — `production`;

(имена файлов, исходники) раздаются всем, кто откроет вкладку разработчика.

**Приёмка.** `pm2 list` — четыре воркера `cluster`; `SELECT count(*) FROM pg_stat_activity`
под работой не превышает расчётных 68.

### D3. Убрать Prisma Studio из постоянно работающих (P1, администратора)

## Волна 2. Оптимизация — три N+1 и одна раздача

### O1. Список заданий: 81 запрос → 3 (P0, наша)

**Факт (замер).** `BatchService.list(org, 20)` вызывает `progress(id)` в цикле; каждый
`progress` делает ~4 запроса, первый — `UPDATE`. Итого 81 запрос и 73 мс на один опрос, а
опрос идёт раз в 3 с, пока что-то выполняется: ~27 запросов и 7 записей в секунду.

**Что сделать.** Один `UPDATE ... WHERE batch_id = ANY($1)`, один `SELECT` с агрегатами
(`GROUP BY batch_id`), один `SELECT` строк-команд. Метод `progress(id)` оставить для одного
задания, `list` собрать отдельно.

**Приёмка.** Тот же экран «Задания» работает на трёх запросах; замер повторить тем же
скриптом — время опроса падает кратно.

### O2. Срез баз: один upsert вместо 111 (P1, наша)

**Факт.** `BaseService.sync` шлёт запрос на каждую базу; при 111 базах это 111
round-trip'ов на каждый полный срез (heartbeat и кнопка «Обновить»).

**Что сделать.** Многострочный upsert через `unnest($1::text[], …)`, сохранив трёхзначность
`published` и `dbMissing` (COALESCE-семантику «поля нет — не трогаем»).

**Приёмка.** Тест на трёхзначность полей остаётся зелёным, в журнале запросов — один upsert
на срез.

### O3. Публикации: 270 запросов → 2 (P1, наша)

**Факт.** `applyPublications` на каждую строку ответа делает `SELECT` поиска базы и
`UPDATE`. Последний срез: 135 строк — 270 запросов на одно нажатие.

**Что сделать.** Один `SELECT key, name` в словарь (поиск по ключу ИЛИ имени сохранить) и
один `UPDATE ... FROM (VALUES …)`.

### O4. Разобрать главный чанк (P2, наша)

**Факт.** 620 кБ (194 кБ gzip). Тяжёлые библиотеки уже ленивые, модели — 56 динамических
импортов; остаток — ядро: `useFormStore` 1832 строки, `Table` 1030, `SubTable` 988,
`LookupField` 949.

**Что сделать.** Замерить состав (`rollup-plugin-visualizer`), вынести `SubTable` и
`DocumentItemsTable` в отдельный чанк — они нужны только документным формам.

**Приёмка.** Главный чанк меньше 500 кБ без потери скорости открытия форм.

## Волна 3. Панель 1С — то, чего людям не хватает сегодня

### A1. Настоящая отмена начатой команды (P1, нужна работа агента)

**Факт.** Отменяются только команды в очереди. Забранную агентом остановить нельзя, и она
держит место до 15 минут — при `AGENT_IB_PARALLEL = 1` за ней стоит вся очередь.

**Что сделать.** Команда `AGENT_CANCEL_COMMAND` (идентификатор команды): агент снимает свой
`ibcmd`/COM-процесс и отвечает `CANCELED`. В панели кнопка перестаёт гаснуть для начатых.

**Зависимость.** Спецификацию агенту оформить так же, как `TASK_SERVICE_DROP_INFOBASE.md`.

### A2. Оценка времени массовой операции (P1, наша)

**Факт.** 110 баз по ~25 с ≈ 45 минут, а человек видит только счётчик и не знает, ждать ли.

**Что сделать.** В помощнике групповых операций и в «Прогрессе» показывать оценку из
измеренной средней длительности по типу команды (данные есть в `commands`).

### A3. Очередь объясняет, чего ждёт (P2, наша)

**Факт.** `queued` в «Прогрессе» выглядит как «выполняется». Человек не различает «агент
занят другой базой» и «агент не забрал команду».

**Что сделать.** В записи операции показывать: сколько её команд ещё в очереди и причина
ожидания (занят агент / нет агента на связи). Оба факта уже есть в данных.

### A4. Снять временное ограничение параллелизма (P2, наша, после измерения)

**Факт.** `AGENT_IB_PARALLEL` не задан → умолчание 1. Ограничение вводилось, когда две
параллельные `IB_LIST_EXTENSIONS` клинили агента на 12 минут; перестроенный агент отвечает
за 78 с.

**Что сделать.** Прогнать два параллельных чтения по разным базам, посмотреть heartbeat;
при успехе поднять значение НАСТРОЙКОЙ (без правки кода) до 3–4 и замерить массовую
проверку заново.

**Цена единицы измерена 12.09 (23:14).** При обновлении службы агента забранная ею
`IB_LIST_USERS` осталась без ответа, заняла единственное место — и ВСЕ внутрибазовые команды
встали на девять минут, до истечения срока. Сам этот случай закрыт (миграция 021: команда
помнит процесс, который её забрал, и при регистрации нового процесса команды прежнего
закрываются сразу), но при параллелизме 1 любая одна застрявшая команда по-прежнему
останавливает работу по всем ста десяти базам.

### A5. Актуальные данные приходят самой командой (P1, нужна работа агента + наша)

**Факт.** После каждого изменения сервис ставит ВТОРУЮ команду — чтение того же содержимого
(`agentRouter.ts:392`, `REFRESH_AFTER`), а панель на всякий случай перечитывает всё дважды с
паузой 5 с (`progress.ts:165`). Изменение одного пользователя стоит двух входов в базу; пакет
по 110 базам — 220 команд вместо 110.

**Что сделать.** Изменяющая команда возвращает новое состояние в своём же ответе (`state.users`
/ `state.extensions`), прочитанное тем же открытым COM-соединением; сервис применяет его сразу
и не ставит чтение; панель кладёт полученное в кэш вместо повторного запроса.

**Приёмка.** Создание пользователя: в журнале нет `IB_LIST_USERS` следом, таблица обновляется
без пятисекундной паузы; пакет по 10 базам — 10 команд, а не 20; агент без способности
`ib.echo` работает как раньше.

**Спецификация.** [TASK_FRESH_STATE_AFTER_COMMAND.md](TASK_FRESH_STATE_AFTER_COMMAND.md) — там
же следующим шагом живое обновление через уже существующий SSE-канал (нужен `LISTEN/NOTIFY`,
связано с **D2**).

**Состояние 12.09 (вечер).** Сервис и агент сделаны, тесты зелёные; на стенде не прогонялось —
нужен перезапуск сервиса и сборка агента. Панель — отдельно, её раздел в спецификации переписан
под то, как получилось.

## Волна 4. Новая функциональность

### F1. Проверить все базы одной кнопкой (P1, нужна работа агента)

**Факт.** Проверка «есть ли база в СУБД» существует только как CLI `bpapi-agent bases check`
на сервере; в панели фантом виден лишь после того, как по нему промахнулись командой.

**Что сделать.** Команда `CLUSTER_CHECK_BASES` (вопрос к СУБД, не вход в базу) и кнопка
«Проверить все базы» в списке. Фоновая проверка агентом уже присылает `dbMissing` в срезе —
эта команда даёт ответ по требованию, а не «когда дойдут руки».

### F2. Обслуживание по расписанию (P2, наша)

**Факт.** Выгрузка и проверка баз запускаются только руками. В сервисе 1С периодические
задачи есть (очистка файлов, ретенция), планировщика для обслуживания — нет.

**Что сделать.** Расписание на группу баз (ночная выгрузка, проверка `ibcmd`), с записью
результатов в те же «Задания» и в журнал сообщений.

**Цена бездействия.** Копия базы существует ровно тогда, когда о ней кто-то вспомнил.

### F3. Экран состояния очереди (P2, наша)

**Факт.** Данные есть все — состояния команд, занятость агентов, длительности; экрана нет.

**Что сделать.** На вкладке «Прогресс»: сколько команд ждёт, средняя длительность по типам,
кто держит очередь. Это же даёт материал для оценки времени из A2.

### F4. Поиск и отбор в «Технических сообщениях» (P2, наша)

**Факт.** Есть группировка (объект / дата / без группировки), поиска нет. Предел журнала —
200 записей.

**Что сделать.** Строка поиска по тексту и источнику плюс отбор по типу (ошибки / всё).

### F5. Разделить права на операции 1С (P2, наша)

**Факт.** `onecRouter` проверяет одно: `isSuperAdmin || canOnecAdmin`. Чтение сеансов и
удаление регистрации базы требуют одного и того же права.

**Что сделать.** Два права: чтение (списки, сеансы, состояние) и разрушающее (удаление
регистрации, снятие публикации, правка пользователей ИБ, выгрузка/загрузка).

### F6. Довести Kaspi и ЭСФ до реального API (P3, наша + внешние документы)

**Факт.** `kaspiProvider.js` — пять `TODO(kaspi-docs)`: авторизация, QR, статус, фискализация,
возврат; по умолчанию работает stub с выдуманными данными, вебхук не проверяет подпись.
В ЭСФ `invoiceMapper` подставляет категорию товара умолчанием.

**Что сделать.** Получить документацию и ключи, заменить заглушки, добавить проверку подписи
вебхука. До этого момента фискальная часть существует только на бумаге — так и писать в
интерфейсе.
