# Промпт для сессии разработки bpapi_agent (внутрибазовые операции + кодировка)

Копия того, что отдаётся в другую сессию. Здесь — на случай, если понадобится повторить.
Полный контракт: `docs/ONEC_AGENT_CLUSTER_CONTRACT.md` (эта машина, Linux; та сессия его не видит).

---

В bpapi_agent нужно закрыть три вещи. Серверная сторона (AI Service) уже готова и ждёт:
команды заведены, гейт по способностям работает, панель в aleppo.kz построена.

## 1. Кодировка вывода rac — казахские буквы теряются

Имена баз приходят как `Жа?аш М?ратхан ИП`, `ИП ?БД?Л?`. Проверка байтов в реестре:
`d096 d0b0 3f` — `3f` это ASCII `?`, буква потеряна ДО отправки. Русские целы, пропали
только казахские (ә ғ қ ң ө ұ ү һ і) — след транскодирования через CP1251: русский там
есть, казахского нет, непредставимое заменяется на `?`. Преобразование одностороннее.

Чинить на границе с rac: вывод нельзя декодировать как CP1251 или CP866 (в обеих казахских
букв нет вовсе). Запускать через `cmd /c chcp 65001 >nul && rac.exe …` и читать stdout
БАЙТАМИ с явным UTF-8, не полагаясь на кодировку по умолчанию. Если rac игнорирует chcp —
имена баз лежат в `1CV8Clst.lst` в каталоге данных сервера, он в UTF-8.

После исправления: один прогон «Обновить из кластера» перезапишет имена. Сервис защищён —
целое имя не затирается битым, так что старый агент реестр уже не испортит.

## 2. Способность ib.admin

Сейчас агент регистрируется с `capabilities: ["cluster.admin", …]`. Все команды внутри баз
отклоняются гейтом ДО постановки в очередь: `CAPABILITY_MISSING`.

`POST /agent/v1/register` должен слать:

```jsonc
{
  "agentId": "…", "version": "…", "os": "…",
  "role": "admin",
  "capabilities": ["cluster.admin", "ib.admin"],
  "server": { "name": "Сервер 1С (офис)", "rasHost": "localhost", "rasPort": 1545 }
}
```

`server.name` обязан совпадать с бизнес-агентом того же сервера — по нему базы связываются
с агентами. Разные имена дадут два «сервера» в реестре и команду, которой некому исполнить.

## 3. Шесть внутрибазовых команд

Транспорт прежний: `GET /agent/v1/commands` → `POST /agent/v1/commands/{id}/result`.
Требуют входа в базу (COM или расширение) под служебным администратором ИБ
(`BPAPI_IB_USER`/`BPAPI_IB_PWD`).

| Команда | Payload | Результат при SUCCESS |
|---|---|---|
| `IB_LIST_USERS` | `{baseKey}` | `{items:[{name, fullName?, disabled?, roles?[]}]}` |
| `IB_CREATE_USER` | `{baseKey, name, fullName?, password?, roles?[], osUser?, showInList?}` | `{ok:true}` |
| `IB_DELETE_USER` | `{baseKey, name}` | `{ok:true}` |
| `IB_LIST_EXTENSIONS` | `{baseKey}` | `{items:[{name, version?, purpose?, safeMode?}]}` |
| `IB_INSTALL_EXTENSION` | `{baseKey, name, contentBase64, safeMode?}` | `{ok:true}` |
| `IB_DELETE_EXTENSION` | `{baseKey, name}` | `{ok:true}` |
| `IB_UNPUBLISH` | `{baseKey, alias?, webServer?}` | `{ok:true}` |

Тело результата:

```jsonc
{ "commandId": "…", "agentId": "<uuid>", "status": "SUCCESS",
  "result": { }, "error": {"code":"…","message":"…"} }
```

Что обязательно соблюсти:

- **Списки полные.** Результат `IB_LIST_*` замещает кэш базы целиком: чего нет в ответе,
  сервис удаляет. Частичный список молча «потеряет» пользователей или расширения.
- **Идемпотентность.** Команды живут 900 с, панель показывает TIMEOUT через 120 и НЕ снимает
  их с очереди — пользователь повторит операцию, которая уже идёт. Повторное создание
  существующего пользователя и повторное удаление отсутствующего = `SUCCESS`, не ошибка.
- **`contentBase64`** — содержимое `.cfe` без префикса `data:`. Файл приходит телом команды,
  в сеть за ним ходить не нужно.
- **`IB_UNPUBLISH`** — снятие публикации (`webinst -delete` или эквивалент), идемпотентно:
  снять публикацию с неопубликованной базы = `SUCCESS`. Панель уже шлёт эту команду
  группой по отмеченным базам; агенту нужно объявить её в способностях, иначе задание
  честно отметит все базы как пропущенные.
- **Публикация не нужна внутрибазовым командам** — они идут по COM к серверу 1С, а не по
  HTTP. Неопубликованная база остаётся полноценной целью.
- **Пароль не логировать** — ни в лог агента, ни в текст ошибки.
- **Параллелизм** через `max_parallel`: каждое COM-соединение занимает сеанс и лицензию 1С.
  Групповая операция — это N обычных команд, по одной на базу; протокол тот же.


### Работа с расширениями через COM — точные имена

С поля пришла ошибка установки расширения:

```
IB_ERROR: Exception calling "InvokeMember" with "5" argument(s):
"Member not found. (Exception from HRESULT: 0x80020003 (DISP_E_MEMBERNOTFOUND))"
```

`DISP_E_MEMBERNOTFOUND` значит: у COM-объекта нет ТОГО ЧЛЕНА, который вызвали. Три причины,
все на стороне агента:

1. **Имена приходят на языке конфигурации.** COM-соединение отдаёт члены так, как они
   называются в конфигурации: у русскоязычной 1С это `РасширенияКонфигурации`,
   `Создать`, `Записать`, `Получить`, `Удалить`, а НЕ `ConfigurationExtensions.Create`.
   Английские имена на русской платформе не находятся — и наоборот.
2. **`РасширенияКонфигурации` — свойство СОЕДИНЕНИЯ,** а не глобального объекта агента:
   обращаться нужно к `$conn.РасширенияКонфигурации`, полученному от
   `V83.COMConnector.Connect(...)`.
3. **Платформа старше 8.3.11** — в ней скриптового API расширений нет вовсе; тогда
   единственный путь — `1cv8 DESIGNER /LoadCfg`-подобные пакетные режимы, и команду надо
   честно возвращать с `ERROR`, а не молча.

Ожидаемая последовательность (русскоязычная конфигурация, платформа ≥ 8.3.11):

```powershell
$conn = $connector.Connect("Srvr=""host"";Ref=""$baseKey"";Usr=""$user"";Pwd=""$pwd"";")

# Список: РасширенияКонфигурации.Получить() → массив расширений
$list = $conn.РасширенияКонфигурации.Получить()
foreach ($e in $list) { $e.Имя; $e.Синоним; $e.Назначение; $e.БезопасныйРежим }

# Установка: создать → записать двоичные данные .cfe
$ext = $conn.РасширенияКонфигурации.Создать()
$ext.БезопасныйРежим = $safeMode
$data = $conn.NewObject("BinaryData", $cfePath)   # ДвоичныеДанные из файла
$ext.Записать($data)

# Удаление: найти по Имени и вызвать Удалить()
```

Та же природа и у ошибки `Method 'System.Object[].Find' not found`: `ПолучитьПользователей()`
отдаёт через COM массив .NET, а не коллекцию 1С — искать в нём `Найти` бесполезно, нужен
менеджер `ПользователиИнформационнойБазы.НайтиПоИмени(Имя)`. Разбор с примером — в
`docs/PROMPT_AGENT_MAINTENANCE.md`, раздел `IB_UPDATE_USER`.

Проверять надо не «есть ли метод», а **что вернул `Получить()`**: если `IB_LIST_EXTENSIONS`
уже работает, значит имя `РасширенияКонфигурации` подобрано верно и ломается именно
`Создать`/`Записать` — сравните регистр и язык этих двух имён с рабочим.

Панель теперь сама приписывает к таким ошибкам расшифровку («у COM-объекта нет вызванного
метода… исправляется в агенте»), но исходный текст 1С сохраняется целиком — он остаётся
единственным доказательством.

Коды ошибок, которые уже понимает панель: `RAC_UNAVAILABLE`, `RAC_TIMEOUT`,
`CLUSTER_NOT_FOUND`, `RAC_ERROR`. Для внутрибазовых заводите свои, текст — по-русски и по
делу: панель показывает `error.message` пользователю как есть.

## 4. `payload.auth` — учётная запись КОНКРЕТНОЙ базы (задача от 2026-09-10)

**Что не так сейчас.** У агента один служебный администратор баз на всех. К части
клиентских баз он не подходит: их заводили до нас, там такого пользователя нет либо у него
другой пароль. Сейчас это выглядит как «вход в базу не выполнен: проверьте служебного
администратора базы», и лечится только правкой конфига агента — то есть ради одной базы
трогают все.

**Что уже сделано на стороне сервиса.** В карточке базы появилась вкладка «Доступ к базе»:
там задают пару «пользователь + пароль» ДЛЯ ЭТОЙ БАЗЫ. Сервис хранит пароль зашифрованным и
подставляет пару в команду в момент выдачи:

```jsonc
{ "id": "cmd_…", "baseKey": "bustravel_ip", "type": "IB_LIST_USERS",
  "payload": { "baseKey": "bustravel_ip", "auth": { "user": "support", "password": "…" } } }
```

**Что сделать агенту.**

1. **Читать `payload.auth`** во ВСЕХ внутрибазовых командах (`IB_*`), где происходит вход в
   базу: COM, ibcmd, конфигуратор — везде, где сейчас подставляется служебный администратор.
2. **Порядок попыток строго такой:**
   1. свой служебный администратор из конфига;
   2. если он **не прошёл аутентификацию** — повтор с `payload.auth`;
   3. если и он не прошёл — ошибка, в тексте назвать ОБЕ попытки: по какой учётной записи
      какой отказ. Сейчас по тексту невозможно понять, чьи учётные данные не подошли.
   Повторять по `auth` **только на отказе аутентификации**. «База занята», «нет лицензии»,
   «сервер недоступен» — не тот случай: второй вход туда же ничего не изменит, а сеанс
   займёт.
3. **Объявить способность `ib.auth`** в списке capabilities при регистрации. Панель на неё
   смотрит: пока её нет, вкладка «Доступ к базе» показывает предупреждение «агент этой
   сборки учётную запись игнорирует», а в тексте отказа сервис пишет, что отказ получен по
   администратору из настроек агента. Без этого признака человек, задавший пароль и
   получивший тот же отказ, не отличает «пароль неверен» от «пароль не применили».
4. **Пароль не логировать** — ни в лог агента, ни в текст ошибки. Общее правило контракта.

**Как проверить.** В карточке базы, к которой служебный администратор НЕ подходит, задать
её собственную учётную запись → «Проверить пользователей» → список читается. Предупреждение
про `ib.auth` во вкладке «Доступ к базе» должно исчезнуть.

Полное описание — `docs/ONEC_AGENT_CLUSTER_CONTRACT.md`, раздел «`payload.auth`».

## Как проверить, что готово

1. В логе агента при старте — `role=admin`, в способностях `ib.admin`.
2. В aleppo.kz → «Администрирование 1С» → «Расширения»: жёлтое предупреждение
   «нет способности ib.admin» должно исчезнуть.
3. Отметить 2–3 базы → «Проверить расширения» → вкладка «Задания» показывает результат по
   каждой базе; в «Базах» вместо «не проверялось» появляются числа.
4. Имена баз с казахскими буквами отображаются целиком, без `?`.
