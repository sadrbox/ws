# План: задачи и заметки по организации в чате 1С

22.09.2026. Общий для трёх сессий: расширение `buhprof_api` (РА), AI-сервис `W:\app\ai` (СВ), бэкенд ERP
`W:\app\backend` (БЭ). Продолжение [PLAN_1C_CHAT_2026-09-19.md](PLAN_1C_CHAT_2026-09-19.md) и
[CONTRACT_1C_CHAT_2026-09-19.md](CONTRACT_1C_CHAT_2026-09-19.md).

## Суть

Бухгалтер, работающий в 1С, видит в форме чата задачи и заметки по организации — те самые, что ведутся в панели
BuhProf AI, — и может создавать их, править и закрывать, не выходя из 1С. Модель видит их как контекст диалога.

**Хранилище одно — ERP.** Задачи (`todos`) и заметки (`notes`) живут в базе ERP; у AI-сервиса своего списка задач
нет и не будет, иначе появится второй список, расходящийся с панелью. AI-сервис — посредник: он знает базу 1С по
токену, организацию по БИН, и ходит в ERP служебным ключом.

```
Форма BPAPI_Чат (1С)  ──X-Base-Token──►  AI-сервис  ──X-Api-Key──►  бэкенд ERP  ──►  todos / notes
       ▲                                     │                            
       └──── задачи, заметки, подтверждения ──┘                            
```

Бизнес-агент в этом канале не участвует: задачи лежат не в 1С.

## Решения

1. **Авторство (Д1).** Пользователь 1С записывается в ERP как реальный пользователь: ищем по имени, при
   отсутствии создаём — тем же приёмом, что `POST /pipe` (`backend/services/pipeActor.js`, `utils/pipeAuth.js`).
   Пользователь создаётся с `password = null`: войти под ним через форму нельзя, он существует, чтобы у задачи и
   заметки был настоящий автор, видимый в панели и в истории действий.
2. **Организация (Д2).** Организация ERP определяется по БИН организации 1С, выбранной в ходе диалога. Нет
   в ERP — создаётся по БИН (как в `resolveOrganization`). Без БИН работа с задачами недоступна: по нему
   определяется адресат, выдумывать его нельзя.
3. **Организация по умолчанию.** Задаёт администратор в форме «Подключение к BuhProf AI»; пользователь может
   переключиться в форме чата на любую доступную ему организацию, выбор запоминается лично ему.
4. **Заметки организации** хранятся как `notes` с `entityType = "organizations"` и `entityUuid` = uuid
   организации ERP. Это тот же механизм, которым панель ведёт заметки к любой записи.
5. **Изменяющие действия — с подтверждением.** Создание задачи, её изменение и закрытие, создание заметки
   проходят карточку подтверждения, как `create_sale`. Чтение — без подтверждения.
6. **Права остаются за 1С.** Список организаций в форме строится с `РАЗРЕШЕННЫЕ`; чужую организацию выбрать
   нельзя. Сервис дополнительно проверяет, что БИН принадлежит этой базе.

## Контракт

### Бэкенд ERP: служебный канал для AI-сервиса

Префикс `/bpai`, вне `/api/v1` (как `/pipe` и `/api1/esf-license`): у AI-сервиса нет JWT пользователя ERP.
Аутентификация — `X-Api-Key: BPAI_API_KEY`. Каждый запрос называет организацию БИНом и пользователя именем;
обоих резолвит сервер.

| Маршрут | Назначение |
|---|---|
| `GET /bpai/tasks?bin=&state=open\|all&limit=` | задачи организации, новые сверху |
| `POST /bpai/tasks` | создать: `{bin, user:{name}, name, description?, deadline?}` |
| `PATCH /bpai/tasks/:uuid` | изменить: `{bin, user:{name}, name?, description?, deadline?, status?}` |
| `GET /bpai/notes?bin=&limit=` | заметки организации |
| `POST /bpai/notes` | создать: `{bin, user:{name}, body}` |
| `GET /bpai/task-statuses` | справочник статусов (код, имя, признак завершающего) |

Конверт ответа — как в ERP: `{success: true, items|item}` / `{success: false, message}`.

### AI-сервис: маршруты для формы 1С

Внутри `/v1/onec-chat`, аутентификация прежняя (`X-Base-Token` + `X-1C-User-Id`).

| Маршрут | Назначение |
|---|---|
| `GET /v1/onec-chat/tasks?bin=&state=` | задачи организации |
| `POST /v1/onec-chat/tasks` | создать |
| `PATCH /v1/onec-chat/tasks/:uuid` | изменить или закрыть |
| `GET /v1/onec-chat/notes?bin=` | заметки организации |
| `POST /v1/onec-chat/notes` | создать |

БИН обязан принадлежать одной из организаций этой базы (список известен с регистрации базы).

### Инструменты модели

Новый вид: **серверный инструмент** — исполняется самим сервисом, а не агентом и не формой. В реестре у него нет
`commandType`; вместо него — обработчик, вызывающий ERP.

| Инструмент | Класс | Что делает |
|---|---|---|
| `list_tasks` | READ | задачи организации хода |
| `create_task` | WRITE | создать задачу |
| `update_task` | WRITE | изменить срок, текст или статус |
| `complete_task` | WRITE | закрыть задачу |
| `list_notes` | READ | заметки организации хода |
| `add_note` | WRITE | создать заметку |

Контекст диалога: в промпт хода подмешивается короткая сводка — открытые задачи со сроками и последние заметки
организации, не более десяти строк каждого вида.

## Этапы и задачи

### Этап 1. Бэкенд ERP

- **БЭ1.** `utils/bpaiAuth.js`: проверка `X-Api-Key` по `BPAI_API_KEY`, сравнение без утечки времени, отказы
  с причиной в журнал. Отдельный ключ от `PIPE_API_KEY`.
- **БЭ2.** `services/bpaiActor.js`: резолв организации по БИН и пользователя по имени с созданием при
  отсутствии; повторно использует `pipeActor.js`, а не копирует его.
- **БЭ3.** `api/router/bpai.js`: маршруты задач и заметок по контракту выше, org-изоляция, мягкое удаление не
  трогаем.
- **БЭ4.** Атрибуция источника: в задаче и заметке видно, что запись пришла из 1С (через `sourceType`/
  `sourceLabel` у задачи и текст автора у заметки).
- **БЭ5.** Уведомление исполнителя — существующей шиной (`notifyTaskAssigned`).

### Этап 2. AI-сервис

- **СВ1.** `src/erp/tasks.ts`: клиент к `/bpai`, адрес и ключ из конфига (`ERP_API_URL`, `ERP_API_KEY`),
  таймаут, разбор отказов.
- **СВ2.** Организации базы: хранить список БИНов базы (приходит при регистрации) и проверять, что БИН хода
  принадлежит базе.
- **СВ3.** Маршруты `/v1/onec-chat/tasks|notes`.
- **СВ4.** Серверные инструменты в реестре и их исполнение в `ChatWorkflow`.
- **СВ5.** Сводка задач и заметок в контексте хода.
- **СВ6.** Аудит (`channel: "1c"`) и ограничение частоты изменяющих вызовов.

### Этап 3. Расширение buhprof_api

- **РА1.** Константа «организация по умолчанию» и её выбор в форме настроек.
- **РА2.** Переключение организации в форме чата списком доступных; выбор запоминается пользователю.
- **РА3.** Панель «Задачи и заметки» в форме чата: список по организации, обновление при переключении и после
  каждого хода.
- **РА4.** Действия: создать задачу, создать заметку, закрыть задачу — с подтверждением.
- **РА5.** Поведение без связи: панель сообщает, что сведения не получены, чат продолжает работать.
- **РА6.** Права роли `BPAPI_ЧатПользователь`.
- **РА7.** Версия 1.5.0, CHANGELOG, копия в `releases/`.

### Этап 4. Панель

- **ПН1.** В карточке задачи и заметки видно, что запись создана из 1С и из какой базы.

### Этап 5. Проверка

- **П1.** Сквозная проверка на `Dev_01`: задача из панели видна в 1С, заметка из 1С видна в панели, закрытие из
  чата, переключение организации меняет список.
- **П2.** Проверка прав: пользователь с урезанными правами не видит чужих организаций.
- **П3.** Выпуск обеих сторон.

## Порядок

Этап 1 → этап 2 → этап 3. РА1, РА2 и РА6 не зависят от серверной части и могут идти параллельно. Минимальный
полезный результат — чтение: РА1–РА3 плюс БЭ1–БЭ3 и СВ1–СВ3.
