# Контракт кластерного модуля админ-агента (bpapi_agent, role = admin)

Версия 1.0 · 2026-09-04 · извлечено из работающего кода `ai/`, не из планов

Что должен реализовать модуль `cluster` в `bpapi_agent`, чтобы кнопка **«Администрирование 1С» →
«Базы» → «Обновить из кластера»** в aleppo.kz наполнила реестр баз.

Сторона сервиса готова целиком: `ai/src/commands/admin.ts` (список команд), `ai/src/http/onecRouter.ts`
(HTTP панели), `ai/src/bases/service.ts` (реестр), миграция `004_bases.sql`, панель
`frontend/src/models/OneCAdmin`. Ничего из этого дописывать не требуется.

## 1. Транспорт: как команда доходит до модуля

Ничего нового — тот же long-poll, что у бизнес-агента:

```
GET  /agent/v1/commands                 → { commands: [ { id, requestId?, type, payload } ] }
POST /agent/v1/commands/{id}/result     ← результат
```

Тело результата (`resultSchema`, `ai/src/http/agentRouter.ts:61`):

```jsonc
{
  "commandId": "…",            // = id команды
  "agentId": "<uuid агента>",  // обязателен, сверяется с токеном
  "status": "SUCCESS",         // или "ERROR"
  "result": { },               // при SUCCESS — см. §3
  "error":  { "code": "…", "message": "…", "details": {} },  // при ERROR
  "startedAt": "…", "finishedAt": "…"   // необязательно
}
```

⚠ **Сроки (сверено 14.09, аудит С2/С13).** Сервис ждёт ответа на запрос панели
`ONEC_COMMAND_TIMEOUT_SECS` (20 с); не дождался — отвечает 202 с номером команды, и панель
опрашивает `GET /v1/onec/commands/:id`, **не снимая команду с очереди** (чат ждёт
`CHAT_COMMAND_TIMEOUT_SECS`, 120 с). Срок выполнения — 900 с, у загрузки, выгрузки, проверки и
обновления базы — 15 000 с; он отсчитывается **от выдачи агенту**. Ожидание очереди до выдачи —
отдельный предел: 900 с у одиночной команды, 12 ч у группового задания; не дождавшаяся команда
закрывается кодом `COMMAND_QUEUE_TIMEOUT` («агент был занят»), а не «агент не на связи».
Команда, скорее всего, всё же выполнится после 202 — модуль обязан быть идемпотентным по
`requestId`.

## 2. Регистрация: без неё команды не придут

`POST /agent/v1/register` должен прислать роль, сервер и способности:

```jsonc
{
  "agentId": "…", "version": "…", "os": "…",
  "role": "admin",
  "capabilities": ["cluster.admin"],
  "server": { "name": "Сервер 1С (офис)", "rasHost": "localhost", "rasPort": 1545 }
}
```

- **`role: "admin"`** и **`capabilities: ["cluster.admin"]`** — гейт в `agentCanRun()`
  (`admin.ts`). Без них сервис откажет сразу: `CAPABILITY_MISSING`, «Агент не умеет …».
- **`server.name`** обязан совпадать с именем у бизнес-агента того же сервера — по нему базы
  связываются с агентами. Разные имена дадут два «сервера» в реестре.

## 3. Команды: что приходит и что вернуть

Payload валидируется схемами Zod **строго** (`.strict()`) — лишних полей быть не может.

### `CLUSTER_LIST_INFOBASES` — READ, база не нужна

Payload: `{}`. Это команда кнопки «Обновить из кластера».

```jsonc
{ "items": [
  { "key": "buh_alma",           // ИМЯ ИБ В КЛАСТЕРЕ — им она адресуется во всех остальных командах
    "name": "ТОО Алма (бухгалтерия)",
    "status": "OK",              // необязательно; при отсутствии останется прежний
    "onecVersion": "8.3.25.1257",// необязательно
    "sessionsCount": 3,          // необязательно
    "published": true,           // необязательно: есть ли публикация на веб-сервере
    "publishUrl": "http://localhost/buh_alma" }
] }
```

Как это применяется (`bases.sync(serverId, items, { complete: true, authoritative: true })`):

- `key` — единственное обязательное поле, ключ upsert'а `(server_id, key)`;
- **`null`/отсутствие поля означает «не знаю», а не «пусто»**: прежнее значение сохраняется
  (`COALESCE`). Не присылайте `null`, чтобы «очистить» — очистить так нельзя;
- `extVersion` присылает **бизнес**-агент, админ-агент его не знает и слать не должен;
- срез считается полным: базы, которых нет в `items`, получают `status = 'MISSING'`.
  Поэтому частичный список **недопустим** — либо все базы кластера, либо `ERROR`;
- `published` — **три состояния**: `true` (публикация есть), `false` (точно нет),
  отсутствие поля (не проверяли). Не подставляйте `false` вместо «не проверял»: панель
  по `false` предлагает публиковать, и ложное «нет» отправит администратора публиковать
  уже опубликованные базы. Признак берётся из конфигурации веб-сервера (наличие
  каталога публикации и записи в `default.vrd`/`web.config`), а не из кластера.

После успешного `IB_PUBLISH` сервис сам ставит базе `published = true` и `publishUrl`
из ответа команды — ждать ближайшего среза не требуется.

> **`X-Agent-Instance` обязателен.** Каждый ЗАПУЩЕННЫЙ ПРОЦЕСС агента шлёт этот заголовок на
> любом запросе: значение произвольное, но стабильное в пределах жизни процесса и разное у
> разных процессов (`"<host>#<pid>"` подойдёт). Сервис пускает работать ТОЛЬКО ОДИН экземпляр
> на токен; второй получает **409 `AGENT_INSTANCE_CONFLICT`** и не выполняет ни одной команды.
> Владение — аренда: молчащий дольше `AGENT_OFFLINE_AFTER_SECS` владелец уступает место сам,
> поэтому перезапуск службы и переезд на другую машину работают без вмешательства; снять
> владение вручную можно в панели («Агенты» → «Освободить экземпляр»).
>
> Агент со своей стороны обязан не запускать вторую копию на машине (именованный mutex под
> Windows) и, получив 409, **остановиться с внятным сообщением в лог, а не ретраить молча**.
> Это защита от ошибки, а не от злого умысла: идентификатор экземпляра агент называет сам.
> От умысла защищает один токен на машину и его ротация.

> **`details` в ошибке.** Кладите в `error.details` машину и процесс: `{host, pid, build}`.
> Сервис показывает это в отчёте («Ответил агент на машине X57, pid 3316») и по этим же
> данным считает экземпляры — пока не реализован `X-Agent-Instance`, это единственный способ
> увидеть, что под одним токеном работают два процесса.

> **Аутентификация rac.** Если в кластере заведён администратор, каждый вызов `rac` обязан
> представляться `--cluster-user`/`--cluster-pwd` (операции уровня центрального сервера —
> `--agent-user`/`--agent-pwd`). Иначе любая READ-команда возвращает «Администратор кластера
> не аутентифицирован». Учётные данные хранит агент; сервис их не передаёт.

### `CLUSTER_LIST_PUBLICATIONS` — READ, база не нужна

Payload: `{}`. Читает веб-сервер (каталоги публикаций + `default.vrd`/`web.config`), а не
кластер, поэтому базу не адресует: спрашиваем сразу все.

```jsonc
{ "items": [ { "key": "buh_alma",              // ИМЯ БАЗЫ В КЛАСТЕРЕ — то же, что в срезе баз
               "name": "Бухгалтерия Алматы",   // наименование базы, только для чтения человеком
               "published": true,
               "url": "http://localhost/buh_alma" } ],
  "complete": true,                            // просмотрены ВСЕ веб-серверы машины
  "source": "iis",                             // "iis" | "scan" — чем собран срез
  "lookedIn": ["C:\\inetpub\\wwwroot\\db"] }   // где именно искали
```

- `key` — **имя базы в кластере**, которым она адресуется во всех остальных командах.
  Наименование сюда не кладётся никогда: сопоставить такую запись с реестром нечем. С
  2026-09-11 агент отдаёт наименование отдельным полем `name`;
- `complete: true` — обещание, что список полный. Только тогда сервис помечает
  `published = false` базы, которых в списке нет. Без этого флага (или при `false`) он лишь
  отмечает найденное: агент, видящий один веб-сервер из двух, иначе объявил бы
  неопубликованными сотню работающих баз;
- **срез, в котором нет ни одной публикации, полным не объявляется никогда** (`complete:
  false`): веб-сервер без публикаций и чтение не того каталога снаружи неотличимы;
- пустой список не применяется вовсе — по той же причине, что и пустой срез баз;
- `url` — адрес публикации; при снятии публикации сервис его стирает;
- `source` и `lookedIn` — диагностика для человека: чем собран срез и какие каталоги
  просмотрены. Показывать их стоит рядом с пустым срезом — это единственный способ отличить
  «не опубликовано» от «искали не там», не заходя на сервер.

Эта команда закрывает пробел, из-за которого признак публикации у ста баз оставался
«не проверялся» до тех пор, пока публикацию не сделают из панели.

### `CLUSTER_LIST_SESSIONS` / `CLUSTER_LIST_CONNECTIONS` — READ

Payload: `{ "baseKey"?: "buh_alma" }` — без него весь кластер, с ним одна база.

```jsonc
{ "items": [ { "session": "12", "user": "Иванов", "host": "WS-14", "app-id": "1CV8C", "started-at": "…" } ] }
```

Строка — **словарь строк**, набор ключей задаёт `rac` (панель типизирует его как
`Record<string, string>` и показывает как есть). Отдавайте поля `rac` без переименования.

### `CLUSTER_INFOBASE_INFO` — READ, база обязательна

Payload: `{ "baseKey": "buh_alma" }`. Результат — свободный объект со сведениями `rac`.

### `CLUSTER_LIST_LOCKS` / `CLUSTER_LIST_PROCESSES` / `CLUSTER_LIST_LICENSES` — READ

Payload: `{"baseKey"?: "…"}` для блокировок (без него — весь кластер), `{}` для остальных.
Результат — `{items: [ … ]}`, строки словарями строк, ключи как отдаёт `rac` (панель
показывает их как есть, переименовывать не нужно).

Зачем именно эти три: «база висит» почти всегда означает блокировку, а отказы при
одновременных подключениях упираются в лицензии — без этих списков и то и другое
диагностируется вслепую.

### `CLUSTER_DISCONNECT` — **CRITICAL**

Payload: `{"connectionId": "<uuid соединения>", "baseKey"?: "…"}` → `{ok: true}`.
Как и у сеанса, идентификатор — **UUID**, а не номер.

### `CLUSTER_TERMINATE_SESSION` — **CRITICAL**

Payload: `{ "sessionId": "<uuid сеанса>", "baseKey"?: "buh_alma" }`.

⚠ `sessionId` — это **UUID** сеанса (поле `session` в строке `rac`), а НЕ его номер
(`sessionId` в той же строке). Проверено зондом: на UUID `rac` отвечает «Сеанс с указанным
идентификатором не найден», на номер — «Ошибка разбора параметра: session».
`baseKey` — только для маршрутизации и аудита.
Результат: `{ "ok": true }`. Снятие уже снятого сеанса — тоже `SUCCESS` (идемпотентность).

### `CLUSTER_SET_SESSIONS_LOCK` — **CRITICAL**, база обязательна

```jsonc
{ "baseKey": "buh_alma", "enabled": true,
  "message": "Обслуживание до 19:00",   // необязательно, ≤500 символов
  "from": "…", "to": "…",               // окно блокировки, ≤40 символов
  "permissionCode": "…" }               // код входа в заблокированную базу
```

Результат: `{ "ok": true, "baseKey": "…", "enabled": true, "state": { "lock": {…} } }` — блокировка,
прочитанная `rac infobase info` ПОСЛЕ изменения (форма — в разделе «Эхо состояния»). Если
блокировку включили, а вход сейчас не закрыт (`state.lock.active: false`: в кластере осталось окно
прошлой блокировки), в ответе ещё и `warning` с этим окном. Единственная кластерная команда, которой
нужен служебный администратор ИБ (`BPAPI_IB_USER`/`BPAPI_IB_PWD`), — остальным хватает
администратора кластера.

**Включение сбрасывает незаданное** (агент после `2026-09-14 23:16`): окно — нулевой датой 1С,
сообщение и код разрешения — пустыми; прежде они оставались от прошлой блокировки. Как `rac`
принимает пустые значения, на кластере ещё не проверено, поэтому по ступеням: всё → только окно →
как прежде. В ответе `reset: "all" | "dates" | "none"` и `note`, если сброшено не всё; действует
ли итог — `state.lock.active`. Выключение — только `--sessions-deny=off`.

Загрузка и обновление конфигурации (`IB_RESTORE`, `IB_APPLY_UPDATE` с `lockSessions`) после
установки своей блокировки проверяют, что она **действует**. Не действует — ставят окно «сейчас —
сутки вперёд»; не помогло и это — снимают блокировку и отказывают кодом `SESSIONS_LOCK_NOT_ACTIVE`,
операцию не начиная (агент с `2026-09-14`, после сборки `22:38`).

## 3.1. Кодировка вывода `rac` — казахские буквы

**Симптом.** Имена баз приходят как `Жа?аш М?ратхан ИП`, `Айбек Абай Жолдасбек?лы ИП`.
Проверка байтов в реестре: `d096 d0b0 3f` — `3f` это обычный ASCII `?`, то есть буква
потеряна ДО отправки, а не при показе. Русские буквы целы, пропали только казахские
(ә ғ қ ң ө ұ ү һ і) — характерный след транскодирования через **CP1251**: русский там
есть, казахского нет, и всё непредставимое заменяется на `?`. Восстановить нечем:
преобразование одностороннее.

**Где чинить.** Только в агенте, на границе с `rac`. Вывод утилиты нельзя декодировать
как CP1251 или CP866 — в обеих кодировках казахских букв нет вовсе.

Основной способ (не проверен на живом кластере — подтвердите): запускать `rac` с
консолью в UTF-8 и читать поток как UTF-8.

```cmd
cmd /c chcp 65001 >nul && "C:\Program Files\1cv8\8.3.25.1257\bin\rac.exe" infobase summary list …
```

В коде агента: читать stdout **байтами** и декодировать UTF-8 явно, не полагаясь на
кодировку по умолчанию (для .NET — `Console.OutputEncoding`/`StandardOutputEncoding =
new UTF8Encoding(false)`, для Node — `spawn` без `encoding` и затем `Buffer.toString("utf8")`).

Запасной путь, если `rac` игнорирует `chcp`: имена баз лежат в файле кластера
`1CV8Clst.lst` в каталоге данных сервера — он в UTF-8, и `rac` для получения имён тогда
не нужен вовсе.

**После исправления** нужен один прогон «Обновить из кластера»: имена в реестре
перезапишутся правильными. Сервис при этом защищён — целое имя не затирается битым
(`bases.sync`: имя с `?` принимается, только когда своего ещё нет), так что случайный
запуск старого агента реестр больше не испортит.

## 3.2. Внутрибазовые команды: пользователи и расширения

Другой транспорт и другая способность: эти команды требуют **входа в базу** (COM-соединение
или расширение), поэтому агент обязан объявить `capabilities: ["cluster.admin", "ib.admin"]`.
Без `ib.admin` сервис откажет сразу, не ставя команду в очередь.

Каждой нужен служебный администратор ИБ в целевой базе (`BPAPI_IB_USER`/`BPAPI_IB_PWD`).

| Команда | Payload | Результат |
|---|---|---|
| `IB_LIST_USERS` | `{baseKey}` | `{items:[{name, fullName?, disabled?, roles?[]}]}` |
| `IB_CREATE_USER` | `{baseKey, name, fullName?, password?, roles?[], osUser?, showInList?}` | `{ok:true}` |
| `IB_LIST_ROLES` | `{baseKey}` | `{items:[{name, synonym?}]}` |
| `IB_UPDATE_USER` | `{baseKey, name, newName?, fullName?, password?, addRoles?[], removeRoles?[], roles?[], disabled?, showInList?}` | `{ok:true}` |
| `IB_DELETE_USER` | `{baseKey, name}` | `{ok:true}` |
| `IB_LIST_EXTENSIONS` | `{baseKey}` | `{items:[{name, synonym?, version?, purpose?, safeMode?}]}` |
| `IB_INSTALL_EXTENSION` | `{baseKey, name, contentBase64, safeMode?}` | `{ok:true}` |
| `IB_DELETE_EXTENSION` | `{baseKey, name}` | `{ok:true}` |
| `IB_PUBLISH` | `{baseKey, alias?, dir?, webServer?}` | `{ok:true, url:"http://localhost/<alias>"}` |
| `IB_UNPUBLISH` | `{baseKey, alias?, webServer?}` | `{ok:true}` |
| `IB_BACKUP` | `{baseKey, dir?}` | `{ok:true, path, sizeBytes?, transport?}` |

Что важно соблюсти:

- **Списки полные.** Результат `IB_LIST_*` замещает кэш базы целиком: чего нет в ответе,
  сервис удаляет из реестра. Частичный список молча «потеряет» пользователей.
- **`synonym` в `IB_LIST_EXTENSIONS`** — Синоним расширения из 1С. Служебное Имя часто
  нечитаемо (`EF_00_00062442`), и сводка по расширениям без синонима превращается в список
  идентификаторов. Поле необязательное, но без него панель показывает только имя.
- **`contentBase64`** — содержимое `.cfe` без префикса `data:`. Файл приходит телом команды:
  агент не ходит за ним в сеть.
- **Идемпотентность НЕ отменяет проверку базы.** «Повторное действие = SUCCESS» верно только
  для базы, которая на этом сервере ЕСТЬ. Если базы нет — `INFOBASE_NOT_FOUND`, а не `SUCCESS`.
  Живой случай: `IB_UNPUBLISH` по базе `_transition` вернул `SUCCESS` с машины, где этой базы
  нет вовсе; сервис поверил и записал «публикация снята», а на боевом сервере публикация
  осталась. Успех за невыполненную работу хуже честной ошибки: он ломает реестр.
- **Идемпотентность обязательна.** Панель перестаёт ждать ответ через 20 с и дальше следит за
  командой по номеру (§1), а команда живёт 900 с и дольше — пользователь может повторить
  операцию, которая на самом деле идёт. Долгие изменяющие команды сервис склеивает с идущей по
  `requestId`, но на агенте повтор всё равно должен быть безопасен.
  Повторное создание существующего пользователя и повторное удаление отсутствующего должны
  завершаться `SUCCESS`, а не ошибкой.
- **`IB_BACKUP` обязан вернуть `path`.** Отчёт «выгружено 110 баз» без пути не отвечает на
  единственный вопрос, который после него задают, — куда легло. Имя файла назначает агент:
  раскладку дисков сервера панель не знает и знать не должна; `dir` лишь перенаправляет
  выгрузку. Подробности и остальные команды обслуживания — в `docs/PROMPT_AGENT_MAINTENANCE.md`.
- **`IB_UNPUBLISH` — обратная публикации:** снятие виртуального каталога и записи о базе
  (`webinst -delete` или эквивалент). Идемпотентна: снятие публикации с неопубликованной
  базы — `SUCCESS`, а не ошибка. После успеха сервис ставит базе `published = false` и
  СТИРАЕТ `publishUrl`: ссылка на несуществующую страницу хуже её отсутствия.
- **Публикация НЕ требуется внутрибазовым командам.** `IB_LIST_USERS`, `IB_CREATE_USER`,
  `IB_DELETE_USER`, `IB_LIST_EXTENSIONS`, `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` идут
  через COM-соединение с сервером 1С напрямую. Веб-публикация нужна только каналу HTTP
  (расширение `buhprof_api` бизнес-агента). Не отказывайте в этих командах неопубликованной
  базе: её как раз готовят к публикации.
- **`IB_PUBLISH` — не операция над базой.** Публикация делается настройкой веб-сервера
  (виртуальный каталог + `default.vrd`), в скриптовом API 1С её нет: агент выполняет её
  запуском `webinst`, как запускает `rac`. Публиковать **только на localhost** — агент ходит
  в HTTP-сервис с той же машины. `alias`, `dir`, `webServer` необязательны: при отсутствии
  агент подставляет свои умолчания.
- **Расширения — по-русски.** COM-соединение отдаёт члены на языке конфигурации:
  `РасширенияКонфигурации.Получить()/Создать()`, `Расширение.Записать(ДвоичныеДанные)`.
  Английские имена дают `0x80020003 DISP_E_MEMBERNOTFOUND` — эту ошибку панель уже
  расшифровывает пользователю как «исправляется в агенте». Подробности — в
  `docs/PROMPT_AGENT_IB.md`.
- **Пароль не логировать.** Он приходит в payload и не должен попадать ни в лог агента, ни
  в текст ошибки. Сервис его у себя не хранит: в задание пакета `password` и `contentBase64`
  не записываются.

### `IB_CHECK` — проверка базы (WRITE, база обязательна, срок 15 000 с)

Payload: `reindex`, `logicalIntegrity`, `recalcTotals`, `repair`, `dryRun` — все булевы и
необязательны (`.strict()`). Без `repair` — только осмотр: агент идёт в режим
`/IBCheckAndRepair` с `-LogAndRefsIntegrity -TestOnly`; переиндексация и пересчёт итогов меняют
базу и **не выполняются**. С `repair` — выбранное плюс восстановление созданием объектов
(`-BadRefCreate -BadDataCreate`). Проверка с `repair` доступна только полному доступу к 1С
(аудит С4), без него — и просмотру.

Ответ (агент с `2026-09-14 22:05`):

```jsonc
{
  "ok": true,
  "keys": ["-LogAndRefsIntegrity", "-TestOnly"],  // с какими ключами шёл конфигуратор
  "skipped": ["reindex", "recalcTotals"],           // выбрано, но без repair не выполнялось
  "issues": 0, "repaired": 0, "report": "…"
}
```

Строки «ошибок не обнаружено» ошибкой не считаются. `dryRun` возвращает план (ключи и то, что
без «Исправлять» не выполнится) и в базу не входит: его успех **не снимает** отметку «в базу не
войти» (аудит С5), а в очереди он идёт впереди и с обычным сроком 900 с.

### Эхо состояния: `state` в ответе изменяющей команды (способность `ib.echo`)

Изменение выполняется в открытом соединении с базой — прочитать в нём список сразу после
записи стоит миллисекунды. Поэтому изменяющие команды прикладывают новое содержимое к своему
же ответу, и сервис не ставит следом читающую команду (второй вход в базу с сеансом и
лицензией; на пакете по ста десяти базам — сто десять лишних входов).

| Команда | Поле | Содержимое |
|---|---|---|
| `IB_CREATE_USER`, `IB_UPDATE_USER`, `IB_DELETE_USER` | `state.users` | то же, что `IB_LIST_USERS` |
| `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` | `state.extensions` | то же, что `IB_LIST_EXTENSIONS` |
| `CLUSTER_TERMINATE_SESSION` | `state.sessions` | то же, что `CLUSTER_LIST_SESSIONS` без `baseKey` (весь кластер) |
| `CLUSTER_DISCONNECT` | `state.connections`, `state.locks` | соединения и блокировки кластера после разрыва (`CLUSTER_LIST_CONNECTIONS` / `CLUSTER_LIST_LOCKS` без `baseKey`) |
| `CLUSTER_SET_SESSIONS_LOCK` | `state.lock` | блокировка после изменения — `{enabled, active?, message, from, to, scheduledJobsDenied?, permissionCodeSet, readAt}` |
| `CLUSTER_DROP_INFOBASE` | `state.infobases` | `{items, complete, readAt, stillListed}` — строки как у `CLUSTER_LIST_INFOBASES` |
| `IB_RESTORE`, `IB_APPLY_UPDATE` | `state.users`, `state.extensions`, `state.config` | списки как у `IB_LIST_*`; конфигурация `{name, version, synonym?, readAt}`; каждый блок независим |
| `AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND` | `state.processes` | `{items, readAt, stillRunning}` — строки как у `AGENT_LIST_PROCESSES`; у отмены — только при `killed: true` |
| `IB_PUBLISH`, `IB_UNPUBLISH` | `state.publication` | `{published, url, webServer, readAt}` — только IIS (`appcmd`); у Apache блока нет |

У сеансов и соединений `state` — не для реестра, а для панели: сервис его не применяет и
оставляет в результате. Список всего кластера (панель держит именно такой и замещает его
целиком); `complete: true` — только если ответили все кластеры сервера, иначе `state` нет.
`stillListed` (у сеансов, соединений и `infobases` — всегда, `false` тоже) — снятие прошло, но
строка на момент `readAt` ещё в списке кластера.

**Блокировка `lock`.** Кода разрешения нет никогда — только `permissionCodeSet`. `from`/`to` —
в виде `rac` (`ГГГГ-ММ-ДДTчч:мм:сс`, местное время сервера), пусто и «нулевая» дата — `null`.
`active` — действует ли блокировка сейчас: включена И текущее время внутри окна; поля нет, если
даты в незнакомом виде. Тот же объект приходит в строке `CLUSTER_LIST_INFOBASES` и в полном срезе
баз heartbeat (поле `lock`) — из фонового чтения агента (до 20 баз в минуту, база раз в 10 мин,
отказ — пауза 6 ч); старше 30 мин или не читали — поля нет, и прежнее знание сохраняется.
`CLUSTER_INFOBASE_INFO` код разрешения тоже не отдаёт: вместо `permissionCode` — `permissionCodeSet`.

```jsonc
{ "ok": true,
  "state": { "users": { "items": [ { "name": "…", "fullName": "…", "disabled": false,
                                     "roles": ["…"] } ],
                        "complete": true,
                        "readAt": "2026-09-12T14:21:03Z" } } }
```

- **`complete: true` обязателен** — это обещание полноты: сервис замещает кэш базы ЦЕЛИКОМ, и
  строки, которых в списке нет, считаются удалёнными из базы;
- **перечитать не удалось — `state` не шлём вовсе.** Изменение при этом успешно: сервис, не
  увидев состояния, поставит читающую команду, как делал всегда. Неполный список хуже его
  отсутствия;
- форма строк — ровно та же, что у `IB_LIST_*`: сервис применяет их одним и тем же кодом;
- **способность `ib.echo`** объявляется в `capabilities` при регистрации. Без неё всё работает
  по-старому — совместимость со сборками без эха обязана сохраняться;
- применённое сервис вырезает из результата команды: в реестре оно уже есть, а задание на сто
  баз положило бы в журнал сто списков. Неприменимое (например `state.sessions` после снятия
  сеанса) остаётся в ответе — панель читает его оттуда.

Спецификация целиком: [TASK_FRESH_STATE_AFTER_COMMAND.md](TASK_FRESH_STATE_AFTER_COMMAND.md).

### Правка ролей применяется так, как прислана (способность `ib.roles`)

`IB_UPDATE_USER` принимает роли двумя способами: поправками (`addRoles`, `removeRoles`) и полным
набором (`roles`, в том числе пустым). Сборки агента до 13.09.2026 на поправки и на пустой набор
отвечали успехом, ничего не меняя. Панель обходила это чтением `IB_LIST_USERS` перед каждой
правкой прав и слала полный набор — лишний вход в базу и гонка с конфигуратором между чтением и
записью.

Способность `ib.roles` — обещание сборки:

- `addRoles` / `removeRoles` применяются в том же соединении, в котором пишется пользователь:
  снимается только выданная роль, добавляется только отсутствующая. Читать роли перед командой
  не нужно, повтор команды безопасен;
- `roles: []` снимает все роли, а отсутствие поля `roles` роли не трогает — это разные запросы;
- порядок внутри команды фиксирован: полный набор → снятие → добавление;
- все имена разбираются до первого изменения: роль, которой нет в конфигурации базы, — отказ
  `IB_ROLE_NOT_FOUND` с её именем, и в базу не пишется ничего;
- `state.users` в ответе прочитан после записи — по нему сервис сверяет, что роли легли
  (`checkRoleIntent`), и при расхождении отвечает отказом.

Панель при `ib.roles` шлёт поправки без предварительного чтения; без способности — прежний обход.
Задача панели: [TASK_PANEL_ROLES_WITHOUT_PREREAD.md](TASK_PANEL_ROLES_WITHOUT_PREREAD.md).

### «Показывать в списке выбора» не читается — и сервис помнит своё

`IB_LIST_USERS` возвращает `{name, fullName, disabled, roles}`; признака «показывать в списке
выбора» там нет. Пока записанное никто не запоминал, панель вела себя так, будто запись не
проходит: человек включает тумблер, команда `IB_UPDATE_USER` с `showInList: true` завершается
успехом, карточка перечитывает базу — и показывает «выключено», потому что значения не знает
(жалоба 12.09, дважды за вечер).

Теперь сервис запоминает признак по факту СВОЕЙ успешной команды (`onec/writeBack.ts` →
`base_users.show_in_list`, миграция 019), а карточка подписывает показанное: «по последней
успешной записи из панели». Это не догадка: значение взято из payload выполненной команды.

**Что нужно от агента, чтобы это перестало быть полумерой:** возвращать `showInList` в
`IB_LIST_USERS` (и в эхе). Тогда значение станет читаемым, расхождение «записали одно, в базе
другое» станет видно, а `COALESCE` в `syncUsers` сам предпочтёт ответ базы нашей памяти.

> **СДЕЛАНО агентом, сборка `0.1.0+2026-09-12 23:59 (+05)`.** `IB_LIST_USERS` и эхо состояния
> отдают `showInList` — они собираются одним кодом, поэтому расхождения между ними быть не
> может. Значение читается свойством «ПоказыватьВСпискеВыбора»/«ShowInList»; **если платформа
> его не отдаёт, поле не отправляется вовсе** — `false` от незнания затёр бы то, что сервис
> помнит о собственной записи. То есть `COALESCE` получает либо факт из базы, либо молчание.

> **Проверка записи, сборка агента `2026-09-14 12:46`.** Запрошенный `showInList` (`IB_UPDATE_USER`, и
> `IB_CREATE_USER`, когда поле есть в payload) агент пишет строго: платформа не приняла свойство —
> отказ `IB_FIELD_NOT_APPLIED` до записи; приняла, но у пользователя, найденного в базе заново,
> значение другое — `IB_FIELD_NOT_APPLIED` после записи (остальные поля команды записаны);
> прочитать нечем — успех с `unverified: ["showInList"]`. Необязательные свойства, не принятые
> платформой, перечислены в `skipped`. Сервису и панели: [TASK_SERVICE_SHOW_IN_LIST.md](TASK_SERVICE_SHOW_IN_LIST.md).

### `newName` в `IB_UPDATE_USER` — переименование, а не пересоздание

Панель разрешает править имя входа прямо в карточке пользователя базы, и тогда в payload
приходит `newName`. Это смена свойства «Имя» У ТОГО ЖЕ пользователя
(`Пользователь.Имя = newName; Пользователь.Записать()`), а не «удалить и создать заново»:
пересоздание теряет внутренний идентификатор, а с ним — ссылки на пользователя в самой базе
(автор документов, настройки, права на уровне записей).

* `newName` отсутствует или равен `name` — имя не трогать.
* Имя уже занято другим пользователем базы — вернуть ошибку с этим текстом, а не молча
  ничего не делать: панель показывает отказ пользователю.
* Остальные поля применяются в той же команде и по прежнему правилу: отсутствующее поле
  значит «не трогать».

### `payload.auth` — учётная запись КОНКРЕТНОЙ базы (обязательно к реализации)

У агента один администратор баз на всех (у нас — `support`). К части клиентских баз он не
подходит: их заводили до нас, и такого пользователя там нет либо у него другой пароль.
Раньше это лечилось правкой настроек агента — то есть ради одной базы трогали все.

Теперь в панели у базы можно задать свою пару «пользователь + пароль», и сервис подставляет
её в команду **в момент выдачи**:

```jsonc
{ "id": "cmd_…", "baseKey": "BUH_ALPHA", "type": "IB_LIST_USERS",
  "payload": { "baseKey": "BUH_ALPHA", "auth": { "user": "Администратор", "password": "…" } } }
```

**Порядок входа в базу — строго такой:**

1. свой администратор из конфига агента;
2. если он **не прошёл аутентификацию** — повтор с `payload.auth`;
3. если и он не прошёл — ошибка с текстом ОБЕИХ попыток (по какой учётной записи отказ).

Повторять по `auth` нужно **только на отказе аутентификации**. «База занята», «нет
лицензии», «сервер недоступен» — не тот случай: второй вход туда же ничего не изменит,
зато займёт ещё один сеанс.

Поле может отсутствовать — значит, для базы ничего не задано, и работает пункт 1.

**Объявите способность `ib.auth`** в списке capabilities при регистрации — ею агент
сообщает, что читает `payload.auth`. Панель на неё смотрит: пока способности нет, она
показывает у вкладки «Доступ к базе» предупреждение «агент этой сборки учётную запись
игнорирует», а в тексте отказа на входе пишет, что отказ получен по администратору из
настроек агента, а не по заданной учётной записи. Без этого признака человек, задавший
пароль и получивший тот же отказ, не может отличить «пароль неверен» от «пароль не
применили» — и чинит не то.

`auth.password` подпадает под общее правило: **в лог и в текст ошибки не попадает никогда.**
В команде он не хранится и на стороне сервиса — подставляется только в HTTP-ответ агенту.

### По одной команде на базу за раз (гарантия сервиса)

Сервис не выдаёт вторую команду по ТОЙ ЖЕ базе, пока не получит результат первой. Команды
одной базы не независимы: переименовать пользователя и тут же выдать ему роли — это две
операции над одним объектом, и порядок здесь не деталь. Раньше они уходили вместе, агент
выполнял их параллельно, и роли ложились на старое имя либо приходило «в базе нет
пользователя».

Что это значит для агента:

* по одной базе одновременно приходит не больше одной команды — второе COM-соединение к
  той же базе не нужно, и сеанс с лицензией не тратятся дважды;
* `max_parallel` продолжает работать МЕЖДУ базами — сто баз по-прежнему обрабатываются
  параллельно;
* команды кластера друг друга не ждут вовсе — **и очереди базы тоже не ждут, даже с `baseKey`**
  (аудит С1): снятие сеанса, блокировка входа, удаление регистрации идут через `rac`, в базу
  не входят. Иначе снятие сеансов стояло бы за загрузкой той же базы, которая ждёт их выхода.
  Место базы и агента (`AGENT_IB_PARALLEL`) занимают только команды `ib.admin`;
* команда, у которой вышел срок, а результата нет, **держит место ещё 10 минут** (аудит С3):
  агент мог продолжать работу, и вторая команда внутрь той же базы легла бы поверх первой;
* **`IB_BUSY`** (база занята) у команды группового задания сервис повторяет сам: копия встаёт
  в конец очереди задания, до трёх попыток (аудит С10). Отвечать `IB_BUSY` — правильно, ждать
  освобождения базы внутри команды не нужно;
* **результат надо присылать всегда** — и на успех, и на отказ. Пока результата нет,
  очередь этой базы стоит; забытый результат останавливает работу по базе до истечения
  срока команды.

### Пакетные операции

Групповая операция — это N обычных команд, по одной на базу, связанных общим заданием на
стороне сервиса. Для агента ничего нового: те же команды, тот же протокол. Единственное
требование — **параллелизм**: `max_parallel` в конфиге ограничивает число одновременных
COM-соединений, потому что каждое занимает сеанс и лицензию 1С.

| `AGENT_LOG_TAIL` — хвост журнала агента, READ, без базы | `{lines?: 1–1000 (200), level?: "all" \| "problems", contains?: строка ≤100}` | `{file, lines[], matched, truncated}`; файлов ещё нет — `{file: null, lines: [], note}`; пароли и токены вырезаны до отбора. Отказы: `VALIDATION_ERROR`, `LOG_UNAVAILABLE` (журнал пишется только в консоль) |
| `IB_SELFTEST` — прогон операций на живой базе, база обязательна | `{baseKey}` | `{ok, steps[{name, ok, note}]}` — создаёт и удаляет временного пользователя `bpapi_selftest_<процесс>`, других пользователей и расширения не трогает; неудачный шаг — не отказ команды, а `ok: false` |
| `IB_BATCH` — одна операция по многим базам | `{type, bases?[] \| baseKeys?[], payload, dryRun?}` | `{items[{baseKey, ok, result \| code, message}], total, done, failed, seconds}`; без списка — все базы кластера (так пакет задаёт расписание агента); весь пакет — под одним пределом долгой команды, при его превышении отчёт по базам теряется. Сервис групповые операции ведёт сам, одиночными командами, и `IB_BATCH` не использует |

`AGENT_HEALTH` и `AGENT_LOG_TAIL` исполняет служба, пропуска на исполнение они не ждут (отвечают и
тогда, когда все места заняты). Та же самопроверка есть в окне агента — «Состояние» → «Проверить
операции в базе» или «Отладочная информация» с отметкой «с самопроверкой базы»: отчёт копируется.

## 4. Коды ошибок

⚠ **Сервис не отвечает 5xx на ошибки 1С.** Отказ агента — это ошибка предметной области,
и панель получает её как `422` с телом `{success:false,error:{code,message}}`. Причина
практическая: Cloudflare трактует 5xx от источника буквально и подменяет ответ своей
HTML-страницей без заголовков CORS — текст ошибки до браузера не доезжает вовсе, а
пользователь видит «Access-Control-Allow-Origin missing» вместо причины.


Панель показывает `error.message` как есть, поэтому текст пишите по-русски и по делу.
Коды, на которые уже ссылается [ONEC_ADMIN_SETUP.md](ONEC_ADMIN_SETUP.md):

| Код | Когда |
|---|---|
| `RAC_UNAVAILABLE` | не найден `rac.exe` по `cluster.rac_path` |
| `RAC_TIMEOUT` | `rac` не ответил за `cluster.timeout_secs` (обычно молчит RAS) |
| `TIMEOUT` | агент прервал команду по своему пределу времени (не путать со сроком сервиса); сервис добавляет подсказку — увеличить предел в настройках агента или запускать в окно обслуживания |
| `IB_AUTH_FAILED` | в базу не пустили: неверная учётная запись базы; сервис ставит базе причину «нет доступа» по коду, а не по тексту (аудит С6) |
| `IB_FIELD_NOT_APPLIED` | запрошенный реквизит пользователя не сохранился («Показывать в списке выбора»): платформа отвергла свойство — до записи, ничего не записано; или после записи в базе прежнее значение — остальные поля команды записаны |
| `SESSIONS_LOCK_NOT_ACTIVE` | загрузка или обновление конфигурации не начаты: блокировка начала сеансов включена, но не действует (окно прошлой блокировки) и после окна «сейчас — сутки вперёд»; блокировка снята |
| `IB_CONNECTION_LOST` | во время операции оборвалась связь с рабочим процессом кластера 1С (например `tcp://SERVER:1560 … 10054`): процесс упал, перезапущен кластером или оборвал вызов. Операция не завершена. Агент дописывает к тексту, какие рабочие процессы запущены после её начала, и настройки перезапуска и памяти кластера, а с агента после `23:52` — и пределы памяти рабочих серверов (`rac server list`: критический и временно допустимый объём памяти процессов, безопасный расход памяти за один вызов; «0» — без ограничения). Если процесс перезапущен, а пределы не заданы ни у кластера, ни у рабочего сервера, агент дописывает вывод: процесс не снят правилом, а, вероятнее всего, аварийно завершился (журнал «Приложение» Windows, дампы) — совет «поднять пределы» тогда не к месту; повторять — после разбора причины |
| `CLUSTER_NOT_FOUND` | RAS отвечает, кластера по адресу нет |
| `RAC_ERROR` | сам `rac` вернул ошибку — вложите его текст в `message` |

Набор аргументов `rac` собран по документации и на живом кластере не проверялся: при
`RAC_ERROR` полезно класть в `details` фактическую командную строку (без пароля).

## 5. Что модулю НЕ нужно делать

- **Не заходить в базы.** Секция `[onec]` админ-агенту не нужна, расширение `buhprof_api`
  не используется. Исключение — блокировка сеансов, и то через администратора ИБ, а не через
  расширение.
- **Не опрашивать кластер по своей инициативе** на каждую базу. Реестр отдаётся панели из БД
  сервиса; состояние приходит с heartbeat (`bases[]` + `basesComplete`), а кнопка «Обновить
  из кластера» существует ровно для случая, когда ждать heartbeat не хочется. Сто баз каждые
  30 секунд опрашивать нельзя.
- **Не изобретать команд сверх списка.** `ADMIN_COMMANDS` закрыт: незнакомый тип сервис не
  поставит, а агент не должен исполнять ничего, чего нет в §3 и §3.2.

## Экземпляр агента: `instanceId` (обязателен к отправке)

Каждый ЗАПУЩЕННЫЙ ПРОЦЕСС агента обязан называть себя — заголовком `X-Agent-Instance`
на любом запросе либо полем `instanceId` в `register`/`heartbeat`. Значение произвольное,
но стабильное в пределах жизни процесса и разное у разных процессов: подойдёт
`"<pid>@<время старта>"`.

**Зачем.** Два запущенных экземпляра под одним токеном — авария, невидимая с сервера: оба
разбирают ОДНУ очередь команд. Пока настройки совпадают, это лишь лишняя нагрузка; стоит им
разойтись (старый процесс с прежним паролем кластера, новый — с исправленным), и одна и та
же команда начинает отказывать ЧЕРЕЗ РАЗ. Отладка такого без счёта экземпляров сводится к
гаданию: `rac` отвечает то «не аутентифицирован», то данными, а пароль при этом верный.

Сервис считает экземпляры, отзывавшиеся за `AGENT_OFFLINE_AFTER_SECS`, и показывает их
число во вкладке «Агенты» — больше одного даёт предупреждение прямо в панели.

**Токен — на одну машину.** Копировать рабочий токен на вторую машину нельзя: обе будут
разбирать одну очередь команд от имени одного агента, и различить их в отчётах невозможно.
Так и вышло на практике — один токен стоял и на сервере 1С, и на машине разработки; команды
отказывали через раз, потому что настройки кластера у них разошлись. Для разработки
заводится ОТДЕЛЬНЫЙ агент со своим токеном («Администрирование 1С» → «Агенты» → «Создать»).

Сервис запоминает адрес источника каждого экземпляра, и если экземпляры приходят с разных
адресов, панель говорит об этом прямо: «один токен используется на разных машинах».

Вторая причина двойного запуска, уже на одной машине: служба агента работает и одновременно
запущен экземпляр из среды разработки.
