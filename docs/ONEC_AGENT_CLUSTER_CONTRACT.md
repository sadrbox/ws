# Контракт кластерного модуля админ-агента (bpapi_agent, role = admin)

Версия 1.0 · 2026-09-04 · извлечено из работающего кода `ai/`, не из планов
Сверено с кодом агента (`bpapi_agent/src`) и сервиса (`ai/src`) 2026-09-15: §1, §2, §3, §3.2, §3.3, §4, «Экземпляр агента».
Пометка «агент после `2026-09-15 01:06`» — поведение сборки агента новее этого времени.

Что должен реализовать модуль `cluster` в `bpapi_agent`, чтобы кнопка **«Администрирование 1С» →
«Базы» → «Обновить из кластера»** в aleppo.kz наполнила реестр баз.

Сторона сервиса готова целиком: `ai/src/commands/admin.ts` (список команд), `ai/src/http/onecRouter.ts`
(HTTP панели), `ai/src/bases/service.ts` (реестр), миграция `004_bases.sql`, панель
`frontend/src/models/OneCAdmin`. Ничего из этого дописывать не требуется.

## 1. Транспорт: как команда доходит до модуля

> Со сборки агента `2026-09-15 16:48` (А30): `expiresAt` (ISO 8601; сервис с `b806507`, С31) — срок команды у сервиса. Агент ждёт свободного исполнителя до него за вычетом своего предела работы (`command_timeout_secs` / `long_command_timeout_secs`) и, со сборки `17:30`, запаса 60 с на сеть и часы (А33; сухой прогон долгой команды — с обычным пределом, А32), чтобы ответить до истечения срока; остатка нет — берёт исполнителя, только если он свободен сразу, иначе `AGENT_BUSY` (§4). Без `expiresAt` — по разнице сроков за вычетом запаса (240 / 540 с).

Ничего нового — тот же long-poll, что у бизнес-агента:

```
GET  /agent/v1/commands?wait=N          → { commands: [ { id, requestId?, baseKey?, type, payload } ] }
POST /agent/v1/commands/{id}/result     ← результат
```

Выдача (`WireCommand`, `ai/src/commands/queue.ts:112`, сборка — `queue.ts:482-505`):

| Поле | Когда есть | Что это |
|---|---|---|
| `id` | всегда | `cmd_` + 16 шестнадцатеричных знаков; им адресуется результат |
| `requestId` | только если его назначил сервис (см. «Смысл `requestId`» ниже) | ключ склейки повторов в очереди |
| `baseKey` | у команды, адресованной базе | то же, что `payload.baseKey`. Агент верхнее поле не читает (`Command` в `cloud/protocol.rs`: `id`, `requestId`, `type`, `payload`) и берёт базу из `payload` |
| `type` | всегда | тип из `ADMIN_COMMANDS` (§2.1) |
| `payload` | всегда | прошёл схему Zod при постановке; в момент выдачи сервис может добавить `payload.auth` (§3.2) |

Ответ опроса — голый объект `{commands: [...]}`, без конверта `{success, data}` (`agentRouter.ts:397`). `wait`
сервис урезает до `POLL_MAX_WAIT_SECS` (по умолчанию 30 с), без параметра — 20 с (`agentRouter.ts:371-372`); агент
просит `cloud.poll_wait_secs` (по умолчанию 25 с, `config.rs`).

Тело результата (`resultSchema`, `ai/src/http/agentRouter.ts:113`):

```jsonc
{
  "commandId": "…",            // 1–64 символа; сервис берёт номер из пути, поле тела им перекрывается
  "agentId": "<uuid агента>",  // обязателен, сверяется с X-Agent-Id; не совпал — 400 VALIDATION_ERROR
  "status": "SUCCESS",         // или "ERROR"
  "result": { },               // при SUCCESS — см. §3
  "error":  { "code": "…", "message": "…", "details": {} },  // при ERROR; code и message — строки
  "startedAt": "…", "finishedAt": "…",  // сервису необязательны; агент шлёт всегда (RFC3339)
  "onecHttpStatus": 200                  // необязательно, целое; только для журнала
}
```

Сервис отвечает `{success: true, data: {ok: true}}`. Результат по отменённой или неизвестной команде — тоже 200, но
`{ok: true, ignored: true}` (`agentRouter.ts:511-524`): иначе агент досылал бы его из spool вечно. Результат по
истёкшей команде принимается и помечается поздним (`late`, `queue.ts:536`).

⚠ **Сроки (сверено 15.09 по коду, аудит С2/С13/С19/С21/С22).**

| Предел | Значение | Где в коде | Отсчёт и исход |
|---|---|---|---|
| Ответ в запросе панели | `ONEC_COMMAND_TIMEOUT_SECS`, 20 с | `onecRouter.ts:254-266` | не дождался — 202 `{pending, commandId, state, dispatchedAt}`; команда остаётся в очереди, панель опрашивает `GET /v1/onec/commands/:id` |

| Ожидание очереди до выдачи | 900 с у одиночной, 12 ч у группового задания (`BATCH_QUEUE_WAIT_SECS`) | `onecRouter.ts:227`, `batchRunner.ts:21,119` | от постановки; истекло — `COMMAND_QUEUE_TIMEOUT` («агент был занят»), а не «агент не на связи» |

| Срок бизнес-команды чата | 600 с; ожидание очереди — столько же | `chat/workflow.ts:303`, `queue.ts:180-181` | от выдачи агенту |

| Предел агента, долгая команда (`IB_BACKUP`, `IB_RESTORE`, `IB_CHECK`, `IB_APPLY_UPDATE`, `IB_BATCH` — `Kind::is_long`) | `agent.long_command_timeout_secs`, 14 400 с (0 — без предела, иначе не меньше 300) | `config.rs`, `commands/mod.rs` | то же |

Сроки сервиса и агента считаются от разных моментов. Между выдачей и пропуском команда ждёт у агента свободного места
(`agent.max_parallel`) — со сборки `2026-09-15 16:05` не дольше этого запаса, а со сборки `2026-09-15 16:48` — до `expiresAt` из выдачи за вычетом предела работы агента (А30) и запаса 60 с (с `17:30`, А33), иначе команда не выполняется и ответ — `AGENT_BUSY` (§4; опрос команд при этом не закрывается дольше 5 с, и команды управления агентом доходят), — и это ожидание съедает запас: 900 − 600 = 300 с у обычной команды и 15 000 − 14 400 = 600 с у
долгой. Ждала пропуска дольше — сервис закроет её `COMMAND_EXPIRED` раньше, чем агент ответит `TIMEOUT`; поздний
результат всё равно будет принят. Команды `AGENT_*` пропуска не ждут (`needs_permit`, `agent.rs`).

Команда, скорее всего, всё же выполнится после 202, а человек может нажать ещё раз, — повтор на агенте обязан быть
безопасным по смыслу операции (§3.2). `requestId` для этого есть не у каждой команды.

### Смысл `requestId`

`requestId` назначает **сервис** (`commandRequestId`, `admin.ts:702-709`); агент его не придумывает и для админ-команд
не использует:

| Команда | `requestId` |
|---|---|
| любое чтение (`READ`) | `<TYPE>:<baseKey>`, без базы — `<TYPE>:-`; у `AGENT_LOG_TAIL` и `CLUSTER_CHECK_BASES` вместо базы — ключ из параметров (`readKey`) |
| долгая изменяющая по базе (`IB_BACKUP`, `IB_CHECK`, `IB_RESTORE`, `IB_APPLY_UPDATE`), кроме `dryRun` | `<TYPE>:<baseKey>` |
| чтение, поставленное сервисом после изменения | `refresh:<TYPE>:<baseKey>` (`agentRouter.ts:686`) |
| копия команды задания после `IB_BUSY` | нет (`queue.ts:577`) |
| прочие изменяющие админ-команды | нет |
| бизнес-команды чата | передаёт чат (`chat/workflow.ts:302`); изменяющие без него агент отвергает `MISSING_REQUEST_ID` и кладёт его в тело запроса к 1С |

**Склейка — только среди незавершённых.** Повторная постановка с тем же `(агент, baseKey, requestId)` возвращает уже
стоящую команду, пока та `queued` или `dispatched` (частичный уникальный индекс, `queue.ts:188-208`). Завершённая
команда повтор не останавливает: `IB_LIST_USERS:buh_alma` получат все чтения этой базы по очереди. Значит,
`requestId` уникален лишь среди незавершённых команд агента и со временем переиспользуется. Хранить его как ключ
«уже сделано» и отвечать по нему прежним результатом агенту нельзя — ответ окажется устаревшим.

## 2. Регистрация: без неё команды не придут

`POST /agent/v1/register` (`registerSchema`, `agentRouter.ts:61-77`; что шлёт агент — `register`, `agent.rs`):

| Поле | Тип и предел | Обяз. | Что шлёт агент |
|---|---|---|---|
| `agentId` | UUID | да | идентификатор из настроек; обязан совпасть с `X-Agent-Id` |
| `agentName` | ≤ 200 | нет (`""`) | имя из настроек |
| `version` | ≤ 50 | да | `<версия>+<дата сборки>` |
| `instanceId` | ≤ 200 | нет | то же, что в `X-Agent-Instance` (см. «Экземпляр агента») |
| `os` | ≤ 50 | нет (`""`) | `windows` |
| `capabilities` | массив ≤ 100 строк ≤ 50 | нет (`[]`) | §2.1 |
| `role` | `business` \| `admin` | нет (`business`) | из настроек |
| `server` | `{name ≤ 200, rasHost ≤ 200 \| null, rasPort 1–65535 \| null}` | нет | `rasHost`/`rasPort` — только у админ-агента |
| `bases` | ≤ 500 строк среза (§2.2) | нет | админ-агент — полный срез баз кластера, бизнес-агент — одну свою строку |

Не прошло схему или `agentId` чужой — 400 `VALIDATION_ERROR` «Некорректная регистрация».

```jsonc
{
  "agentId": "00000000-0000-0000-0000-000000000000", "agentName": "Админ-агент",
  "version": "0.1.0+2026-09-15 01:06 (+05)", "os": "windows",
  "instanceId": "SERVER/BPAPIAgentAdmin/3316/2026-09-15T01:10:00Z",
  "role": "admin",
  "capabilities": ["CLUSTER_LIST_INFOBASES", "…", "IB_LIST_USERS", "…", "AGENT_LOG_TAIL",
                   "cluster.admin", "ib.admin", "ib.auth", "agent.procs", "agent.cancel", "agent.cancel.check", "ib.echo", "ib.roles"],
  "server": { "name": "Сервер 1С (офис)", "rasHost": "localhost", "rasPort": 1545 },
  "bases": [ { "key": "buh_alma", "name": "ТОО Алма", "status": "ONLINE", "onecVersion": "8.3.25.1257" } ]
}
```

Ответ: `{success: true, data: {ok: true, pollMaxWaitSecs, basesFullEverySecs}}` (`agentRouter.ts:304-308`). Агент тело
ответа не читает (`Client::register`, `cloud/mod.rs:94-101`): ожидание опроса у него своё, полный срез он шлёт по
`wantFullBases` из heartbeat.

При регистрации сервис переименовывает сервер агента или заводит его по `server.name`, закрывает команды, выданные
ДРУГОМУ экземпляру (`AGENT_RESTARTED`, `queue.ts:290-307`), применяет `bases` как полный срез и пишет в журнал
способности, пропавшие по сравнению с прошлой регистрацией.

- **`role: "admin"`** и нужная способность — гейт в `agentCanRun()` (`admin.ts:648-658`). Без них сервис откажет
  сразу: 409 `CAPABILITY_MISSING`, «Агент не умеет …».
- **`server.name`** обязан совпадать с именем у бизнес-агента того же сервера — по нему базы
  связываются с агентами. Разные имена дадут два «сервера» в реестре.

### 2.1. Способности

Способности агент объявляет сам (`Kind::capabilities_for`, `commands/mod.rs:375-429`), сервис им верит: способность
не даёт прав, она говорит, что служба умеет и настроена. Список из двух частей — имена типов команд и признаки с точкой.

| Способность | Что обещает | Когда объявляет агент | Что с ней делает сервис |
|---|---|---|---|
| `cluster.admin` | служба настроена на кластер (`rac`, RAS) | всегда при `role = admin` | гейт всех `CLUSTER_*` |
| `ib.admin` | умеет работать внутри баз | только если задан служебный администратор базы (`cluster.infobase_user`) **и** проба входа прошла хотя бы в одну базу (`ib_ready`/`probe_ib`, `agent.rs`; список баз не прочитан или баз нет — считается готовым). Вход появился позже — агент перерегистрируется сам (`readiness_loop`) | гейт `IB_*`; команда `ib.admin` занимает место базы в очереди (`runsInsideBase`, `admin.ts:668`) |
| `ib.auth` | читает `payload.auth` | всегда при `role = admin`, от `ib.admin` не зависит | не гейт: меняет только текст отказа входа (`onecRouter.ts:63,85`, `errorHints.ts:154-164`) |
| `agent.procs` | показывает и снимает свои процессы | всегда при `role = admin` | гейт `AGENT_LIST_PROCESSES`, `AGENT_KILL_PROCESS`, `AGENT_HEALTH`, `AGENT_LOG_TAIL` |
| `agent.cancel` | отмена начатой команды доходит до агента | всегда при `role = admin` | гейт `AGENT_CANCEL_COMMAND`; без неё панель не предлагает прерывание (`isAbortable`, `admin.ts:767-775`) |
| `agent.cancel.check` | при отмене `IB_CHECK` без `repair` агент снимает её конфигуратор | всегда при `role = admin` — **со сборки `2026-09-15 15:31`** (до неё не объявлялась) | без неё прерывание `IB_CHECK` — 409 `ABORT_AGENT_OLD` (`admin.ts:755`, `onecRouter.ts:1134-1141`) |
| `agent.running` | heartbeat сообщает выполняемые команды (`running`) — сервис продлевает их срок (В2) | всегда, у обеих ролей — со сборки `2026-09-15 18:00` | без неё срок команды — только из спецификации (С33) |
| `ib.echo` | изменяющие команды прикладывают `state` | всегда при `role = admin` | сервис способность не проверяет: `state` разбирает, если он пришёл (`agentRouter.ts:434`) |
| `ib.roles` | правка ролей применяется так, как прислана | всегда при `role = admin` | `IB_UPDATE_USER` с `addRoles`/`removeRoles`/`roles` без неё — 409 `CAPABILITY_MISSING` (`requiredCapability`, `admin.ts:724-743`) |
| `agent.log` | журнал службы отдаётся отдельной способностью | сборки с 2026-09-20 | гейт `AGENT_LOG_TAIL`; годится и прежняя `agent.procs` (`capabilityAlt`, `admin.ts`) |
| `agent.config` | читает и меняет свои настройки | сборки с удалённым управлением (`TASK_AGENT_REMOTE_CONTROL_2026-09-19.md`) | гейт `AGENT_CONFIG_GET`, `AGENT_CONFIG_SET` |
| `agent.restart` | перезапускает свою службу | там же | гейт `AGENT_RESTART` |
| `agent.update` | ставит новую сборку себе | там же | гейт `AGENT_UPDATE`; узел загрузки должен быть доверенным (`UPDATE_HOST_NOT_ALLOWED`) |
| `onec.business` | это бизнес-агент | всегда при `role ≠ admin` | не проверяется: бизнес-агента выбирают по роли (`pickAgentFor`, `agents/service.ts:247-249`) |
| имена типов | конкретные команды, которые знает сборка | админ-агент: все `CLUSTER_*` и `AGENT_*`, `IB_*` — только вместе с `ib.admin`; бизнес-агент — типы документов (`HEALTH`, `CREATE_SALE`, …) | если в списке есть хоть одно имя типа, команда ставится, только когда её тип в списке (`agentKnowsType`, `admin.ts`). С 22.09 правило действует и на БИЗНЕС-команды — чат и панель отказывают сразу («обновите агента»), вместо минуты ожидания и `UNKNOWN_COMMAND` по сети |

`IB_BATCH` агент **не объявляет** (`commands/mod.rs:380-383`): его исполняет только расписание самого агента, а в
`ADMIN_COMMANDS` сервиса такого типа нет.

Сводка `AGENT_HEALTH` показывает признаки с точкой, но `ib.admin` в ней считается по одному лишь заданному
администратору (`health.rs:52`, `rt.ib.is_some()`), без пробы входа: там он может быть, хотя при регистрации не объявлен.

### 2.2. Heartbeat: `POST /agent/v1/heartbeat`

> **Продление срока выполняемых команд** (решение В2 по С24; агент со сборки `2026-09-15 18:00`, сервис — С33). Heartbeat несёт `running: [{commandId, type, startedAt}]` — команды, по которым агент уже работает (исполнитель получен); ждущие исполнителя не входят, пустой список — «ничего не выполняю». Сервис продлевает `expires_at` перечисленных выданных команд этого агента не меньше чем на три периода heartbeat (≥ 90 с) от приёма, но не дальше потолка от выдачи; команда не перечислена или heartbeat не пришёл — срок не продлевается, и она истекает как обычно. Продление сервис объявляет в ответе регистрации: `runningLease: true` — тогда агент оставляет до `expiresAt` запас только до первого heartbeat (`heartbeat_secs` + 60 с), а не весь предел работы, и большой предел агента не обнуляет ожидание исполнителя. Способность — `agent.running`; тот же список — в `AGENT_HEALTH` (`commands.running`), признак объявленного продления — `agent.serviceLease`.

Агент шлёт его отдельной задачей раз в `cloud.heartbeat_secs` (по умолчанию 30 с, не чаще раза в 5 с;
`heartbeat_loop`, `agent.rs`), сразу после регистрации и при остановке (прощание, ниже). Долгая команда его не задерживает.

Схема (`heartbeatSchema`, `agentRouter.ts:79-111`). Лишние поля отбрасываются молча; неверное поле — 400
`VALIDATION_ERROR` «Некорректный heartbeat» на весь heartbeat:

> `activationRequests` — единственное поле heartbeat, описанное НЕ здесь: это запросы бизнес-агента на
> активацию БИН, и весь их разбор (лимит `activeBins`, решения панели, аудит) живёт в
> [CONTRACT_BASE_REGISTRATION_2026-09-19.md](CONTRACT_BASE_REGISTRATION_2026-09-19.md). Сервис их принимает.

| Поле | Тип и предел | Обяз. | Что шлёт агент (`Heartbeat`, `cloud/protocol.rs:117-154`; `send_heartbeat`, `agent.rs`) |
|---|---|---|---|
| `agentId` | UUID, = `X-Agent-Id` | да | всегда |
| `version` | ≤ 50 | нет | `<версия>+<дата сборки>` |
| `instanceId` | ≤ 200 | нет | всегда; сервис по нему только ведёт учёт экземпляров |
| `status` | строка ≤ 20 | да | `STARTING`, `CONNECTING`, `ONLINE`, `BUSY`, `OFFLINE`, `ERROR`, `STOPPING` (`state.rs:24-32`); `OFFLINE` — только прощание при остановке (со сборки `2026-09-15 15:31`, `state::wire_status`; ниже) |
| `onec` | `{reachable: boolean, version?: string \| null}` | нет | всегда; у админ-агента `version` — версия платформы |
| `commandsDone`, `commandsFailed` | целые | нет | счётчики с запуска процесса |
| `bases` | ≤ 500 строк среза | нет | только по просьбе сервиса (ниже) |
| `basesComplete` | boolean | нет | `true`, когда `bases` непуст |
| `processes` | ≤ 200 строк `{pid: целое, tool ≤ 50, what? ≤ 200, base? ≤ 200 \| null, ageSecs? целое ≥ 0, orphan? boolean}` | нет | всегда, пустой список тоже: «процессов нет» — ответ, а не незнание (форма строки — §3.3) |
| `failuresByCode`, `durationsByType` | любое | нет | отказы по кодам и время команд; не разобралось — пропускается, heartbeat принят (`agents/commandStats.ts`) |

Агент шлёт ещё `timestamp`, `uptimeSecs` и `readiness` — схема их отбрасывает. Поле `commandId` строк `processes`
(агент после `2026-09-15 01:06`) схема тоже отбрасывает: в снимок процессов у сервиса оно не попадает.

**Строка среза базы** (`baseStateSchema`, `agentRouter.ts:41-59`): `key` 1–200 (обяз.), `id` ≤ 64, `published`
boolean \| null, `publishUrl` ≤ 500 \| null, `name` ≤ 200, `status` ≤ 20, `onecVersion` ≤ 50 \| null, `extVersion`
≤ 50 \| null, `sessionsCount` 0–100 000, `dbMissing` boolean \| null, `lock` — объект, разбирает `parseLock`.
Админ-агент собирает строку из `CLUSTER_LIST_INFOBASES` (`BaseState::from_cluster_item`, `protocol.rs:92-112`):
`key`, `id`, `name`, `published`, `publishUrl`, `dbMissing`, `lock` (только с булевым `enabled`), `status: "ONLINE"`,
`onecVersion` — версия платформы. Бизнес-агент — одну строку: `key`, `status` (`ONLINE`/`OFFLINE`), `extVersion`.

**Полный и частичный срез.** `basesComplete: true` — полный: сервис применяет его с `complete: true` (базы, которых в
срезе нет, у админ-агента получают `MISSING`) и запоминает время среза. Без флага — частичный: обновляются только
присланные строки (`agentRouter.ts:349-357`). Агент частичных срезов не шлёт: `bases` у него только полный и только по
просьбе. Не собрался за 25 с — heartbeat уходит без `bases`, и сервис попросит снова. Регистрация тоже несёт полный срез.

**Ответ сервиса** `{success: true, data: {ok: true, wantFullBases, basesFullEverySecs}}` (`agentRouter.ts:361-367`):

| Поле | Как считает сервис | Что делает агент |
|---|---|---|
| `wantFullBases` | у агента есть сервер и последний полный срез старше `AGENT_BASES_FULL_EVERY_SECS` (по умолчанию 300 с, 30–3600) или его не было; полный срез в этом же heartbeat считается свежим (`needsFullBases`, `bases/service.ts:904-907`) | запоминает и прикладывает полный срез к следующему heartbeat; heartbeat не доставлен — просьба сохраняется |
| `basesFullEverySecs` | значение настройки | не читает (`HeartbeatData` — только `wantFullBases`, `protocol.rs:164-169`) |

`pollMaxWaitSecs` приходит только в ответе регистрации, агент со сборки `2026-09-15 16:23` ждёт опроса не дольше него (`poll_wait`, задача А29); `basesFullEverySecs` пишет в журнал — полный срез баз по-прежнему шлёт по `wantFullBases`.

**Прощание при остановке** (`run`, `agent.rs:458-494`). Агент переходит в `STOPPING`, закрывает мост, до 10 с ждёт
начатые команды, отвечает по взятым и не законченным (`AGENT_STOPPED` / `AGENT_STOPPING`, §4), переходит в `OFFLINE` и
шлёт последний heartbeat (ждёт до 5 с). Сервис по `status = "OFFLINE"` (`isFarewell`, `instances.ts:62`) снимает
владение с этого экземпляра (`releaseOwnershipIf`, `agentRouter.ts:331-336`), и сменивший его процесс не получает 409.
Команды при этом не закрываются: оставшиеся за прежним процессом закроет регистрация нового (`AGENT_RESTARTED`).

**`OFFLINE` — только прощание** (со сборки `2026-09-15 15:31`, задача А26). При недоступности сервиса главный цикл
тоже переходит в `OFFLINE` (`on_cloud_error`, `agent.rs`), но heartbeat отправляет его как `ONLINE`: дошедший до
сервиса heartbeat сам доказывает связь (`state::wire_status`). `OFFLINE` уходит лишь после признака остановки
(`FAREWELL`). ⚠ Сборки до 15:31 первым heartbeat после сбоя связи (пока шли команды) слали `OFFLINE`: сервис снимал
владение с живого процесса, следующий запрос того же процесса занимал его снова.

## 3. Команды: что приходит и что вернуть

Payload валидируется схемами Zod **строго** (`.strict()`) — лишних полей быть не может.

### `CLUSTER_LIST_INFOBASES` — READ, база не нужна

Payload: `{}`. Это команда кнопки «Обновить из кластера».

```jsonc
{ "items": [
  { "key": "buh_alma",           // ИМЯ ИБ В КЛАСТЕРЕ — им она адресуется во всех остальных командах
    "name": "ТОО Алма (бухгалтерия)",
    "status": "OK",              // необязательно; при отсутствии останется прежний
    "onecVersion": "8.3.25.1257",// необязательно
    "sessionsCount": 3,          // необязательно
    "published": true,           // необязательно: есть ли публикация на веб-сервере
    "publishUrl": "http://localhost/buh_alma" }
] }
```

Как это применяется (`bases.sync(serverId, items, { complete: true, authoritative: true })`):

- `key` — единственное обязательное поле, ключ upsert'а `(server_id, key)`;
- **`null`/отсутствие поля означает «не знаю», а не «пусто»**: прежнее значение сохраняется
  (`COALESCE`). Не присылайте `null`, чтобы «очистить» — очистить так нельзя;
- `extVersion` присылает **бизнес**-агент, админ-агент его не знает и слать не должен;
- срез считается полным: базы, которых нет в `items`, получают `status = 'MISSING'`.
  Поэтому частичный список **недопустим** — либо все базы кластера, либо `ERROR`;
- `published` — **три состояния**: `true` (публикация есть), `false` (точно нет),
  отсутствие поля (не проверяли). Не подставляйте `false` вместо «не проверял»: панель
  по `false` предлагает публиковать, и ложное «нет» отправит администратора публиковать
  уже опубликованные базы. Признак берётся из конфигурации веб-сервера (наличие
  каталога публикации и записи в `default.vrd`/`web.config`), а не из кластера.

После успешного `IB_PUBLISH` сервис сам ставит базе `published = true` и `publishUrl`
из ответа команды — ждать ближайшего среза не требуется.

> **`X-Agent-Instance` и `details` отказа** описаны в одном месте — раздел «Экземпляр агента» в конце документа.
> Коротко: заголовок обязателен на каждом запросе, и владение токеном сервис решает только по нему.

> **Аутентификация rac.** Если в кластере заведён администратор, каждый вызов `rac` обязан
> представляться `--cluster-user`/`--cluster-pwd` (операции уровня центрального сервера —
> `--agent-user`/`--agent-pwd`). Иначе любая READ-команда возвращает «Администратор кластера
> не аутентифицирован». Учётные данные хранит агент; сервис их не передаёт.

### `CLUSTER_LIST_PUBLICATIONS` — READ, база не нужна

Payload: `{}`. Читает веб-сервер (каталоги публикаций + `default.vrd`/`web.config`), а не
кластер, поэтому базу не адресует: спрашиваем сразу все.

```jsonc
{ "items": [ { "key": "buh_alma",              // ИМЯ БАЗЫ В КЛАСТЕРЕ — то же, что в срезе баз
               "name": "Бухгалтерия Алматы",   // наименование базы, только для чтения человеком
               "published": true,
               "url": "http://localhost/buh_alma" } ],
  "complete": true,                            // просмотрены ВСЕ веб-серверы машины
  "source": "iis",                             // "iis" | "scan" — чем собран срез
  "lookedIn": ["C:\\inetpub\\wwwroot\\db"] }   // где именно искали
```

- `key` — **имя базы в кластере**, которым она адресуется во всех остальных командах.
  Наименование сюда не кладётся никогда: сопоставить такую запись с реестром нечем. С
  2026-09-11 агент отдаёт наименование отдельным полем `name`;
- `complete: true` — обещание, что список полный. Только тогда сервис помечает
  `published = false` базы, которых в списке нет. Без этого флага (или при `false`) он лишь
  отмечает найденное: агент, видящий один веб-сервер из двух, иначе объявил бы
  неопубликованными сотню работающих баз;
- **срез, в котором нет ни одной публикации, полным не объявляется никогда** (`complete:
  false`): веб-сервер без публикаций и чтение не того каталога снаружи неотличимы;
- пустой список не применяется вовсе — по той же причине, что и пустой срез баз;
- `url` — адрес публикации; при снятии публикации сервис его стирает;
- `source` и `lookedIn` — диагностика для человека: чем собран срез и какие каталоги
  просмотрены. Показывать их стоит рядом с пустым срезом — это единственный способ отличить
  «не опубликовано» от «искали не там», не заходя на сервер.

Эта команда закрывает пробел, из-за которого признак публикации у ста баз оставался
«не проверялся» до тех пор, пока публикацию не сделают из панели.

### `CLUSTER_LIST_SESSIONS` / `CLUSTER_LIST_CONNECTIONS` — READ

Payload: `{ "baseKey"?: "buh_alma" }` — без него весь кластер, с ним одна база.

```jsonc
{ "items": [ { "session": "12", "user": "Иванов", "host": "WS-14", "app-id": "1CV8C", "started-at": "…" } ] }
```

Строка — **словарь строк**, набор ключей задаёт `rac` (панель типизирует его как
`Record<string, string>` и показывает как есть). Отдавайте поля `rac` без переименования.

### `CLUSTER_INFOBASE_INFO` — READ, база обязательна

Payload: `{ "baseKey": "buh_alma" }`. Результат — свободный объект со сведениями `rac`.

### `CLUSTER_LIST_LOCKS` / `CLUSTER_LIST_PROCESSES` / `CLUSTER_LIST_LICENSES` — READ

Payload: `{"baseKey"?: "…"}` для блокировок (без него — весь кластер), `{}` для остальных.
Результат — `{items: [ … ]}`, строки словарями строк, ключи как отдаёт `rac` (панель
показывает их как есть, переименовывать не нужно).

Зачем именно эти три: «база висит» почти всегда означает блокировку, а отказы при
одновременных подключениях упираются в лицензии — без этих списков и то и другое
диагностируется вслепую.

### `CLUSTER_DISCONNECT` — **CRITICAL**

Payload (`admin.ts:199`): `{"connectionId": "<uuid соединения>", "baseKey"?: "…"}` — `connectionId` 1–64 символа,
`baseKey` 1–200. Как и у сеанса, идентификатор — **UUID**, а не номер. `baseKey` агент не читает: он нужен сервису
для маршрутизации и аудита.

Ответ — не просто `{ok: true}`, а с эхом (`Cluster::disconnect`, `CLUSTER_DISCONNECT` в `execute_cluster`):

```jsonc
{ "ok": true, "connectionId": "…", "processId": "…",   // processId — рабочий процесс, в котором было соединение
  "state": {
    "connections": { "items": [ … ], "complete": true, "readAt": "…", "stillListed": false },
    "locks":       { "items": [ … ], "complete": true, "readAt": "…" } } }
```

`state.connections` — соединения всего кластера после разрыва (`stillListed: true` — строка ещё видна на момент
`readAt`), `state.locks` — блокировки всего кластера: разрыв их освобождает. Блоки независимы: не ответил хоть один
кластер — этого блока нет, а разрыв неудачным не становится. Сервис `state` не применяет и оставляет в записи команды —
панель берёт его оттуда. Соединение не найдено ни в одном кластере — `RAC_ERROR` «соединение … не найдено в кластере —
возможно, оно уже закрыто. Идентификатор должен быть UUID соединения, а не его номером».

### `CLUSTER_TERMINATE_SESSION` — **CRITICAL**

> Со сборки агента `2026-09-15 16:48` (А31): `sessionId` — только UUID сеанса (8-4-4-4-12); иное — `VALIDATION_ERROR`, `rac` не вызывается. Сервис с `b806507` пропускает только UUID (С27).

Payload (`admin.ts:158`): `{ "sessionId": "<uuid сеанса>", "baseKey"?: "buh_alma" }` — `sessionId` 1–64 символа,
`baseKey` 1–200.

⚠ `sessionId` — это **UUID** сеанса (поле `session` в строке `rac`), а НЕ его номер
(`sessionId` в той же строке). Проверено зондом: на UUID `rac` отвечает «Сеанс с указанным
идентификатором не найден», на номер — «Ошибка разбора параметра: session».
`baseKey` — только для маршрутизации и аудита.

Результат: `{ "ok": true, "sessionId": "…", "state": { "sessions": { "items", "complete": true, "readAt", "stillListed" } } }`.
Агент перебирает кластеры сервера; первый успешный `rac session terminate` — успех (`Cluster::terminate_session`,
`cluster/mod.rs:1967-1992`).

**Сеанса уже нет** (агент после `2026-09-15 01:06`): если «не найден» ответили ВСЕ кластеры, это `SUCCESS`
`{ok: true, sessionId, alreadyGone: true}` с тем же эхом `state.sessions` — повтор после 202 и двойное нажатие
безопасны. Ответил иначе хоть один кластер — отказ этого кластера (`RAC_*`). Сборки до этого времени на уже снятый
сеанс отвечали отказом `RAC_ERROR`.

### `CLUSTER_SET_SESSIONS_LOCK` — **CRITICAL**, база обязательна

Payload (`admin.ts:619-628`):

```jsonc
{ "baseKey": "buh_alma",                // обязательно, 1–200
  "enabled": true,                      // обязательно, boolean; без него агент отвечает VALIDATION_ERROR
  "message": "Обслуживание до 19:00",   // необязательно, ≤ 500 символов
  "from": "…", "to": "…",               // необязательно, ≤ 40 символов каждое: окно блокировки
  "permissionCode": "…" }               // необязательно, ≤ 64 символов: код входа в заблокированную базу
```

Результат: `{ "ok": true, "baseKey": "…", "requested": true, "enabled": true, "state": { "lock": {…} } }` —
блокировка, прочитанная `rac infobase info` ПОСЛЕ изменения (форма — в разделе «Эхо состояния»). С агента
`2026-09-16 23:45` (А48) `enabled` — **факт** из этого чтения, а не повтор запроса: не прочиталось — поля нет и
`unverified: ["enabled"]`; кластер не изменил блокировку — `enabled` прежний и `warning` «блокировка начала
сеансов после записи по-прежнему …». Если
блокировку включили, а вход сейчас не закрыт (`state.lock.active: false`: в кластере осталось окно
прошлой блокировки), в ответе ещё и `warning` с этим окном. Единственная кластерная команда, которой
нужен служебный администратор ИБ (`BPAPI_IB_USER`/`BPAPI_IB_PWD`), — остальным хватает
администратора кластера.

**Включение сбрасывает незаданное** (агент после `2026-09-14 23:16`): окно — нулевой датой 1С,
сообщение и код разрешения — пустыми; прежде они оставались от прошлой блокировки. Как `rac`
принимает пустые значения, на кластере ещё не проверено, поэтому по ступеням: всё → только окно →
как прежде. В ответе `reset: "all" | "dates" | "none"` и `note`, если сброшено не всё; действует
ли итог — `state.lock.active`. Выключение — только `--sessions-deny=off`.

Загрузка и обновление конфигурации (`IB_RESTORE`, `IB_APPLY_UPDATE` с `lockSessions`) после
установки своей блокировки проверяют, что она **действует**. Не действует — ставят окно «сейчас —
сутки вперёд»; не помогло и это — снимают блокировку и отказывают кодом `SESSIONS_LOCK_NOT_ACTIVE`,
операцию не начиная (агент с `2026-09-14`, после сборки `22:38`). Порядок и ответ этих команд — в §3.2,
«`IB_RESTORE` и `IB_APPLY_UPDATE`».

> **Время по этапам, агент `2026-09-16 12:37`.** Внутрибазовые команды, идущие через COM-мост, отдают
> в успехе `data.stages` — `[{ "name": "вход в базу", "ms": 192000 }, …]`: вход в базу, чтение файла
> расширения, поиск расширения в базе, запись и применение, удаление, эхо состояния. Отказ несёт ту же
> раскладку хвостом текста: «. Время по этапам: вход в базу 3 мин 12 с; до отказа 41 с» — этап «до
> отказа» покрывает участок, на котором операция прервалась. Панели это отвечает на вопрос «почему так
> долго»: у типовой на БСП минуты обычно уходят на вход в базу (обновление информационной базы при
> внешнем соединении), а не на саму операцию.

### `CLUSTER_SET_SCHEDULED_JOBS` — **CRITICAL**, база обязательна

Агент с `2026-09-16 12:13`. Запрет регламентных и фоновых заданий базы (`rac infobase update
--scheduled-jobs-deny=on|off`).

```jsonc
{ "baseKey": "buh_alma",   // обязательно
  "denied": true }          // обязательно, boolean; true — задания запрещены
```

Поле названо `denied`, а не `enabled`: у блокировки сеансов `enabled: true` значит «вход закрыт», и
одинаковое имя с обратным смыслом в соседних командах — готовая ошибка на живой базе. Без поля —
`VALIDATION_ERROR`.

Результат: `{ "ok": true, "baseKey": "…", "requested": true, "denied": true, "was": false, "state": { "lock": {…} } }`.

- `requested` — что просили; есть всегда.
- **`denied` — ФАКТ, прочитанный ПОСЛЕ записи** (агент с `2026-09-16 23:45`, А47; в `12:13` это был повтор
  запроса). Прочитать не удалось — поля **нет**, а в ответе `unverified: ["denied"]`. Прочитано и расходится с
  `requested` — в `denied` факт, и `warning` («кластер принял команду, но после записи регламентные задания
  по-прежнему …»).
- `was` — как было до команды (из `rac infobase info`, поле `scheduled-jobs-deny`); без него нельзя узнать,
  нужно ли возвращать прежнее состояние.
- `state.lock` — блокировка, прочитанная ПОСЛЕ изменения; признак заданий в ней — `scheduledJobsDenied`.

Сервису: в реестр — `state.lock.scheduledJobsDenied`, затем `denied`; значение из payload — только когда нет
ни того, ни другого, и **без отметки «прочитано»** (источник — команда).

**Зачем отдельная команда.** Фоновое задание базы держит её разделённым доступом, и монопольная
операция (установка расширения, меняющего структуру данных; выгрузка; проверка) отказывает. Снятие
сеанса помогает ровно до следующего запуска по расписанию, а блокировка начала сеансов уже
запущенные задания не останавливает. Порядок для панели: запретить задания → снять оставшиеся
сеансы (`CLUSTER_TERMINATE_SESSION`) → выполнить операцию → **вернуть прежнее значение** по `was`.
Агент сам ничего не возвращает: команда одна, и обратный вызов делает тот, кто её ставил.

### `CLUSTER_DROP_INFOBASE` — **CRITICAL**, база обязательна

Удаляет **регистрацию** базы в кластере, а не данные: ключи `--drop-database`/`--clear-database` агент не передаёт
никогда (`Cluster::drop_infobase`). Место базы в очереди сервиса команда не занимает: в базу не входит.

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `baseKey` | строка 1–200 | да | имя базы в кластере |
| `confirm` | литерал `true` | да | иное значение сервис не пропустит (`z.literal(true)`, `admin.ts:564-567`); агент проверяет ещё раз и без `true` отвечает `VALIDATION_ERROR` |

`dryRun` у команды нет. Перед удалением агент убеждается через СУБД (`ibcmd`), что базы данных нет. Любое сомнение —
отказ, и со сборки `2026-09-15 16:23` у каждого свой код (§4: `INFOBASE_DB_ALIVE`, `DB_PASSWORD_MISSING`, `IBCMD_UNAVAILABLE`, `DB_PARAMS_UNAVAILABLE`, `DB_CHECK_FAILED`; задача А28), а до неё все приходили кодом `RAC_ERROR`, различаясь текстом: база **РАБОТАЕТ** (данные на месте); не задан
пароль СУБД (`cluster.db_password`); рядом с `rac.exe` нет `ibcmd.exe`; кластер не отдал параметры базы данных; вход в
СУБД не принят или ответ не распознан. Базы нет в кластере — `INFOBASE_NOT_FOUND`.

```jsonc
{ "ok": true, "baseKey": "buh_alma",
  "note": "регистрация удалена из кластера; база данных не трогалась — её не было",
  "state": { "infobases": { "items": [ … ], "complete": true, "readAt": "…", "stillListed": false } } }
```

`state.infobases` — список баз после удаления в форме `CLUSTER_LIST_INFOBASES`. Его нет, если не ответил хоть один
кластер или удалена последняя база (пустой срез агент не отдаёт). Сервис с полным `state.infobases` замещает им реестр
баз сервера, без него помечает базу отсутствующей (`planWriteState`, `writeState.ts:93-100`); блок остаётся в записи
команды.

### `CLUSTER_CHECK_BASES` — READ, база не нужна

> Со сборки `2026-09-15 16:23` (задача А24): база, по которой идёт операция агента (занят её замок), в проверку через `ibcmd` не открывается — в `items[]` у неё `reason` «не проверялась: по базе идёт операция агента — ibcmd её не открывает, чтобы не помешать» и, со сборки `2026-09-15 17:30`, признак `busy: true` (А34) — проверять его, а не текст. Это не ошибка: на сутки такая база не откладывается, её решит следующая проверка. Фоновая проверка агента поступает так же.

Есть ли у баз кластера их база данных в СУБД — по требованию: сначала один запрос к СУБД на сервер, что так не решилось —
`ibcmd` пачками (`Cluster::check_bases`, `cluster/mod.rs`).

Payload (`admin.ts:584`): `{ "baseKeys"?: ["buh_alma", …] }` — массив ≤ 1000 строк 1–200. Поля нет или список пуст —
все базы кластера. Одинаковый набор имён (без учёта порядка и повторов) склеивается в одну команду (`readKey`).

```jsonc
{ "items": [ { "key": "buh_alma", "dbMissing": false },
             { "key": "aibek",    "dbMissing": true },
             { "key": "abdali",   "reason": "рядом с rac.exe нет ibcmd.exe" } ],
  "checked": 2, "skipped": 1, "byQuery": 2,
  "note": "рядом с rac.exe нет ibcmd.exe — 1 баз(ы), не решённых запросом к СУБД, проверить нечем; прежнее знание о них не изменено" }
```

| Поле | Смысл |
|---|---|
| `items[].key` | имя базы в кластере |
| `items[].dbMissing` | `true` — базы данных в СУБД нет, `false` — есть. Поля нет — проверить не удалось |
| `items[].reason` | почему не проверена; есть только у непроверенных. Без пароля СУБД строки приходят голыми `{key}`, причина — в `note` |
| `checked` | сколько баз проверено (строк с `dbMissing`) |
| `skipped` | сколько не проверено |
| `byQuery` | сколько решено одним запросом к СУБД; остальные проверены `ibcmd` или не проверены. По нему видно, работает ли быстрый путь на этом сервере |
| `note` | пустая строка или объяснение: СУБД не приняла вход (проверки приостановлены на час), нет `ibcmd.exe`, не задан пароль СУБД, сколько баз не проверено |

Сервис применяет только строки с булевым `dbMissing`: `true` ставит базе причину «нет в СУБД» (`NO_DB`), `false`
снимает только её (`applyCheckResult`/`applyDbPresence`, `bases/service.ts:538-578`); строки без признака не трогает.
Применяется при приёме результата, а не в запросе панели: на сотне баз проверка дольше 20 с. `reason`, `checked`,
`skipped`, `byQuery`, `note` остаются в записи команды для панели. Без `baseKeys` агент сначала читает список баз
кластера; не прочитал — отказ `RAC_*`.

## 3.1. Кодировка вывода `rac` — казахские буквы

**Симптом.** Имена баз приходят как `Жа?аш М?ратхан ИП`, `Айбек Абай Жолдасбек?лы ИП`.
Проверка байтов в реестре: `d096 d0b0 3f` — `3f` это обычный ASCII `?`, то есть буква
потеряна ДО отправки, а не при показе. Русские буквы целы, пропали только казахские
(ә ғ қ ң ө ұ ү һ і) — характерный след транскодирования через **CP1251**: русский там
есть, казахского нет, и всё непредставимое заменяется на `?`. Восстановить нечем:
преобразование одностороннее.

**Где чинить.** Только в агенте, на границе с `rac`. Вывод утилиты нельзя декодировать
как CP1251 или CP866 — в обеих кодировках казахских букв нет вовсе.

Основной способ (не проверен на живом кластере — подтвердите): запускать `rac` с
консолью в UTF-8 и читать поток как UTF-8.

```cmd
cmd /c chcp 65001 >nul && "C:\Program Files\1cv8\8.3.25.1257\bin\rac.exe" infobase summary list …
```

В коде агента: читать stdout **байтами** и декодировать UTF-8 явно, не полагаясь на
кодировку по умолчанию (для .NET — `Console.OutputEncoding`/`StandardOutputEncoding =
new UTF8Encoding(false)`, для Node — `spawn` без `encoding` и затем `Buffer.toString("utf8")`).

Запасной путь, если `rac` игнорирует `chcp`: имена баз лежат в файле кластера
`1CV8Clst.lst` в каталоге данных сервера — он в UTF-8, и `rac` для получения имён тогда
не нужен вовсе.

**После исправления** нужен один прогон «Обновить из кластера»: имена в реестре
перезапишутся правильными. Сервис при этом защищён — целое имя не затирается битым
(`bases.sync`: имя с `?` принимается, только когда своего ещё нет), так что случайный
запуск старого агента реестр больше не испортит.

## 3.2. Внутрибазовые команды: пользователи и расширения

Другой транспорт и другая способность: эти команды требуют **входа в базу** (COM-соединение
или расширение), поэтому агент обязан объявить `capabilities: ["cluster.admin", "ib.admin"]`.
Без `ib.admin` сервис откажет сразу, не ставя команду в очередь.

Каждой нужен служебный администратор ИБ в целевой базе (`BPAPI_IB_USER`/`BPAPI_IB_PWD`).

| Команда | Payload | Результат |
|---|---|---|
| `IB_LIST_USERS` | `{baseKey}` | `{items:[{name, fullName?, disabled?, roles?[]}]}` |
| `IB_CREATE_USER` | `{baseKey, name, fullName?, password?, roles?[], addRoles?[], osUser?, showInList?}` | `{ok:true, roles?[], catalog?}` |
| `IB_LIST_ROLES` | `{baseKey}` | `{items:[{name, synonym?}]}` |
| `IB_UPDATE_USER` | `{baseKey, name, newName?, fullName?, password?, addRoles?[], removeRoles?[], roles?[], disabled?, showInList?}` | `{ok:true, catalog?}` |
| `IB_DELETE_USER` | `{baseKey, name}` | `{ok:true, catalog?}` |
| `IB_LIST_EXTENSIONS` | `{baseKey}` | `{items:[{name, synonym?, version?, purpose?, safeMode?}]}` |
| `IB_INSTALL_EXTENSION` | `{baseKey, name, contentBase64, safeMode?}` | `{ok:true}` |
| `IB_DELETE_EXTENSION` | `{baseKey, name}` | `{ok:true}` |
| `IB_PUBLISH` | `{baseKey, alias?, dir?, webServer?: "iis" \| "apache22" \| "apache24"}` | `{ok:true, url, urlConfirmed, urlNote}` |
| `IB_UNPUBLISH` | `{baseKey, alias?, webServer?: "iis" \| "apache22" \| "apache24"}` | `{ok:true, alias, note?}` |
| `IB_BACKUP` | `{baseKey, dir?}` | `{ok:true, path, sizeBytes?, transport?}` |

Что важно соблюсти:

- **Списки полные.** Результат `IB_LIST_*` замещает кэш базы целиком: чего нет в ответе,
  сервис удаляет из реестра. Частичный список молча «потеряет» пользователей.
- **`synonym` в `IB_LIST_EXTENSIONS`** — Синоним расширения из 1С. Служебное Имя часто
  нечитаемо (`EF_00_00062442`), и сводка по расширениям без синонима превращается в список
  идентификаторов. Поле необязательное, но без него панель показывает только имя.
- **`contentBase64`** — содержимое `.cfe` без префикса `data:`. Файл приходит телом команды:
  агент не ходит за ним в сеть.
- **Идемпотентность НЕ отменяет проверку базы.** «Повторное действие = SUCCESS» верно только
  для базы, которая на этом сервере ЕСТЬ. Если базы нет — `INFOBASE_NOT_FOUND`, а не `SUCCESS`.
  Живой случай: `IB_UNPUBLISH` по базе `_transition` вернул `SUCCESS` с машины, где этой базы
  нет вовсе; сервис поверил и записал «публикация снята», а на боевом сервере публикация
  осталась. Успех за невыполненную работу хуже честной ошибки: он ломает реестр.
- **Идемпотентность обязательна.** Панель перестаёт ждать ответ через 20 с и дальше следит за
  командой по номеру (§1), а команда живёт 900 с и дольше — пользователь может повторить
  операцию, которая на самом деле идёт. Долгие изменяющие команды сервис склеивает с идущей по
  `requestId` — только пока идущая не завершена (§1, «Смысл `requestId`»), — но на агенте повтор всё равно
  должен быть безопасен.
  Повторное создание существующего пользователя и повторное удаление отсутствующего должны
  завершаться `SUCCESS`, а не ошибкой.
- **`IB_BACKUP` обязан вернуть `path`.** Отчёт «выгружено 110 баз» без пути не отвечает на
  единственный вопрос, который после него задают, — куда легло. Имя файла назначает агент:
  раскладку дисков сервера панель не знает и знать не должна; `dir` лишь перенаправляет
  выгрузку. Подробности и остальные команды обслуживания — в `docs/PROMPT_AGENT_MAINTENANCE.md`.
- **`IB_UNPUBLISH` — обратная публикации:** снятие виртуального каталога и записи о базе
  (`webinst -delete` или эквивалент). Идемпотентна: снятие публикации с неопубликованной
  базы — `SUCCESS`, а не ошибка. После успеха сервис ставит базе `published = false` и
  СТИРАЕТ `publishUrl`: ссылка на несуществующую страницу хуже её отсутствия.
- **Публикация НЕ требуется внутрибазовым командам.** `IB_LIST_USERS`, `IB_CREATE_USER`,
  `IB_DELETE_USER`, `IB_LIST_EXTENSIONS`, `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` идут
  через COM-соединение с сервером 1С напрямую. Веб-публикация нужна только каналу HTTP
  (расширение `buhprof_api` бизнес-агента). Не отказывайте в этих командах неопубликованной
  базе: её как раз готовят к публикации.
- **`IB_PUBLISH` — не операция над базой.** Публикация делается настройкой веб-сервера
  (виртуальный каталог + `default.vrd`), в скриптовом API 1С её нет: агент выполняет её
  запуском `webinst`, как запускает `rac`. Публиковать **только на localhost** — агент ходит
  в HTTP-сервис с той же машины. `alias`, `dir`, `webServer` необязательны: при отсутствии
  агент подставляет свои умолчания (поля, умолчания и отказы — «`IB_PUBLISH` и `IB_UNPUBLISH`» ниже).
- **Расширения — по-русски.** COM-соединение отдаёт члены на языке конфигурации:
  `РасширенияКонфигурации.Получить()/Создать()`, `Расширение.Записать(ДвоичныеДанные)`.
  Английские имена дают `0x80020003 DISP_E_MEMBERNOTFOUND` — эту ошибку панель уже
  расшифровывает пользователю как «исправляется в агенте». Подробности — в
  `docs/PROMPT_AGENT_IB.md`.
- **Пароль не логировать.** Он приходит в payload и не должен попадать ни в лог агента, ни
  в текст ошибки. Сервис его у себя не хранит: в задание пакета `password` и `contentBase64`
  не записываются.

### `IB_PUBLISH` и `IB_UNPUBLISH`: поля, умолчания, отказы

Схемы — `admin.ts:409-416` и `admin.ts:524-529`; исполнение — `Ib::publish`, `Ib::unpublish` (`ib/mod.rs`).

| Поле | Тип и предел | Умолчание агента | Проверка агента |
|---|---|---|---|
| `baseKey` | строка 1–200, обязательно | — | нет базы в кластере — `INFOBASE_NOT_FOUND` |
| `alias` | ≤ 200 | `baseKey` | у публикации — только латиница, цифры, `-`, `_`, иначе `IB_BAD_PAYLOAD` |
| `dir` | ≤ 500, только `IB_PUBLISH` | `C:\inetpub\1c\<alias>` | каталог не создался — `IB_ERROR` |
| `webServer` | `"iis"` \| `"apache22"` \| `"apache24"` | `iis` | иное значение — `IB_BAD_PAYLOAD` (сервис его и не пропустит) |

`IB_PUBLISH` отвечает `{ok: true, url, urlConfirmed, urlNote}`: адрес агент спрашивает у IIS; подтвердил —
`urlConfirmed: true`, иначе `http://localhost/<alias>` с `urlConfirmed: false` и причиной в `urlNote`. `webinst` вернул
ошибку — `IB_PUBLISH_FAILED` (обычно права на веб-сервер или каталог), не ответил вовремя — `IB_TIMEOUT`, нет
`webinst.exe` — `IB_UNAVAILABLE`. `IB_UNPUBLISH` отвечает `{ok: true, alias}`; если `webinst` ответил «не найден» или
«отсутствует» — тоже успех с `note: "публикации не было"`, прочий отказ — `IB_ERROR`. Эхо `state.publication` — только
для `iis` (таблица «Эхо состояния»).

#### `IB_INFO` — сведения о базе (со сборки агента `2026-09-15 23:24`, задача А38)

Только чтение, по запросу; фонового чтения нет (версия конфигурации меняется загрузкой и обновлением — там она приходит в эхе). Тип объявляется вместе с остальными командами внутрь базы — при подтверждённом входе (`ib.admin`). Команда внутрь базы: у агента — замок базы, срок — обычный.

payload: `{ baseKey, auth? }` — `auth` подставляет сервис при выдаче, как у остальных команд внутрь базы.

Ответ:

```json
{
  "ok": true,
  "baseKey": "_transition",
  "config": { "name": "БухгалтерияПредприятия", "version": "3.0.180.20", "synonym": "Бухгалтерия предприятия", "readAt": "2026-09-15T18:24:00Z" },
  "registration": { "…": "поля info из CLUSTER_INFOBASE_INFO" },
  "state": {
    "config": { "name": "…", "version": "…", "synonym": "…", "readAt": "…" },
    "extensions": { "items": [], "complete": true, "readAt": "…" },
    "lock": { "enabled": false, "…": "форма state.lock" }
  }
}
```

Конфигурация и расширения — одним входом (COM, действие моста `read-state`); расширения, не прочитанные через COM, — через `ibcmd`. `version` — `null`, если в конфигурации версия не задана. Не вошли в базу — отказ с кодом входа (`IB_AUTH_FAILED`, `IB_CONNECT_FAILED`, …). Блоки `state.*` — той же формы, что эхо изменяющих команд: сервис применяет их тем же разбором (С35). `registration` и `state.lock` — только у админ-агента с кластером.

`IB_INSTALL_EXTENSION` через COM со сборки `23:24` кладёт в ответ `config {name, version, synonym, readAt}` — конфигурацию базы, к которой встало расширение, а в отказ записи дописывает «[конфигурация базы: имя версия]».

**Сервис (С35).** Спецификация — READ, `ib.admin`, база обязательна, срок 900 с; повторные запросы по базе склеиваются. Панель спрашивает `GET /v1/onec/bases/:key/ib-info` (кнопка «Обновить сведения» в карточке базы; путь `/bases/:key/info` — это `CLUSTER_INFOBASE_INFO`). Применение (`planWriteState`, `onec/writeState.ts`): `state.lock` — блокировка, источник `cluster`; `state.config`, а без него поле `config` — конфигурация «как прочитана»: `version: null` записывается (`setConfig(…, exact)`), и карточка пишет «версия не задана»; `state.extensions` — общим разбором эха (`parseEcho`), из ответа вырезается. `config` в ответе `IB_INSTALL_EXTENSION` применяется так же; текст отказа сервис не разбирает. `registration` не применяется — остаётся в ответе. Реестр обновляется до того, как команда объявлена выполненной (С36), поэтому прочитанное уже там, когда панель получает ответ. Сборка без типа `IB_INFO` при `ib.admin` — в «Нет в этой сборке» (`missingFeatures`: `info`), кнопка недоступна.

### `IB_CHECK` — проверка базы (WRITE, база обязательна, срок 15 000 с)

Payload (`admin.ts:450-462`, `.strict()`):

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `baseKey` | строка 1–200 | да | база |
| `reindex` | boolean | нет | переиндексация (`-ReIndex`) — только с `repair` |
| `logicalIntegrity` | boolean | нет | логическая и ссылочная целостность (`-LogAndRefsIntegrity`) |
| `recalcTotals` | boolean | нет | пересчёт итогов (`-RecalcTotals`) — только с `repair` |
| `repair` | boolean | нет | чинить, а не только смотреть |
| `dryRun` | boolean | нет | план без входа в базу |

Без `repair` — только осмотр: агент идёт в режим `/IBCheckAndRepair` с `-LogAndRefsIntegrity -TestOnly`;

выбранное плюс восстановление созданием объектов (`-BadRefCreate -BadDataCreate`); ничего не выбрано — целостность
(`Ib::check_keys`, `ib/mod.rs`). Проверка с `repair` доступна только полному доступу к 1С (аудит С4), без него — и
просмотру. Есть активные сеансы — `IB_BUSY` до запуска конфигуратора, и без `repair` тоже (`execute_ib`, проверка
сеансов перед `IB_BACKUP` и `IB_CHECK`).

Ответ (`Ib::check`, агент с `2026-09-14 22:05`):

```jsonc
  "repairMode": false,                      // = payload.repair (нет поля — false)
```

снимается. Прерывание `IB_CHECK` из панели сервис разрешает только агенту со способностью `agent.cancel.check` (§2.1).

3. Ожидание выхода пользователей — до 120 с, опрос раз в 3 с. Остались — `IB_BUSY` «осталось N активных сеансов».
4. Операция.
5. Снятие блокировки при любом исходе. Не снялась — у успеха поле `warning`, у отказа дописка к тексту «ВНИМАНИЕ:
   снять блокировку начала сеансов не удалось … — база закрыта для входа».


  загрузку» (`timeout_message`, `commands/mod.rs:1084-1100`). Процесс виден в `AGENT_LIST_PROCESSES` с `orphan: true` и
  `commandId` (§3.3).

### Эхо состояния: `state` в ответе изменяющей команды (способность `ib.echo`)

Изменение выполняется в открытом соединении с базой — прочитать в нём список сразу после
записи стоит миллисекунды. Поэтому изменяющие команды прикладывают новое содержимое к своему
же ответу, и сервис не ставит следом читающую команду (второй вход в базу с сеансом и
лицензией; на пакете по ста десяти базам — сто десять лишних входов).

| Команда | Поле | Содержимое |
|---|---|---|
| `IB_CREATE_USER`, `IB_UPDATE_USER`, `IB_DELETE_USER` | `state.users` | то же, что `IB_LIST_USERS` |
| `IB_INSTALL_EXTENSION`, `IB_DELETE_EXTENSION` | `state.extensions`; у установки через COM с агента `23:24` и `config` (не в `state`) | то же, что `IB_LIST_EXTENSIONS`; `config` — `{name, version, synonym, readAt}` конфигурации базы |
| `IB_INFO` (чтение, С35) | `state.config`, `state.extensions`, `state.lock`; `config` — и отдельным полем | конфигурация `{name, version, synonym, readAt}` (`version: null` — не задана); расширения как у `IB_LIST_EXTENSIONS`; `lock` — только у агента с кластером |
| `CLUSTER_TERMINATE_SESSION` | `state.sessions` | то же, что `CLUSTER_LIST_SESSIONS` без `baseKey` (весь кластер) |
| `CLUSTER_DISCONNECT` | `state.connections`, `state.locks` | соединения и блокировки кластера после разрыва (`CLUSTER_LIST_CONNECTIONS` / `CLUSTER_LIST_LOCKS` без `baseKey`) |
| `CLUSTER_SET_SESSIONS_LOCK`, `CLUSTER_SET_SCHEDULED_JOBS` | `state.lock` | блокировка после изменения — `{enabled, active?, message, from, to, scheduledJobsDenied?, permissionCodeSet, readAt}` |
| `CLUSTER_DROP_INFOBASE` | `state.infobases` | `{items, complete, readAt, stillListed}` — строки как у `CLUSTER_LIST_INFOBASES` |
| `IB_RESTORE`, `IB_APPLY_UPDATE` | `state.users`, `state.extensions`, `state.config`; с агента после `2026-09-15 01:06` и `state.lock` | списки как у `IB_LIST_*`; конфигурация `{name, version, synonym?, readAt}`; `lock` — блокировка после её снятия, форма как у `CLUSTER_SET_SESSIONS_LOCK`, только при `lockSessions`; каждый блок независим |
| `AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND` | `state.processes` | `{items, readAt, stillRunning}` — строки как у `AGENT_LIST_PROCESSES`; у отмены — только при `killed: true` |
| `IB_PUBLISH`, `IB_UNPUBLISH` | `state.publication` | `{published, url, webServer, readAt}` — только IIS (`appcmd`); у Apache блока нет; эха нет (Apache, публикация без подтверждённого адреса) — с агента `2026-09-18 13:13` в ответе `unverified: ["publication"]` |

У сеансов и соединений `state` — не для реестра, а для панели: сервис его не применяет и
оставляет в результате. Список всего кластера (панель держит именно такой и замещает его
целиком); `complete: true` — только если ответили все кластеры сервера, иначе `state` нет.
`stillListed` (у сеансов, соединений и `infobases` — всегда, `false` тоже) — снятие прошло, но
строка на момент `readAt` ещё в списке кластера.

**Блокировка `lock`.** Кода разрешения нет никогда — только `permissionCodeSet`. `from`/`to` —
в виде `rac` (`ГГГГ-ММ-ДДTчч:мм:сс`, местное время сервера), пусто и «нулевая» дата — `null`.
`active` — действует ли блокировка сейчас: включена И текущее время внутри окна; поля нет, если
даты в незнакомом виде. Тот же объект приходит в строке `CLUSTER_LIST_INFOBASES` и в полном срезе
баз heartbeat (поле `lock`) — из фонового чтения агента (до 20 баз в минуту, база раз в 10 мин,
отказ — пауза 6 ч); старше 30 мин или не читали — поля нет, и прежнее знание сохраняется.
`CLUSTER_INFOBASE_INFO` код разрешения тоже не отдаёт: вместо `permissionCode` — `permissionCodeSet`.

```jsonc
{ "ok": true,
  "state": { "users": { "items": [ { "name": "…", "fullName": "…", "disabled": false,
                                     "roles": ["…"] } ],
                        "complete": true,
                        "readAt": "2026-09-12T14:21:03Z" } } }
```

- **`complete: true` обязателен** — это обещание полноты: сервис замещает кэш базы ЦЕЛИКОМ, и
  строки, которых в списке нет, считаются удалёнными из базы;
- **перечитать не удалось — `state` не шлём вовсе.** Изменение при этом успешно: сервис, не
  увидев состояния, поставит читающую команду, как делал всегда. Неполный список хуже его
  отсутствия;
- форма строк — ровно та же, что у `IB_LIST_*`: сервис применяет их одним и тем же кодом;
- **способность `ib.echo`** объявляется в `capabilities` при регистрации. Без неё всё работает
  по-старому — совместимость со сборками без эха обязана сохраняться;
- из результата команды сервис вырезает **только `state.users` и `state.extensions`**, и только узнанной формы
  (`parseEcho`, `onec/echo.ts:109-130`): в реестре они уже есть, а задание на сто баз положило бы в журнал сто
  списков. Все остальные блоки — `sessions`, `connections`, `locks`, `lock`, `infobases`, `config`, `processes`,
  `publication` — остаются в записи команды, в том числе те, что сервис применил к реестру (`planWriteState`,
  `onec/writeState.ts`). Панель читает их оттуда. Разбор не зависит от типа команды: `state.extensions` у `IB_INFO`
  тоже применяется и вырезается. `config`, прочитанный агентом (эхо, `IB_INFO`, установка расширения), записывается
  как есть, с `version: null`; версия из `versionTo` без эха прежнее имя не затирает.

Спецификация целиком: [TASK_FRESH_STATE_AFTER_COMMAND.md](TASK_FRESH_STATE_AFTER_COMMAND.md).

### Правка ролей применяется так, как прислана (способность `ib.roles`)

`IB_UPDATE_USER` принимает роли двумя способами: поправками (`addRoles`, `removeRoles`) и полным
набором (`roles`, в том числе пустым). Сборки агента до 13.09.2026 на поправки и на пустой набор
отвечали успехом, ничего не меняя. Панель обходила это чтением `IB_LIST_USERS` перед каждой
правкой прав и слала полный набор — лишний вход в базу и гонка с конфигуратором между чтением и
записью.

Способность `ib.roles` — обещание сборки:

- `addRoles` / `removeRoles` применяются в том же соединении, в котором пишется пользователь:
  снимается только выданная роль, добавляется только отсутствующая. Читать роли перед командой
  не нужно, повтор команды безопасен;
- `roles: []` снимает все роли, а отсутствие поля `roles` роли не трогает — это разные запросы;
- порядок внутри команды фиксирован: полный набор → снятие → добавление;
- все имена разбираются до первого изменения: роль, которой нет в конфигурации базы, — отказ
  `IB_ROLE_NOT_FOUND` с её именем, и в базу не пишется ничего;
- `state.users` в ответе прочитан после записи — по нему сервис сверяет, что роли легли
  (`checkRoleIntent`), и при расхождении отвечает отказом.

Панель при `ib.roles` шлёт поправки без предварительного чтения; без способности — прежний обход.
Задача панели: [TASK_PANEL_ROLES_WITHOUT_PREREAD.md](TASK_PANEL_ROLES_WITHOUT_PREREAD.md).

### «Показывать в списке выбора» не читается — и сервис помнит своё

`IB_LIST_USERS` возвращает `{name, fullName, disabled, roles}`; признака «показывать в списке
выбора» там нет. Пока записанное никто не запоминал, панель вела себя так, будто запись не
проходит: человек включает тумблер, команда `IB_UPDATE_USER` с `showInList: true` завершается
успехом, карточка перечитывает базу — и показывает «выключено», потому что значения не знает
(жалоба 12.09, дважды за вечер).

Теперь сервис запоминает признак по факту СВОЕЙ успешной команды (`onec/writeBack.ts` →
`base_users.show_in_list`, миграция 019), а карточка подписывает показанное: «по последней
успешной записи из панели». Это не догадка: значение взято из payload выполненной команды.

**Что нужно от агента, чтобы это перестало быть полумерой:** возвращать `showInList` в
`IB_LIST_USERS` (и в эхе). Тогда значение станет читаемым, расхождение «записали одно, в базе
другое» станет видно, а `COALESCE` в `syncUsers` сам предпочтёт ответ базы нашей памяти.

> **СДЕЛАНО агентом, сборка `0.1.0+2026-09-12 23:59 (+05)`.** `IB_LIST_USERS` и эхо состояния
> отдают `showInList` — они собираются одним кодом, поэтому расхождения между ними быть не
> может. Значение читается свойством «ПоказыватьВСпискеВыбора»/«ShowInList»; **если платформа
> его не отдаёт, поле не отправляется вовсе** — `false` от незнания затёр бы то, что сервис
> помнит о собственной записи. То есть `COALESCE` получает либо факт из базы, либо молчание.

> **Проверка записи, сборка агента `2026-09-14 12:46`.** Запрошенный `showInList` (`IB_UPDATE_USER`, и
> `IB_CREATE_USER`, когда поле есть в payload) агент пишет строго: платформа не приняла свойство —
> отказ `IB_FIELD_NOT_APPLIED` до записи; приняла, но у пользователя, найденного в базе заново,
> значение другое — `IB_FIELD_NOT_APPLIED` после записи (остальные поля команды записаны);
> прочитать нечем — успех с `unverified: ["showInList"]`. Необязательные свойства, не принятые
> платформой, перечислены в `skipped`. Сервису и панели: [TASK_SERVICE_SHOW_IN_LIST.md](TASK_SERVICE_SHOW_IN_LIST.md).

> **Роли при создании, сборка агента `2026-09-16 09:23`.** `IB_CREATE_USER` назначает роли ПОСЛЕ того, как пользователь записан в базу, и сверяет их чтением: роль, которой у него не оказалось, — отказ `IB_FIELD_NOT_APPLIED` («создан, но платформа не сохранила роли: …»), причём пользователь уже создан, и права выдаются правкой. Назначенные роли команда возвращает полем `roles`. Принимается и `addRoles` — у нового пользователя добавлять не к чему, поэтому поправка значит тот же набор. Роль, переданная не строкой (объектом, числом), — отказ `IB_BAD_PAYLOAD`: прежде такие молча выбрасывались и пользователь заводился без прав.
> **Справочник «Пользователи», агент `2026-09-17 19:16`.** Агент справочники конфигурации **не пишет** — ни при
> создании, ни при правке (в том числе `disabled`), ни при удалении пользователя ИБ: элемент справочника создаёт сама
> типовая при первом входе администратора или человек в форме «Пользователи». Агент их только считает — по
> `ИдентификаторПользователяИБ` в справочниках `Пользователи` и `ВнешниеПользователи`, если они есть в конфигурации:
>
> - успех `IB_CREATE_USER`, `IB_UPDATE_USER`, `IB_DELETE_USER` несёт `catalog: {found, created: false, items:
>   [{ref, name, catalog, deleted}]}`; у удаления — то, что осталось в справочнике после удаления пользователя ИБ.
>   Справочника нет — поля нет; не прочиталось — `{found: null, created: false, error}`, команда не останавливается;
> - у `IB_CREATE_USER` (для уже существующего пользователя) и `IB_UPDATE_USER` больше одного элемента — отказ
>   `IB_USER_DUPLICATE` **до записи**, ссылки — в `error.details.duplicates: [{ref, catalog, deleted}]`. Удаление
>   пользователя с дублем не запрещено. Разбор случая — [TASKS_ONEC_USER_DUPLICATE_2026-09-17.md](TASKS_ONEC_USER_DUPLICATE_2026-09-17.md).

### `newName` в `IB_UPDATE_USER` — переименование, а не пересоздание

Панель разрешает править имя входа прямо в карточке пользователя базы, и тогда в payload
приходит `newName`. Это смена свойства «Имя» У ТОГО ЖЕ пользователя
(`Пользователь.Имя = newName; Пользователь.Записать()`), а не «удалить и создать заново»:
пересоздание теряет внутренний идентификатор, а с ним — ссылки на пользователя в самой базе
(автор документов, настройки, права на уровне записей).

* `newName` отсутствует или равен `name` — имя не трогать.
* Имя уже занято другим пользователем базы — вернуть ошибку с этим текстом, а не молча
  ничего не делать: панель показывает отказ пользователю.
* Остальные поля применяются в той же команде и по прежнему правилу: отсутствующее поле
  значит «не трогать».

### `payload.auth` — учётная запись КОНКРЕТНОЙ базы (обязательно к реализации)

У агента один администратор баз на всех (у нас — `support`). К части клиентских баз он не
подходит: их заводили до нас, и такого пользователя там нет либо у него другой пароль.
Раньше это лечилось правкой настроек агента — то есть ради одной базы трогали все.

Теперь в панели у базы можно задать свою пару «пользователь + пароль», и сервис подставляет
её в команду **в момент выдачи**:

```jsonc
{ "id": "cmd_…", "baseKey": "BUH_ALPHA", "type": "IB_LIST_USERS",
  "payload": { "baseKey": "BUH_ALPHA", "auth": { "user": "Администратор", "password": "…" } } }
```

**Порядок входа в базу — строго такой:**

1. свой администратор из конфига агента;
2. если он **не прошёл аутентификацию** — повтор с `payload.auth`;
3. если и он не прошёл — ошибка с текстом ОБЕИХ попыток (по какой учётной записи отказ).

Повторять по `auth` нужно **только на отказе аутентификации**. «База занята», «нет
лицензии», «сервер недоступен» — не тот случай: второй вход туда же ничего не изменит,
зато займёт ещё один сеанс.

Поле может отсутствовать — значит, для базы ничего не задано, и работает пункт 1.

**Объявите способность `ib.auth`** в списке capabilities при регистрации — ею агент
сообщает, что читает `payload.auth`. Панель на неё смотрит: пока способности нет, она
показывает у вкладки «Доступ к базе» предупреждение «агент этой сборки учётную запись
игнорирует», а в тексте отказа на входе пишет, что отказ получен по администратору из
настроек агента, а не по заданной учётной записи. Без этого признака человек, задавший
пароль и получивший тот же отказ, не может отличить «пароль неверен» от «пароль не
применили» — и чинит не то.

`auth.password` подпадает под общее правило: **в лог и в текст ошибки не попадает никогда.**
В команде он не хранится и на стороне сервиса — подставляется только в HTTP-ответ агенту.

### По одной команде на базу за раз (гарантия сервиса)

Сервис не выдаёт вторую команду по ТОЙ ЖЕ базе, пока не получит результат первой. Команды
одной базы не независимы: переименовать пользователя и тут же выдать ему роли — это две
операции над одним объектом, и порядок здесь не деталь. Раньше они уходили вместе, агент
выполнял их параллельно, и роли ложились на старое имя либо приходило «в базе нет
пользователя».

Что это значит для агента:

* по одной базе одновременно приходит не больше одной команды — второе COM-соединение к
  той же базе не нужно, и сеанс с лицензией не тратятся дважды;
* `max_parallel` продолжает работать МЕЖДУ базами — сто баз по-прежнему обрабатываются
  параллельно;
* команды кластера друг друга не ждут вовсе — **и очереди базы тоже не ждут, даже с `baseKey`**
  (аудит С1): снятие сеанса, блокировка входа, удаление регистрации идут через `rac`, в базу
  не входят. Иначе снятие сеансов стояло бы за загрузкой той же базы, которая ждёт их выхода.
  Место базы и агента (`AGENT_IB_PARALLEL`) занимают только команды `ib.admin`, и не `dryRun`: сухой прогон в
  базу не входит (С22, `onecRouter.ts:217`);
* у агента есть и свой замок базы (`base_lock`, `execute_ib`): вторая внутрибазовая команда по той же базе ждёт его
  до 60 с и получает `IB_BUSY`. С агента после `2026-09-15 01:06` замок держится, пока живы процессы снятой команды
  (конфигуратор после `TIMEOUT` или отмены), а `dryRun` замка не ждёт;
* команда, у которой вышел срок, а результата нет, **держит место ещё 10 минут** (аудит С3):
  агент мог продолжать работу, и вторая команда внутрь той же базы легла бы поверх первой;
* **`IB_BUSY`** (база занята) у команды группового задания сервис повторяет сам — единственный код, который он
  повторяет: копия встаёт в очередь того же задания не сразу, а после паузы — 120 с перед второй попыткой, 300 с
  перед третьей; всего до трёх попыток (аудит С10, С19; `retryBusy`, `queue.ts:89-92,566-594`). Одиночную команду
  панели сервис не повторяет. Отвечать `IB_BUSY` — правильно, ждать освобождения базы внутри команды не нужно;
* **результат надо присылать всегда** — и на успех, и на отказ. Пока результата нет,
  очередь этой базы стоит; забытый результат останавливает работу по базе до истечения
  срока команды.

### Пакетные операции

Групповая операция — это N обычных команд, по одной на базу, связанных общим заданием на
стороне сервиса. Для агента ничего нового: те же команды, тот же протокол. Единственное
требование — **параллелизм**: `max_parallel` в конфиге ограничивает число одновременных
COM-соединений, потому что каждое занимает сеанс и лицензию 1С.

### Служебные команды агента: `AGENT_HEALTH`, `AGENT_LOG_TAIL`, `IB_SELFTEST`, `IB_BATCH`

агент объявляет, сервис и панель их используют (`TASKS_DEV_2026-09-14.md`, R1, R2, R4); `IB_BATCH` агент
со сборки `2026-09-14 23:52` **не объявляет** — его исполняет только расписание самого агента, сервису он
не нужен. Ниже — как они устроены.

| Команда | Payload | Ответ |

операции в базе» или «Отладочная информация» с отметкой «с самопроверкой базы»: отчёт копируется.

## 3.3. Процессы агента и отмена: `AGENT_LIST_PROCESSES`, `AGENT_KILL_PROCESS`, `AGENT_CANCEL_COMMAND`

Команды о самом агенте: в кластер и базы не ходят и пропуска на исполнение не ждут (`needs_permit`, `agent.rs`) — они
нужны именно тогда, когда места заняты зависшей работой. Способности — `agent.procs` и `agent.cancel` (§2.1).

### `AGENT_LIST_PROCESSES` — READ

Payload `{}`. Ответ `{items: [...]}`, строки по убыванию `ageSecs` (`procs::snapshot`, `procs.rs:194-204`):

| Поле | Тип | Смысл |
|---|---|---|
| `pid` | целое | номер процесса Windows |
| `tool` | строка | `rac`, `ibcmd`, `1cv8` (конфигуратор), `webinst`, `powershell` (мост) |
| `what` | строка | что делает: «проверка базы», «extension list», действие моста |
| `base` | строка | база; пустая строка, если операция не по базе |
| `ageSecs` | целое ≥ 0 | сколько работает |
| `orphan` | boolean | `true` — за процессом не следит ни одна задача агента: остался с прошлого запуска службы, а с агента после `2026-09-15 01:06` — ещё и конфигуратор команды, которую агент перестал ждать (`TIMEOUT`) или отменил (`Ticket::drop`, `procs.rs:173-191`) |
| `commandId` | строка, необязательно | с агента после `2026-09-15 01:06` — номер команды сервиса, запустившей процесс; у собственных операций агента (расписание, проверка готовности) поля нет (`procs.rs:61-66`) |

Тот же снимок агент кладёт в каждый heartbeat (§2.2). Сервис замещает им снимок процессов агента (`planWriteState` →
`agents.setProcesses`), но берёт из строки шесть полей (`parseProcesses`, `writeState.ts:53-67`): `commandId` в
снимок не попадает и остаётся только в записи самой команды.

### `AGENT_KILL_PROCESS` — CRITICAL

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `pid` | целое > 0 | да | номер из `AGENT_LIST_PROCESSES`; нет — агент отвечает `VALIDATION_ERROR` |
| `force` | boolean | нет (`false`) | согласие снять конфигуратор или процесс вне списка агента |

Порядок (`execute_local`, `commands/mod.rs`; `procs::terminate`, `procs::terminate_unknown`):

1. Процесс есть в списке агента, это не `rac`/`ibcmd`/`powershell`/`webinst` (то есть `1cv8`), а `force` нет —
   `AGENT_PROCESS_UNSAFE`: обрыв обновления оставит базу непригодной, обрыв выгрузки — обрезанный `.dt`.
2. Процесс в списке, но уже завершился — успех с `note` «процесс … уже завершился».
3. Процесса нет в списке или номер уже занят другим образом — без `force` `AGENT_PROCESS_NOT_FOUND` с советом; с
   `force` агент снимает его, только если имя образа — `rac`, `ibcmd`, `powershell` или `webinst`, иначе тоже
   `AGENT_PROCESS_NOT_FOUND`. Рабочие процессы сервера 1С (`rphost`, `rmngr`, `ragent`) и конфигуратор вне списка не
   снимаются никогда.

Ответ: `{ok: true, note, state: {processes: {items, readAt, stillRunning}}}` — снимок процессов после снятия;
`stillRunning: true`, если процесс жив и после четырёх проверок с паузой 0,4 с. Сервис замещает им снимок процессов агента.

### `AGENT_CANCEL_COMMAND` — CRITICAL

| Поле | Тип | Обяз. | Смысл |
|---|---|---|---|
| `commandId` | строка 1–64 | да | номер начатой команды; нет — агент отвечает `VALIDATION_ERROR` |
| `force` | boolean | нет (`false`) | снять и конфигуратор этой команды |

```jsonc
{ "ok": true, "commandId": "cmd_…", "killed": true,
  "note": "IB_LIST_EXTENSIONS прервана; сняты процессы: powershell 5120",
  "state": { "processes": { "items": [ … ], "readAt": "…", "stillRunning": false } } }

{ "ok": false, "commandId": "cmd_…", "reason": "NOT_RUNNING" }
```

- `ok: true` — задача команды снята, в том числе ещё ждавшая пропуска (`cancel::cancel`, `cancel.rs:67-88`). `killed`
  при `ok: true` всегда `true` и значит «задача прервана», а не «процессы сняты» — что снято, пишет `note`. Результата
  по прерванной команде агент не шлёт: её закрывает сервис (`COMMAND_ABORTED`, `queue.abort`).
- `ok: false, reason: "NOT_RUNNING"` — у агента такой команды нет: закончилась сама или не приходила. Это не ошибка.
- Без `force` снимаются только `rac`, `ibcmd`, `powershell`, `webinst` этой команды; конфигуратор остаётся — кроме
  осмотра `IB_CHECK` без `repair` (агент после `2026-09-15 01:06`). Живой конфигуратор агент этой сборки называет в
  `note` («продолжают работу: 1cv8 1234 — конфигуратор снимается только с явным согласием (force)…»), держит замок
  базы (новые команды по ней — `IB_BUSY`) и блокировку входа, поставленную операцией, снимает после его завершения.

Какие команды можно прерывать, решает сервис, а не агент: маршрут панели пропускает только чтения и `IB_CHECK` без
`repair`, а `IB_CHECK` — лишь агенту с `agent.cancel.check` (`abortAllowed`, `admin.ts:762-765`;
`onecRouter.ts:1128-1141`). Сама команда `AGENT_CANCEL_COMMAND` тип прерываемой команды не проверяет.

## 4. Коды ошибок

⚠ **Сервис не отвечает 5xx на ошибки 1С.** Отказ агента — это ошибка предметной области,
и панель получает её как `422` с телом `{success:false,error:{code,message}}`. Причина
практическая: Cloudflare трактует 5xx от источника буквально и подменяет ответ своей
HTML-страницей без заголовков CORS — текст ошибки до браузера не доезжает вовсе, а
пользователь видит «Access-Control-Allow-Origin missing» вместо причины.


Панель показывает `error.message` как есть, поэтому текст пишите по-русски и по делу. Некоторые коды уже упоминает
[ONEC_ADMIN_SETUP.md](ONEC_ADMIN_SETUP.md).

### 4.1. Коды агента

Всё, что агент реально отдаёт (сверено по коду 15.09). «Повтор» — есть ли смысл повторить ту же команду без
изменений. По коду сервис делает три вещи, остальное — подсказки к тексту:

- **повтор в задании** — только `IB_BUSY` и только у команды группового задания: до трёх попыток, пауза 120 и 300 с
  (С10, С19; `agentRouter.ts:527-536`);
- **отметка «в базу не войти»** — только у команд `ib.admin` по базе и не `dryRun` (`marksReachability`,
  `ibFailureReason`, `bases/service.ts:210-244`): `IB_AUTH_FAILED` → `NO_ACCESS`, `IB_DB_MISSING` → `NO_DB`,
  `INFOBASE_NOT_FOUND` → `NO_INFOBASE`, `IB_CONNECTION_LOST` — никогда. У прочих кодов причина ищется в тексте
  («база данных отсутствует», «идентификация пользователя не выполнена» и т. п.); не нашлась — отметки нет. Успех
  команды внутрь базы отметку снимает;

| `AGENT_FIELD_NOT_APPLIED` | запись команды | агент ответил `SUCCESS`, а в эхе «Показывать в списке выбора» не равно записанному (`checkShowInListIntent`) | — |
| `COMMAND_FAILED` | 422 | отказ, у которого нет `error` | — |
| `NOT_QUEUED`, `COMMAND_LOST` | отчёт задания (`onec/batches.ts`) | команда задания не поставлена; не найдена — срок жизни истёк | повторить |
| `FORBIDDEN`, `FORBIDDEN_READONLY` | 403, панель | нет права «Администрирование 1С»; право только на просмотр | — |
| `RATE_LIMITED` | 429, панель | превышен предел обращений к кластеру (`rateLimit.ts`) | повторить через `retryAfterSec` |
| `UNKNOWN_COMMAND`, `VALIDATION_ERROR` | 400, панель | типа нет в `ADMIN_COMMANDS`; payload не прошёл схему (текст по-русски, `describeIssue`) | в очередь не попало |
| `UNKNOWN_BASE` | 404, панель | базы нет в реестре | обновить список из кластера |
| `CAPABILITY_MISSING` | 409, панель | у агента нет способности, типа в списке или `ib.roles` для правки ролей | обновить или настроить агента |
| `ADMIN_AGENT_UNAVAILABLE`, `ADMIN_AGENT_OFFLINE` | 409, панель | агент не зарегистрирован или база за другим сервером; ни одного агента роли на связи | — |
| `COMMAND_NOT_STARTED`, `COMMAND_FINISHED`, `ABORT_NOT_ALLOWED`, `ABORT_AGENT_OLD` | 409, прерывание | команда ещё в очереди; уже завершена; прерывать можно только чтение и `IB_CHECK` без `repair`; агент без `agent.cancel.check` | — |
| `NOTHING_TO_RETRY` | 409, повтор задания | неуспешных баз нет | — |
| `NOT_FOUND` | 404, панель | нет команды, задания или агента | — |

Отказ агента панель получает как 422 с его кодом и текстом (с подсказками); незавершённая команда — 202
`{pending: true, commandId, state, dispatchedAt}`. `TIMEOUT` и `EXPIRED` в ответах инструментов чата — коды чата
(`chat/workflow.ts:309-312`), а не протокола агента. Прочие коды маршрутов управления агентами и расписаниями
(`AGENT_ENABLED`, `AGENT_REFERENCED`, `ORGANIZATION_REQUIRED`, `BAD_REQUEST`) к протоколу агента не относятся.

## 5. Что модулю НЕ нужно делать

- **Не заходить в базы.** Секция `[onec]` админ-агенту не нужна, расширение `buhprof_api`
  не используется. Исключение — блокировка сеансов, и то через администратора ИБ, а не через
  расширение.
- **Не опрашивать кластер по своей инициативе** на каждую базу. Реестр отдаётся панели из БД
  сервиса; состояние приходит с heartbeat (`bases[]` + `basesComplete`), а кнопка «Обновить
  из кластера» существует ровно для случая, когда ждать heartbeat не хочется. Сто баз каждые
  30 секунд опрашивать нельзя.
- **Не изобретать команд сверх списка.** `ADMIN_COMMANDS` закрыт: незнакомый тип сервис не
  поставит, а агент не должен исполнять ничего, чего нет в §3 и §3.2.

## Экземпляр агента: `X-Agent-Instance` (обязателен к отправке)

**Проверяется только заголовок.** Каждый ЗАПУЩЕННЫЙ ПРОЦЕСС агента шлёт `X-Agent-Instance` на **каждом** запросе к
`/agent/v1/*`, включая опрос команд. Владение токеном, отказ 409 и снятие владения сервис решает только по нему
(`agentRouter.ts:153-214`). Поле `instanceId` в теле `register`/`heartbeat` (≤ 200, необязательно) заголовка **не
заменяет**: по нему сервис лишь ведёт учёт экземпляров (`touchInstance`), а владения без заголовка не возникает вовсе.
Сборка без заголовка работает как старая: без 409, без прощания и без закрытия команд прежнего процесса — номер
забравшего команду экземпляра пишется из заголовка опроса (`dispatched_instance`, `queue.ts:469`).

Агент шлёт и то и другое: `X-Agent-Instance` вместе с `X-Agent-Id` и `X-Agent-Version` на каждом запросе
(`Client::authed`, `cloud/mod.rs:84-92`), `instanceId` — в регистрации и heartbeat. Значение —
`<машина>/<служба>/<pid>/<время старта RFC3339>` (`Runtime::new`, `agent.rs:122-128`), до его установки —
`<машина>/<pid>`. Оно стабильно в пределах жизни процесса, разное у разных процессов и сразу называет копию, которую
надо остановить.

**Как работает владение.** Сервис пускает работать ТОЛЬКО ОДИН экземпляр на токен; второй получает
**409 `AGENT_INSTANCE_CONFLICT`** с `details: {ownerInstanceId, ownerSeenSecsAgo}` и не получает ни одной команды.
Владение — аренда: молчащий дольше `AGENT_OFFLINE_AFTER_SECS` (по умолчанию 90 с) владелец уступает место сам;
уходящий агент освобождает его прощальным heartbeat (§2.2); вручную — в панели («Агенты» → «Освободить экземпляр»).
Это защита от ошибки, а не от злого умысла: идентификатор экземпляра агент называет сам. От умысла защищает один токен
на машину и его ротация.

Агент со своей стороны не запускает вторую копию на машине (именованный mutex `Global\bpapi-agent-<agentId>`,
`single_instance_guard`, `agent.rs`). Получив 409, он сравнивает машину и службу владельца со своими — по
`details.ownerInstanceId`, без поля — по тексту отказа (`conflict_is_our_restart`): совпали — это его же прежний
процесс, агент ждёт 20 с и повторяет; не совпали — останавливается с записью в журнал, а не ретраит молча
(`stop_on_conflict`).

**`details` в отказе команды.** Метку исполнителя `{host, server, service, pid, build, role, ibReady}` агент кладёт в
`error.details`, когда своих подробностей нет (§4.1). Сервис показывает её в тексте («Ответил агент на машине X57,
pid 3316, сборка …», `describeResponder`), но экземпляры по ней больше не заводит — только по заголовку
(`agentRouter.ts:566-570`).

**Зачем.** Два запущенных экземпляра под одним токеном — авария, невидимая с сервера: оба
разбирают ОДНУ очередь команд. Пока настройки совпадают, это лишь лишняя нагрузка; стоит им
разойтись (старый процесс с прежним паролем кластера, новый — с исправленным), и одна и та
же команда начинает отказывать ЧЕРЕЗ РАЗ. Отладка такого без счёта экземпляров сводится к
гаданию: `rac` отвечает то «не аутентифицирован», то данными, а пароль при этом верный.

Сервис считает экземпляры, отзывавшиеся за `AGENT_OFFLINE_AFTER_SECS`, и показывает их
число во вкладке «Агенты» — больше одного даёт предупреждение прямо в панели.

**Токен — на одну машину.** Копировать рабочий токен на вторую машину нельзя: обе будут
разбирать одну очередь команд от имени одного агента, и различить их в отчётах невозможно.
Так и вышло на практике — один токен стоял и на сервере 1С, и на машине разработки; команды
отказывали через раз, потому что настройки кластера у них разошлись. Для разработки
заводится ОТДЕЛЬНЫЙ агент со своим токеном («Администрирование 1С» → «Агенты» → «Создать»).

Сервис запоминает адрес источника каждого экземпляра, и если экземпляры приходят с разных
адресов, панель говорит об этом прямо: «один токен используется на разных машинах».

Вторая причина двойного запуска, уже на одной машине: служба агента работает и одновременно
запущен экземпляр из среды разработки.
