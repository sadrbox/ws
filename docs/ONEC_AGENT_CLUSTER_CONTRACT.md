# Контракт кластерного модуля админ-агента (bpapi_agent, role = admin)

Версия 1.0 · 2026-09-04 · извлечено из работающего кода `ai/`, не из планов

Что должен реализовать модуль `cluster` в `bpapi_agent`, чтобы кнопка **«Администрирование 1С» →
«Базы» → «Обновить из кластера»** в aleppo.kz наполнила реестр баз.

Сторона сервиса готова целиком: `ai/src/commands/admin.ts` (список команд), `ai/src/http/onecRouter.ts`
(HTTP панели), `ai/src/bases/service.ts` (реестр), миграция `004_bases.sql`, панель
`frontend/src/models/OneCAdmin`. Ничего из этого дописывать не требуется.

## 1. Транспорт: как команда доходит до модуля

Ничего нового — тот же long-poll, что у бизнес-агента:

```
GET  /agent/v1/commands                 → { commands: [ { id, requestId?, type, payload } ] }
POST /agent/v1/commands/{id}/result     ← результат
```

Тело результата (`resultSchema`, `ai/src/http/agentRouter.ts:61`):

```jsonc
{
  "commandId": "…",            // = id команды
  "agentId": "<uuid агента>",  // обязателен, сверяется с токеном
  "status": "SUCCESS",         // или "ERROR"
  "result": { },               // при SUCCESS — см. §3
  "error":  { "code": "…", "message": "…", "details": {} },  // при ERROR
  "startedAt": "…", "finishedAt": "…"   // необязательно
}
```

⚠ Команда живёт **300 секунд** (`ttlSeconds: 300` при постановке), а панель ждёт ответа
`CHAT_COMMAND_TIMEOUT_SECS` (по умолчанию 120 с) и затем показывает `TIMEOUT`, **не снимая
команду с очереди**. Для `CLUSTER_TERMINATE_SESSION` это важно: команда, скорее всего, всё же
выполнится, поэтому модуль обязан быть идемпотентным по `requestId`.

## 2. Регистрация: без неё команды не придут

`POST /agent/v1/register` должен прислать роль, сервер и способности:

```jsonc
{
  "agentId": "…", "version": "…", "os": "…",
  "role": "admin",
  "capabilities": ["cluster.admin"],
  "server": { "name": "Сервер 1С (офис)", "rasHost": "localhost", "rasPort": 1545 }
}
```

- **`role: "admin"`** и **`capabilities: ["cluster.admin"]`** — гейт в `agentCanRun()`
  (`admin.ts`). Без них сервис откажет сразу: `CAPABILITY_MISSING`, «Агент не умеет …».
- **`server.name`** обязан совпадать с именем у бизнес-агента того же сервера — по нему базы
  связываются с агентами. Разные имена дадут два «сервера» в реестре.

## 3. Команды: что приходит и что вернуть

Payload валидируется схемами Zod **строго** (`.strict()`) — лишних полей быть не может.

### `CLUSTER_LIST_INFOBASES` — READ, база не нужна

Payload: `{}`. Это команда кнопки «Обновить из кластера».

```jsonc
{ "items": [
  { "key": "buh_alma",           // ИМЯ ИБ В КЛАСТЕРЕ — им она адресуется во всех остальных командах
    "name": "ТОО Алма (бухгалтерия)",
    "status": "OK",              // необязательно; при отсутствии останется прежний
    "onecVersion": "8.3.25.1257",// необязательно
    "sessionsCount": 3 }         // необязательно
] }
```

Как это применяется (`bases.sync(serverId, items, { complete: true, authoritative: true })`):

- `key` — единственное обязательное поле, ключ upsert'а `(server_id, key)`;
- **`null`/отсутствие поля означает «не знаю», а не «пусто»**: прежнее значение сохраняется
  (`COALESCE`). Не присылайте `null`, чтобы «очистить» — очистить так нельзя;
- `extVersion` присылает **бизнес**-агент, админ-агент его не знает и слать не должен;
- срез считается полным: базы, которых нет в `items`, получают `status = 'MISSING'`.
  Поэтому частичный список **недопустим** — либо все базы кластера, либо `ERROR`.

### `CLUSTER_LIST_SESSIONS` / `CLUSTER_LIST_CONNECTIONS` — READ

Payload: `{ "baseKey"?: "buh_alma" }` — без него весь кластер, с ним одна база.

```jsonc
{ "items": [ { "session": "12", "user": "Иванов", "host": "WS-14", "app-id": "1CV8C", "started-at": "…" } ] }
```

Строка — **словарь строк**, набор ключей задаёт `rac` (панель типизирует его как
`Record<string, string>` и показывает как есть). Отдавайте поля `rac` без переименования.

### `CLUSTER_INFOBASE_INFO` — READ, база обязательна

Payload: `{ "baseKey": "buh_alma" }`. Результат — свободный объект со сведениями `rac`.

### `CLUSTER_TERMINATE_SESSION` — **CRITICAL**

Payload: `{ "sessionId": "<uuid сеанса>", "baseKey"?: "buh_alma" }`.

⚠ `sessionId` — это **UUID** сеанса (поле `session` в строке `rac`), а НЕ его номер
(`sessionId` в той же строке). Проверено зондом: на UUID `rac` отвечает «Сеанс с указанным
идентификатором не найден», на номер — «Ошибка разбора параметра: session».
`baseKey` — только для маршрутизации и аудита.
Результат: `{ "ok": true }`. Снятие уже снятого сеанса — тоже `SUCCESS` (идемпотентность).

### `CLUSTER_SET_SESSIONS_LOCK` — **CRITICAL**, база обязательна

```jsonc
{ "baseKey": "buh_alma", "enabled": true,
  "message": "Обслуживание до 19:00",   // необязательно, ≤500 символов
  "from": "…", "to": "…",               // окно блокировки, ≤40 символов
  "permissionCode": "…" }               // код входа в заблокированную базу
```

Результат: `{ "ok": true }`. Единственная кластерная команда, которой нужен служебный
администратор ИБ (`BPAPI_IB_USER`/`BPAPI_IB_PWD`), — остальным хватает администратора кластера.

## 3.1. Кодировка вывода `rac` — казахские буквы

**Симптом.** Имена баз приходят как `Жа?аш М?ратхан ИП`, `Айбек Абай Жолдасбек?лы ИП`.
Проверка байтов в реестре: `d096 d0b0 3f` — `3f` это обычный ASCII `?`, то есть буква
потеряна ДО отправки, а не при показе. Русские буквы целы, пропали только казахские
(ә ғ қ ң ө ұ ү һ і) — характерный след транскодирования через **CP1251**: русский там
есть, казахского нет, и всё непредставимое заменяется на `?`. Восстановить нечем:
преобразование одностороннее.

**Где чинить.** Только в агенте, на границе с `rac`. Вывод утилиты нельзя декодировать
как CP1251 или CP866 — в обеих кодировках казахских букв нет вовсе.

Основной способ (не проверен на живом кластере — подтвердите): запускать `rac` с
консолью в UTF-8 и читать поток как UTF-8.

```cmd
cmd /c chcp 65001 >nul && "C:\Program Files\1cv8\8.3.25.1257\bin\rac.exe" infobase summary list …
```

В коде агента: читать stdout **байтами** и декодировать UTF-8 явно, не полагаясь на
кодировку по умолчанию (для .NET — `Console.OutputEncoding`/`StandardOutputEncoding =
new UTF8Encoding(false)`, для Node — `spawn` без `encoding` и затем `Buffer.toString("utf8")`).

Запасной путь, если `rac` игнорирует `chcp`: имена баз лежат в файле кластера
`1CV8Clst.lst` в каталоге данных сервера — он в UTF-8, и `rac` для получения имён тогда
не нужен вовсе.

**После исправления** нужен один прогон «Обновить из кластера»: имена в реестре
перезапишутся правильными. Сервис при этом защищён — целое имя не затирается битым
(`bases.sync`: имя с `?` принимается, только когда своего ещё нет), так что случайный
запуск старого агента реестр больше не испортит.

## 3.2. Внутрибазовые команды: пользователи и расширения

Другой транспорт и другая способность: эти команды требуют **входа в базу** (COM-соединение
или расширение), поэтому агент обязан объявить `capabilities: ["cluster.admin", "ib.admin"]`.
Без `ib.admin` сервис откажет сразу, не ставя команду в очередь.

Каждой нужен служебный администратор ИБ в целевой базе (`BPAPI_IB_USER`/`BPAPI_IB_PWD`).

| Команда | Payload | Результат |
|---|---|---|
| `IB_LIST_USERS` | `{baseKey}` | `{items:[{name, fullName?, disabled?, roles?[]}]}` |
| `IB_CREATE_USER` | `{baseKey, name, fullName?, password?, roles?[], osUser?, showInList?}` | `{ok:true}` |
| `IB_DELETE_USER` | `{baseKey, name}` | `{ok:true}` |
| `IB_LIST_EXTENSIONS` | `{baseKey}` | `{items:[{name, version?, purpose?, safeMode?}]}` |
| `IB_INSTALL_EXTENSION` | `{baseKey, name, contentBase64, safeMode?}` | `{ok:true}` |
| `IB_DELETE_EXTENSION` | `{baseKey, name}` | `{ok:true}` |

Что важно соблюсти:

- **Списки полные.** Результат `IB_LIST_*` замещает кэш базы целиком: чего нет в ответе,
  сервис удаляет из реестра. Частичный список молча «потеряет» пользователей.
- **`contentBase64`** — содержимое `.cfe` без префикса `data:`. Файл приходит телом команды:
  агент не ходит за ним в сеть.
- **Идемпотентность обязательна.** Пакетные команды живут 900 секунд, а панель показывает
  `TIMEOUT` через 120 — пользователь может повторить операцию, которая на самом деле идёт.
  Повторное создание существующего пользователя и повторное удаление отсутствующего должны
  завершаться `SUCCESS`, а не ошибкой.
- **Пароль не логировать.** Он приходит в payload и не должен попадать ни в лог агента, ни
  в текст ошибки. Сервис его у себя не хранит: в задание пакета `password` и `contentBase64`
  не записываются.

### Пакетные операции

Групповая операция — это N обычных команд, по одной на базу, связанных общим заданием на
стороне сервиса. Для агента ничего нового: те же команды, тот же протокол. Единственное
требование — **параллелизм**: `max_parallel` в конфиге ограничивает число одновременных
COM-соединений, потому что каждое занимает сеанс и лицензию 1С.

## 4. Коды ошибок

Панель показывает `error.message` как есть, поэтому текст пишите по-русски и по делу.
Коды, на которые уже ссылается [ONEC_ADMIN_SETUP.md](ONEC_ADMIN_SETUP.md):

| Код | Когда |
|---|---|
| `RAC_UNAVAILABLE` | не найден `rac.exe` по `cluster.rac_path` |
| `RAC_TIMEOUT` | `rac` не ответил за `cluster.timeout_secs` (обычно молчит RAS) |
| `CLUSTER_NOT_FOUND` | RAS отвечает, кластера по адресу нет |
| `RAC_ERROR` | сам `rac` вернул ошибку — вложите его текст в `message` |

Набор аргументов `rac` собран по документации и на живом кластере не проверялся: при
`RAC_ERROR` полезно класть в `details` фактическую командную строку (без пароля).

## 5. Что модулю НЕ нужно делать

- **Не заходить в базы.** Секция `[onec]` админ-агенту не нужна, расширение `buhprof_api`
  не используется. Исключение — блокировка сеансов, и то через администратора ИБ, а не через
  расширение.
- **Не опрашивать кластер по своей инициативе** на каждую базу. Реестр отдаётся панели из БД
  сервиса; состояние приходит с heartbeat (`bases[]` + `basesComplete`), а кнопка «Обновить
  из кластера» существует ровно для случая, когда ждать heartbeat не хочется. Сто баз каждые
  30 секунд опрашивать нельзя.
- **Не изобретать команд сверх списка.** `ADMIN_COMMANDS` закрыт: незнакомый тип сервис не
  поставит, а агент не должен исполнять ничего, чего нет в §3 и §3.2.
