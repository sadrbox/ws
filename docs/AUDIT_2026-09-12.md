фактом с числом — не «кажется медленным», а «81 запрос за опрос, опрос раз в три секунды».

# I. Эксплуатация — самое дорогое по последствиям

Эти четыре пункта не про код, но перевешивают всё остальное в разделе «оптимизация».

### D1. Прод работает dev-сервером Vite

`ecosystem.config.js`: процесс `frontend` запускает `npx vite --host` с
`NODE_ENV=development`. Люди получают неминифицированный код, dev-предупреждения React,
sourcemaps наружу и HMR-сокет, который стучится на `192.168.1.112:5173`. Сборка уже есть и
работает (27 с, 194 кБ gzip главного чанка) — не хватает только раздачи `dist`.

**Что сделать.** Отдельный процесс раздачи статики (или nginx/cloudflared на `dist`),
`NODE_ENV=production` у бэкенда, dev-сервер — только для разработки.

### D2. Кластер объявлен, но не работает

В конфиге у `backend-node` стоит `exec_mode: "cluster", instances: 4` с расчётом «4 × пул
Prisma(17) = 68 < max_connections 100». `pm2 list` показывает **один процесс в режиме
fork**. То есть многоядерность заявлена, оплачена расчётом пула — и не включена.

### D3. Prisma Studio висит в проде

Процесс `prisma-studio` работает постоянно: это админский доступ ко всей базе без
разграничения прав. Инструмент разработчика, поднимаемый по требованию, а не круглосуточно.

### D4. Автобэкап выключен

Планировщик есть (`services/scheduler.js`, задача `backup`), но `BACKUP_INTERVAL_HOURS` в
`backend/.env` не задан → интервал 0 → задача не регистрируется. Резервные копии делаются
только вручную из панели.

# II. Оптимизация кода

### O1. «Задания»: 81 запрос на один опрос, и 20 из них — записи (P0)

`BatchService.list(org, 20)` вызывает `progress(id)` в цикле, а каждый `progress` делает
~4 запроса, первый из которых **UPDATE** (закрытие просроченных команд). Замерено на живой
базе: **20 заданий → 81 запрос, 73 мс**. Панель опрашивает задания раз в 3 с, пока что-то
выполняется, — это ~27 запросов в секунду и 7 записей в секунду на ровном месте.

**Что сделать.** Один `UPDATE ... WHERE batch_id = ANY($1)` на весь опрос, один `SELECT` с
агрегатами по всем заданиям (`GROUP BY batch_id`) и один `SELECT` строк-команд. Три запроса
вместо восьмидесяти одного.

### O2. Срез баз: по одному UPSERT на базу (P1)

`BaseService.sync` шлёт отдельный запрос на каждую базу: 111 баз = 111 round-trip'ов на
каждый полный срез (heartbeat + кнопка «Обновить»).

**Что сделать.** Один многострочный upsert через `unnest($1::text[], $2::text[], …)`.

### O3. Публикации: два запроса на базу (P1)

`applyPublications` для каждой строки ответа делает `SELECT` (поиск базы по ключу или имени)
и `UPDATE`. Последний замер среза: 135 строк → **270 запросов** на одно нажатие «Проверить
публикации».

**Что сделать.** Один `SELECT key, name FROM bases WHERE server_id = $1` в словарь и один
`UPDATE ... FROM (VALUES …)`.

### O4. Главный чанк 620 кБ (P2)

Тяжёлое уже вынесено правильно: `xlsx`, `mammoth`, `pdfjs` грузятся динамически в просмотре
файлов, `recharts` — отдельным чанком, 56 моделей в `modelRegistry` — ленивыми импортами.
Остаток главного чанка — ядро: `useFormStore` (1832 строки), `Table` (1030), `SubTable`
(988), `LookupField` (949).

**Что сделать.** `SubTable` и `DocumentItemsTable` нужны только в документных формах —
вынести в отдельный чанк; замерить состав главного чанка (`rollup-plugin-visualizer`), а не
гадать.

### O5. `useFormStore.ts` — последний файл-город (P2)

1832 строки, самый большой файл фронта. `Table` (T4) и `SubTable` уже разобраны на модули,
и это сработало: их правки перестали задевать соседей. Здесь — не разобрано.

### O6. Журнал сообщений пишется в localStorage на каждое изменение (P3)

`persist()` сериализует до 200 записей при каждом `emit`. Рядом, в `queryPersist`, ровно та
же задача решена debounce'ом — взять оттуда.

### O7. Задел, который уже закрыт (для памяти)

Единый маршрутизатор ошибок (`services/errors/route.ts`), единая область сообщений, срок
жизни журнала, ширина колонок таблицы цепочкой, `dbMissing` из среза баз — сделано 11–12
сентября, переделывать не нужно.

# III. Что не доделано

### U1. Панель 1С: три задачи из разбора 11 сентября открыты

- **A1.** Отмена работает только для команд в очереди; начатую остановить нельзя — нужна
  команда агенту `AGENT_CANCEL_COMMAND`.
- **A2.** Массовая проверка идёт последовательно (`AGENT_IB_PARALLEL = 1`): 110 баз × ~25 с
  ≈ 45 минут, и человек не видит оценки времени.
- **A3.** Очередь не объясняет, чего ждёт: `queued` выглядит как «выполняется».

### U2. Защита от зависания агента не снята

`AGENT_IB_PARALLEL` не задан в `ai/.env` → действует умолчание 1. Оно вводилось, когда две
параллельные `IB_LIST_EXTENSIONS` клинили агента на 12 минут; агент с тех пор перестроен и
отвечает за 78 с. Значение стоит поднимать измерением, а не верой.

### U3. Kaspi — каркас без API

`services/fiscal/kaspiProvider.js`: пять `TODO(kaspi-docs)` — авторизация, создание QR,
статус платежа, фискализация, возврат. По умолчанию работает stub-провайдер с выдуманными
данными. Вебхук `fiscalreceipts.js` не проверяет подпись.

### U4. ЭСФ — маппер с допущением

`services/esf/invoiceMapper.js`: категория товара не выводится (TODO), подставляется
умолчание. SOAP-сессия с ИС ЭСФ — отдельный незакрытый этап.

### U5. Ollama-провайдер не реализован

`ai/src/server.ts` при выборе Ollama пишет предупреждение и отключает чат.

### U6. Тестовое покрытие неровное

62 тестовых файла на 460 исходных (фронт), 53 на 258 (бэк), 6 на 35 (ai). Покрыто самое
дорогое (проводки, себестоимость, таблица, очередь команд), но 109 роутеров бэкенда
покрывает 53 файла тестов, и у большинства моделей фронта тестов нет вовсе.

### U7. Линт-долг зафиксирован, но не гасится

26 ошибок (трещотка держит их от роста) и 167 предупреждений; `any` в 26 местах. Трещотка
умеет опускать базу, но за два месяца база не двигалась.

### U8. `console.log` в проде

10 мест в `backend/api` и `backend/services` пишут в stdout мимо логгера.

### U9. Свежий код сервиса не развёрнут

Миграция 018 применена в 12:09, но правки после неё — приём `dbMissing` из среза баз и
повтор задания по отмеченным базам — ждут `pm2 restart all`. Пока сервис их не видит, ни
одна база не помечена «Нет в СУБД» (в реестре 0 из 111), хотя агент уже умеет об этом
сообщать.

# IV. Рекомендации по развитию

Порядок — по отношению «польза / цена», а не по интересности.

### R1. Массовая проверка баз-фантомов одной кнопкой

Агент умеет `bases check` только из командной строки на сервере. Нужна команда
`CLUSTER_CHECK_BASES` (вопрос к СУБД, не вход в базу) — и в панели появляется «Проверить
все базы» вместо обхода по одной. Задача агенту; формат — как в
`TASK_SERVICE_DROP_INFOBASE.md`.

### R2. Настоящая отмена начатой команды

Закрывает A1 и снимает главную боль очереди: зависшая команда держит место до 15 минут.

### R3. Обслуживание по расписанию

Выгрузка баз и проверка `ibcmd` сейчас только вручную. Планировщик уже есть на бэкенде
(`services/scheduler.js`) — в сервисе 1С его нет; регулярная ночная выгрузка десятка баз
снимает целый класс разговоров «а есть ли копия».

### R4. Поиск и отбор в «Технических сообщениях»

Группировка есть, поиска нет. При двух сотнях записей и десяти объектах это первое, чего
хватятся.

### R5. Экран состояния очереди

Данные есть все (состояние команд, занятость агентов, длительности), экрана нет: сколько
команд ждёт, средняя длительность по типам, кто держит очередь.

### R6. Права на операции 1С уже разделены — довести до конца

`onecRouter` проверяет `isSuperAdmin || canOnecAdmin`. Стоит развести дальше: чтение
(сеансы, списки) — одному праву, разрушающее (удаление регистрации, снятие публикации,
правка пользователей ИБ) — другому.

### R7. Довести Kaspi и ЭСФ до реального API

Оба каркаса написаны и ждут документации/ключей. Пока они stub, фискальная часть системы
существует только на бумаге.

### R8. Тесты на роутеры бэкенда

Самое дешёвое усиление: контрактные тесты на 10–15 самых используемых роутеров (документы,
цены, остатки). Сейчас их защищают только тесты сервисов.

# V. Что в хорошем состоянии

Чтобы не переделывать заодно: индексы БД (462 на 101 модель, проверенные планами), разбор
`Table` и `SubTable` на модули, единый реестр моделей с ленивой загрузкой, ворота качества
(трещотка + css-lint + 825 тестов на три пакета), журнал аудита с ретенцией, единый
планировщик, и — отдельно — качество комментариев в коде 1С-панели: причины решений записаны
там, где их будут искать.
